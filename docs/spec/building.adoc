= Building
include::_attributes.adoc[]
:page-slug: building

How code gets written against this book.  Every task in xref:backlog.adoc[Backlog] and on the
feature pages is picked up by one agent (or one person) working alone; this page is the
contract they work under.

== Before starting a task

. Read the task: its page, the task's `Delivers` and `Done when`, and every page it xrefs.
. Read xref:architecture.adoc[Architecture], xref:stack.adoc[Technology stack] and the
  spec page for the track (xref:api-conventions.adoc[], xref:crdt-model.adoc[],
  xref:server.adoc[], xref:client.adoc[], xref:testing.adoc[]).
. Check the dependencies are merged: a task starts only when every `Depends on` id is done.

== While working

* Stay inside the track's directory: `proto/` for proto, `server/` for server,
  `client/` for the client tracks, `crdt-conformance/` and `client/Packages/WTCRDT` +
  `server/wt-crdt` together for crdt, `docs/` for docs.  Edits to shared root files
  (`Makefile`, `README.adoc`, `.gitignore`, `docker-compose.yml`) are proposed in the report,
  not made silently.
* The spec is normative.  Where code must deviate (an API that does not exist, a limit that is
  wrong), the deviation is recorded on the page in the same change, under the relevant
  subsection, and named in the report.  The book and the code move together.
* Every task ends green: its own tests pass with the commands named below, the previous tests
  still pass, and the coverage gate -- 95% line and 95% branch coverage on the server, 95% line
  and 95% region coverage on the client (xref:testing.adoc[Testing], xref:decisions.adoc#D-066[D-066])
  -- stays green, in CI and on SonarQube.  Code that is hard to cover is
  restructured until it is not; exclusions are for generated code only.
* No temporal words in file names.  Match the surrounding code's idiom.

== Commands

[cols="1,3"]
|===
|Track |Verify with

|proto
|`buf format --diff --exit-code && buf lint && buf breaking --against '.git#branch=main' && buf generate`

|server
|`cd server && JAVA_HOME=$(sdk home java 25-amzn) ./mvnw -q verify` (Testcontainers need Docker running); coverage lands in each module's `target/site/jacoco/jacoco.xml`; `tools/coverage/jacoco-gate.sh server/*/target/site/jacoco/jacoco.xml` applies the 95% line and branch gate; `make sonar-server` uploads it (token from `SONAR_TOKEN` or `~/.sonar-token`).  Performance budgets are not part of this run (they would fail on a loaded machine for no fault of the code): `cd server && JAVA_HOME=$(sdk home java 25-amzn) ./mvnw -Pperf -pl wt-crdt,api -am verify -Dgroups=perf` runs them locally, best on an idle machine -- under load each skips with the measured load as its reason -- and writes the figures to `wt-crdt/target/perf-results.md` and `api/target/perf-results.md` (xref:testing.adoc#perf-runs[Testing, Where budgets run])

|client
|`make client-test` (every package's `swift test --enable-code-coverage`, then `xcodebuild test -enableCodeCoverage YES`), which also writes `client/build/coverage/sonar.xml` and the `*.regions.json` exports and fails below 95% lines or 95% llvm-cov regions (the client's branch gate, D-066); `make sonar-client` uploads it (token from `SONAR_TOKEN` or `~/.sonar-token`).  Timing budgets are not part of this run (debug builds on a loaded machine say nothing about the code): `make client-perf` runs them -- every package that holds a `PerfBudget` in release with `WT_PERF=1`, one test at a time, then the app's two budget suites -- best on an idle machine; under load each skips with the measured load as its reason, and the figures go to `client/build/perf-results.md`.  One package: `WT_PERF=1 swift test -c release -Xswiftc -enable-testing --no-parallel` (xref:testing.adoc#client-perf-runs[Testing, Client budgets])

|crdt
|Both engines' tests plus `make conformance`

|docs
|`make docs-check` (which runs `make help-catalog-check` first)
|===

[[help-catalog]]
=== Help catalog

The app's Help panel (BASIC-007) searches and shows the user guide from a generated Swift file,
`client/WTApp/Help/HelpCatalog.swift`: per guide page its slug, title, group, summary, section
headings and most frequent words, read from `docs/guide` and the guide half of each included
page (everything before its `ifdef::spec[]`).  `tools/help/help-catalog.py` writes it
deterministically, so the committed file is compared byte for byte:

* `make help-catalog` regenerates it; run it after editing a guide page and commit the Swift
  beside the page.
* `make help-catalog-check` fails when the committed file differs from what the guide gives.
  `make docs-check` runs it, and the client workflow runs it before the package tests, as the
  proto workflow fails on generated-Swift drift.

[[help-book]]
=== Help Book

The Help panel shows the rendered guide when the app carries it (BASIC-007): `make help-book`
(`tools/help/help-book.sh`, which needs the asciidoctor CLI) renders every guide page to
`client/build/HelpBook/<slug>.html` and checks each catalog slug has one, and the app target's *Help
Book* build phase copies the folder into the bundle's `Resources/HelpBook`.  Run it before a release
build; without it the panel falls back to pages generated from the catalog.

== Reporting a task

The report names: the task id; files created and changed; the exact verify commands run and
their result; deviations from the spec and where they were recorded; anything left for the
next task.  The coordinator commits one task per commit with the id in the subject.
