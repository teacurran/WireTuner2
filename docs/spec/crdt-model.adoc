= CRDT model
include::_attributes.adoc[]
:page-slug: crdt-model

A {product} document is an operation-based CRDT whose schema is written in protobuf.  Every
replica -- each Mac with the document open, and the server's snapshotter -- applies the same
operations and reaches the same state regardless of the order in which it received them.

We do not adopt Automerge, Yjs or Loro.  None of them has production-ready bindings for both
Swift and the JVM today, and each would put an FFI layer and an opaque binary between our
protobuf schema and our merge logic (xref:decisions.adoc#D-001[D-001]).  Instead we implement
well-published algorithms directly, in both languages, against one generated schema:

* last-writer-wins registers ordered by Lamport ids, for properties;
* Kleppmann et al.'s highly-available *move* operation for the node tree
  (https://martin.kleppmann.com/papers/move-op.pdf[TPDS 2021]), the same algorithm as Loro's
  movable tree;
* jittered fractional indexing for sibling order (z-order) and short ordered lists, as Figma
  does (https://www.figma.com/blog/realtime-editing-of-ordered-sequences/[Evan Wallace]);
* Fugue for character sequences, with Peritext's anchoring for formatting marks
  (https://www.inkandswitch.com/peritext/[Ink & Switch]).

== Identifiers

`OpId`:: `(counter: uint64, replica: fixed64)`.  Every operation has one.  `counter` is a Lamport
clock: a replica's next counter is one more than the largest counter it has created *or seen*.
Ids are totally ordered by `counter`, then `replica` as an unsigned integer.  This total order
decides every last-writer-wins tie, so it is the most important comparison in the system; it
never involves wall-clock time or floating point.

Replica id:: A random 64-bit value chosen by the client for each (install, document) pair, and
stored in the document's local store.  It is regenerated whenever the store is restored from
backup or copied to another Mac (the store records the hardware UUID it was created on) and
whenever the server answers `REPLICA_CONFLICT`.  The server binds a replica id to the user and
device that first used it and rejects it from anyone else.  Replica `0` is reserved for the
well-known nodes below.

Node id:: The `OpId` of the operation that created the node.

Element id:: The `OpId` of the operation that inserted an element into a sequence (a point in a
contour, a fill in an appearance stack, a character in text).  An insert of *n* elements takes
*n* consecutive counters.

== The node tree

Everything in a document is a *node*: pages, layers, paths, groups, text blocks, swatches,
styles, symbols.  Nodes form one tree.  Each node has an immutable `kind`, a mutable parent, a
position among its siblings, a `deleted` flag and typed properties.

[listing]
....
document (0:0)
├── settings    (0:1)   units, default attributes, print & export settings; ── custom_view …
├── pages       (0:2)   ── page …                       (order = page order)
├── masters     (0:3)   ── master page …
├── layers      (0:4)   ── layer …  ── object …         (order = stacking, bottom first)
│                                        └── group ── object …
├── swatches    (0:5)   ── color / tint / gradient swatch …
├── styles      (0:6)   ── graphic style / text style …
├── symbols     (0:7)   ── symbol ── object …           (Library panel; also hose_set ── object …)
├── brushes     (0:8)   ── brush …
├── assets      (0:9)   ── asset (image, font, embedded file blobs) / script …
├── trash       (0:10)  (reserved; deleted nodes stay in place, see Deletion)
├── glyphs      (0:11)  ── glyph …   (typeface documents only; a glyph is a canvas like a page)
└── comments    (0:12)  ── comment_thread …   (conversation, not artwork; never rendered or exported by default)
....

The well-known nodes (replica `0`, counters `0`--`15`) exist in every document without being
created; counters `13`--`15` are reserved for future collections.  Their counters are the
`WellKnown` enum in `doc/v1/node.proto` (`WELL_KNOWN_DOCUMENT = 0` ... `WELL_KNOWN_COMMENTS =
12`).  `glyphs` is empty in an illustration document (xref:typeface-documents.adoc[Typeface
documents]).

A node's kind is the set case of the `NodeProps.kind` oneof (`doc/v1/node.proto`).  Its field
numbers are allocated in blocks per epic so parallel schema tasks never collide
(xref:decisions.adoc#D-065[D-065]); the table is repeated at the top of `node.proto` and a task
adds its case there:

Artwork lives under layers: a top-level object's parent is its layer, and its
position among the layer's children is its stacking order.  Objects sit on one large pasteboard
in pasteboard coordinates (points, 1/72 inch, y down, origin at the pasteboard's top left); a
page is a rectangle on the pasteboard, and "the objects on page 3" is a geometric query, not a
tree relationship.  Master pages are separate canvases: a top-level object carries
`CommonProps.canvas`, unset for the main pasteboard or the id of the master page it belongs
to, so layers remain the single stacking hierarchy for every canvas.

== Merge policies [[options]]

Every field of every props message has a merge policy, declared with a `wt.crdt` field option:

[source,protobuf]
----
// proto/wt/crdt/options.proto
syntax = "proto3";
package wt.crdt;

import "google/protobuf/descriptor.proto";

enum Merge {
  // Scalars, strings, bytes, enums and repeated scalars: ATOMIC.
  // Singular message fields: STRUCT.
  MERGE_UNSPECIFIED = 0;
  // The whole value is one register; the op with the greatest OpId wins.
  MERGE_ATOMIC = 1;
  // Each field of the message is its own register (recursively).
  MERGE_STRUCT = 2;
  // A repeated message whose first field is `ElementId id = 1`.  Elements are inserted,
  // moved and deleted individually; order is a fractional position per element (LWW);
  // each element's fields merge as STRUCT.
  MERGE_SEQUENCE = 3;
  // A RichText field: Fugue character sequence plus Peritext formatting marks.
  MERGE_TEXT = 4;
  // A repeated scalar, or a repeated ElementId/OpId, treated as an add-wins observed-remove
  // set; members compare by value.
  MERGE_SET = 5;
  // A message with an enum discriminator (`kind`) and one sibling STRUCT message per case.
  // The discriminator is a register; every case's fields are registers that survive a
  // concurrent kind switch, so switching back restores them.  Preferred over `oneof` for
  // anything users toggle between (fill kinds, effect kinds): a protobuf oneof drops the
  // inactive case and has no defined merge for its discriminator.
  MERGE_VARIANT = 6;
}

enum RefFallback {
  // Reference to a deleted or unknown node reads as unset.
  REF_FALLBACK_UNSET = 0;
  // Read the value cached beside the reference (see NodeRef.cached).
  REF_FALLBACK_CACHED = 1;
  // The referencing node renders as a placeholder until the reference resolves.
  REF_FALLBACK_PLACEHOLDER = 2;
}

message FieldOptions {
  Merge merge = 1;
  RefFallback on_dangling = 2;
  // Never leaves the device: view state stored in the document for convenience
  // (<<local-only>>).  Only on an ATOMIC field, or a STRUCT or VARIANT one with nothing but
  // registers beneath it.
  bool local_only = 3;
}

extend google.protobuf.FieldOptions {
  FieldOptions field = 51234;
}
----

Annotate a field only when its default is not what you mean.  The two defaults cover most
fields: a `double width` is ATOMIC, a `BasicStroke stroke` is STRUCT.

.Choosing a policy
[cols="1,3"]
|===
|Use |When

|ATOMIC on a message
|Its fields only make sense together.  `Color`, `Transform` (a 2×3 matrix), `Point`,
`DashPattern`, a gradient's axis.  Merging a rotation from one user with a scale from another
per matrix component produces a shear nobody drew; one of them winning is correct.

|STRUCT
|Its fields are independent choices.  A stroke's width, cap, join and miter limit; a text
block's inset and column count.

|SEQUENCE
|An ordered list whose elements have identity and are edited in place: contour points, the
fill/stroke/effect stack, gradient stops, tab stops, table columns, chart data rows.

|TEXT
|User-typed text.  Only `RichText` fields.

|SET
|Membership with no order: the members of a named selection, keyword tags.
|===

----

Registers are addressed by a *field path*: a list of segments from `NodeProps`, each either a
field number or, inside a SEQUENCE, an element id (`FieldPath` / `PathSegment` in
`common.proto`).  `[kind.path=20, contours=2, <elem 91:7>, points=3, <elem 91:12>, anchor=2]`
addresses one anchor point.  The generated merge tables tell both engines which segments are
STRUCT, SEQUENCE and so on; the engines themselves contain no per-feature code.

[[field-paths]]
=== Field paths and registers

Both engines resolve a path the same way (CRDT-001, extended by CRDT-004 and CRDT-007;
`PathResolver` in `WTCRDT` and `wt-crdt`).  The first segment must be the node's kind (the set
case of `NodeProps.kind`); each later segment is looked up in the merge table of the message
reached so far, and an element segment may follow only a SEQUENCE field.

* A path ending at an ATOMIC field is one register.  Its value is that field's protobuf records
  in `values` exactly as they arrived (tag and payload, every occurrence in order), or *unset* when
  `values` holds none.  Proto3 cannot tell a default scalar from an absent one, so writing a
  default value and clearing the field are the same write.
* A path ending at a STRUCT field, or at a sequence element, stands for every register beneath it
  in the table, each written from `values` (leaves absent from `values` are written unset).  A
  message already on the current branch of the walk is not entered again, so a recursive schema
  expands finitely and identically in both engines.  An element's `id` (field 1) is never a
  register: it is the element segment.
* Beneath a MERGE_VARIANT message that is present in `values`, only the case messages present are
  written; the discriminator and non-case fields are written as usual.  A kind switch therefore
  never touches another case's registers.  A variant that is cleared (absent from `values`) clears
  every case.
* A SEQUENCE field is entered only through an element segment naming an element that exists
  (inserted and not collected; a tombstone counts), so `[kind, contours, <elem 91:7>, points,
  <elem 91:12>, anchor]` addresses one register of a nested element.  `ElementInsert` names the
  SEQUENCE field itself; `ElementMove` and `ElementDelete` name elements; `SetAdd` and `SetRemove`
  name a SET field.  Each op uses only the targets its kind takes.
* A TEXT field is entered only through an element segment naming one of its newline characters
  (CRDT-006): `[kind, text, <char 40:3>, paragraph=6, alignment=1]` addresses one paragraph
  register.  Inside a character, fields 1--5 (`id`, `codepoint`, `deleted` and the two origins
  of `TextChar`) belong to the engine and are never registers; the character message is the
  type of field 1 (`chars`) of the TEXT field's message in the table.  `TextInsert`, `TextDelete`
  and `TextMark` name the TEXT field itself.
* A path is a no-op when a segment is unknown, runs past an ATOMIC or SET field, names an element
  that does not exist (or a character that is not a newline), puts an element segment anywhere
  but directly after a SEQUENCE or TEXT field, or names a field the op does not take (a whole
  SEQUENCE, SET or TEXT field in `SetFields`, a repeated or untyped message anywhere).  The other
  paths of the same op still apply.
* Element segments are transparent in `values`: at a SEQUENCE field the sparse message holds only
  the element the path names (its `id` is not checked), and the walk reads it like a STRUCT; at a
  TEXT field it holds a `RichText` whose `chars` hold only the character the path names.
* The engines walk `values` at the wire level with the table, not through generated classes, so a
  field newer than the replica still merges and is kept byte for byte.  `values` that are not
  well-formed protobuf (for example an unknown group) make the whole op a no-op.

`CreateNode` writes, with its own OpId, only the leaves present in `props`; it is causally before
every other op on the node, so "never written" and "unset at the creation id" read the same.
SEQUENCE and SET fields in `props` are ignored: elements and members arrive by their own ops.  A
kind case must be a length-delimited record (as a protobuf parser reads a oneof of messages);
`props` without a known kind creates nothing.  Of the well-known nodes, `document` (0:0, kind
`document`) and `settings` (0:1, kind `settings`) carry properties; the other collections have
no kind, and field-path ops on them are no-ops.  A replay of an op already applied to a register,
element or set is ignored and not logged twice.

The engines use the table's policies as given.  A singular `NodeRef` field is one ATOMIC register
(*References* below) because `protoc-gen-wtcrdt` emits ATOMIC as its default policy, so an id's
counter and replica can never come from two different writes.  (CRDT-001 normalised this in the
engines; the generator does it since CRDT-002, which changed the merge table's `version`.)

[[local-only]]
=== Local-only fields

A `local_only` field is view state or a per-Mac value the document keeps for convenience -- zoom
and scroll (`SettingsProps.view`), the HTML setting selection and output folder, a linked file's
security-scoped bookmark (`AssetProps.bookmark`) -- that never leaves the device.  A register is
local-only when the walk to it crosses a field whose merge-table row says `local_only`: the field
itself, or a STRUCT, VARIANT or SEQUENCE field above it (`LocalOnly.enters` in both engines; the
walk is the one of <<field-paths>>, element segments skipped, so it needs no state).
`protoc-gen-wtcrdt` accepts `local_only` only on an ATOMIC field or on a STRUCT or VARIANT field
with no SEQUENCE, SET or TEXT field beneath it: local-only state is registers, never elements,
members or characters.

* *Merging.*  Neither engine merges a local-only register from a change: applied remotely (and
  replayed from a log), a write to one is a deterministic no-op, whether it comes from
  `SetFields`, `CreateNode.props` or `ElementInsert.values`, and a whole-STRUCT write above one
  neither sets nor clears it.  Local-only registers are therefore never in the state hash, a
  snapshot or garbage collection, and every replica's hash agrees
  (`registers/local-only-writes-ignored`).  A register an older engine merged into the shared
  state before this rule stays there, hashed like any other, and reads until this replica writes
  its own.
* *Local writes.*  WTCRDT's `applyLocal` -- the one way a replica applies its own new change --
  writes local-only registers into the replica's local registers (`NodeStore.localRegisters`,
  last writer wins by OpId, no change log), which `register` and WTModel's `props` read like the
  rest, and lists them in `localOnlyWrites`.  Undo records and restores them like any register;
  the undo stack is local.  wt-crdt never writes one: every change is remote to the server.
* *The outbox.*  `LocalOnly.strip` takes a change's local-only content out: a `SetFields` loses
  the paths that enter a local-only field and becomes a `Noop` (keeping its counter) when none is
  left, and the `NodeProps` of `CreateNode`, `SetFields`, `ElementInsert`, `SetAdd` and `SetRemove`
  loses its local-only fields at any depth -- the wire records of a STRUCT, VARIANT or SEQUENCE
  field are stripped in place (an element's `id` and a character's engine fields 1-5 untouched),
  a changed record written again as tag, length and payload, everything else copied as it came.
  Both engines strip alike (`registers/local-only-strip`); the walk looks only into messages a
  local-only field can be reached from (`Schema.localOnlyReach` in WTCRDT).  WTModel's
  `DocumentCore` applies the whole change and hands the backend the stripped one
  (`Outcome.outbox`; `applyLocal` notes, from the bytes it applies, whether the change carries
  anything to strip -- `localOnlyCarried` -- so a change without any is passed on as it is) with
  the local-only writes (`Outcome.localOnly`); `WTSync.LocalStore` appends the stripped change to the outbox and
  keeps the writes in the `view` table in the same transaction (offline.adoc), and restores them
  whenever it loads or replaces the state (open, snapshot install, salvage, discard).  Since the
  outbox, the snapshot and the shared state never hold them, nothing built from those -- a push,
  a bulk upload, salvage, a branch, a fork, a package export (`PackageReissue` also skips them) --
  carries a local-only value.
* *The server* strips every pushed change the same way before it checks and logs it
  (sync-protocol.adoc, "Server log"), so an older client's local-only writes are neither refused
  nor stored.

As built to close the gap DOC-022 and WEB-007 recorded as deviations (their workarounds -- values
kept under ad-hoc `view` keys -- are gone); the merge semantics' version is 0.5.0 in both
engines.

== Operations

Operations are fixed; features add fields, not operations.

[source,protobuf]
----
// proto/wiretuner/doc/v1/ops.proto (PROTO-003; the file is normative and adds the
// protovalidate caps: positions <= 1 KiB, <= 32,000 elements per insert or delete,
// <= 64 KiB of characters per TextInsert)
message Op {
  oneof op {
    CreateNode create = 1;
    SetFields set = 2;
    MoveNode move = 3;
    SetDeleted set_deleted = 4;
    ElementInsert element_insert = 5;
    ElementMove element_move = 6;
    ElementDelete element_delete = 7;
    TextInsert text_insert = 8;
    TextDelete text_delete = 9;
    TextMark text_mark = 10;
    SetAdd set_add = 11;
    SetRemove set_remove = 12;
    Noop noop = 13;            // keeps a counter slot when the outbox coalesces an op away
  }
}

message CreateNode {        // node id = this op's id
  OpId parent = 1;
  bytes position = 2;       // fractional index among the parent's children
  NodeProps props = 3;      // kind (the oneof case) + initial values
}
message SetFields {
  OpId node = 1;
  repeated FieldPath paths = 2;   // registers written by this op
  NodeProps values = 3;           // a sparse NodeProps holding the new values; a path listed
                                  // in `paths` with no value in `values` CLEARS that register
                                  // (writes unset with this op's OpId), e.g. removing a style override
}
message MoveNode { OpId node = 1; OpId parent = 2; bytes position = 3; }
message SetDeleted { OpId node = 1; bool deleted = 2; }
message ElementInsert {     // element ids = this op's counter, counter+1, ...
  OpId node = 1;
  FieldPath sequence = 2;
  repeated bytes positions = 3;
  NodeProps values = 4;     // sparse, holding the inserted elements
}
message ElementMove { OpId node = 1; FieldPath element = 2; bytes position = 3; }
message ElementDelete {     // writes each element's `deleted` register; `deleted = false` restores it
  OpId node = 1;
  repeated FieldPath elements = 2;
  bool deleted = 3;         // default true; false = restore (the review sheet's Restore)
}
message TextInsert {        // character ids = this op's counter, counter+1, ...
  OpId node = 1;
  FieldPath text = 2;
  ElementId left_origin = 3;   // Fugue origins; zero id = start / end
  ElementId right_origin = 4;
  string chars = 5;
}
message TextDelete { OpId node = 1; FieldPath text = 2; repeated ElementIdRange ranges = 3; }
message TextMark {
  OpId node = 1;
  FieldPath text = 2;
  Anchor start = 3;          // Peritext: before/after a character id
  Anchor end = 4;
  TextMarkValue value = 5;   // font, size, color, style ref, ... (see Type pages)
}
----

A *change* is the atomic unit a user action produces -- one drag of fifty objects, one
paste, one typed word -- and the unit of sync, undo and history.

[source,protobuf]
----
message Change {
  fixed64 replica = 1;
  uint64 seq = 2;               // 1, 2, 3 ... per replica, no gaps
  uint64 start_counter = 3;     // op i has counter start_counter + i, plus the extra counters
                                // the inserts before it took (one per element or character)
  uint64 base_server_seq = 4;   // causal past: everything the server had sequenced up to here
  int64 wall_time_ms = 5;       // informational only (history UI); never used to merge
  string label = 6;             // "Move 3 objects": history and undo menu
  repeated Op ops = 7 [(buf.validate.field).repeated.max_items = 10000];
}
----

The server is the hub, which keeps causality cheap: everything a client knows about other
replicas came from the server's log in order, so a change's causal past is exactly "the server
log up to `base_server_seq`, plus this replica's earlier changes".  No vector clocks or hash
DAGs travel with changes (xref:sync-protocol.adoc[Sync protocol]).

[[changes]]
In detail (CRDT-008; `apply(change, serverSeq)` in both engines): a change applies as a unit --
its ops in order, op _i_ at `start_counter` plus the counters the ops before it took -- and is
then recorded against its replica: the highest `seq` applied and the greatest `base_server_seq`
seen, which is how far the replica has acknowledged the server's log (`ReplicaState`).  Every op
is recognised by its OpId, so a change delivered again, or a replica's changes delivered out of
seq order when they do not depend on each other, converge with one in-order delivery
(`changes/replay-whole-changes-out-of-order`).  A `Noop` takes one counter and changes nothing.
A `MoveNode` whose own id is the node it names is a no-op: a node's id is the id of the
`CreateNode` that made it, so only a malformed change can say that (and a snapshot can then tell
a logged create from a logged move by `op == node` alone).  Losing writes stay in each register's
change log (the conflict review's source); they are not part of the state, the hash or a
snapshot.

== Merge rules

Registers:: A register holds `(value, OpId)`.  Applying a write whose OpId is greater than the
register's replaces it; otherwise the write is ignored but *retained in the change log*, so the
conflict review can show the losing value and offer it back.  Unset is a value: a
`SetFields` that lists a path without a value writes `(unset, OpId)`, so clearing a field (a
style override, an attached URL) competes with concurrent writes by the same rule instead of
reverting to the schema default silently.

Tree moves:: Parent and position change only through `CreateNode` and `MoveNode`.  All tree
ops are applied in OpId order using the undo-do-redo scheme of Kleppmann et al.: when an op
arrives out of order, later moves are undone, the new op applied, and the later ones redone.  A
move that would make a node its own ancestor is skipped.  Only moves not yet causally stable
need to be kept for this, which keeps the log short.
+
In detail (CRDT-002; `Tree` in both engines): every `CreateNode` and `MoveNode` is logged
(`MoveLogEntry`: the op, the node's placement before it, whether it applied), so a replayed op is
recognised by its OpId and ignored.  In OpId order, a `CreateNode` makes its node exist and
places it under its parent when the parent exists; otherwise the node exists without a parent
(not rendered) until a move places it.  A `MoveNode` applies when the node and the parent exist,
the node is not well-known, and the parent is neither the node nor one of its descendants;
otherwise it is skipped (logged with `applied = false`).  A node's placement records the op that
set it.  The well-known nodes always exist and never move: 1..15 sit under the document (0:0)
with an empty position, so they sort by id before any user node placed under the root.  Under
causal delivery a late op is at worst a few hundred entries from the end of the log; applying a
move that precedes the last 1,000 tree ops on a 50,000-node tree takes 0.77 ms (Swift, release,
M-series) and 0.4 ms (Java, under JaCoCo).

Sibling order:: Children sort by `position` (bytewise), then by node id.  Positions are
fractional-index byte strings generated between neighbors with a random suffix, so two people
inserting "between the same two objects" at once almost never produce equal keys, and the node
id breaks any tie.  Positions are never rebalanced.  Interleaving of concurrent inserts, a
known weakness of fractional indexing, is harmless for stacked objects and list items.
+
Generation (CRDT-003; `FractionalIndex` in both engines, which produce the same key from the same
random value): digits are bytes, and a generated key is never empty and never ends in `0x00`, so
there is always room below it and between it and a longer key.  With no neighbours the body is
`80`; after the last key `lo`, `lo` up to its first byte below `FF`, that byte plus one; before
the first key `hi`, `hi`'s leading zeros then its first other byte minus one (`01` becomes
`00 FF`); between `lo` and `hi`, their common prefix, then the midpoint digit when the next digits
differ by two or more, else `lo`'s digit followed by the "after" body of the rest of `lo`.  The
body is never a prefix of `hi`.  Two suffix bytes follow, from one 64-bit random value `r`:
`r & FF` and `1 + (r >> 8) mod 255`.  Appends grow by one byte per ~128 keys (1,000 sequential
appends stay at 11 bytes), and so do prepends.

Deletion:: `deleted` is a register on the node.  A deleted node keeps its properties, children
and history; it is simply not rendered or selectable.  Edits to a deleted node still apply, so
restoring it (writing `deleted = false`) restores them too.  The conflict review lists "edited
something that was deleted" and offers *Restore*.  `SetDeleted` on a well-known node or on a node
not created is a no-op.

Sequences:: An element is an id, a position register, a deleted register and STRUCT fields.
Inserting, moving and deleting elements are independent registers, so one user reordering the
fill stack while another edits a fill's color keeps both.
+
In detail (CRDT-004): an `ElementInsert` of _n_ positions takes _n_ counters; element _i_ has id
`(counter + i, replica)`, its position register holds `positions[i]` stamped with that id, and its
initial fields are the leaves present in the _i_-th occurrence of the SEQUENCE field in `values`
(written with the element's id, `id` ignored; fewer occurrences than positions leave the rest
without fields).  An element that already exists is not inserted again.  `ElementMove` writes the
position register and `ElementDelete` the deleted register of each named element, both by
last-writer-wins with the losing writes retained; `deleted = false` restores.  Elements read by
position (bytewise), then id, tombstones included until collected.

Text:: Fugue ordering of character elements (maximally non-interleaving for concurrent typing
at the same spot).  Deleted characters remain as tombstones until causally stable.  Formatting
is a set of marks anchored to character ids (Peritext): a mark's span grows as text is typed
inside it and follows its characters when others edit nearby.  Paragraph properties (alignment,
indents, tabs, rules, spacing, paragraph style) are STRUCT registers on the paragraph's
terminating newline element, so they travel with the paragraph.
+
In detail (CRDT-005; `TextSequence` in both engines): a `TextInsert` of _n_ Unicode scalars takes
_n_ counters; character _i_ has id `(counter + i, replica)` and origins (`left_origin`,
`right_origin`) for the first, (character _i_ - 1, `right_origin`) for the rest.  Each character
is placed in the Fugue tree from its origins alone, so every replica places it alike: it becomes
the *left child* of its right origin when that character is deeper in the tree than its left
origin (the start of the text has depth 0), otherwise the *right child* of its left origin (or of
the start).  For origins a client took from adjacent characters this is exactly Fugue's rule (one
origin is always an ancestor of the other), and a typed run becomes one chain, so two runs typed
at one spot never interleave; comparing depths instead of walking ancestors keeps an insert
constant-time in a deep chain.  Siblings order by id, ascending, and the text reads in order:
left children, the character, right children -- so concurrent runs at one spot read in the order
of their first characters' OpIds (`text/concurrent-forward-typing`, `text/concurrent-backward-typing`,
`text/concurrent-typing-into-empty-text`).  An origin that is not a character of the field makes
the op a no-op (the hub delivers causally, so a legitimate origin always exists); a character
already present is not inserted again.  `TextDelete` names runs of consecutive ids; each character
of the field among them becomes a tombstone that keeps the greatest delete OpId.  Read-outs: the
plain string of live characters, character id <-> live offset (a tombstone's offset is where it
would be), and the origins a client gives an insert at an offset (the live character before it and
that character's successor, tombstones included -- except tombstones stable at the replica's horizon,
which the right origin skips, <<gc>>).  The order is kept in blocks of at most 512
characters with live counts: an insert into a 200,000-character text takes 0.57 µs (Swift,
release, M-series) and 1.0 µs (Java), against the 50 µs budget.
+
In detail (CRDT-006): a `TextMark` is kept by its OpId with its two anchors and its
`TextMarkValue` bytes; an anchor naming a character the field does not hold makes the op a no-op.
A character is covered when it lies between the anchors, each anchor sitting just before or just
after its character (the zero id is the start with `before` and the end with `after`), so an
anchor `before` the next character grows with typing at the end of the span and one `after` the
last character does not -- the per-attribute choice on xref:creating-text.adoc[Creating text] is
the client's, made when it writes the anchors.  A mark formats one attribute, its *key*: the field
number of the value's last record (a oneof case), and for the case named `feature` in the table
(`RichText.marks` -> `TextMark.value` -> the row named `feature`) also that message's `tag`
records, so features of different tags stack.  Each character shows, per key, the value of the
covering mark with the greatest OpId; a value whose payload is its default (a zero scalar, an empty
string, a feature with nothing but its tag) reads as the attribute *cleared* and is left out.
*Runs* are the maximal ranges of live characters with the same winning marks, with their
attributes ascending by key (`marks/typing-inside-and-at-the-edges`, `marks/overlapping-marks`).
Paragraph registers live under the newline's element segment (<<field-paths>>) and merge like any
register (`marks/paragraph-split-vs-style-change`, `marks/paragraph-join-vs-style-change`).

Sets:: Add-wins: a concurrent add and remove of the same member keeps it.
+
In detail (CRDT-007): a set is an observed-remove set whose tags are the `SetAdd` ops.  A
`SetRemove` carries only values, so what it observed is its causal past as the hub defines it
(*Operations* above): an add is observed by a remove when it is an earlier op of the same replica,
or when the server sequenced the add's change at or before the remove's `base_server_seq`.  A
member is present while any of its adds is observed by none of its removes.  The engines are
therefore told each change's `server_seq` when it is known -- `apply(change, serverSeq)` for a
change from the server's log, `acknowledge(replica, seq, serverSeq)` when a local change is acked
-- and presence is computed from the logged adds and removes, so a late ack or any arrival order
gives the same result.  Members compare by value in a canonical form: a string's or bytes'
payload; a varint scalar's value as a big-endian uint64 (packed or not); a fixed-width scalar's
little-endian wire bytes; an `ElementId` or `OpId` as its counter and replica, big-endian (field
order and unknown fields ignored).  A record of the wrong wire type, or a packed run or id that
does not parse, holds no member.  (Deviation, CRDT-007: the rule needs the server's sequence
numbers, which `SetRemove` cannot carry; the engine API takes them beside the change.)

References:: A `NodeRef` is an ATOMIC register.  If its target is deleted, unknown or the wrong
kind, readers apply the field's `on_dangling` fallback; references never block a merge.

Totality:: Every op applies to every state.  An op naming an unknown node, a wrong-kind field,
or a malformed path is a deterministic no-op in both engines.  The server rejects such ops on
ingest where it can cheaply tell, but the engines never assume it did.

== Normalize on read

The model layer (`WTModel`) interprets merged states that violate an invariant, deterministically,
without writing anything:

* A text flow chain that forms a loop is cut at the link with the smallest node id.
* A blend whose endpoint is no longer a path renders as its endpoints only.
* A symbol instance whose symbol is deleted renders as a hatched placeholder with the symbol's
  name (`REF_FALLBACK_PLACEHOLDER`).
* A clipping group with no remaining clip path renders its contents unclipped.

Each feature page lists its own read-time normalizations under *Merge semantics*.  If a user
then edits the object, the ordinary command writes a valid state.

== Undo

Undo is per user and local.  Undoing never rewinds the shared document; it writes a new change.

* When `WTModel` applies a local command, it records the inverse of each op against the state
  just before: the prior `(value, OpId)` of each register written, the prior parent and
  position of each moved node, the inserted element ids, the deleted characters.
* *Undo* emits a change restoring each prior value *only where nobody else has written the
  register since*: it still holds the value this user wrote, or a later one of this replica's own
  (its undo of a later change, say).  If someone else has since changed it, that part of the undo
  is skipped: undo never reverts other people's work.  Redo is symmetric.
* Undo of a creation sets `deleted = true`; undo of a deletion sets it back to `false`.  Undo of
  typed text deletes the inserted character ids; undo of a deletion re-inserts the text as new
  characters at the original anchor.
+
The engines record and build this (CRDT-008): `applyLocal(change)` applies a local change and
returns its `Inverse`, one step per effect in application order -- a register's prior
`(value, OpId)` and the OpId written, a node's prior placement, a `deleted` flag's prior write, an
inserted element, an element's prior position or flag, a set member added (and whether it was a
member before) or removed, the characters inserted, the characters deleted with their scalars, the
attribute values they showed and a newline's paragraph registers, and for a mark each covered
character's prior value of its attribute.  `undoChange(inverse, replica, seq, startCounter, ...)`
returns the change that undoes it against the current state, or none when nothing is left: the
change is undone as a unit, so where several of its ops touched one target the value before the
first is restored if no other replica has written the target since the last write (the state holds
that write or a later one by `replica`, CRDT-010); a creation or insert is undone unless another
replica wrote its `deleted` flag since; a member is re-added only if it is absent now and removed
only if the change's own adds and `replica`'s are all that hold it; a target garbage collection
dropped is skipped; deleted text goes back as new
characters after the last tombstone of each adjacent run, with marks restoring its attributes
(anchored `before` the first and `after` the last new character) and its newlines' paragraph
registers; a mark is undone by marks restoring the prior values (or a cleared value) on the
characters it still wins; characters the change itself inserted are not re-inserted.  Applying the
undo with `applyLocal` gives the inverse that redoes it.  `InverseTest`/`InverseTests` apply every
op kind, undo and redo, and compare the document a user sees (values, live nodes, elements,
members, strings, runs, paragraphs -- not OpIds, which an undo writes anew), and check that undo
skips each kind of target someone else changed.
* The undo stack survives relaunch (it is kept in the local store) and is capped by the
  *Undo levels* preference (xref:undo.adoc[Undoing actions]).

== Snapshots

A `DocumentSnapshot` (`doc/v1/snapshot.proto`) is the full merge state at a server sequence
number: every node with its registers and their OpIds (`NodeState`: a plain `Node` plus a
`RegisterStamp` per written path and an `ElementState` per sequence or text element), sequence
elements including unstable tombstones, the unstable part of the move log (`MoveLogEntry`), and
each replica's highest applied seq and acknowledged server sequence (`ReplicaState`).  Snapshots
are zstd-compressed protobuf, chunked to 1 MiB for transfer (`SnapshotFrame`: a `SnapshotHeader`
first, then `bytes chunk` frames, mirroring the blob service), and carry a `state_hash` (SHA-256
over the canonical encoding of the state, <<canonical-encoding>>) that both engines compute
identically.  Clients compare their own hash to the server's at the same sequence number and
collection point (<<gc>>) whenever their outbox is empty.  A mismatch is a bug report plus an
automatic re-bootstrap from the snapshot.

[[snapshot-encoding]]
=== Snapshot encoding

As built by CRDT-009 (`Snapshot` and `SnapshotTransfer` in both engines).  The engines write the
`DocumentSnapshot` themselves, field by field in field-number order with proto3 defaults left
out, rather than through generated classes: a register's value is its records exactly as they
arrived, which swift-protobuf and protobuf-java re-serialise differently when fields are unknown
to them.  The bytes are therefore canonical, the same in both engines for the same state, and
independent of delivery order; every conformance vector pins them (`snapshot_hash`).

* `nodes`: every node the state hash covers, by id.  `Node.props` is assembled from the register
  paths: the kind case, fields in number order, a SEQUENCE field as one occurrence per element
  (tombstones included, in sequence order, `id` first), a TEXT field as its `RichText` (`chars`
  in document order with `id`, `codepoint`, `deleted`, the origins and the paragraph registers,
  then `marks` by id).  `registers` stamps every written register by path; an unset register has
  a stamp and no value.  `elements` holds every sequence element and every character by path (a
  character's position is empty; its `deleted_op` is its greatest delete).  `tree_op` and
  `deleted_op` as the proto describes.
* `move_log` in OpId order, `replicas` by id (highest seq, greatest `base_server_seq`, stable
  counter), `stable_seq` (the stable point last collected at, <<gc>>), `max_counter` (the clock);
  `feature_level` 0 until the feature levels exist.
* `state_hash` is `StateHash` of the state (<<canonical-encoding>>), not a hash of the snapshot's
  own bytes: the client compares it with the hash of its own state without encoding a snapshot,
  and it does not change with the move log's pruning or replica bookkeeping.  Decoding recomputes
  it and refuses a snapshot that differs.
* The engine bookkeeping CRDT-009 wrote at proposed numbers is declared in snapshot.proto since
  CRDT-010, which added what garbage collection needs: `NodeState.sets` (`SetState`: path;
  `SetMemberState`s, each its canonical value and every `SetTag` add and remove with op, seq and,
  for removes, `base_server_seq` -- presence is computed from the history), `NodeState.texts`
  (the node's TEXT fields), `NodeState.deleted_wall_time_ms` (the wall time of the change that
  wrote the current `deleted` value, which starts the 30 days before compaction; 0 when unknown),
  `MoveLogEntry.old_op` (the op of the placement the entry replaced, which undoing it restores),
  `ReplicaState.stable_counter` (every op of the replica below it is stable) and
  `DocumentSnapshot.sequenced` (`SequencedChange`: replica, seq, the server_seq when known, which
  set removes are judged by, and `end_counter`, one past the change's last counter, which
  collection folds into the replica's stable counter; every change the state records, sequenced
  or not).  A logged `CreateNode` is the entry whose `op` equals its `node` (*Operations*,
  CRDT-008).  The generated classes read every field the engines write (`CollectionTests` /
  `CollectionTest`).
* The change log (losing writes) is not in a snapshot; a decoded state logs only what it applies
  afterwards.  Round trips are lossless for everything else: decoding and re-encoding gives the
  same bytes, and the decoded state merges any later change exactly as the original does.

Transfer: `SnapshotTransfer.frames` writes the header (sizes, chunk and node counts, the
snapshot's `state_hash`) and the zstd-compressed snapshot in chunks of at most 1 MiB;
`assemble` checks the frames against the header and decompresses; `state` also checks that the
header names the snapshot's hash and decodes.  zstd is zstd 1.5.7 on both sides: zstd-jni in
wt-crdt, and in WTCRDT the upstream single-file library vendored as the `CZstd` C target
(`client/Packages/WTCRDT/Sources/CZstd`, BSD licence; Compression.framework has no zstd), built
without coverage instrumentation.  Both compress the design point to the same 3,843,456 bytes (3,661,516 before CRDT-010 added the change records' end counters).

The design point -- 50,000 nodes with 20 registers each (1,000,000) and five sequence elements,
plus a 200,000-character text; a 75 MB snapshot -- bootstraps (decompress, decode, verify the
hash) in 0.76 s (Swift, release, M-series; the decoder takes each node on its own, in parallel
across cores, and interns the register paths nodes share) and loads in 2.2 s on the JVM (the
server's snapshotter, not the budget).  `PerformanceTests` enforces the 1.5 s budget in release
builds.

[[canonical-encoding]]
=== Canonical encoding

CRDT-001 fixed the register part of the canonical encoding; CRDT-002, CRDT-004 and CRDT-007
added the tree placement, the `deleted` register, sequence elements and set members, and
CRDT-005/006 the TEXT fields (and every conformance vector's expected hash was re-recorded).
CRDT-009 left the move log and replica state out: they are bookkeeping of how the state was
reached, and CRDT-010's pruning of them must not change the hash.  The tombstones, set tags and
deleted nodes a collection drops are part of the state and leave the hash with it; the collected
state, and so its hash, depends only on the changes and the collection points, never on when a
collection ran (<<gc>>).  `StateHash` in both engines is SHA-256
over these bytes.  All integers are big-endian and fixed width:

[listing]
....
state    = u32 node_count, node*                                   nodes ascending by OpId
node     = id, u32 kind, tree, flag, u32 register_count, register*,
           u32 element_count, element*, u32 set_count, set*, u32 text_count, text*
tree     = u8 placed, [id parent, block position, id op]          placed = 1 iff it has a parent
flag     = u8 written, [u8 value, id op]                          the deleted register; written = 1 iff set
register = block path, id, u8 set, [block value]                  ascending by path; set = 1 iff not unset
element  = block path, block position, id position_op, flag       ascending by path
set      = block path, u32 member_count, member*                  ascending by path; non-empty sets only
member   = block value, u32 tag_count, id*                        ascending bytewise; live tags ascending
text     = block path, u32 char_count, char*, u32 mark_count, mark*   ascending by path; non-empty only
char     = id, u32 codepoint, id left_origin, id right_origin, u8 deleted, [id op]   document order
mark     = id, anchor start, anchor end, block value              ascending by id
anchor   = id, u8 before
path     = segment*
segment  = 0x01, u32 field_number | 0x02, id                      0x02: an element id
block    = u32 length, bytes
id       = u64 counter, u64 replica
....

* The nodes are every node created by an op plus every well-known node holding a register, a
  `deleted` write, an element, a set member's history or a TEXT field.  `kind` is the field number of the
  node's `NodeProps.kind` case (0 for none).  A well-known node 1..15 encodes as placed under 0:0
  with an empty position and op 0:0; the document root and a node without a parent as not placed.
* Paths order by their encoding compared bytewise, which equals comparing segments in order,
  shorter prefix first.  An element's path is its SEQUENCE field's path plus its element segment;
  a register inside an element continues from there.
* `value` is the register's stored records (see <<field-paths>>).  Losing writes retained in the
  change log are not part of the state and not hashed.  A set member's live tags are the OpIds of
  its adds that no remove observed (*Sets* above); a member without live tags is absent.
* The hash of one node is SHA-256 of its `node` encoding; the conformance runners use it to name
  the first differing node.

* A character's origins are the ones it was inserted with; `deleted` is 1 for a tombstone,
  followed by its greatest delete.  A mark's value is its `TextMarkValue` bytes.  A paragraph
  register is an ordinary register under its newline's path.

The empty state hashes to `df3f6198…b81119` (SHA-256 of four zero bytes); `StateHashTest` in both
engines pins a sample encoding (placement, `deleted`, a register, an element, a set member and a
text with a tombstone and a mark) byte for byte.

[[gc]]
== Garbage collection

Tombstones (deleted characters, deleted sequence elements) and move-log entries can be dropped
once they are *causally stable*: every replica that could still send an op referencing them has
acknowledged a server sequence past them.  The server tracks each replica's acknowledged
sequence and publishes the stable point.

* A replica silent for longer than the retention window (90 days by default, per team setting)
  is *retired* and stops holding back the stable point.  If it comes back, its unsent changes go
  through salvage (xref:offline.adoc#expiry[Offline]).  One or two days offline is far inside
  the window and never triggers this.
* Deleted *nodes* are not purged by stability alone: they stay restorable for 30 days, then are
  compacted out of new snapshots.  They remain in the cold change log for version history.

[[collection-points]]
=== Stable points, horizons and collection points

As built by CRDT-010.  A server sequence number _S_ is a *stable point* when every change
sequenced after it, and every change any replica will still push, has `base_server_seq` at least
_S_: all of them are causally after everything sequenced at or before _S_.  The smallest
acknowledged server_seq over the replicas that are not retired (`stablePoint(retired:)` in both
engines, from the `base_server_seq`s the state has seen; the server also counts the acks of
replicas that only subscribed) bounds every future change, but not a change pushed before its
author acknowledged further: min(acks) alone is *not* a stable point.  An op is *stable at* _S_
when its change was sequenced at or before _S_; a replica's changes are sequenced in seq order
and take increasing counters, so that is "its counter is below the replica's stable counter at
_S_" (`isStable(op, at:)`, `stableCounters(at:)`).

Replicas collect at different moments, so a collection must drop nothing that a change some
replica has not applied yet still names.  The protocol that guarantees it has two parts.

* *Horizon.*  Each replica keeps the newest stable point and clock the server has published to
  it, its horizon, and never writes an op that names something collectable there: the right
  origin of a text insert skips tombstones whose delete is stable at the horizon
  (`insertionOrigins(node, path, at:, stableSeq:)`; `TextSequence.insertionOrigins(at:skippingStable:)`),
  and no op names a stable tombstone (a delete, restore, move, edit or mark anchor) or a node that
  would compact at the horizon, or one below it (`isCompactable(node, stableSeq:, now:)`).  A
  change's horizon is the publication its author last received before pushing it.
* *Collection point.*  The server publishes a collection point (_C_, _T_): the stable point and
  clock it published at the moment every replica had received them (the smallest horizon over the
  replicas), lowered until no change sequenced after _C_ has a horizon below _C_ (or a clock below
  _T_).  Every replica collects at the collection points it receives, and so does the server's
  snapshotter; _C_ never exceeds what the collecting replica has applied.

A change some replica has not applied is either a future one (its horizon is at least the
smallest horizon) or one sequenced after _C_ (lowered past), so its author knew _C_ and _T_ and
named nothing a collection at (_C_, _T_) drops; and _C_ is a stable point, since a change's
`base_server_seq` is at least its horizon.  `FuzzGenerator.collectionPoint` in `WTCRDTTests` is
the reference computation; the fuzzer (xref:testing.adoc#fuzzing[Testing]) runs every replica
under this protocol.  The server side is built (SRV-007, SRV-013): each accepted change is stored
with its author's horizon, the Stability job computes (_C_, _T_) as above, `AckResponse` carries it
(`collect_seq`, `collect_time_ms`), and the snapshotter collects at it.  Deviation: the server
takes a change's horizon to be the publication its author had confirmed receiving when the change
arrived (xref:server.adoc[Server], Jobs, As built, which records where that can be too new).

[[collect]]
=== Collecting

`collect(stableSeq: C, now: T)` (`Engine.collect(stableSeq, Clock)` in wt-crdt; `now` defaults
to the system clock and is injectable) drops what _C_ makes stable, in this order:

. *Set history.*  A stable add that some remove observed is dead for good; a stable remove observes
  no add that is not stable (an add it observes was sequenced before it); both go.  A stable add no
  remove observed stays, and is judged from then on as sequenced at the stable point: every later
  remove's causal past reaches it.  A member left with no history goes.
. *Sequence tombstones* whose `deleted` write is stable go, with every register, nested element,
  set and text beneath them.
. *Character tombstones* whose greatest delete is stable go when no mark anchors them and no
  character hangs below them in the Fugue tree (`TextSequence.collectable`), deepest first, with
  their paragraph registers.  Dropping a childless character moves, re-orders and re-depths
  nothing, so the tree stays the one the remaining characters' origins build; a snapshot restores a
  character whose other origin was dropped from the origin that remains (only a character whose
  right origin was skipped as a stable tombstone can lose one).  A tombstone that later characters
  hang from stays until they go -- the interior tombstones of a run typed in one go are kept (the
  Eg-walker note under *Performance budget* is the way out if that ever matters).
. *Move-log entries* whose op is stable go.  Every later tree op is causally after them and has a
  greater OpId, so they are never undone again; the entries left keep the placement each replaced
  (`old_op`), which is all undoing them needs.
. *Change records* sequenced at or before _C_ go, folded into each replica's stable counter.
. *Deleted nodes* whose `deleted` write is stable and whose deletion's wall time (the writing
  change's `wall_time_ms`) is at least 30 days before _T_ are compacted with their subtree --
  unless an unstable move-log entry still names one of them (a node moved out of the subtree by a
  move not yet stable keeps the subtree until it is).

A point below the last one collects nothing; the same point again only compacts, by a later clock.
After a collection, an op below its replica's stable counter, and a change sequenced at or before
_C_, is a replay and is ignored (its effects are already in the state), and a late op naming a
dropped tombstone or node is a deterministic no-op by the rules above: an unknown text origin or
mark anchor drops the op (*Text*), an element segment naming no element makes the path a no-op
(<<field-paths>>), and ops on a node that does not exist are no-ops (*Totality*).  Only a replica
outside the protocol (a retired one bypassing salvage) sends such ops.

The state a collection reaches depends only on the changes applied and the collection points, not
on when each collection ran: collecting at _C_ and then applying more changes gives the same state,
snapshot bytes included, as applying them and then collecting
(`gc/hash-unaffected-by-prune-timing`).  Hashes are compared at the same server_seq *and*
collection point.  Vectors: `gc/prune-then-late-delete`, `gc/prune-then-late-insert-with-collected-origin`.

A node created and deleted within one replica's outbox stays in that replica's state -- deleted,
with its registers, in the hash -- until a collection compacts it, which needs the deletion to be
sequenced and stable: an outbox that coalesces the pair away never sends the deletion, so the
creating replica's hash keeps the node while every other replica's lacks it.

== Schema evolution [[evolution]]

* Fields and kinds are only added, never renumbered or retyped (`buf breaking`).
* `protoc-gen-wtcrdt` emits a merge table (field path → policy) that is also serialized into
  every `Welcome`, so a client that meets a field newer than itself still merges it correctly
  and preserves it for others.  The serialized form is JSON, not a protobuf message, so no
  schema of its own has to be versioned beside `doc.v1`: `Welcome.merge_table` carries the
  UTF-8 bytes of `MergeTable.json` (Swift) / `merge-table.json` (Java resource), the same
  document the generated `WTMergeTable` and `MergeTable` embed.  Its shape is
  `{"version", "messages": {"<message fqn>": {"fields": {"<field number>": {"name", "policy",
  "on_dangling", "local_only", "type", "repeated", "type_name", "element_message", "oneof"}}}},
  "variants": {"<message fqn>": {"kind_field", "case_fields"}}}`, with policies and fallbacks
  spelled as the `wt.crdt` enum value names without their `MERGE_` / `REF_FALLBACK_` prefix and
  field numbers as decimal strings.  `version` is the hex SHA-256 of the canonical encoding (keys
  sorted, no whitespace, `version` itself left out), so replicas compare tables without parsing
  them; readers ignore keys they do not know, and keys are only ever added.  The generator
  walks every message reachable from `NodeProps`, `CommonProps` and `Node` and fails on a policy
  that does not fit its field (a SEQUENCE element without `ElementId id = 1`, TEXT on anything
  but `RichText`, VARIANT without an enum `kind`, SET on anything but repeated scalars or ids, an
  unannotated repeated message or map).
* A feature whose *rendering* matters (a new effect type) bumps the document's feature level
  when first used; clients below it open the document read-only with an update prompt.

== Performance budget

Design point: 50,000 live nodes, 1,000,000 registers, 200,000 characters of text, 100,000 ops
per day across all collaborators.  Applying a typical remote change (under 50 ops) must take
under 1 ms on an M1; bootstrapping the design-point document from a snapshot must take under
1.5 s.  If text history becomes the bottleneck, the Eg-walker approach (store plain text plus
the event graph, rebuild CRDT state transiently to merge) is the planned optimization
(https://arxiv.org/abs/2409.14252[Gentle & Kleppmann, EuroSys 2025]).
