== Accounts

NOTE: As built (SEC-003): the account window lists every device (`ListDevices`) with its sign-in method and Revoke for other Macs; adding or removing linked identities opens the realm's account console on its linked-accounts page (*Add Sign-in Method…*, *Remove…*; `AccountService` has no RPC for it), and the list is read back with Refresh.  The team settings sheet covers members, invitations (resend = `InviteMember` again), default document access, domains with status and TXT record, and the three workspace switches; transfer, delete and leave team are not in the sheet, and the default role cannot be set back to None because `UpdateTeam` refuses UNSPECIFIED.  The history window (`history_retention_days`) is the sheet's *History* row: admins choose 30 days to 10 years (`TeamHistory`, `UpdateTeam`).  `wiretuner://invite/<token>`, an `https://…/invite/<token>` link or a bare token opens the Join Team sheet; the links host comes from `WT_LINKS_URL` (default `https://wiretuner.app`).

Every person has one *personal account*, identified by a Keycloak subject.  Sign-in is OIDC
with PKCE from the Mac (`ASWebAuthenticationSession`); Keycloak owns every credential and
the server never sees one.  The realm declares, in this order of preference:

Passkeys (WebAuthn)::
The preferred credential.  Keycloak's passwordless WebAuthn flow is the first option on the
sign-in page and is offered to every account that does not yet have one after its first
sign-in by any other means.  `ASWebAuthenticationSession` runs the platform authenticator, so
a passkey created on one Mac is in iCloud Keychain on the next.
Sign in with Apple::
Required by App Store guideline 4.8 as soon as any third-party sign-in is offered, and the
natural choice on a Mac.  Keycloak has no built-in Apple provider: it is configured as a
generic OIDC identity provider with `response_mode = form_post`, the `name` and `email`
scopes, and a client secret that is a JWT signed with the developer team's `.p8` key and
valid for at most six months -- the *Apple secret* job (xref:server.adoc[Server]) rotates
it every 30 days through the admin API.  Apple sends the user's name only on the first
authorization; the first-broker-login flow stores it then.  The generic OIDC provider is the
decision (xref:decisions.adoc#D-064[D-064]): no community extension to track, and the secret
rotation is a job we already run.
Email and password::
The fallback, with Keycloak's email verification and brute-force protection.
Workspace SSO::
A SAML or OIDC identity-provider connection per company workspace (below); a workspace may
require it for its members.

Every method ends in the same Keycloak subject, so the server sees one account.  Which method
signed in on a device is a claim in the access token (`wt_auth_method`, a protocol mapper:
`passkey`, `apple`, `password` or `sso:<idp alias>`) that SRV-002 records on the device row
the first time it sees the device; the account page's device list shows it beside each Mac.

Account linking:: A person who signs in by a second method must end up in the same account.
The rules, implemented as Keycloak's first-broker-login flow plus a server-side check:

* An identity whose email the provider asserts as *verified* links automatically to the
  existing account with that email (Apple sets `email_verified`; workspace SSO asserts it;
  email+password verifies by mail before the account is usable).  An unverified email never
  links: the person is asked to sign in the existing way and add the method from the account
  page.
* Apple *private relay* addresses (`@privaterelay.appleid.com`) are treated as verified for
  linking -- they are Apple's, and unique per app, so they only ever match an account created
  through Apple -- but are *never* used for workspace domain matching: a relay address neither
  auto-admits anyone to a workspace nor satisfies a require-SSO rule.  A person who hid their
  email and later joins a workspace links their work identity from the account page, which
  adds the verified work address to the account.
* Passkeys never link anything: a passkey is registered on an account that is already signed
  in.
* Linked identities are rows in `account_identity`; unlinking the last remaining identity is
  refused.  The device list shows the method; the account page lists the identities and lets
  the person add or remove them.

.As built (SEC-004)
* *The realm* (`server/keycloak/wiretuner-realm.json`, imported by compose and by the tests' Keycloak
  Dev Service) has the browser flow `wiretuner browser`: a cookie, an identity-provider hint, or the
  username followed by the passwordless WebAuthn execution (platform authenticator, resident key,
  user verification required) with the password form as "Try another way".  Keycloak 26.4's
  conditional-UI passkeys inside the password form are left off: a passkey used there would be
  recorded as the password execution.  Email and password: registration on, `verifyEmail` on (mail
  through mailpit), brute-force protection on.  The WebAuthn passwordless registration required
  action is enabled but not a default action; the app offers it after a first sign-in by any other
  means through Keycloak's application-initiated action (`kc_action=webauthn-register-passwordless`).
* *`wt_auth_method`* is two mappers on every client, because Keycloak has no single mapper that
  knows both brokered and local sign-ins: a user-session-note mapper copies the note
  `wt_auth_method` into the claim, and each identity provider sets that note with a
  hardcoded-user-session-attribute mapper (`apple`, `sso:acme`); a local sign-in sets no note, and
  Keycloak's AMR mapper writes `amr` from the reference values the realm gives the executions
  (`passkey` on the passwordless WebAuthn execution, `password` on the password ones).  The server
  (`TokenClaims`) takes `wt_auth_method`, else the first `amr` value that is a method, else
  `password`.  The test client `wiretuner-test-passkey` runs a password grant through a flow whose
  password execution carries the `passkey` reference, so the real mapping is tested end to end;
  `wiretuner-test-sso` keeps a hardcoded `sso:acme` claim (no browser brokering in tests).
* *Sign in with Apple* is the generic OIDC identity provider `apple` (client_secret_post, scopes
  `openid name email`, `trustEmail`, user info off -- Apple has none -- signature checked against
  Apple's JWKS).  In the committed realm it points at the compose mock `apple-mock` (issuer
  `http://apple-mock:8080/apple`, authorize at `localhost:8190`); production points it at
  `https://appleid.apple.com`.  Deviation: Keycloak 26.4's generic OIDC broker endpoint answers
  only GET, and Apple returns with `response_mode=form_post` whenever `name` or `email` is
  requested, so in production the reverse proxy in front of Keycloak turns the POST to
  `/realms/wiretuner/broker/apple/endpoint` into a 303 to the same URL with the form fields as query
  parameters.  Apple's first-authorization `user` field (the name) is then ignored by Keycloak and
  the review-profile step of first-broker-login asks for the name when the ID token has none
  (xref:decisions.adoc#Q-027[Q-027]).
* *The Apple secret job* (`AppleSecretJob`) signs the client secret as an ES256 JWT with the
  `.p8` key (`kid` = key id, `iss` = team id, `sub` = Services ID, `aud` =
  `https://appleid.apple.com`, valid 180 days, never more than Apple's 15,777,000 s) and writes
  it, with the Services ID as `clientId`, into the `apple` provider by a read-modify-write of its
  representation through the admin API (password grant on `master`'s `admin-cli`).  Settings:
  `WT_APPLE_TEAM_ID`, `WT_APPLE_KEY_ID`, `WT_APPLE_CLIENT_ID`, `WT_APPLE_PRIVATE_KEY` (the PEM
  contents), `WT_KEYCLOAK_URL`, `WT_KEYCLOAK_ADMIN_USERNAME` / `_PASSWORD`.  Tested against a
  fake admin endpoint (what was written, signature and claims) and against the test realm, after
  which a sign-in succeeds.
* *Linking.*  The first-broker-login flow `wiretuner first broker login` reviews the profile only
  for missing fields, creates the account when the email is unique, and otherwise detects the
  existing user and links automatically; both identity providers trust their providers' emails as
  verified.  Keycloak cannot make that automatic link depend on the *existing* user's email being
  verified, so the "unverified never links" rule rests on two other things: `verifyEmail` (an
  unverified email+password account cannot sign in, so it never gets a WireTuner account) and the
  server-side check -- `Principals` refuses to link a new identity whose token does not assert a
  verified email to an account that already has another identity (`FAILED_PRECONDITION /
  EMAIL_NOT_VERIFIED`, no row).  Relay addresses link and are recorded `is_relay`.
* *First sight is race-free.*  The account and identity rows are inserted with `ON CONFLICT DO
  NOTHING` and read back, as the device row already was, so the pipelined first calls of a new
  person make one account.

An account owns: a personal space of documents, a list of devices, its linked identities,
preferences, and its team memberships.  Personal documents can be shared with anyone by
invitation or link (xref:sharing.adoc[Sharing]).

== Teams

A *team* is a named group of accounts with a shared document space, shared libraries
(xref:library.adoc[Library]) and shared settings.  Requirements:

* A person can belong to *any number* of teams at once, and switches between Personal and each
  team in the library window without signing out.  A document belongs to exactly one space.
* Team roles: `owner` (billing, delete team, transfer), `admin` (members, workspace settings,
  team libraries), `member` (create and edit team documents per the team's default document
  role), `guest` (only documents explicitly shared with them; cannot see the team list).
* A team may be bound to a *company workspace*: one or more verified email domains and,
  optionally, a Keycloak identity-provider connection (SAML/OIDC SSO).  A workspace-bound team
  can auto-admit anyone who signs in with a verified address on its domain, can require SSO for
  its members, and can restrict sharing of its documents to team members only.  Domain
  verification is by DNS TXT record.  Only addresses asserted verified by their provider
  count, and Apple private relay addresses never count (Accounts, above).
* Leaving or being removed from a team removes access to the team's documents at the next
  change or session open (xref:sync-protocol.adoc[Sync protocol]); local stores remain on the
  device until the user deletes them, but the app will not open them past the role check
  without a fresh token (they can be exported as a package if the team allows it; a
  workspace-bound team may disallow this).
* Deleting a team trashes its documents for 30 days; the owner can transfer documents to
  another space before that.

The owner-only powers the role list names (delete team, transfer) and the administration an
admin needs (list members and pending invitations, withdraw an invitation, drop a domain) are
RPCs of their own rather than modes of `UpdateTeam`, so each has its own role check.  Lists
page with opaque cursors (`cursor`, `page_size` ≤ 50, `next_cursor`), as every list in the
API does.  Every request carries protovalidate constraints; the team-specific refusals
(last owner leaving, an invitation for an existing member, a domain another team verified)
use `FAILED_PRECONDITION` and `ALREADY_EXISTS` with reasons SEC-001 adds to the error table
on xref:api-conventions.adoc[API conventions].

.As built (SEC-001)
* A caller who is not a member of the team -- or any caller of anything but `GetTeam` and
  `ListTeams` once the team is deleted -- gets `NOT_FOUND / TEAM_NOT_FOUND`; a member below the
  RPC's role gets `PERMISSION_DENIED / ROLE_INSUFFICIENT` (a guest calling `ListMembers`
  included).  `GetTeam` and `ListTeams` are open to guests.
* Only the owner invites at the admin role, promotes to or demotes from admin, and removes an
  admin; an admin does the rest of the member administration.
* An invitation lives 7 days; its token (32 random bytes, base64url) is only in the mail, the row
  keeps its sha256.  Inviting an address with a pending invitation replaces it.  The mail is the
  Qute template `templates/InviteMailer/invite.{html,txt}` with the link
  `<wt.links.base-url>/invite/<token>`.  `AcceptInvite` needs an `account_identity` row of the
  caller with the invited address and `email_verified`; a workspace with require-SSO also needs
  the session's `wt_auth_method` to be `sso:<its alias>`.  Accepting while already a member keeps
  the current role.
* Leaving or being removed deletes the membership *and* the account's `document_member` rows and
  link uses on the team's documents, so the next role check (every RPC, the ingest path) finds no
  role: `RoleGuard` answers `NOT_FOUND / DOCUMENT_NOT_FOUND` for a role of none, and
  `ROLE_INSUFFICIENT` only for a role that is merely too low.
* `UpdateTeam` also sets the team's history window, `history_retention_days` (30 to 3650 days;
  `Team` reads 0 while it is unset, the default 30), which the History retention job honours
  when it is longer than the default (COLLAB-020; xref:history.adoc[Version history], Server).
* `DeleteTeam` sets `deleted_at`, trashes the team's live documents, ends every membership but
  the owner's (the owner keeps the owner's powers on the documents to move them out) and drops
  pending invitations.
* A domain is verified when one of its TXT records is `wiretuner-verification=<token>` (the token
  is 16 random bytes as hex); lookups use the non-blocking Vert.x DNS client against one resolver
  (`wt.dns.host`, `wt.dns.port`; 1.1.1.1:53 by default) and any failed lookup reads as not
  verified.  SEC-002's periodic re-verification reuses `DomainVerifier`.
* Tokens for test sign-ins by workspace SSO come from the realm's test-only client
  `wiretuner-test-sso` (hardcoded `wt_auth_method = sso:acme`); the realm also gains the test
  people alice, bob, carol, dave and erin.

.As built (SEC-002)
* *Domains job*: hourly re-verification with `DomainVerifier`; a verified domain survives two
  missed lookups and loses its verification at the third (xref:server.adoc[Server], Jobs).
* *Auto-admit* runs at sign-in -- when the principal resolution sees a new account, a newly linked
  identity or a Mac it has not seen for the account (`SignInEffects`): the account joins, as a
  member, every live team whose workspace auto-admits and has verified the domain of one of the
  account's identities whose provider asserted the address verified.  Relay addresses never count.
  A workspace that also requires SSO admits only a session signed in through its connection.
  Turning auto-admit on does not admit existing accounts until they next sign in on a new Mac or
  link an identity.
* *Require-SSO* is checked on every call that reaches the team's documents (`RoleGuard`) or its
  library space (`Spaces`): a member (owner, admin or member; not a guest, and not an outsider a
  document was shared with) whose token's `wt_auth_method` is not `sso:<alias>` gets
  `FAILED_PRECONDITION / SSO_REQUIRED` -- a password or passkey session alike.  TeamService is not
  held to it, so an admin can always turn the switch off.
* *Restrict-sharing* is enforced by ShareService: invitations of anyone who is not a member of the
  team (a pending invitation by email included), links that are not team-members-only, and opening
  any link as an outsider are refused.  Deviation: `sync.v1.ErrorReason` has no reason for it yet,
  so the first two answer `FAILED_PRECONDITION / TEAM_ROLE_INVALID` and an outsider opening a link
  `PERMISSION_DENIED / ROLE_INSUFFICIENT`; a `SHARING_RESTRICTED` reason is proposed for the proto
  track (xref:decisions.adoc#Q-028[Q-028]).

SEC-001 added the reasons `TEAM_NOT_FOUND`, `MEMBER_NOT_FOUND`, `INVITE_INVALID`, `DOMAIN_NOT_FOUND`,
`SLUG_TAKEN`, `ALREADY_MEMBER`, `DOMAIN_TAKEN`, `OWNER_MUST_TRANSFER`, `TEAM_ROLE_INVALID`,
`EMAIL_NOT_VERIFIED`, `SSO_REQUIRED` and `DOMAIN_UNVERIFIED`; they are rows of the Errors table in
xref:api-conventions.adoc[API conventions] and values of `sync.v1.ErrorReason`.

== Document roles

Per document, independent of team role: `owner`, `editor`, `commenter`, `viewer`.  A document
has exactly one owner, who can do everything on it (share, change roles, transfer, move between
spaces, manage its credentials, delete); an editor has every editing privilege, including
fetching with the document's credentials and every command a script can run, but none of the
owner's administrative ones.  In a team document the team's admins hold the owner's
administrative powers; its single owner is its one `document_member` row with role `owner`.  `commenter` (may write only under the
`comments (0:12)` collection: start threads, reply, mention, react, edit and delete own comments,
resolve own threads -- xref:comments.adoc[Comments]), `viewer`.  A change from a `commenter`
session is accepted only if every op targets a node under `0:12` and obeys the per-comment
ownership rules on the Comments page; a `viewer` session may not write under `0:12` at all (as built by COLLAB-030, the same rules also bind editors' and owners' ops on comment threads, with their extra powers; xref:comments.adoc[Comments], As built).  Effective role = max(explicit membership, team default for members, share
link role if the link was used).  The server evaluates it on every RPC and at every session
open; a change from a session whose role dropped below `editor` is rejected with
`ROLE_INSUFFICIENT` (xref:api-conventions.adoc[API conventions]).

== Replica binding

A replica id is bound to `(account, device)` on first use.  Changes carrying that replica id
from any other principal are rejected, so a leaked local store cannot impersonate its owner's
history.  Devices can be revoked from the account page; a revoked device's token refresh
fails and its outbox is offered for export as a package.

== Tokens and transport

* Access tokens: 15 minutes; refresh tokens: 30 days rotating, stored in the Keychain.  The
  access token carries `wt_auth_method`; a workspace's require-SSO rule is checked against it
  on every call, not only at sign-in.
* TLS everywhere; the compose stack terminates TLS at the API for parity with production.
* Server-side rate limits per account and per document (SRV-014), `RESOURCE_EXHAUSTED` with
  `RetryInfo`.  As built: token buckets in Valkey, taken in `RoleGuard` and per pushed change
  (xref:server.adoc[Server], Observability).

== Data protection

* Documents are private by default; share links are unguessable (128-bit) and can expire.
* Blobs are content-addressed but only served to principals with a role on a document that
  references them.
* Exports and packages are produced on the client; the server never renders artwork.
* Data-source credentials are stored envelope-encrypted in `data_credential`, decrypted only
  inside one outbound request, never returned by any RPC (xref:data-merge.adoc[Data merge]).
* Account deletion: personal documents trashed, team memberships removed, personal data purged
  after 30 days; change-log attribution keeps an opaque author id.
