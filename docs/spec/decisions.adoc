= Decisions

:page-slug: decisions

Every choice that could have gone another way, with the reason it went this way.  Choices that
matter to one page only are explained on that page; the ones with consequences beyond one page
are collected here.  Open questions are at the end.

== Architecture

[[D-001]]
=== D-001 Custom op-based CRDT in Swift and Java, not Automerge / Yjs / Loro

No existing CRDT library has production-grade bindings for *both* Swift and the JVM
(automerge-swift is usable but automerge-java is 0.0.x; loro-swift is experimental and Loro has
no JVM binding; yrs bindings for both are early).  Each would also put an FFI layer and an
opaque binary blob between our protobuf schema and the merge logic, and none understands a
vector document's semantics (tree moves, z-order, appearance stacks).  We implement published
algorithms directly against one generated schema and prove the two engines equal with a shared
conformance suite (xref:crdt-model.adoc[CRDT model], xref:testing.adoc[Testing]).  Cost: we own
the hard parts (tree move, tombstone GC, text).  Mitigation: the algorithms are well specified
and small; the fuzzer runs nightly.

[[D-002]]
=== D-002 Server as hub; no peer-to-peer

Causality becomes a single integer per replica, access control applies to every op, and
"how far behind am I" is trivial.  Peer sync (AirDrop-style) is not planned.

[[D-003]]
=== D-003 Merge policies as protobuf field options

The schema is the merge contract; the engines contain no per-feature code.  Adding a field is a
schema change plus vectors, never an engine change.

[[D-004]]
=== D-004 macOS 15 minimum

`CGPath` boolean and offset operations, Swift 6 strict concurrency, current
SwiftUI/AppKit interop.  Revisited every September.

[[D-005]]
=== D-005 AppKit for the document window, SwiftUI for panel bodies

The interaction model (modifier keys mid-drag, precise tracking, docked tabbed panel groups)
is an AppKit model; SwiftUI is faster for the many form-like panels.

[[D-006]]
=== D-006 Metal on screen, Core Graphics as the truth

One renderer-agnostic display list, two renderers.  Metal (tile atlas, stencil-then-cover
fills, glyph atlas, Core Image into textures) draws the screen and must hold 120 Hz while
zooming, panning and rotating.  Core Graphics draws PDF, print, export, golden images and the
fallback canvas; it is the reference, and the Metal output is tested against it per tile with a
stated tolerance (REND-007).  Stencil-then-cover over Loop-Blinn: no interior triangulation,
exact winding rules and self-intersections, and coverage that matches CG's scan converter
(xref:modernizations.adoc#M-02[M-02]).

[[D-007]]
=== D-007 Last-writer-wins by Lamport order, never by wall clock

Clocks on laptops drift and can be set backwards; a Lamport counter with replica id tie-break
is total, deterministic and cheap.  Wall time is stored for history display only.

[[D-008]]
=== D-008 `Transform` is ATOMIC

Merging matrix components from two users produces a shear nobody drew.  One transform wins;
the review sheet shows the other.

[[D-009]]
=== D-009 Undo is local and never rewinds shared state

Undo writes a new change that re-asserts prior values only where the register still holds the
user's own write.  Other people's work is never undone by someone else.

[[D-010]]
=== D-010 Normalize on read, never repair on merge

Every client would write the same repair at once, producing a storm of identical changes.
Readers interpret odd states deterministically instead.

[[D-011]]
=== D-011 Deleted nodes stay in the tree with a flag

Edits to deleted nodes still apply, so restore is exact and the review can show "edited
something that was deleted".  Compaction after 30 days keeps snapshots small.

[[D-012]]
=== D-012 Reconcile thresholds: silent under 500 ops with no overlap; ask on overlap

From Ink & Switch's local-first work and Figma's branch review: merge what does not overlap,
show what does, let the person choose, including "keep both".  Thresholds are preferences.

[[D-013]]
=== D-013 Replica retirement after 90 days of silence

Causal stability needs every replica's ack; a device that vanished cannot block garbage
collection forever.  Salvage on return rebases unsent changes rather than discarding them.

[[D-014]]
=== D-014 grpc-swift 2 via buf; validators generated instead of protovalidate on the client

protovalidate has no Swift runtime (no Swift CEL interpreter).  `protoc-gen-wtcrdt` emits
validators for the standard rules; CEL rules stay server-only and are listed by the generator.

PROTO-004 outcome (2026-09): the BSR plugin `buf.build/grpc/swift` is a grpc-swift *1.x*
generator -- its newest version is v1.27.6 (published 2026-09-03, runtime library
`grpc-swift` 1.27.6, product `GRPC`), and its output is `import GRPC` / `GRPCClient` /
`UnaryCall` code that cannot link against `GRPCCore`.  No v2 emitter exists on the BSR.  The
grpc-swift 2 stubs therefore come from `protoc-gen-grpc-swift-2`, the plugin in the
`grpc/grpc-swift-protobuf` package, built from source by `tools/proto/install-plugins.sh` at
the version WTProto's `Package.resolved` pins (2.4.1, so stubs and runtime move together),
installed under `tools/bin/` (gitignored) and run by `buf.gen.yaml` as a `local` plugin with
`Client=true, Server=false, Visibility=Public, FileNaming=PathToUnderscores`.  CI caches the
binary by the installer's hash and only sets up a Swift toolchain on a miss
(`.github/workflows/proto.yml`).  The plugin emits a header-only `<file>.grpc.swift` for
files without services, which is committed like the rest.  Re-check the BSR when
grpc-swift-protobuf is bumped; if a v2 remote plugin appears, the `local` entry becomes a
pinned `remote` one and nothing else changes.

[[D-015]]
=== D-015 No Save; Cmd-S names a version

Every change is saved locally at once and synced when online.  A Save command that talked to
the network would lie about the state of the document.  Cmd-S becomes "name this version",
which is what designers use Save for in a cloud document (xref:saving.adoc[Saving]).

[[D-016]]
=== D-016 Personal accounts, unlimited team memberships, optional company workspaces

A person has one account, joins any number of teams, and a team can be bound to verified
domains and SSO.  Documents belong to exactly one space (xref:security.adoc[Accounts, teams
and security]).

[[D-017]]
=== D-017 Typeface documents model glyphs as pages

A glyph is a canvas like a page, so every drawing tool, layer and guide works unchanged; font
properties are extra attributes on the glyph and the document
(xref:typeface-documents.adoc[Typeface documents]).

[[D-018]]
=== D-018 SVG animations are the vector animation format

Animation, interactivity and placed animations are built on SVG animations, PDF and HTML
(xref:animation.adoc[Animation], xref:interactivity.adoc[Interactivity],
xref:svg-animation.adoc[SVG animations]).

[[D-019]]
=== D-019 Third-party plug-ins out of scope for v1

Every extension ships built in under *Extensions*; an SDK is an open question
(xref:extensions.adoc[Extensions]).

== Decisions from the feature chapters

Recorded by the chapter authors; the full reasoning is on the page named.

[[D-020]]
=== D-020 Registers can be cleared, and `MERGE_VARIANT` exists
A `SetFields` that lists a path without a value writes *unset* with a fresh OpId, so removing
a style override or a link competes with concurrent writes like any value.  Messages users
toggle between kinds (fills, strokes, effects) use an enum discriminator with one STRUCT per
case rather than a protobuf `oneof`, so a concurrent kind switch never discards the other
user's settings (xref:crdt-model.adoc[CRDT model], xref:attribute-stack.adoc[Attributes],
xref:live-effects.adoc[Live effects]).

[[D-021]]
=== D-021 Fills, strokes and effects share one position space
The three sequences on an appearance are ordered by one fractional index, so a fill can sit
above a stroke, with no engine change (xref:attribute-stack.adoc[]).

[[D-022]]
=== D-022 Randomness is seeded
Brush variation, Ragged and Sketch effects and random fills store a seed so every Mac, every
print and every export renders the same pixels; a *Reseed* button gives a new look
(xref:stroke-attributes.adoc[], xref:live-effects.adoc[]).

[[D-023]]
=== D-023 PostScript strokes, fills and imports are dropped
There is no PostScript interpreter on macOS, and user-supplied printer code is a security
liability.  Custom and Pattern strokes and Textured fills are rendered natively instead; EPS
files are placed with their preview and passed through to PostScript printers only
(xref:stroke-attributes.adoc[], xref:fill-attributes.adoc[], xref:import-formats.adoc[]).

[[D-024]]
=== D-024 Everything imported lives in the document
No link-by-path mode: a local path means nothing to a collaborator.  A link is only a source
for *Update from source* (xref:importing.adoc[], xref:linking-embedding.adoc[]).

[[D-025]]
=== D-025 Background layers are a per-layer flag; locks are advisory
A separator *position* gives random results under concurrent reorders; a `printing` flag ends
up with whoever last touched that layer, which the review can show.  A lock is respected by
every client's own tools and never enforced against a remote change, because refusing an
offline editor's work would lose it (xref:layers.adoc[], xref:collaboration.adoc[]).

[[D-026]]
=== D-026 Styles resolve on read; objects store only explicit overrides
Redefining a style is one node write and never collides with an override on the same
register.  Deleting a style bakes the resolved look into its users first
(xref:styles.adoc[], xref:text-styles.adoc[]).

[[D-027]]
=== D-027 Deleting an in-use color is never refused
A refusal cannot close the race with an offline user.  Safety is the cached fallback on every
reference, undo, *Restore Deleted Colors* for 30 days, and a review-sheet row
(xref:swatches.adoc[]).

[[D-028]]
=== D-028 Shapes, extrusions, blends, envelopes and perspective are node kinds with derived geometry
Rectangles, ellipses and polygons keep their parameters; extrusion, envelope and perspective
attachment are wrapper nodes with one child; blends and charts regenerate their intermediate
objects on read.  Nothing derived is ever stored or synced (xref:vector-basics.adoc[],
xref:extrude.adoc[], xref:blends.adoc[], xref:charts.adoc[]).

[[D-029]]
=== D-029 Join and Split copy points into new identities
There is no cross-node element move.  A concurrent edit to a copied point surfaces as
edit-vs-delete with *Restore*; this is the one documented merge loss in path editing
(xref:editing-paths.adoc[]).

[[D-030]]
=== D-030 Linked text lives on the chain head
The chain is defined by `next_link` only; loops are cut at the smallest node id; deleting a
middle block splices its neighbours (xref:text-blocks.adoc[]).

[[D-031]]
=== D-031 Text on a path owns its path; inline graphics are child nodes
The path is a child of the text node, so both move together and a dangling reference cannot
occur (xref:text-on-path.adoc[], xref:text-effects.adoc[]).

[[D-032]]
=== D-032 Shared vs. per-user document settings
Shared: ruler zero point, guide lock, grid size, page order, print settings, color settings,
HTML and animation settings, document defaults, named custom views.  Per user (`local_only`):
zoom and scroll, show/snap toggles, grid and guide colors, hidden objects, proof-colors
toggle, current colors, printer and paper, the Preview-in-Browser browser
(xref:grid-guides.adoc[], xref:document-view.adoc[], xref:arranging.adoc[],
xref:printing.adoc[], xref:color-management.adoc[]).

[[D-033]]
=== D-033 Review-sheet exceptions
Always listed, whatever the counts: a change to the document's color settings or to
font-level metrics of a typeface.  Never listed: print settings and the output area (low
stakes, cheap to redo).  These amend the rules in xref:reconcile.adoc[Reconciling]
(xref:color-management.adoc[], xref:printing.adoc[], xref:font-info.adoc[]).

[[D-034]]
=== D-034 Every share link requires sign-in
No anonymous access: every collaborator has a name, a color and a place in blame
(xref:sharing.adoc[]).

[[D-035]]
=== D-035 Team libraries copy on use
Symbols, styles and colors taken from a team library are copied with provenance and updated
by an explicit command; no live cross-document references in v1 (xref:library.adoc[],
xref:exporting-colors.adoc[], xref:sharing.adoc[]).

[[D-036]]
=== D-036 Branches do not nest and do not hold back garbage collection
Merging is a server-side replay with a client-reviewed exclusion list; a branch whose parent
compacted a node loses only the ops on that node, and lists them (xref:branches.adoc[]).

[[D-037]]
=== D-037 Restore is a change, never a rewind
Restoring a version or an object's history writes ops that re-assert the old state on top
of everyone's current work (xref:history.adoc[]).

[[D-038]]
=== D-038 The `.wiretuner` package
A zip with a manifest, a zstd snapshot, blobs, a thumbnail and a page-1 PDF preview for Quick Look; importing one re-issues its
state as fresh ops from the importing replica, so the server never accepts a client-built
snapshot (xref:saving.adoc[]).

[[D-039]]
=== D-039 Own PDF writer
`CGPDFContext` cannot emit separation color spaces, overprint, output intents, PDF/X,
optional content groups or embedded files, all of which a print-oriented tool needs
(xref:export-pdf.adoc[]).

[[D-040]]
=== D-040 Separations and halftones are rendered on the client
Plates are drawn by the renderer into a PDF; halftone screens are honored only through the
in-app screener because the macOS print path carries no halftone dictionaries
(xref:output-devices.adoc[], xref:halftones.adoc[]).

[[D-041]]
=== D-041 ColorSync is the only CMM; color settings are document data
Kodak Digital Science is gone; the working profiles and proof setup travel in the document so
every collaborator sees the same intent, while the monitor profile is per Mac
(xref:color-management.adoc[]).

[[D-042]]
=== D-042 Preferences are a map with per-key newest-wins
Feature epics add preference ids without schema churn; synced categories resolve per key on
the server, local categories never leave the Mac (xref:preferences.adoc[]).

[[D-043]]
=== D-043 Uploads outlive the window, not the app
Closing a document keeps uploading while the app runs; quitting with pending changes offers
*Quit When Uploaded*; the next launch drains pending stores before opening windows.  No
separate agent process (xref:saving.adoc[]).

[[D-044]]
=== D-044 No bidirectional streams: one subscription plus unary commands
`SyncService.Session` (bidi) became server-streaming `Subscribe` plus unary `PushChange`,
`UpdatePresence` and `Ack`, with `PushChangeBatch` as the unary fallback for `PushChanges`.
gRPC-Web and Connect cannot do bidi from a browser and HTTP/1.1 balancers mishandle duplex
streams; causality is unchanged because the ack is the response.  Quarkus 3.39 serves HTTP/2
gRPC only, so a browser client means an Envoy or Vanguard gateway, not a schema change
(xref:sync-protocol.adoc[], xref:api-conventions.adoc[], xref:modernizations.adoc#M-01[M-01]).

[[D-045]]
=== D-045 Server-side search index from snapshots; thumbnails rendered by the client
The snapshotter extracts a per-document search record (names, text, notes, keywords, page
names) into Postgres (`pg_trgm` + `simple` tsvector) so the library searches content without
the server interpreting artwork; lag is the snapshot cadence.  Thumbnails are a client render
uploaded as a tagged blob and referenced from the document row -- the server never renders
(xref:server.adoc[], xref:creating-opening.adoc[], xref:modernizations.adoc#M-04[M-04]).

[[D-046]]
=== D-046 Passkeys first, Sign in with Apple, linking by verified email
The realm offers passkeys as the preferred credential, Sign in with Apple (App Store
guideline 4.8), email+password as fallback and workspace SSO; identities link to one account
by provider-verified email, Apple relay addresses link but never match a workspace domain, and
the device list shows the method (xref:security.adoc[], xref:modernizations.adoc#M-06[M-06]).

[[D-047]]
=== D-047 Smart guides and Option measurements, client-only
Edge, centre, equal-spacing and size-match guides plus kbd:[Option]-hover measurements are
computed per gesture from the REND-003 spatial index within the viewport and write nothing --
not even view state.  Priority sits between ruler guides and the grid (GEO-005).  Toggle is the
synced preference *Smart guides* on kbd:[Cmd+U], the Illustrator binding, which {product} freed
by moving Preferences to kbd:[Cmd+,] (xref:moving.adoc[], xref:modernizations.adoc#M-07[M-07]).

[[D-048]]
=== D-048 Command palette on the command registry
A fuzzy-searched palette over APP-005's registry (plus panels, pages, layers, named views and
recent documents as registered sources) runs exactly what the menu item runs.  Ranking is
recent-first from a local history file; nothing syncs.  kbd:[Cmd+K] (Keyline) and
kbd:[Cmd+Shift+P] are taken in the default shortcut set, so the default is kbd:[Cmd+/]; APP-005's
conflict report is final (xref:customizing.adoc[], xref:modernizations.adoc#M-08[M-08]).

[[D-049]]
=== D-049 Canvas rotation is view state
`ViewState.rotation_degrees` (`local_only`) turns the whole canvas; rulers, grid, guides and
smart guides are pasteboard geometry drawn through the view transform.  Tiles are rendered in
rotated view space and keyed by angle, so a settled angle is never resampled.  Named views do
not record rotation (xref:document-view.adoc[], xref:modernizations.adoc#M-16[M-16]).

[[D-050]]
=== D-050 Comments in v1, as document data under a well-known collection
Comment threads are `comment_thread` nodes under `comments (0:12)`, not server rows: they sync,
work offline, fork with branches and merge back as threads with no extra machinery.  The cost is
that the server must read op content for the first time -- mention notifications, unread
counters and the commenter role check all inspect ops under `0:12` -- which is confined to the
existing ingest parse.  Read state and notifications stay in Postgres, never in the document.
The `commenter` role stops being reserved (xref:comments.adoc[],
xref:modernizations.adoc#M-05[M-05]).

[[D-051]]
=== D-051 Inspect mode as a client-only presentation mode
A read-only mode with measurements, a properties panel and copy-as-SVG/CSS/Swift/PNG needs no
document or server data: snippets are a client library over the SVG writer and rasterizer,
colors convert through ColorSync, and the only server touch is resolving a
`wiretuner://doc/<id>/node/<id>` link.  Viewers open in it by default, which makes "read-only"
a useful mode rather than a disabled one (xref:inspect.adoc[], xref:modernizations.adoc#M-12[M-12]).

[[D-052]]
=== D-052 Colors carry their space; Display P3 and OKLab are first-class
Every `Color` carries a `ColorSpace` tag (sRGB default, Display P3, CIELAB D50, OKLab) beside
CMYK; the tag is inside the ATOMIC register, so a space change is a value change and merges
like a recolor.  Working RGB becomes the document's RGB *output* space rather than the meaning
of artwork colors.  Display and print convert from each color's own space through ColorSync;
sRGB↔P3 and the Lab spaces use deterministic formulas and CSS Color 4 gamut mapping.  Exports
carry the Display P3 profile or CSS Color 4 values with sRGB fallbacks when the document needs
them; a display that cannot show a color clips it and the Mixer says so, never the document.
An unknown tag from a newer client reads as sRGB with components as-is and is preserved
(xref:spot-process.adoc[], xref:color-mixer.adoc[], xref:modernizations.adoc#M-03[M-03]).

[[D-053]]
=== D-053 Accessibility metadata lives on the object
`CommonProps.alt` and `CommonProps.decorative` beside name and note, plus an optional per-page
`reading_order` sequence defaulting to stacking order; SVG, tagged PDF (PDF/UA-1) and HTML
output derive from them.  Link alt text (Navigation panel) describes the destination, object
alt text the picture; both are exported (xref:names-notes.adoc[],
xref:modernizations.adoc#M-13[M-13]).

[[D-054]]
=== D-054 Native macOS integration without iCloud
Quick Look and thumbnail extensions read `preview.pdf` and `thumbnail.png` from the package;
Core Spotlight indexes local documents and packages; Handoff carries only a document id, page
and zoom and opens the cloud document on the other Mac.  iCloud is not used for documents
(xref:saving.adoc[], xref:exporting.adoc[], xref:modernizations.adoc#M-14[M-14]).

[[D-055]]
=== D-055 On-device machine learning only; no generative features in v1
Remove Background, Select Subject, the Photo tracer and Select Similar's shape class run on
Vision or a small bundled Core ML model, need no network, and produce ordinary changes (a new
image blob, paths, a selection).  No generative drawing, text-to-vector or cloud AI in v1;
models are optional bundle resources and every feature degrades without them
(xref:bitmaps.adoc[], xref:tracing.adoc[], xref:selecting.adoc[],
xref:modernizations.adoc#M-15[M-15]).

[[D-056]]
=== D-056 Live Corners and Combine effects
Corner rounding and boolean combination are live vector effects (`CornersEffect`,
`CombineEffect`) beside the destructive commands.  Corners takes a `MERGE_SET` of point ids
(add-wins; a deleted point drops out on read) and supersedes a rectangle's own radius while
present; Combine is a boolean over a group in stacking order, members still editable, and
*Expand* bakes it (xref:live-effects.adoc[], xref:modernizations.adoc#M-09[M-09]).

[[D-057]]
=== D-057 Symbol instance overrides as a sequence keyed by master node
Instances may override text, fill and stroke color, visibility and image per master node, so
overrides survive symbol edits and are set aside on swap.  A SEQUENCE of `Override` elements
rather than a map: a map would need a new keyed-collection policy in both engines and has no
defined removal for a text register; the sequence reduces every case to existing rules
(xref:library.adoc[], xref:modernizations.adoc#M-10[M-10]).

[[D-058]]
=== D-058 Variable font axes and OpenType features
`axes` is one ATOMIC `FontVariation` per mark (a named instance is one choice).  Features are
one tri-state mark per tag, identity `(feature, tag)`, chosen over a set of signed tags (which
would keep `+liga` and `-liga` together) and over a single struct mark (which collides across
features).  PDF export instances `glyf`/`gvar` fonts with an own instancer; CFF2 fonts are
outlined and listed (xref:type-specifications.adoc[], xref:modernizations.adoc#M-11[M-11]).

[[D-059]]
=== D-059 Data-merge API calls run on the server
The client never calls a customer's API.  `DataSourceService` executes the request definition
with the credential injected, behind a per-team or per-account host allowlist, an SSRF guard
(https only, resolve-once-and-pin, blocked private and metadata ranges, no cross-host
redirects), rate limits, size caps and a 90-day audit log.  Credentials never reach a laptop;
customers can allowlist one egress address; every collaborator gets identical records.  Cost:
the server gains its first outbound HTTP client, and API sources are online-only (offline =
embedded sample).  `wt.fetch` in scripts is the same proxy (xref:data-merge.adoc[],
xref:scripting.adoc[]).

[[D-060]]
=== D-060 Merge data is never in the document
A document carries field definitions, bindings and source definitions; records are fetched on
demand and streamed to the merge.  Only a pasted table, an explicit *Embed All Records* or a
five-record *Embed Sample* is stored, as a blob, so a leaked local store or package discloses
nothing the user did not choose to embed (xref:data-merge.adoc[]).

[[D-061]]
=== D-061 Credentials never in the document; outbound hosts allowlisted
Sources and scripts reference a credential by name only; the secret is written once via
`PutCredential`, envelope-encrypted, never returned, bound to one host.  Outbound hosts are
allowlisted per team by admins or per account by a first-use consent prompt; scripts run only on
explicit user action, never on open or by timer (xref:data-merge.adoc[], xref:scripting.adoc[]).

[[D-062]]
=== D-062 Team credentials are written by admins only
Only team admins add, replace or remove a team's data-source credentials; editors use them.
Personal documents' credentials belong to the owner (xref:data-merge.adoc[]).

[[D-063]]
=== D-063 One owner per document; editors are full editors
A document has exactly one owner, the superuser for that document (sharing, roles, transfer,
space moves, credentials, deletion).  Everyone else with the editor role has every editing
privilege -- including fetching with the document's configured credentials and running scripts
-- and none of the administrative ones.  Team admins hold the owner powers on team documents
(xref:security.adoc[], xref:sharing.adoc[]).

[[D-064]]
=== D-064 Sign in with Apple through Keycloak's generic OIDC provider
Configured as a generic OIDC identity provider with a JWT client secret rotated by the *Apple
secret* job, rather than a community Apple extension: nothing to fork or track, and the
rotation job already exists (xref:security.adoc[], xref:server.adoc[]).

[[D-065]]
=== D-065 Field numbers are allocated in blocks per epic; CommonProps is numbered
PROTO-003 fixed the `NodeProps.kind` blocks (DOC 1--19, DRAW 20--49, OBJ 50--69, COLOR 70--79,
ATTR 80--99, FX 100--129, TYPE 130--149, LIB 150--169, IMG 170--189, WEB 190--209, COLLAB
210--219, FONT 220--239, DATA 240--259; recorded at the top of `doc/v1/node.proto`) and the
`CommonProps` numbering (1--7 as first sketched, `navigation` 8, `alt` 9, `decorative` 10,
`halftone` 11, `data_binding` 12, `text_wrap` 13, `origin_layer` 14; 15--19 held, features
continue from 20; recorded at the top of `doc/v1/common.proto` and on
xref:crdt-model.adoc[CRDT model]).  Two page sketches had claimed number 8 (`halftone`,
`origin_layer`) already taken by `navigation`; they moved.  Because `buf breaking` runs the
`FILE` category, a message stays in the file it first appeared in: the kind messages PROTO-003
had to name (`DocumentProps`, `SettingsProps`, `PageProps`, `MasterPageProps`, `LayerProps`,
`GroupProps`, `Anchor`, `TextMarkValue`) were created as stubs in their eventual files
(`document.proto`, `layer.proto`, `group.proto`, `text.proto`), and `Color`, `ColorRef`,
`NavigationProps`, `Halftone`, `TextWrap` and `DataBinding` live in `common.proto` for good.
Per-kind and per-settings numbers inside those messages are allocated by the task that fills
each message in, in a comment at its top, the same way.

[[D-066]]
=== D-066 Client branch gate is llvm-cov region coverage
The Swift toolchain (Xcode 26.4, Swift 6.3) emits no branch records in its coverage mapping, so
the client cannot be held to a branch or condition figure: Sonar would show none for
`wiretuner-client` and a branch condition would pass vacuously.  The client's gate is 95% lines
*and* 95% llvm-cov *regions* -- each `if`/`guard`/`switch` arm and `?:`/`??` operand is its own
region, so an untaken arm counts against the gate as an untaken branch would.  CI enforces both
with `tools/coverage/regions-gate.swift` before the Sonar upload and prints the figures in the
job summary, since Sonar's generic coverage format cannot carry regions; the `wiretuner-client`
Sonar gate has line conditions only.  Approximating branches from per-line region counts and
feeding them to Sonar as `branchesToCover` was rejected: a line's regions are not its branches,
and the fabricated figure would read as a measured one.  If a toolchain starts emitting `BRDA`
records, the converter passes them through and the client gate can gain Sonar's branch
conditions (xref:testing.adoc[Testing]).

[[D-067]]
=== D-067 Garbage collection runs at a published collection point, not min(acks)
`min(acks)` is unsafe: a change pushed before its author acknowledged further can be sequenced
after that point, be concurrent with a deletion, and still name the tombstone.  Each replica
keeps a *horizon* (the newest stable point and clock the server published to it) and never
writes an op naming something collectable there; the server stores each change's horizon and
publishes a collection point (C, T) lowered until no change sequenced after C has a lower
horizon.  Every replica and the snapshotter collect at (C, T).  `AckResponse` gains
`collect_seq` and `collect_time_ms`; SRV-007 and SRV-013 implement the server side
(xref:crdt-model.adoc[CRDT model]).  The server learns a replica's horizon only when the replica
acks again after receiving it, so a client confirms every answer that raised the stable point and
polls, backing off, while the point is below what it applied; it confirms only once the changes it
made before the answer are accepted, and keeps its horizon across relaunches (TEST-001; the
confirmation rule is on xref:sync-protocol.adoc[Sync protocol], "The client as built").

=== D-068 The color module lives in WTRender
`WTColor` -- color arithmetic, CSS Color 4 gamut mapping, the profile registry, the conversion

[[D-070]]
=== D-070 A brief reconnect never holds the outbox; the share rule needs five objects in common
The reconcile rules (xref:reconcile.adoc[Reconciling]) ran on every reconnect, so a connection
dropped for a few seconds while people edit the same object held the outbox behind a review --
and, since one object in common is 100% of a small session, the whole-document review.  The
simulator found it (TEST-001).  The requirement the review serves is offline work of a day or
two, with a choice only when the edits diverge heavily; a few seconds apart is live
collaboration, which merges the same edits every second without asking.  So: a reconnect within
15 minutes of the last sync with fewer unsent ops than *Auto-merge below* merges and uploads
whatever overlaps, offering the overlap read-only in the toast's *Review what changed* (*Always
ask when anything overlaps* still asks); and the 25% share opens the whole-document review only
when at least five objects overlap, so one or two objects in common are listed one by one.  The
15 minutes and the five objects are not preferences.  The gap stays measured from before the
offline work while a review is pending, so a relaunch or a reconnect does not take the pending
review for a brief drop.  Rejected: keeping the per-object hold for brief drops (still a sheet
on every network blip, for conflicts live editing would have resolved the same way).

=== D-071 Fonts compile with a built-in Swift compiler; fontc is deferred
The stack named fontc, bundled as an XCFramework, with CI carrying a pinned Rust toolchain.  The
build machines have no Rust toolchain, and FONT-018 was built as `WTInterchange.FontCompiler`

[[D-075]]
=== D-075 Public channels come after v1; keep documents postable and forkable
After the collaborative editor ships, WireTuner gains public *channels*: a curated list of feeds,
like Instagram for vector and typeface documents.  Planned shape, to be specified when the work
starts:

* Posting shares a *frozen copy*: the server copies the document (or, for a typeface, a single
  glyph) at the posted version into an immutable post, so later edits to the author's document
  never change what was posted.  The author keeps editing their own copy.
* Channels are curated (a fixed list chosen by WireTuner, not user-created); a post belongs to one
  channel.
* The feed shows rendered images, not live documents: each post has WebP renditions (a few
  sizes) stored in R2 beside the blobs, so scrolling a feed never opens a document.  The posting
  client renders them with WTRender and uploads them with the post: WTRender is built on Core
  Graphics, which the Linux server cannot run, and a second server-side renderer would drift from
  what the author saw.  A server renderer is only worth building if posts must be re-rendered
  without a Mac (a web or Android client, a rendering change).  Opening a post can show the
  read-only document.
* Viewers can *like* a post and *edit* it; editing forks the post into the viewer's personal
  collection (the existing duplicate/fork path, with provenance back to the post).
* Moderation, reporting and ranking are part of that work.

Consequences for the work before then: documents and glyphs must be copyable server-side into a
new immutable container (today's `DocumentService.Duplicate` and branch forks are the path to
extend); WTRender must be able to render a document or a single glyph to a bitmap headlessly, off
the main thread (it already does for export); and provenance fields should allow a source post as
well as a source document.

[[D-076]]
=== D-076 Edits never wait on storage; the document records intent, not input events
Found in use (2026-09-27): dragging a Bezier handle and typing each performed one command per
input event, and every command waited, in a serial queue, for a SQLite transaction, a state read
back, a scene rebuild and a tile re-render before the next.  The queue drained slower than events
arrived, so the canvas replayed old positions seconds behind the cursor, and every write dropped
the object's tiles to grey.  The rules, for every tool, panel and command:

* *The UI never waits on persistence.*  A local command is applied to the in-memory engine state
  and the scene on the main actor and is on screen in the same frame.  Writing it to the local
  store and outbox happens off the main actor, in batches: pending changes are written together
  in one transaction at most every 250 ms, and at once when the app deactivates or quits, a
  document closes, or the sync client is about to push.  A crash loses at most the unwritten
  batch (at most 250 ms of work); that is accepted.
* *Gestures write intent.*  A continuous gesture -- dragging points, handles, objects, guides or
  sliders, scrubbing a field, nudging with the arrow keys -- previews in the overlay and emits
  one change when it ends (the rule `Tool.swift` already states).  Typing is applied to the text
  immediately and written as one change per word or pause (the undo grouping of TYPE-003), not
  per key.
* *Batches collapse.*  Inside a batch not yet written, consecutive writes to the same register
  keep only the latest (a register is last-writer-wins, and the earlier values were never seen
  by anyone else), and sequence edits of one text node go into one change.  The outbox's
  coalescing before upload (SYNC-002) still applies on top.
* *Rendering never shows a hole.*  An edit keeps an object's old tiles on screen until their
  replacements are drawn; the pasteboard colour never shows through an edited object.

NOTE: As built (2026-09-27).  *UI never waits*: `WTModel.DocumentEngine` holds the one
`DocumentCore` behind a lock shared by the `Document` façade and the backend actor; local commands,
undo and redo apply synchronously on the main actor and queue their outcome, and `WTSync.LocalStore`
writes the queue in one transaction at most 250 ms later, and at once before the outbox is read or
sent, before any other write, on close, and when the app deactivates or quits (`DocumentController.flushAll`).
Undo grouping, labels, dense replica seqs, reconcile, review holds, salvage and snapshots are
unchanged; a failed batch write leaves the store diverged as before (xref:client.adoc[Client],
"Concurrency"; xref:offline.adoc[Offline], "Outbox and coalescing").  *Gestures*: the handle drag
previews in the overlay and writes one `SetHandles`; the other per-event writers found (corner
widgets, effect centres, polygon, gradient and lens handles, text on a path with kbd:[Option],
attribute and mixer sliders, the Halftones slider, colour panels, held arrow keys in fields, nudge
bursts) preview and write once (client.adoc, "Tools").  *Batches*: same-register writes within a
batch collapse to the latest; a word's keystrokes extend one open change (`DocumentCore.open`),
not sent while it can still grow.  *Holes*: retired tiles keep drawing until their replacements are
ready, on Metal and on the Core Graphics fallback (client.adoc, "Metal tile renderer").  Batched and
unbatched edits give the same state hash, locally and on a replica that receives the uploads.

[[D-077]]
=== D-077 Panels take the macOS 26 design: Liquid Glass tabs, resizable groups, dock and float
The panel framework (xref:panels.adoc[Panels]) keeps FreeHand's model -- tabbed groups that dock
at an edge or float, panels dragged between groups to make one's own tab sets, named layouts --
and takes the look and behaviour of a current Mac app:

* A group's tabs are a Liquid Glass tab strip (the system glass effect on a segmented control of
  tabs), not filled buttons: the selected tab is marked by the glass selection, the others read
  as unselected tabs, and VoiceOver reads them as a tab group.  Control-dense panels use the same
  strip for their inner sections (Transform's Move, Rotate, Scale, Skew, Reflect).
* The dock is a sidebar on the window's glass layer (the system inspector/sidebar treatment);
  floating groups are panels with the system glass background.  Content inside a panel stays on
  standard materials -- glass is for the navigation and control layer, as the HIG asks.
* Docked groups share the dock's height through draggable dividers; a group's body scrolls when
  its content is taller than its share, and content never draws over the next group's title.
* Dragging a tab out of a strip makes a floating group; dropping a tab or a group on another
  strip joins it; tabs reorder by dragging.  Every arrangement is part of the saved layout.

Revised after use (2026-09-27): the first glass tab strip did not read as tabs, nor show which tab
is open or focused, and a toolbar docked among panels laid out as a vertical strip.  So:

* *Content extends beneath the dock.*  The canvas runs the full window width; the dock floats
  over its right side as a translucent glass sidebar, and the artwork shows through it.  Fit,
  zoom-to-fit and centring use the unobscured area (the canvas's safe area), so nothing is placed
  under the dock by default.  Panel cards are frosted glass with vibrant text -- a heavier frost
  for control-dense content -- rather than opaque cards; floating groups get the same.  A *Panel
  transparency* preference and the system's Reduce Transparency make them solid.
* *Tabs are our own control* (the system segmented look was not clear enough): the selected tab
  is a tinted surface joined to the content below it like a folder tab, with an accent bar, bold
  label and full-contrast icon; unselected tabs are secondary labels with a hover highlight; the
  keyboard-focused tab shows a focus ring.  Crowded strips drop unselected labels to icons, then
  overflow into a menu.  A group with one panel shows no tab strip; it drags by its title.
* *A toolbar docked in a panel flows horizontally* and wraps into rows; wide controls (the font
  family) take a full row.  The font family control is a picker whose list is sized to the
  longest name (not the button), shows each family in its own face, and filters as you type.

Revised again after use (2026-09-27, later): the right-hand panels looked floating although docked,
the Tools panel did not look like the other panels, and a group dragged out of the dock left
the others behind.  So panels become *magnetic*:

* *Every group snaps.*  A group or a set of groups moves as a unit called a *cluster*.  Dragged by
  its title bar or gripper, a cluster clicks to the window's left or right edge, to another
  cluster's side (it becomes a new column beside it), or above or below one of its columns (its
  groups join that column), when the edge comes within 10 points; over a docked column it drops
  between groups, as the dock did.  The window's top and bottom stay the toolbar strips.  While
  it is in range the cluster jumps into line, an accent line (or, at a window edge, the area it
  will take) previews the join, and a haptic tick marks it; releasing settles it there.
* *Dragging moves the whole cluster; Option-drag pulls one group out.*  Option is FreeHand's and
  Photoshop's modifier for "just this one"; no panel drag used it (tabs drag with no modifier,
  their context menu is Control-click).  *Float Group* in the Options menu does the same from the
  keyboard.  Tabs keep their behaviour: dragging one out makes its own group, dropping it on a
  strip joins that group.
* *Docked reads as docked.*  A cluster at a window edge is flush with it -- no gap, square corners
  on that side, rounded corners on the canvas side, a hairline and a soft shadow over the canvas
  -- and runs the height of the content area; it moves and resizes with the window, and the
  canvas's safe area leaves it out.  A floating cluster has rounded corners all round and a drop
  shadow, and the safe area ignores it.  Both keep the translucent glass.
* *The Tools panel is a panel like the others*: the same glass, title bar, card and snapping,
  docked left by default; a narrow group keeps its title readable by hiding the gripper and the
  disclosure triangle (the title still drags and collapses).
* The saved layout holds clusters (docked at an edge, or floating with a frame), their columns
  and widths, and the groups in each column; an older layout's docked groups become the cluster
  at that edge and each floating group its own cluster.

[[D-078]]
=== D-078 A live shape keeps its live handles; editing its points converts it to a path in the same change
Found in use (2026-09-28): "After making a shape I couldn't edit it like I could a polygon path."
The spec followed FreeHand, where a rectangle or ellipse behaves like a grouped path that has to be
ungrouped before its points can be edited: the Subselect tool showed and selected a shape's points,
but dragging them wrote nothing.  WireTuner takes the current Mac expectation (Illustrator's live
shapes) instead:

* *The Pointer keeps the live handles.*  A selected rectangle shows a corner-radius handle inside
  each corner (dragging one rounds every corner with *Uniform* on, that corner alone with it off);
  a polygon shows its diamond and a star its circle.  The handles give way to point editing: a
  press with kbd:[Option] (the Pointer's subselect) reaches the point under a handle, and a shape
  with points selected shows none.  Ellipse arcs keep their Object panel fields.
* *Point editing converts.*  The Subselect tool, the Pointer with kbd:[Option], a marquee over
  anchors, the arrow keys, the Object panel's point section, menu:Edit[Clear] on points or
  segments and the Pen's click on a segment all reach a live shape's points as they reach a path's.
  Any edit of them -- moving a point, dragging or retracting a handle, changing the point type or
  *Automatic*, deleting a point or segment, adding a point -- first replaces the shape with an
  ordinary path and then edits the path, in one change labelled "Edit Points".  One undo brings the
  live shape back.
* *Path commands take shapes.*  Add Points, Simplify, Correct Direction, Remove Overlap, Reverse
  Direction, Fractalize, Split at points, the Knife, Eraser and Freeform tools, the distort tools,
  the Mirror tool's *Close paths* and the expert 3D rotation work on a selected shape, converting
  it in the same change under their own label.  A shape the command would leave as it is
  (Correct Direction on a rectangle, Remove Overlap on a shape that does not cross itself,
  Simplify at 0) stays live and nothing is written.  None of these is disabled for a shape.
* *Conversion changes nothing you can see.*  The path has the shape's outline as drawn (a rounded
  corner's two points with quarter-circle handles, an ellipse's four curve points, an arc's pieces
  and centre, a polygon's or star's corners), its transform and other common properties, and its
  attribute stack in the same order; a Corners effect stays and the corners under it are square,
  as they were drawn.  The clip group the shape clipped with and the connectors attached to it name
  the path.  The selection follows: the path is selected with the points that were selected.
* *The status line says so.*  "Rectangle converted to a path. Undo brings the live rectangle
  back." shows each time an edit converts a shape; it blocks nothing and asks nothing, so there is
  no "don't show again" preference.  Illustrator's modal alert was rejected: the conversion is one
  undo step, and the note says which.  menu:Modify[Ungroup] still converts on purpose, without the
  note.

Merge semantics are unchanged: the conversion is the one Ungroup has written since DRAW-009 (a `path`
node created from the geometry the converter saw, the shape node deleted), so a concurrent edit of
the shape is *edit vs delete* with *Restore* bringing the shape back beside the path, and two
concurrent conversions leave two paths.  The point edit that follows writes only to points the same
change created, which no one else can have edited.  No new op, register or conformance vector.

[[D-079]]
=== D-079 Local mode: the app works fully without a server or an account
Found in use (2026-09-27): beta builds go out before the server exists, and an audit showed the app
treating "no account" as "offline" -- every document read *Sign in to sync*, the Library said
*Offline*, every quit with a document open showed the quit sheet, trash, delete and folders failed
with "You are offline…", there was no way to take a document to another Mac as a file except
*Export a Package…*, and the untitled document a launch opens was not in the Library.  The spec
assumed accounts everywhere (D-034, xref:security.adoc[Accounts]).  WireTuner now has a first-class
*Local mode*:

* *When.*  A build is a *Local mode build* when the build setting `WT_LOCAL_MODE` is `YES` (the
  Release default until a server exists, so the beta builds published to GitHub Releases run
  without an account; Debug is `NO` and talks to the compose stack) or when it
  has no server configured (`WT_API_URL` or `WT_AUTH_ISSUER` empty or absent).  A Local mode build
  offers no sign-in: menu:{product}[Sign In…], *Sign In with Apple…*, *Account…* and *Sign Out* are
  not in the menu, and no keychain session is read.  A build with a server runs in Local mode while
  nobody is signed in and the person chose *Use Without an Account* (the account window, and the
  popover of *Sign in to sync*); signing in leaves it and signing out returns to it.
* *No sync, no sign-in, no quit sheet.*  No document connects; the indicator reads *On this Mac*
  (`internaldrive`, never in the attention colour) and its popover explains that the document is
  kept on this Mac and how to move it (menu:File[Save a Copy As…]).  Nothing says *Sign in to sync*.
  *On this Mac* is not waiting work, so quitting never shows the quit sheet.  The launch's
  background uploads are skipped.
* *The Library works on this Mac.*  It reads *On this Mac* where it read *Offline*; rename, move,
  folders (new, rename, delete -- what a deleted folder held moves up, as on the server), duplicate
  (the content re-issued into a new document, as menu:File[Duplicate] does), *Use as Template*,
  *Move to Trash*, and a local *Trash* with *Restore*, *Delete Permanently…* (after a confirmation;
  the store leaves this Mac) and *Empty Trash* all change the library cache alone, one save each.
  *Shared with Me*, *Join Team…*, *Keep Available Offline*, *Remove Local Copy* (this Mac has the
  only copy) and the server's *Archived* and *Trash* are not shown.
* *Server features say why.*  Share, comments (the Comment tool and pins), branches and *Review
  Merge…*, *Restore Version…* (the server's version list), Spotlight and Follow of collaborators,
  team color libraries, *Use as Team Library*, publishing to a web link, and web API data sources
  (with *Credentials…* and *Show Hosts*) are disabled with the reason *Needs a WireTuner account*
  -- never an error or a spinner.  The commands stay in the menus (the command registry's gate), so
  the menus are the same in every build.  menu:File[Save Version…], *Name This Version…* and the
  History panel stay enabled: they work from the history kept on this Mac, and a named version waits
  in the store and uploads after the first sign-in.  *Restore Version…* is disabled because it lists
  the server's versions.
* *Files move work between Macs.*  menu:File[Save a Copy As…] (kbd:[Option+Shift+Cmd+S]) writes the
  document as a `.wiretuner` package; it is the command *Export a Package…* was, which stays as its
  name in the command palette and shortcut sets.  menu:File[Open Package…] and a package
  double-clicked in the Finder open it as a new document on this Mac.
* *The launch's untitled document is a library document.*  With no session to restore, the launch
  makes its document as menu:File[New] does -- recorded in the Library with a UUIDv7, from the
  default template -- so it can be found, renamed and trashed like any other.
* *Upgrading keeps everything.*  A document made in Local mode stays *waiting to upload*: its
  library record is pending and its store keeps its outbox.  When an account exists and the person
  signs in, the library creates the documents in the personal space (folders made on this Mac
  first, parents before children; a trashed document goes to the server's Trash), then every open
  document connects and every closed store with changes uploads in the background -- the paths
  offline work has always used (xref:saving.adoc[Saving], xref:creating-opening.adoc[]).

D-034 is unchanged: sharing still requires sign-in, and Local mode has no sharing at all.  No
protocol, server or conformance change; `WTSync.SyncState` gains `localOnly`, which `SyncClient`
never publishes.

[[D-080]]
=== D-080 Beta distribution: GitHub releases named by date, a DMG and a zip, the appcast on R2
The beta ships outside the App Store (xref:stack.adoc[Technology stack], "Distribution"), so each
release needs an installable download, an update Sparkle can apply inside the sandbox, and a place to
serve both (xref:releasing.adoc[Releasing a beta]):

* *GitHub releases are the download.*  The owner published the first beta by hand as a GitHub
  pre-release on `teacurran/WireTuner2`, and the scripts keep that format: tag and title
  `YYYY.MM.DD-NNN` (the date and that day's three-digit sequence from `001`, the next free one among
  the existing tags), assets `WireTuner-<name>.dmg`, `WireTuner-<name>.zip` and `SHA256SUMS.txt`, a
  pre-release while the build is not notarized.  A date name tells testers at a glance how recent a
  build is and needs no bookkeeping; the app's own version and build number stay in
  `Version.xcconfig`, because Sparkle needs a monotonic `CFBundleVersion`.
* *The appcast is on R2 and points at the GitHub assets.*  A feed needs a fixed URL that the owner's
  domain controls and can cache briefly; GitHub has none that fits (`releases/latest` skips
  pre-releases).  So `appcast.xml` is served from `updates.villagecompute.com`, and each enclosure is
  the zip's GitHub asset URL, so the bytes testers download are the ones on the release page and R2
  holds only the feed and a mirror.  `WT_APPCAST_ENCLOSURE=r2` points the enclosures at the R2 copies
  instead, should GitHub's download limits or redirects get in the way.  The feed is uploaded after
  the release exists (the upload checks the asset answers).

* *A DMG for people, a zip for Sparkle.*  The DMG (the app and an `Applications` link) is what a
  web page links to: it is signed, notarized and stapled, so the first launch passes Gatekeeper
  offline.  The appcast's enclosure is a zip of the stapled app (`ditto --keepParent`): Sparkle's
  sandboxed installer extracts a zip without mounting an image, and the zip is the smaller update.
  One notarization of the DMG covers both, since it notarizes the app inside; the app is stapled from
  the same ticket before it is zipped.  A `.pkg` was rejected: nothing needs installing outside the
  app bundle.
* *One feed per channel*, `https://updates.villagecompute.com/wiretuner/<channel>/appcast.xml`, the
  channel set by `WT_UPDATE_CHANNEL` in `client/Config/Distribution.xcconfig` (`beta` now).
  Sparkle's in-feed `sparkle:channel` was rejected for now: with one audience a separate feed per
  channel keeps a stable release from ever reaching beta testers' feed by a tagging mistake, and a
  build's channel is visible in its `SUFeedURL`.  A stable channel later is a second feed, and a
  build moving a user between feeds is an ordinary update whose `SUFeedURL` differs.
* *The version has one source*, `client/Config/Version.xcconfig`, and the build number only goes up
  across marketing versions (Sparkle orders updates by it); a build number taken from the git commit
  count was rejected because snapshots and squash merges would make it go backwards.  The commit is
  recorded in `release.json`, and the GitHub tag is made at it.
* *An unsigned build has no hardened runtime.*  Ad-hoc code has no team, so library validation under
  the hardened runtime refuses the embedded Sparkle framework and the app aborts at launch; Developer
  ID builds keep it.  Release builds strip our products (not `COPY_PHASE_STRIP`, which breaks
  Sparkle's signatures), and `make release-check` launches the built app every time.
* *Credentials never enter the repository*: the identity, team, notarization profile or API key,
  Sparkle private key and R2 key pair come from the environment or the keychain when used.  The
  public Sparkle key is passed as a build setting at release time rather than committed, so Debug and
  test builds carry none and never start the updater.  Without credentials every step still runs and
  produces an *unsigned test build*, announced so, which goes out only as a GitHub pre-release and
  never to the feed; so the pipeline is exercised before the certificates exist.
* *R2* (production object storage already) serves the files through a custom domain; artifacts are
  immutable and cached for a year, the appcast and the fixed-name DMG for five minutes, and the
  appcast is uploaded last.


[[D-081]]
=== D-081 The default perspective grid reshapes on the canvas; the Perspective tool owns the press
Found in use (2026-09-29): "I can now see the perspective grid, but I can't edit it, and I can't
attach objects to it."  FreeHand MX shows a default grid you drag directly with the Perspective tool
("Using FreeHand MX", "Editing perspective grids"); WireTuner's built-in grid was not stored, so its
handles only said to define a grid first.  WireTuner keeps FreeHand's behaviour, updated where the
Mac expects more feedback (xref:perspective.adoc[Perspective grids]):

* *The built-in grid is editable.*  Dragging or double-clicking any of its handles defines it in the
  same change (a grid "Grid" with the page's built-in geometry and the edit, made the page's grid);
  one undo restores the built-in grid.  Objects attached to the built-in grid follow it, since an
  unset grid reads the default grid, now that element.  Asking the person to open Define Grids and
  click New first was rejected: it is a step FreeHand never had and nothing on the canvas says so.
* *The press says what the keys do.*  A pending attach lists the arrow keys for the grid's
  vanishing-point count in the status line, and names the plane once one is picked; the handle under
  the pointer is highlighted with its hint; a handle drag draws the grid it will leave.  FreeHand's
  arrow badge stays.
* *Objects land where they are held.*  The attach puts the grabbed point of the object under the
  pointer (FreeHand keeps the object under the pointer), not its corner; an object that would reach
  past the horizon is refused with a message rather than drawn inverted.
* *Space belongs to the tool while an object is pressed* (as the shape tools take it to reposition),
  so FreeHand's Space flip works; with nothing pressed Space is still the temporary Hand.

Merge: the definition is an element insert of a new grid, so it merges as Define Grids' btn:[New]
does; two offline definitions keep both and the page register is LWW (perspective.adoc, "Reshaping
the built-in grid").  No new op, register or conformance vector.
