== Client

[cols="1,2,3"]
|===
|Concern |Choice |Why

|Platform
|macOS 15 or later, Apple silicon and Intel
|Needs the `CGPath` boolean and offset operations (macOS 14+) and current SwiftUI/AppKit
interop.  Minimum version is revisited each September (xref:decisions.adoc#D-004[D-004]).

|Language
|Swift 6, strict concurrency
|Data-race safety matters in a client with a network session, a merge engine and a renderer on
different executors.

|UI
|AppKit for the document window, canvas, tools and menus; SwiftUI hosted in `NSHostingView` for
panel contents and dialogs
|The interaction model -- precise mouse tracking, modifier keys mid-drag, docked tabbed panel
groups, floating toolbars -- is an AppKit interaction model.  SwiftUI is faster to build the many
form-like panels in.

|Rendering
|One renderer-agnostic display list behind the `WTRender` protocol, drawn by two renderers: a
Metal tile renderer for the screen (`MTKView` over `CAMetalLayer`, tile atlas textures, path
filling on the GPU by stencil-then-cover, a Core Text glyph atlas, Core Image raster effects
delivered as Metal textures) and Core Graphics as the reference renderer for PDF, print, export
and golden images
|The canvas must hold 120 Hz on a ProMotion display while zooming and panning the design-point
document, which rasterising into `CALayer` stores with Core Graphics cannot promise.  Core
Graphics stays the truth: the same display list drawn through it is what prints, and the Metal
output is tested against it tile by tile (xref:testing.adoc[Testing],
xref:decisions.adoc#D-006[D-006]).  Core Graphics also draws the screen where Metal is
unavailable.

|Geometry
|`CGPath` boolean/offset operations, plus `WTGeometry` (Swift) for Bézier math, fitting,
simplification, blends, envelopes and tracing
|Native, robust on curves; no C++ dependency for the common operations.

|Text
|Core Text for shaping and layout; glyphs rasterised by Core Text into an atlas texture for the
Metal renderer
|Kerning, OpenType features, vertical text, and the same shaping as print output.  One shaping
engine feeds both renderers, so glyph positions cannot differ between screen and PDF.

|gRPC
|grpc-swift 2 (async/await) with the HTTP/2 NIO transport; swift-protobuf messages
|Generated by buf remote plugins (xref:api-conventions.adoc[API conventions]).

|Local store
|SQLite through GRDB
|Transactional outbox, fast range queries over the change log, WAL durability.

|Auth
|`ASWebAuthenticationSession` + PKCE against Keycloak; tokens in the Keychain
|Native sign-in sheet, no embedded web view holding passwords.

|Font compilation
|fontc (Rust, Apache-2.0) bundled as an XCFramework behind a C FFI, fed by our own UFO writer; WOFF2 written in Swift with Brotli from Compression.framework
|Writing a CFF/TTF/feature compiler is a project of its own; fontmake needs a Python runtime.  The seam is UFO, so the compiler is replaceable (xref:font-export.adoc[Generating fonts]).  CI carries a pinned Rust toolchain for this one artifact.

|Scripting
|AppleScript (`NSScriptCommand` + sdef) and App Intents (Shortcuts)
|AppleScript is the established Mac automation route; App Intents is the modern one
(xref:scripting.adoc[Scripting]).

|Distribution
|Developer ID, notarized, Sparkle updates; Mac App Store later
|Sharing and cloud fonts are not App Store blockers, but updates must be fast in beta.
|===

== Server

Same stack as `dissipate-server`, so the two can share runbooks, CI pools and people.

[cols="1,2"]
|===
|Concern |Choice

|Runtime |Java 25, Quarkus 3.36.x (track dissipate-server's version)
|API |`quarkus-grpc` with Mutiny stubs generated by Quarkus `generate-code` from the same `.proto` files buf lints; `protovalidate-java`
|Persistence |PostgreSQL 17 through Hibernate Reactive Panache and the reactive PG client; Flyway migrations run as a separate job (`main-db-migrations` pattern)
|Cache / fan-out |Valkey 8 (`quarkus-redis-client`): pub/sub for live changes and presence across server nodes, short-lived presence state
|Object storage |Cloudflare R2 in production, MinIO locally, through the AWS SDK v2 S3 client: snapshots, cold change-log segments, blobs
|Identity |Keycloak 26 (OIDC); `quarkus-oidc` validates bearer tokens on every call
|Jobs |`quarkus-scheduler` for snapshotting, compaction, retention and trash expiry
|Observability |OpenTelemetry traces (Jaeger locally), Micrometer + Prometheus metrics, JSON logs with trace ids
|Outbound HTTP |`quarkus-rest-client` for server-side data-merge fetches, behind the SSRF guard and allowlists (xref:data-merge.adoc[]); a master key (`WT_DATA_MASTER_KEY` or a KMS key) envelope-encrypts stored credentials
|Mail |`quarkus-mailer` + Qute templates (share invitations); Mailpit locally
|Local dev |`docker compose`: postgres, valkey, keycloak, minio (+ init), jaeger, mailpit, api, migrations
|===

== Shared

[cols="1,2"]
|===
|Concern |Choice

|Schemas |Protobuf in `proto/`, managed by buf (lint `STANDARD`, breaking `FILE`), module `buf.build/villagecompute/wiretuner`
|Merge engines |`WTCRDT` (Swift package) and `wt-crdt` (Java module), generated merge tables from `wt.crdt` options, one conformance suite
|Docs |AsciiDoc, rendered by `asciidoctor-maven-plugin` (this book); proto reference by `protoc-gen-doc` through buf
|CI |GitHub Actions on the self-hosted `ci` pool: buf lint/breaking, server tests, client tests (macOS runner), conformance on both engines, docs render
|===
