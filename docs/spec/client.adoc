= Client
include::_attributes.adoc[]
:page-slug: client

The Mac app is the product.  Everything a designer touches is native AppKit; the
document is a typed Swift model over the merge engine; rendering is one display list drawn by
Metal on screen and by Core Graphics for PDF and print, and the two are tested against each
other so that the screen, the PDF and the printer agree.

Dependency direction is strictly downward in the table: `WTApp` may import everything;
`WTCRDT` imports only `WTProto`.

== Concurrency

* `Engine` and `SyncClient` are actors.  `Document` is a `@MainActor` observable façade over the
  engine's state, updated by applying changes on the main actor after the engine has merged
  them on its own executor.  UI code never touches the engine directly.
* Rendering runs on a render executor; the display list is a value type built from the
  document, so a render in flight never observes a half-applied change.
* Every change, local or remote, produces a `ChangeSummary` (touched nodes, touched fields,
  dirty rect) that the renderer, the panels and the presence overlay subscribe to.

`WTCanvasView` is an `MTKView` (its layer a `CAMetalLayer`) that composites the tile atlas, with
a transparent Core Graphics overlay layer above it for handles, tool previews, smart guides,
measurements and presence; it owns the tracking loop and forwards events -- mouse, pinch,
two-finger rotate, smart zoom, Force click -- to the active `Tool`.  The pasteboard is
222 × 222 inches; pages sit on it.

NOTE: Deviation recorded by APP-002 and APP-003.  There is no `NSScrollView`: the canvas is
`CanvasView` (`WTApp/Document`), a layer-hosting `NSView` whose unflipped root layer holds the
REND-001 `TiledCanvasLayer` and the tool overlay layer above it, beside two plain `NSScroller`s
driven by `CanvasScrollerModel`, which clamps the view to the pasteboard in rotated, scaled
space (`R · S` applied to the 222 × 222 in pasteboard), so a rotated canvas needs no rotated
clip view.  An `NSScrollView` would own the document view's bounds origin and magnification,
which `Viewport` already owns, and it cannot scroll a rotated extent.  The Metal `WTCanvasView`
(REND-006) replaces the tile layer inside `CanvasView`, not the view.  On-screen orientation
of the fallback canvas is checked by a snapshot of the view's layer tree (pasteboard (0, 0)
at the top-left; no flip was needed).  `ToolContext` carries `SnappingContext`, an identity
placeholder reading *Snap distance* and *Pick distance* until GEO-005 and OBJ-039; the
document is a `DocumentHandle` (id, title, pages, a display-list provider and the
`CommandSink`) until `WTModel.Document` lands.  Temporary tools follow
xref:toolbars.adoc[Toolbars]: pushed only between drags (Command pressed mid-drag is a
modifier for the current tool, as xref:moving.adoc[Moving] requires), restored on key-up even
mid-drag, in which case the current tool's drag is ended with a synthesized mouse-up at the
last pointer position and the rest of the drag is swallowed.

== Tools

A tool conforms to `Tool`:

[source,swift]
----
protocol Tool: AnyObject {
    static var id: ToolID { get }
    var cursor: NSCursor { get }
    func activate(in context: ToolContext)
    func deactivate()
    func mouseDown(_ e: CanvasEvent)
    func mouseDragged(_ e: CanvasEvent)
    func mouseUp(_ e: CanvasEvent)
    func flagsChanged(_ e: CanvasEvent)     // modifier change mid-drag; many tools depend on it
    func keyDown(_ e: NSEvent) -> Bool
    func drawOverlay(in ctx: CGContext, viewport: Viewport)  // handles, previews
    func cancel()                            // Esc
}
----

`ToolContext` gives a tool the document, selection, snapping (including the smart-guide
engine, xref:moving.adoc#smart-guides[Smart guides]), the view transform (zoom, scroll and
canvas rotation), tablet pressure, and a `CommandSink` for emitting changes.  `drawOverlay`
draws into the Core Graphics overlay layer above the Metal canvas; it is redrawn per event, not
per frame, so it never competes with tile rendering for the frame budget.  Tools *preview* during a drag by drawing an
overlay and emit exactly one change on mouse-up (or one per segment for the Pen), so a drag is
one undo step and one change on the wire.  Tools that must show live remote-visible feedback
(text typing) emit as they go.

== Panels

Panels are `NSViewController`s registered with the panel framework (APP-004) by id, title,
default group and a SwiftUI body.  A panel body observes the `Document` and the selection; it
never caches document state.  Editing controls follow one rule: a field being edited holds its
text until commit, then writes a command; a remote change to the same field while editing is
shown as a subtle highlight, not applied into the field.

== Rendering

Rendering is split at the display list.  Above it, one pipeline turns the document into
resolved drawing primitives; below it, two renderers turn primitives into pixels: Metal for the
screen and Core Graphics for everything that must be exactly right (xref:decisions.adoc#D-006[D-006]).

=== The display list

* The display list is built per canvas (pasteboard or master page) from the layer order;
  invisible layers, deleted nodes and `local_only` state are skipped.  It is a value type of
  *resolved* primitives -- flattened transform chains, style references resolved to values,
  strokes already expanded to outlines by `WTGeometry` (GEO-003), text as positioned glyph runs
  from `WTText`, raster effects as node ids into the effect cache -- and it knows nothing about
  Metal or Core Graphics.
* Both renderers implement `WTRender` over it.  Everything that can be shared is shared: the
  display list; the view transform (`T(scroll) · R(rotation) · S(zoom)`, rotation being view
  state from xref:document-view.adoc[Setting the document view]); tile geometry (256 px tiles
  keyed by canvas, zoom-ladder step, rotation angle, column and row); the invalidation pipeline
  (REND-004: `ChangeSummary` → dirty rects → dirty tile keys); hit testing (REND-003, which runs
  on the display-list geometry, never on pixels); view modes (REND-005); the per-node effect
  cache; and the curve-flattening tolerance, a function of the view scale that both renderers
  call.
* What differs is only how a dirty tile becomes pixels, and the two answers are held to
  agreement by REND-007's per-tile comparison (xref:testing.adoc[Testing]).

=== Metal tile renderer (primary on screen)

* `WTCanvasView` is an `MTKView` with `isPaused = true` and `enableSetNeedsDisplay = true`: a
  frame is drawn only when the view transform changed or a tile became ready, at the display's
  maximum refresh (`preferredFramesPerSecond` = 120 on ProMotion).  The frame budget is 8.3 ms
  and a frame never waits for rasterisation: it composites the tiles that exist, substituting
  the nearest zoom-ladder neighbour scaled, and blank tiles draw the pasteboard colour.
* *Tile atlas*: tiles are 256 × 256 device-pixel cells of a few 4096² `MTLTexture` atlases per
  document view, in the display's pixel format; a tile key maps to an atlas slot.  Tiles are
  rendered in the *rotated view space*: the tile's own axes are the screen's, so a rotated
  canvas is drawn once at the settled angle and never resampled for display.  While a rotate or
  pinch gesture is in progress the existing tiles are drawn through the changing transform
  (one textured quad each); the angle or zoom step is re-rasterised when the gesture settles or
  every 250 ms during it, whichever comes first.  Pan is a lookup: no rasterisation at all
  until the viewport reaches tiles that do not exist.
* *Path filling* is stencil-then-cover.  A path's curves are flattened to line segments at the
  shared tolerance and drawn as a triangle fan from any anchor into the stencil buffer with
  increment/decrement (non-zero) or invert (even-odd); the fill is then drawn once over the
  path's bounds with the stencil test, which is where the fragment shader evaluates solid
  colours, gradients and tiled fills.  Chosen over Loop-Blinn because it needs no triangulation
  of the interior: self-intersecting and multi-contour paths, both winding rules and any edit
  to any point are handled exactly and without CPU work per path per frame, and it computes the
  same coverage as Core Graphics' scan converter, which is what the parity test needs.
  Loop-Blinn's resolution-independent curves are not worth its per-path triangulation (which
  must be redone on every point drag and breaks on self-intersections) when tiles are
  re-rasterised per zoom step anyway.  Edges are anti-aliased with 4× MSAA on the tile render
  target, resolved into the atlas.
* *Strokes* are filled outlines: the display list carries the stroked outline from
  `WTGeometry` (caps, joins, miter limit, dashes, arrowheads), so both renderers fill the same
  polygon and cannot disagree about a join.  Hairlines and strokes thinner than a device pixel
  are widened to one pixel at reduced alpha, the same rule Core Graphics applies on screen.
* *Text*: `WTText` lays out with Core Text; the renderer holds a glyph atlas texture (glyph
  bitmaps rasterised by Core Text per font, size bucket and quarter-pixel offset, evicted
  least-recently used) and draws glyph runs as textured quads.  Glyphs larger than 256 px,
  text with effects, and text on a path are drawn as paths from `CTFontCreatePathForGlyph`
  through the fill route, so zoomed type stays sharp.
* *Effects*: vector effects are applied to the display path before the list is built; raster
  effects render the node to a `CIImage` at the document raster resolution and the Core Image
  graph is executed by a `CIContext(mtlDevice:)` straight into an `MTLTexture`, composited in
  the tile pass with no CPU round trip.  Results are cached per node and invalidated by
  `ChangeSummary`.
* *Images* are `MTLTexture`s uploaded once per asset at the on-screen resolution the Redraw
  preferences ask for.
* *Fallback*: if `MTLCreateSystemDefaultDevice()` returns nil or a command buffer fails three
  times in a row, the view switches to the Core Graphics renderer for the same tile keys
  (rasterised on the render executor into `CALayer` contents, as REND-001 delivers first) and
  logs the reason.  The fallback is also the on-screen renderer until REND-006 lands.

=== Core Graphics reference renderer

* The same display list drawn into a `CGContext`: a PDF context for print and export, bitmap
  contexts for golden images and the parity test, and layer contents for the fallback canvas.
  Print and PDF export therefore give pixel-identical results to the golden images, and the
  screen is held to them within tolerance.
* Rules that keep the two renderers in agreement are enforced above the seam: one flattening
  tolerance, one stroked outline, one glyph layout, one Core Image graph (Core Graphics receives
  a `CGImage` from the same `CIImage`), one colour pipeline (both draw in the document's working
  space and convert for the display through ColorSync; the CMS epic owns the profiles).
* Hit testing uses the same geometry as both renderers: fills by winding, strokes by distance
  to the stroked outline, points and handles by view-space distance, with the pointer mapped
  through the inverse view transform (rotation included).

NOTE: Deviation recorded by REND-001.  The bitmap and PDF renders of the corpus are
pixel-identical for opaque content (0 tolerance on every interior pixel; anti-aliased edge
pixels within 16/255).  Inside a group composited with opacity below 1, Core Graphics blends
the PDF's transparency group in a different working space than a live transparency layer
does, and single channels of interior pixels shift by up to 4/255 (observed: green 140 vs 144
for 50% red over white); neither the group's colour space nor the rasterizer's is exposed, so
the gate holds translucent-group interiors to 4/255 and everything else to 0.  Until the image
pipeline and `WTText` land, the display list carries an image placeholder (drawn as a neutral
grey block with a cross) and a text-run placeholder (the run's bounds tinted at 15% plus its
baseline); strokes carry width, cap, join, miter limit and dash and are stroked by Core
Graphics until GEO-003 supplies pre-expanded outlines.  Tile keys quantize the rasterization
scale (zoom × backing scale) on a ladder of 64 steps per octave (`ZoomStep`), so the preset
magnifications sit on the ladder and any settled zoom is within 0.55% of its step.

NOTE: Deviations recorded by REND-002, REND-003 and REND-005.  *Attribute stacks*: a
`PathItem` carries a resolved `Appearance` (fills and strokes bottom first in one list);
`Paint` gained `.none`.  Until GEO-003, arrowheads are placed by WTRender itself (the path is
trimmed by `pathTrim × width` with GEO-001's arc-length split and the head mapped by width,
endpoint and GEO-001 tangent) and Core Graphics strokes the trimmed centreline.  *Hairlines*:
Core Graphics paints nothing for line width 0 in bitmap contexts, so a hairline (and every
Keyline line) is one device pixel computed from the CTM: a pixel in bitmaps and tiles, one
point on a PDF page rather than PDF's device-thinnest `0 w`; the bitmap/PDF gate compares
renders containing hairlines at 1× only.  *View modes*: Keyline draws in the nearest enclosing
group's `highlightColor` (the layer highlight colour; black outside any layer, which is what
the guide's "black hairlines" describes for the default layer colour), keeps clips and ignores
opacity; the fast modes composite translucent groups member by member at the group's alpha
instead of through a transparency layer, draw image placeholders as crossed boxes and greek
text runs at most 50 pt tall as grey bars.  Blend steps and raster effects are not in the
display list yet (`ViewMode.drawsRasterEffects` is the switch their renderer path will read).
Tile keys do not carry the mode, so a mode change on the tile canvas swaps the cache's renderer
and drops its tiles (`TileCache.replaceRenderer`, `TiledCanvasLayer.setRenderer`); the
`WTRender` protocol gained `viewMode`.  Overprint preview composites overprinting paint with
the multiply blend mode in the working space until the CMS epic supplies an ink simulation.
*Hit testing*: results address items by index path (the display list carries no node ids
yet); stroke hits measure distance to the centreline against the widest visible stroke's half
width plus the pick distance, honouring butt and square caps at open ends but not excluding
dash gaps or including miter spikes, until GEO-003's stroked outline replaces the centreline;
marquee enclosure and contact are judged on path geometry (not stroke width) in view space.
The R-tree is keyed by top-level item index and maintained incrementally when a changed list
keeps its length, rebuilt (STR bulk load, 8 ms for 50,000 items in release) otherwise.

== Undo

`Command` execution returns a `Change` and its inverse.  The `UndoManager` is per document and
holds pairs; undo emits the inverse *filtered* by the rule in xref:crdt-model.adoc[CRDT model].
Menu titles come from the change label ("Undo Move 3 Objects").  Drags register one entry;
typing coalesces per word and per 1 s pause.

== Help

The guide render of this book ships in the app bundle as an Apple Help Book; menu:Help[] opens
it, and every panel's help button opens its page by slug.

== Accessibility and localisation

* Every control has an accessibility label and identifier (also used by UI tests).
* Strings are in `Localizable.xcstrings`; the guide is English-only in v1.
* Full keyboard access to panels; VoiceOver describes the selection and the canvas objects by
  name and kind.
