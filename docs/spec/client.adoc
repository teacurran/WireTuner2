= Client
include::_attributes.adoc[]
:page-slug: client

The Mac app is the product.  Everything a designer touches is native AppKit; the
document is a typed Swift model over the merge engine; rendering is one display list drawn by
Metal on screen and by Core Graphics for PDF and print, and the two are tested against each
other so that the screen, the PDF and the printer agree.

== Packages

Dependency direction is strictly downward in the table: `WTApp` may import everything;
`WTCRDT` imports only `WTProto`.

NOTE: Deviation recorded by DRAW-002.  `WTModel` builds WTRender's display list and change
summaries (`DocumentDisplayListBuilder`, below), so it imports `WTRender` and `WTGeometry`, which
sit below it in the table; neither imports `WTModel`, so the package graph stays acyclic
(`WTSync` reaches WTRender only through `WTModel`).

== Concurrency

* `Engine` and `SyncClient` are actors.  `Document` is a `@MainActor` observable façade over the
  engine's state, updated by applying changes on the main actor after the engine has merged
  them on its own executor.  UI code never touches the engine directly.
* Rendering runs on a render executor; the display list is a value type built from the
  document, so a render in flight never observes a half-applied change.
* Every change, local or remote, produces a `ChangeSummary` (touched nodes, touched fields,
  dirty rect) that the renderer, the panels and the presence overlay subscribe to.

NOTE: Deviation recorded by SYNC-001 and APP-011.  The merge state of an open document is held
by a `WTModel.DocumentBackend` actor -- `WTSync.LocalStore` for a stored document,
`WTModel.MemoryBackend` otherwise -- as a `DocumentCore` (the `EngineState`, replica, next seq,
last server seq and undo stack), not by a `WTCRDT.Engine` actor: a local change must be applied
and appended to the outbox in one database transaction, which an `await` on a separate actor
cannot give, and `Engine` cannot be created from a decoded snapshot.  `Document` is the
`@MainActor @Observable` façade over the backend; it publishes `revision`, `lastChange` and the
Edit menu state.

NOTE: As built by DRAW-002 and the WTApp integration.  `Document` also keeps `state`, a copy of
the merged `EngineState` as of the last change it published (read back from the backend after each
call), so the main actor can build the display list and the panels without an actor hop; the
backend's copy stays authoritative.  Calls to the backend run one at a time in call order
(`settle()` waits for them), and every published change is delivered to `observe` handlers as a
`DocumentEvent` (the change, its origin -- local, undo, redo, remote -- and the states before and
after).  `Document(memory:)` opens a `MemoryBackend` without suspending.  `ChangeSummary` is
produced by `WTModel.DocumentDisplayListBuilder.apply(_:state:origin:)` from the event: the nodes
each op targets (with the field paths written), their painted bounds before and after, and the
structural flag when items were added, removed or restacked.  The builder reuses the items of
nodes a change did not touch.  It is named `DocumentDisplayListBuilder` because WTRender's
low-level `DisplayListBuilder` would be ambiguous in every file importing both.

`WTCanvasView` is an `MTKView` (its layer a `CAMetalLayer`) that composites the tile atlas, with
a transparent Core Graphics overlay layer above it for handles, tool previews, smart guides,
measurements and presence; it owns the tracking loop and forwards events -- mouse, pinch,
two-finger rotate, smart zoom, Force click -- to the active `Tool`.  The pasteboard is
222 × 222 inches; pages sit on it.

NOTE: Deviation recorded by APP-002 and APP-003.  There is no `NSScrollView`: the canvas is
`CanvasView` (`WTApp/Document`), a layer-hosting `NSView` whose unflipped root layer holds the
REND-001 `TiledCanvasLayer` and the tool overlay layer above it, beside two plain `NSScroller`s
driven by `CanvasScrollerModel`, which clamps the view to the pasteboard in rotated, scaled
space (`R · S` applied to the 222 × 222 in pasteboard), so a rotated canvas needs no rotated
clip view.  An `NSScrollView` would own the document view's bounds origin and magnification,
which `Viewport` already owns, and it cannot scroll a rotated extent.  The Metal `WTCanvasView`
(REND-006) replaces the tile layer inside `CanvasView`, not the view.  On-screen orientation
of the fallback canvas is checked by a snapshot of the view's layer tree (pasteboard (0, 0)
at the top-left; no flip was needed).  `ToolContext` carries `SnappingContext`, an identity
placeholder reading *Snap distance* and *Pick distance* until GEO-005 and OBJ-039; the
document is a `DocumentHandle` (id, title, pages, the display list and the `CommandSink`), backed
by a `WTModel.Document` since the WTApp integration of DRAW-002 (next note).  Temporary tools follow
xref:toolbars.adoc[Toolbars]: pushed only between drags (Command pressed mid-drag is a
modifier for the current tool, as xref:moving.adoc[Moving] requires), restored on key-up even
mid-drag, in which case the current tool's drag is ended with a synthesized mouse-up at the
last pointer position and the rest of the drag is swallowed.

NOTE: As built by the WTApp integration of DRAW-002.  `DocumentHandle` (`WTApp/Document`) is the
window's view of a `WTModel.Document`: it opens the model through `DocumentEnvironment.openModel`
per document id -- `DocumentOpener.localStore` (a `WTSync.LocalStore` at
`LocalStore.defaultURL(documentID:)` with the *Undo levels* preference) in the app, a memory
document in tests and test launches -- and shows the pages alone until the model is open; commands
issued before then wait for it.  It keeps a `DocumentDisplayListBuilder` whose background is the
page furniture (one group at index 0; pages and units are not nodes yet, so Add Page and Change
Units are not undoable changes) and rebuilds the touched nodes on every `DocumentEvent`, handing
the summary and the lists before and after to one `InvalidationBatcher` whose targets are the
canvases' tile canvases (local changes at once, remote ones per frame).  `CommandSink` is
`perform(_ command: WTModel.Command) -> Task<Change?, Never>`; a command that throws is logged
(subsystem `com.villagecompute.wiretuner`, category `document`) and performs nothing.  The local
store is closed when the document's last view closes.

== Tools

A tool conforms to `Tool`:

[source,swift]
----
protocol Tool: AnyObject {
    static var id: ToolID { get }
    var cursor: NSCursor { get }
    func activate(in context: ToolContext)
    func deactivate()
    func mouseDown(_ e: CanvasEvent)
    func mouseDragged(_ e: CanvasEvent)
    func mouseUp(_ e: CanvasEvent)
    func flagsChanged(_ e: CanvasEvent)     // modifier change mid-drag; many tools depend on it
    func keyDown(_ e: NSEvent) -> Bool
    func drawOverlay(in ctx: CGContext, viewport: Viewport)  // handles, previews
    func cancel()                            // Esc
}
----

`ToolContext` gives a tool the document, selection, snapping (including the smart-guide
engine, xref:moving.adoc#smart-guides[Smart guides]), the view transform (zoom, scroll and
canvas rotation), tablet pressure, and a `CommandSink` for emitting changes.  `drawOverlay`
draws into the Core Graphics overlay layer above the Metal canvas; it is redrawn per event, not
per frame, so it never competes with tile rendering for the frame budget.  Tools *preview* during a drag by drawing an
overlay and emit exactly one change on mouse-up (or one per segment for the Pen), so a drag is
one undo step and one change on the wire.  Tools that must show live remote-visible feedback
(text typing) emit as they go.

== Panels

Panels are `NSViewController`s registered with the panel framework (APP-004) by id, title,
default group and a SwiftUI body.  A panel body observes the `Document` and the selection; it
never caches document state.  Editing controls follow one rule: a field being edited holds its
text until commit, then writes a command; a remote change to the same field while editing is
shown as a subtle highlight, not applied into the field.

== Rendering

Rendering is split at the display list.  Above it, one pipeline turns the document into
resolved drawing primitives; below it, two renderers turn primitives into pixels: Metal for the
screen and Core Graphics for everything that must be exactly right (xref:decisions.adoc#D-006[D-006]).

=== The display list

* The display list is built per canvas (pasteboard or master page) from the layer order;
  invisible layers, deleted nodes and `local_only` state are skipped.  It is a value type of
  *resolved* primitives -- flattened transform chains, style references resolved to values,
  strokes already expanded to outlines by `WTGeometry` (GEO-003), text as positioned glyph runs
  from `WTText`, raster effects as node ids into the effect cache -- and it knows nothing about
  Metal or Core Graphics.
* Both renderers implement `WTRender` over it.  Everything that can be shared is shared: the
  display list; the view transform (`T(scroll) · R(rotation) · S(zoom)`, rotation being view
  state from xref:document-view.adoc[Setting the document view]); tile geometry (256 px tiles
  keyed by canvas, zoom-ladder step, rotation angle, column and row); the invalidation pipeline
  (REND-004: `ChangeSummary` → dirty rects → dirty tile keys); hit testing (REND-003, which runs
  on the display-list geometry, never on pixels); view modes (REND-005); the per-node effect
  cache; and the curve-flattening tolerance, a function of the view scale that both renderers
  call.
* What differs is only how a dirty tile becomes pixels, and the two answers are held to
  agreement by REND-007's per-tile comparison (xref:testing.adoc[Testing]).

=== Metal tile renderer (primary on screen)

* `WTCanvasView` is an `MTKView` with `isPaused = true` and `enableSetNeedsDisplay = true`: a
  frame is drawn only when the view transform changed or a tile became ready, at the display's
  maximum refresh (`preferredFramesPerSecond` = 120 on ProMotion).  The frame budget is 8.3 ms
  and a frame never waits for rasterisation: it composites the tiles that exist, substituting
  the nearest zoom-ladder neighbour scaled, and blank tiles draw the pasteboard colour.
* *Tile atlas*: tiles are 256 × 256 device-pixel cells of a few 4096² `MTLTexture` atlases per
  document view, in the display's pixel format; a tile key maps to an atlas slot.  Tiles are
  rendered in the *rotated view space*: the tile's own axes are the screen's, so a rotated
  canvas is drawn once at the settled angle and never resampled for display.  While a rotate or
  pinch gesture is in progress the existing tiles are drawn through the changing transform
  (one textured quad each); the angle or zoom step is re-rasterised when the gesture settles or
  every 250 ms during it, whichever comes first.  Pan is a lookup: no rasterisation at all
  until the viewport reaches tiles that do not exist.
* *Path filling* is stencil-then-cover.  A path's curves are flattened to line segments at the
  shared tolerance and drawn as a triangle fan from any anchor into the stencil buffer with
  increment/decrement (non-zero) or invert (even-odd); the fill is then drawn once over the
  path's bounds with the stencil test, which is where the fragment shader evaluates solid
  colours, gradients and tiled fills.  Chosen over Loop-Blinn because it needs no triangulation
  of the interior: self-intersecting and multi-contour paths, both winding rules and any edit
  to any point are handled exactly and without CPU work per path per frame, and it computes the
  same coverage as Core Graphics' scan converter, which is what the parity test needs.
  Loop-Blinn's resolution-independent curves are not worth its per-path triangulation (which
  must be redone on every point drag and breaks on self-intersections) when tiles are
  re-rasterised per zoom step anyway.  Edges are anti-aliased with 4× MSAA on the tile render
  target, resolved into the atlas.
* *Strokes* are filled outlines: the display list carries the stroked outline from
  `WTGeometry` (caps, joins, miter limit, dashes, arrowheads), so both renderers fill the same
  polygon and cannot disagree about a join.  Hairlines and strokes thinner than a device pixel
  are widened to one pixel at reduced alpha, the same rule Core Graphics applies on screen.
* *Text*: `WTText` lays out with Core Text; the renderer holds a glyph atlas texture (glyph
  bitmaps rasterised by Core Text per font, size bucket and quarter-pixel offset, evicted
  least-recently used) and draws glyph runs as textured quads.  Glyphs larger than 256 px,
  text with effects, and text on a path are drawn as paths from `CTFontCreatePathForGlyph`
  through the fill route, so zoomed type stays sharp.
* *Effects*: vector effects are applied to the display path before the list is built; raster
  effects render the node to a `CIImage` at the document raster resolution and the Core Image
  graph is executed by a `CIContext(mtlDevice:)` straight into an `MTLTexture`, composited in
  the tile pass with no CPU round trip.  Results are cached per node and invalidated by
  `ChangeSummary`.
* *Images* are `MTLTexture`s uploaded once per asset at the on-screen resolution the Redraw
  preferences ask for.
* *Fallback*: if `MTLCreateSystemDefaultDevice()` returns nil or a command buffer fails three
  times in a row, the view switches to the Core Graphics renderer for the same tile keys
  (rasterised on the render executor into `CALayer` contents, as REND-001 delivers first) and
  logs the reason.  The fallback is also the on-screen renderer until REND-006 lands.

=== Core Graphics reference renderer

* The same display list drawn into a `CGContext`: a PDF context for print and export, bitmap
  contexts for golden images and the parity test, and layer contents for the fallback canvas.
  Print and PDF export therefore give pixel-identical results to the golden images, and the
  screen is held to them within tolerance.
* Rules that keep the two renderers in agreement are enforced above the seam: one flattening
  tolerance, one stroked outline, one glyph layout, one Core Image graph (Core Graphics receives
  a `CGImage` from the same `CIImage`), one colour pipeline (both draw in the document's working
  space and convert for the display through ColorSync; the CMS epic owns the profiles).
* Hit testing uses the same geometry as both renderers: fills by winding, strokes by distance
  to the stroked outline, points and handles by view-space distance, with the pointer mapped
  through the inverse view transform (rotation included).

NOTE: Deviation recorded by REND-001.  The bitmap and PDF renders of the corpus are
pixel-identical for opaque content (0 tolerance on every interior pixel; anti-aliased edge
pixels within 16/255).  Inside a group composited with opacity below 1, Core Graphics blends
the PDF's transparency group in a different working space than a live transparency layer
does, and single channels of interior pixels shift by up to 4/255 (observed: green 140 vs 144
for 50% red over white); neither the group's colour space nor the rasterizer's is exposed, so
the gate holds translucent-group interiors to 4/255 and everything else to 0.  Until the image
pipeline and `WTText` land, the display list carries an image placeholder (drawn as a neutral
grey block with a cross) and a text-run placeholder (the run's bounds tinted at 15% plus its
baseline); strokes carry width, cap, join, miter limit and dash and are stroked by Core
Graphics until GEO-003 supplies pre-expanded outlines.  Tile keys quantize the rasterization
scale (zoom × backing scale) on a ladder of 64 steps per octave (`ZoomStep`), so the preset
magnifications sit on the ladder and any settled zoom is within 0.55% of its step.

NOTE: Deviations recorded by REND-002, REND-003 and REND-005.  *Attribute stacks*: a
`PathItem` carries a resolved `Appearance` (fills and strokes bottom first in one list);
`Paint` gained `.none`.  Until GEO-003, arrowheads are placed by WTRender itself (the path is
trimmed by `pathTrim × width` with GEO-001's arc-length split and the head mapped by width,
endpoint and GEO-001 tangent) and Core Graphics strokes the trimmed centreline.  *Hairlines*:
Core Graphics paints nothing for line width 0 in bitmap contexts, so a hairline (and every
Keyline line) is one device pixel computed from the CTM: a pixel in bitmaps and tiles, one
point on a PDF page rather than PDF's device-thinnest `0 w`; the bitmap/PDF gate compares
renders containing hairlines at 1× only.  *View modes*: Keyline draws in the nearest enclosing
group's `highlightColor` (the layer highlight colour; black outside any layer, which is what
the guide's "black hairlines" describes for the default layer colour), keeps clips and ignores
opacity; the fast modes composite translucent groups member by member at the group's alpha
instead of through a transparency layer, draw image placeholders as crossed boxes and greek
text runs at most 50 pt tall as grey bars.  Blend steps and raster effects are not in the
display list yet (`ViewMode.drawsRasterEffects` is the switch their renderer path will read).
Tile keys do not carry the mode, so a mode change on the tile canvas swaps the cache's renderer
and drops its tiles (`TileCache.replaceRenderer`, `TiledCanvasLayer.setRenderer`); the
`WTRender` protocol gained `viewMode`.  Overprint preview composites overprinting paint with
the multiply blend mode in the working space until the CMS epic supplies an ink simulation.
*Hit testing*: results address items by index path (the display list carries no node ids
yet); stroke hits measure distance to the centreline against the widest visible stroke's half
width plus the pick distance, honouring butt and square caps at open ends but not excluding
dash gaps or including miter spikes, until GEO-003's stroked outline replaces the centreline;
marquee enclosure and contact are judged on path geometry (not stroke width) in view space.
The R-tree is keyed by top-level item index and maintained incrementally when a changed list
keeps its length, rebuilt (STR bulk load, 8 ms for 50,000 items in release) otherwise.

NOTE: Deviations recorded by REND-006.  *Coverage, not MSAA*: the stencil is a 16-sample
winding counter per pixel (8 bits per sample in a memoryless `RGBA32Uint` attachment, the
standard 16× sample pattern); each fan triangle covers its pixel bounding box and the fragment
tests the 16 positions against the triangle's edges with the top-left rule, adding +1 or -1 by
the triangle's orientation.  The cover pass turns the counters into coverage with the fill rule,
zeroes them, and blends colour × coverage into the tile by reading it (programmable blending,
ordered by a raster order group).  Hardware 4× MSAA failed REND-007 on 3–25% of the corpus
tiles (edge errors to 128/255); 16 samples by MSAA over a 2× supersampled tile still failed
wherever separately drawn shapes share or repeat an edge, because MSAA blends per sample while
Core Graphics blends each draw at pixel coverage (a pixel covered c by one shape and 1 − c by
the next lets c(1 − c) of the background through in Core Graphics, none under MSAA: up to
64/255).  Blending per draw at pixel coverage matches Core Graphics there and passes every
tile.  Programmable blending needs an Apple-family GPU (`supportsFamily(.apple4)` and raster
order groups); on other GPUs the canvas uses the Core Graphics fallback.  *Tolerance*: the Metal
renderer flattens at a quarter of the shared tolerance (`MetalRenderer.flatteningRefinement`):
Core Graphics subdivides well inside its flatness bound, and flattening at the bound itself puts
the two edges up to a quarter pixel apart on curves.  *Strokes*: until GEO-003's outlines are in
the display list, the stroked outline is Core Graphics' `copy(strokingWithWidth:)` of the
centreline (dashed first with `copy(dashingWithPhase:)` in local units), stroked in local units
scaled to about one per device pixel: the Core Graphics stroker merges points closer than a
fixed epsilon in path units, which breaks the outline of a hairline on a heavily scaled
arrowhead.  *Atlas*: a `texture2DArray` of 256 × 256 slices (256 slices hold one 4096² sheet),
because a render pass can target a slice but not a sub-rectangle.  *Shaders*: the Metal Shading
Language source ships as `Shaders/TileShaders.msl`, a copied resource, and is compiled at run
time with `makeLibrary(source:)`: Xcode 26 installs the offline Metal compiler only on request
(`xcodebuild -downloadComponent MetalToolchain`), and a `.metal` file would make every SwiftPM
and Xcode build and every CI runner need it.  *Canvas*: WTRender delivers `MetalTileCanvas`, a
`CAMetalLayer` driven by a `CAMetalDisplayLink` (paused until `setNeedsDisplay`, 60–120 Hz),
whose `layer` replaces the `TiledCanvasLayer`'s inside WTApp's `CanvasView` (same `update`,
`invalidate`, `settle` surface; gestures add `beginGesture`/`endGesture`); while a new zoom step or angle renders, the last tiling
whose visible tiles were all drawable is drawn beneath it.  The fallback also engages when the
shaders or the atlas cannot be created, and logs under subsystem
`com.villagecompute.wiretuner`, category `render`.  The glyph atlas, Core Image into textures
and image textures wait for the display list to carry glyph runs, raster effects and images
(TXT-001, FX, the image pipeline); until then Metal draws the same placeholders as Core
Graphics.

NOTE: Deviations recorded by BASIC-034, which hosts REND-006's canvas.  `CanvasView` holds a
`MetalTileCanvas` (`DocumentEnvironment.makeTiles`, `CanvasView.makeTiles()`); without Metal or on a
GPU that is not Apple-family the canvas is its own Core Graphics fallback, so WTApp has one path.
The display link starts when the canvas enters a window and stops when it leaves; WTApp never
calls `drawFrame()`.  Pinch, two-finger rotate, a trackpad scroll with its momentum, and the menu's
rotation animation are folded by `CanvasGestureTracker` into one `beginGesture`/`endGesture` span.
Frame timing is `CanvasView.measureFrame()`, the current view drawn offscreen through
`MetalTileCanvas.renderFrame(into:)` (CPU encode plus GPU): panning, pinching and rotating the
50,000-rectangle document at 1200 × 800 pt @2× measured a p95 of 0.3--0.4 ms per frame against the
8.3 ms budget.  Display-link frames are not timed one by one (WTRender exposes no per-frame hook).
Tests build canvases with `CanvasView.makeFallbackTiles()` so layer snapshots (the orientation test)
read Core Graphics tiles, and run the Metal tests only on an Apple-family GPU.  `ViewMode` is
WTRender's; WTApp adds its `title` and the stored `DrawingMode` spelling.

NOTE: As built by REND-004 (`WTRender/ChangeSummary.swift`, `Invalidation.swift`).  WTRender cannot
import the merge engine, so `ChangeSummary` is WTRender's, with its own `NodeID` and `FieldPath`
mirrors of `OpID` and `RegisterPath`; WTModel builds it.  Instead of one dirty rect it carries
touched nodes, touched field paths per node, per-node painted bounds before and after
(`NodeBounds`: canvas, own rect, effect-expanded rect), an origin (local or remote) and a
structural flag; merging keeps each node's earliest `old` and latest `new`.  `InvalidationMapper`
turns a summary into a `DirtyRegion` (rects per canvas, intersecting rects merged, at most 32 per
canvas by least-growth merging, a burst of over 512 collapsed to one bounding rect); a touched
node without recorded bounds is looked up by id in the display lists before and after, for which
`DisplayList` gained optional `nodeIDs` parallel to its top-level items (`DisplayListBuilder.add`
takes a `node`).  `TiledCanvasLayer`, `TileCache` and `MetalTileCanvas` take `update(displayList:
viewport:changes:)` and `invalidate(pasteboardRects:)`; a tile is dirty when its pasteboard bounds
meet a rect grown by half a device pixel at the tile's scale (anti-aliasing and hairlines); the
Metal canvas drops only the dirty keys, without discarding batches in flight.  Without a summary
a changed list still repaints every tile.  `InvalidationBatcher` delivers to `InvalidationTarget`s
(both canvases): local changes at once, remote ones coalesced until the next frame (1/120 s on the
main queue by default), with the list after the burst.  `HitTester.update(displayList:changes:)`
updates the R-tree in place for the touched nodes' items and rebuilds when the change is
structural or an item's index moved.  WTRender and WTText no longer depend on `WTModel`, which
neither imports; the builder from `WTModel` adds the dependency back when it lands.

NOTE: As built by TXT-001 (`WTText`) and its display-list half in WTRender.  *Input*: WTText lays
out a `TextContent` -- attributed runs, one `ParagraphStyle` per paragraph, one `CharID` per
Unicode scalar (the engine's offsets are scalars) -- independent of WTCRDT, which WTModel adapts;
missing styles read as the default and missing ids are synthesised.  *Glyph runs*: `TextRunItem`
gained `glyphRun` (a `GlyphFont` by value -- PostScript name, size, variation axes, horizontal
scale -- and positioned glyphs, each with an optional glyph-to-local transform for paths and
vertical text).  Both renderers fill glyph outlines from `CTFontCreatePathForGlyph` for every
glyph, so there is no glyph atlas yet: the Metal renderer fills glyphs through the path route,
which passes REND-007 parity; PDF output therefore carries outlines rather than text until IO-025;
Keyline fills glyphs in the highlight colour.  *Layout*: cells are `column_height` tall and
`row_width` wide (0 divides the block's text area); ragged width is the percentage of the column
at which non-justified lines break; defaults are flush zone 100, word spacing 80/100/150 and letter
spacing 0/0/5.  Tab stops go to Core Text (a decimal tab is a right tab ending at `.`, which
Core Text centres on the stop), default stops are set explicitly every 36 pt from the column
edge, leaders are WTText's; a wrapping tab positions like a left tab (its sub-column wrapping is
left to TYPE-025).  Justification stretches (never shrinks) and only after a line's last
tab.  Hyphenation needs words of 5 letters and keeps 2 on each side.  Keeps are applied greedily
with one line of look-ahead and give way at the top of a column.  Balance, modify leading,
copyfit, text wrap, inline graphics and text effects are not part of TXT-001.  *Vertical*: lines
are laid out along a logical axis and turned a quarter clockwise; characters in the CJK, kana,
Hangul and fullwidth blocks stand upright with the `vert` feature rather than through
`kCTVerticalFormsAttributeName`, whose runs report positions in a rotated space.  *On a path*: a
closed path's top run uses the first half of the path, the bottom run the first half of the
reversed path, each within the Left and Right offsets; a run aligned *None* consumes its text; on an
open path the text after the first tab flows on; respacing advances a glyph 0.5 pt at a time until
its advance box clears the previous one; text inside a path fills the widest span a scanline of
the flattened contour leaves at the band's top, middle and bottom, narrowed by the left and right
inset (not a GEO-003 offset), skipping bands that fit only part of a word.  *Carets*: `Caret` is a
segment in the container's space; an anchor after a character at a soft break stays on the earlier
line, after a newline it starts the next paragraph; hit tests return the nearest boundary as an
anchor.  Left-to-right text only.  *Incremental*: paragraphs are cached by what their shaping
depends on and lines by (start, column width, hyphens before); a 200,000-character flow through
81 linked blocks relays out in 9--15 ms after a one-paragraph edit (release, M-series; full layout
0.2--0.5 s).

NOTE: As built by ATTR-004, ATTR-007, ATTR-010 to ATTR-012, ATTR-014, ATTR-018, ATTR-019, ATTR-021
and ATTR-027 (the ATTR paints).  This supersedes the "until GEO-003" statements in the REND-001,
REND-002/003/005 and REND-006 notes: no stroke reaches either renderer as a style.  Every stroke
attribute, hairlines and arrowheads included, is filled as its GEO-003 outline, computed once per
path, style and tolerance and cached (`StrokeExpansion`); the view modes' lines are
`HairlineOutline` polygons; neither renderer calls Core Graphics' stroker.  Stack elements lower
to `PaintedRegion`s both renderers fill.  *Paints*: solid colours stay colours in both renderers.
Every other paint (gradients, patterns, Custom, Textured, Tiled and Lens fills) is drawn by
`PaintDrawing` in Core Graphics: the reference renderer clips to the region and paints the clip;
the Metal renderer paints an unclipped bitmap covering the region's pixels on its surface,
aligned with them, uploads it and composites it through its own coverage of the region
(`PaintOperation.texture`, `texturePaintFragment`), with a fast-mode group's alpha and the
overprint preview's multiply applied to the whole texture as Core Graphics applies them to a
transparency layer around the paint.  Interior pixels therefore agree by construction and
REND-007 compares coverage; this is the per-item fallback the ATTR tasks allow, and native Metal
shading of gradients and patterns remains open.  Paints are defined in resolution-independent
spaces (page-anchored ones in canvas space, object-anchored ones in local space) and sampled
paints on grids anchored at their space's origin, because the tile and the texture must sample
the same points; where Core Graphics' own resampling was not translation-invariant (patterns
under rotation) the paint is computed per device pixel instead.  `CoreGraphicsRenderer.rasterScale`
(4 in `renderPDF`) sets the resolution of sampled paints and lens backdrops in PDF.

== Undo

NOTE: Selection lives in `WTApp/Selection` (`SelectionModel`, `SelectionController`).  A
`SelectionID` is the object's node id (the render-side `NodeID` mirror of its `OpId`); points are
`PointReference(node, contour, point)` and segments `SegmentReference(node, contour, from)`, all
element ids, so a selection survives other objects and points being added or deleted; a change
drops only what no longer resolves.  Hit results (index paths) are mapped to them through the
scene (`DocumentScene.object(atItemPath:)`, `SceneObject.point(leafPath:element:)`).  A rectangle's
or ellipse's derived points carry synthetic ids (replica 0, counter = index + 1).  The Pointer
tool is only the selection part of OBJ-005.  menu:Edit[Undo] and menu:Edit[Redo] are
`UndoCommands` (replacing the standard responder items): their titles are the front document's
`undoTitle`/`redoTitle`, and while a text field edits they go to the field's own undo.
menu:Edit[Clear] deletes the selected points (one `DeletePoints` per path, one change) or else the
selected objects.

`Command` execution returns a `Change` and its inverse.  The `UndoManager` is per document and
holds pairs; undo emits the inverse *filtered* by the rule in xref:crdt-model.adoc[CRDT model].
Menu titles come from the change label ("Undo Move 3 Objects").  Drags register one entry;
typing coalesces per word and per 1 s pause.

NOTE: As built by APP-011 (`WTModel`).  A `Command` appends ops to a `ChangeBuilder` against the
current `EngineState`; `Document.perform` has the backend number the change, apply it with
`applyLocal` and record the inverse on `UndoStack` (the per-document stack; there is no
`UndoManager` type).  Commands between `Document.beginGroup()` and `endGroup()` join one entry;
`UndoCoalescing.typing` commands join one entry until a keystroke ends a word or a pause of 1 s.
An undo or redo emits `EngineState.undoChange` of the top entry (labelled `Undo <label>` or
`Redo <label>`) and moves the entry even when nothing was left to change.  Deviation: after
every undo and redo the rest of the stack is *rebased* (`UndoRebase.swift`).  The engine restores
a target only where it still holds the exact OpId the inverse recorded, and an undo is itself a
new write, so without the rebase a second consecutive undo of the same register (or placement,
flag, element, member, or of typing after its deletion was undone) would be skipped as if someone
else had written it.  The rebase makes each step name the reversal's write where the reversal
restored that step's value, counts an un-deletion by the reversal as the creating step's own,
adds a re-added member's tag to the steps that added it, and maps re-inserted characters to the
originals in the steps that typed them.  WTCRDT gives `Inverse` (and `MemberField`,
`DeletedChar`, `ParagraphRegister`, `PriorFormat`) no public initialiser, so `WTModel` assembles
them from their public fields (`InverseAssembly.swift`, checked field for field against recorded
values) to join a group's inverses and to read the persisted stack back.
