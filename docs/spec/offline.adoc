= Offline and large backlogs
include::_attributes.adoc[]
:page-slug: offline

{product} works fully offline.  The user's requirement that drives this page: someone works on a
plane, or in a studio with no network, for one or two days, producing tens of thousands of
operations, then reconnects -- and so does everyone else on the team.  Everything below is about
making that boring.

== Local store

Each open document lives in a SQLite database (GRDB) under
`~/Library/Application Support/WireTuner/Documents/<document id>/store.sqlite`.

[cols="1,3"]
|===
|Table |Holds

|`meta` |Document id, replica id, hardware UUID the store was created on, last applied `server_seq`, feature level, merge table version.
|`snapshot` |The newest local snapshot (compressed) and its `server_seq`.  Rewritten on close and every 5 minutes while open.
|`changes` |Every change applied since the snapshot: remote (with `server_seq`) and local (with `seq`, `sent_at` null until acked).  This is the outbox.
|`undo` |The undo/redo stack with inverse changes.
|`blobs_pending` |Hashes of blobs waiting to upload, with their local file paths and an optional tag.  The document's thumbnail (tag `THUMBNAIL`, rendered on close and at the snapshot interval) is one row here; a newer thumbnail replaces the pending one.
|`view` |Zoom, scroll, open panels, current page -- `local_only` fields: one row per local-only register a local change wrote (`crdt.local/<node>/<path>`), plus window state the app keeps by key.
|===

Opening a document loads the snapshot, replays `changes`, and connects.  If the network is down
the document is simply open.  The title bar shows the sync state (xref:saving.adoc[Saving]).

NOTE: As built by SYNC-001 (`WTSync.LocalStore`, `StoreSchema`).  The database runs in WAL mode
with `synchronous = FULL`.  `meta` also holds `next_seq` (the replica's next change seq, which
must survive the snapshot dropping the rows that would tell it).  `snapshot` holds the
zstd-compressed `DocumentSnapshot` with its uncompressed size.  A `changes` row carries its
`(replica, seq)` (unique, so a remote change delivered twice is stored once), `server_seq`,
`local`, `sent_at` (set with `server_seq` when the change is acknowledged, or when its echo
arrives on the subscription), its label, the serialized `Change`, and `in_snapshot`.  The rewrite
(on close, and every `Options.snapshotInterval`, 5 minutes by default) deletes the rows before
the oldest unacknowledged local change and marks the rest `in_snapshot`, so the outbox -- and the
remote changes between its changes, which coalescing judges against -- survive it while opening
replays only what the snapshot lacks; the state is encoded and compressed off the store's actor
(1.6 s at the design point), so changes keep applying during a rewrite and are simply not marked.
`undo` rows are `(stack, label, inverse, updated_at)` in
id order per stack, the inverse in `WTSync.InverseCodec`'s encoding; `blobs_pending` adds each
blob's size (the upload order is by size) and allows one row per tag.  The store is bound to the
Mac by the IOKit `IOPlatformUUID`; opened on another Mac it takes a new replica id from seq 1 and
reports the old one (`OpenReport.rotatedFrom`); `rotateReplica()` is the same rotation for
`REPLICA_CONFLICT`, and the unsent changes of a retired id are listed by `retiredOutbox()` for
the salvage below.  A write that fails after its change was applied in memory leaves the store
refusing writes (`Failure.diverged`) until it is reopened from the file, which the transaction
left as it was.  The design-point document opens in 0.77 s (release, M-series; snapshot plus a
1,000-change tail, `DesignPointTests`).

== Outbox and coalescing

A local change is appended to `changes` in the same transaction that applies it to the
in-memory state.  Nothing can be lost between "I saw it on screen" and "it is queued".  What is
appended is the change without its local-only writes (xref:crdt-model.adoc#local-only[Local-only
fields]); the registers those wrote go to `view` in the same transaction (`LocalOnlyRows`: node and
op ids, the `FieldPath`, the value or unset) and are restored on top of the state whenever the
store loads or replaces it -- opening, `installSnapshot`, and the reset `beginSalvage` and
`discardLocalChanges` start from.  A branch store (`exportBranch`) does not copy them.

While offline, consecutive local changes are *coalesced* before sending when doing so cannot
change the merged result:

* Two `SetFields` on the same register from the same replica with no other replica's writes
  between them: keep the later one.  Dragging an object for a minute produces one op, not a
  thousand.  The counter slots the dropped ops occupied are kept by `Noop` ops, so a
  replica's counters remain dense and ids never collide.
* A node created and then deleted with nothing else referencing it: drop both, leaving `Noop`s.
* Consecutive `TextInsert`s of adjacent characters: one op.

Coalescing is applied at send time to changes that are not yet acked, preserving change
boundaries (labels) so history remains readable.  It typically shrinks a day's work by 10× or
more.  Undo state is unaffected because the undo stack holds inverses, not the sent ops.

NOTE: Deviations recorded by SYNC-002 (`WTSync.Coalescer`).  Every change keeps its seq, label and
counter range and at least one op: `Change.ops` has `min_items: 1`, and seqs are dense and
acknowledged one by one, so changes are never emptied or merged.  Consequently adjacent
`TextInsert`s join within one change, or across two changes when the second insert opens a change
that has other ops (its `start_counter` moves past the characters it gave up); typing that emits
one single-insert change per keystroke is not joined and is left to compression.  "No other
replica's writes between them" is judged per register path: a `SetFields` by any other change in
between to the same node and path keeps the earlier write; an earlier op that loses only some of
its paths keeps the rest.  *Create-then-delete is off by default* (`Coalescer.Rules.createThenDelete`):
the creating replica keeps the tombstone, which its state hash covers, so dropping the ops would
leave its hash different from every other replica's until garbage collection removes such
tombstones locally; the rule is implemented (a node whose last `deleted` write in the outbox is
`true` and whose id no other op mentions, all its ops taking one counter) for when CRDT-010 does.
With the standard rules an engine fed the coalesced outbox has the raw outbox's state hash; a
minute of dragging (3,600 one-register changes) sends one substantive op, and a 20,000-op outbox
coalesces and encodes in 16 ms (release).

== Reconnecting with a backlog

. The client subscribes with its last applied `server_seq`.  `Welcome` reports head and the
  replica's last accepted seq, which is where the upload will resume.
. *Download first.*  If the gap is small the subscription streams it; if `Welcome` hints at a
  snapshot, the client fetches the snapshot, replays the tail, and applies it.  Local unsent
  changes are already in the local state (they were applied when made) -- applying remote
  changes on top is just more merging.
. *Measure divergence* (xref:reconcile.adoc[Reconciling]).  If the reconcile rules say to ask,
  the client does not send anything yet; the review sheet decides what to send.
. *Upload.*  The outbox is coalesced and sent through `PushChanges`, a client-streaming call
  designed for bulk: frames of up to 1 MiB, progress read from the caller's own changes
  echoing on the subscription, resumable from `Welcome.last_accepted_seq` if the connection
  drops (below the bulk threshold the ordinary pipelined `PushChange` calls are used instead,
  xref:sync-protocol.adoc[Sync protocol]).  Uploading 20,000 ops (about 2 MiB after
  coalescing and compression) takes seconds.
. Blobs in `blobs_pending` upload afterwards on a background queue with retry: the thumbnail
  first (it is small and the library is waiting for it), then the rest, largest last.
+
NOTE: As built by SYNC-008 (`WTSync.BlobQueue`, `BlobCache`).  The cache is content-addressed
and shared by every document: `~/Library/Application Support/WireTuner/Blobs/<first two hex
digits>/<hex sha256>`, written through a scratch file and moved into place.  Adding a file hashes
and copies it in 1 MiB reads off the store's actor; `blobs_pending` gains `media_type`
(migration `offline-2`).  While the session is up (after the reconcile step) the queue takes the
thumbnail, then the rest by size, asks `Stat` first and streams the cached file in 1 MiB chunks
as the upload asks for them; a failure backs off exponentially per blob (1 s to 5 min,
jittered), `UNAUTHENTICATED` refreshes the token once until a call succeeds, and `STORAGE_QUOTA`
parks untagged blobs (`SyncState.storageFull(n)`) until *Retry now* while the exempt thumbnail
still goes up.  A referenced blob not in the cache is downloaded once however often it is asked
for (`BlobQueue.blob(hash)` answers `.pending`, the renderer draws a placeholder), retried while
the server does not have it yet, verified against its hash and announced as
`BlobEvent.available`.  A 100 MiB image placed offline uploads after reconnecting while edits
keep committing in a few milliseconds (`BlobTests`).
* The subscription stays open during upload; other users see the backlog arrive as it is
  sequenced, which is preferable to a stall followed by a single huge burst.

NOTE: As built by SYNC-005 (`WTSync.SyncClient`, `BulkFrames`).  The backlog -- resends first, then
the coalesced outbox -- is packed into frames of at most 1 MiB and 256 changes, a change larger than
a frame travelling alone; the upload's state is `uploadingBacklog(percent)`, the percentage of its
coalesced bytes at or below the highest own seq echoed on the subscription.  A dropped upload ends
the session, and the next `Welcome.last_accepted_seq` says where it resumes (overlapping changes
are silently acked).  The 20,000-op backlog of the done-when (2,000 changes of 10 ops, 64 KiB frames
to force many) uploads through three forced disconnects against the in-process fake server in
`BulkUploadTests`.

== Replica expiry and salvage [[expiry]]

A replica silent for the retention window (90 days) is retired so garbage collection can
proceed (xref:crdt-model.adoc[CRDT model]).  A retired replica that reconnects gets
`REPLICA_EXPIRED`.  Its unsent changes are not lost:

. The client rotates to a new replica id and rebases: for every unsent change, it re-issues the
  ops that still make sense against the current state as new ops from the new replica, with
  fresh counters.  Ops referencing tombstones that were collected are dropped and listed.
. The result is shown in the conflict review as "changes recovered from an expired session",
  with the dropped items named.  The user can send, or keep the whole set as a branch.

`REPLICA_CONFLICT` (a store restored from backup onto a second Mac while the first is still in
use) takes the same rotation path without the salvage prose, and so does an unsent change over
the server's limits (10,000 ops, 4 MiB -- a long paste), which salvage re-issues as several
changes within them.

NOTE: As built by SYNC-010 (`WTSync.SalvageRebase`, `LocalStore.beginSalvage` / `applySalvage`).
The old replica's ops are already applied locally under ids the server never accepted (and, for a
copied store, ids the other Mac may be using for different ops), so re-issuing them on top of the
local state would leave its ids behind.  Salvage therefore starts from the server's state:
`beginSalvage` rotates to a new replica, moves every unacknowledged local change (the retired
replicas' and the current one's) to a `salvage` table, and empties the store in one transaction;
the next session subscribes from 0 and downloads the server's state (snapshot or replay); then,
before anything is pushed, `applySalvage` re-issues each salvaged change as one change of the new
replica through `DocumentCore.perform` (numbered, applied, written to the outbox and undoable) --
or, when it would not fit `ChangeLimits` (by op count, and by encoded size against its own
fields' size), as several consecutive ones with its label.  Its ops take the same counter offsets
within each re-issued change, so every id a salvaged change created maps by one delta per
re-issued change, and a later op naming it -- as target, parent, text origin, field-path element or
anywhere in its values -- is rewritten; a text delete range is split where it crosses changes.  An
op naming something the state lacks (a tombstone garbage collection removed, or what a dropped op
would have created) is dropped, its counters kept by `Noop`s, and listed with the change's label
and the missing id -- unless its `Noop`s would not fit, in which case the re-issued change ends
before it and the next starts after it; a change left with nothing is not issued.  After `REPLICA_EXPIRED`, or when
anything was dropped, the outbox is held and `SyncEvent.reviewNeeded` carries a recovered
`ReviewModel` (send, or keep the set as a branch); a `REPLICA_CONFLICT` that dropped nothing just
sends, and so does an `oversized` salvage (TEST-001: the sync client starts one when the next change
to send is over the limits and everything before it is accepted, rather than send a change the
server must refuse).  A store opened on another Mac (rotated at open) with unsent changes of the
old replica is salvaged the same way when its first session starts.  Deviations: a change the server accepted
whose acknowledgement never arrived before the replica was retired cannot be told from an unsent
one and is re-issued; `Document` has no reload yet, so after `SyncEvent.stateReplaced` WTApp
reopens the window's façade over the store (WTModel follow-up: `Document.reload()`).

== What needs the network

Everything about drawing works offline.  The following do not:

* Opening a document you have never opened on this Mac (no local store).  The library window
  lists documents cached locally and marks the rest unavailable; its search field matches
  document names in the cached list only, since searching contents is a server query.
  Thumbnails already downloaded are shown; new ones wait.
* Sharing, changing roles, creating branches on the server, merging branches, and version
  history beyond what the local log holds.
* Cloud fonts and team libraries not yet cached.
* Publishing (HTML export uploads assets), sending invitations.

Each is disabled with an explanation, not an error after the fact.
