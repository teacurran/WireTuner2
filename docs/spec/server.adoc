= Server
include::_attributes.adoc[]
:page-slug: server

The server is deliberately dumb about artwork.  It authenticates, authorises, sequences,
stores, relays, snapshots and compacts.  It runs the Java merge engine only to build snapshots,
to extract each document's search record from them, and to verify hashes; it never interprets
a path, lays out text or renders a pixel (thumbnails come from the client).  That keeps every feature
task a client task, and keeps the server generic enough that a schema addition needs no server
change beyond regenerating the merge table.

== Modules

[listing]
....
server/
├── pom.xml                  parent (latest Quarkus BOM -- 3.39.4 at writing -- Java 25)
├── wt-crdt/                 the Java merge engine: pure library, no Quarkus
├── api/                     gRPC services, persistence, jobs, Keycloak integration
│   └── src/main/proto -> ../../../../proto   (symlink to the repo's proto/; Quarkus generate-code reads it)
└── conformance/             runs crdt-conformance vectors against wt-crdt
....

`wt-crdt` mirrors `WTCRDT` type for type: `Engine`, `NodeStore`, `Register`, `MoveLog`,
`FugueText`, `MarkSet`, `FractionalIndex`, `Snapshot`, `StateHash`.  The generated merge table
(`protoc-gen-wtcrdt`) is the only feature-specific input.  One difference is deliberate: Swift's
`Engine` is an actor over the value type `EngineState`, and Java's `Engine` is that value type's
twin -- not thread-safe, one instance per document in the snapshotter.

[[generated-code]]
=== Generated code

`wt-crdt` is a plain library with no Quarkus, so it does not use Quarkus `generate-code`; it
generates its own inputs at `generate-sources` (CRDT-001):

* *doc.v1 messages.*  `protobuf-maven-plugin` (org.xolstice, with `os-maven-plugin` picking the
  protoc binary) compiles `proto/wiretuner/doc/v1/*.proto` and `proto/wt/crdt/options.proto` into
  `target/generated-sources/protobuf/java`.  protoc is the Maven artifact
  `com.google.protobuf:protoc` pinned to the protobuf-java runtime the Quarkus BOM manages (4.35.0
  for Quarkus 3.39.4; `version.protoc` in `wt-crdt/pom.xml`, bumped with the BOM), so gencode is
  never newer than its runtime whatever protoc a machine has installed.  `buf/validate/validate.proto`
  is read from the `build.buf:protovalidate` jar, which `wt-crdt` depends on for the classes the
  generated descriptors link against.  The `.proto` sources are attached to the jar.
* *The merge table.*  `exec-maven-plugin` runs `make -C tools/protoc-gen-wtcrdt generate-java`,
  the Java half of the generator's `generate` target, which writes `MergeTable.java` and
  `merge-table.json` into `target/generated-sources/wtcrdt` and never touches the client's
  committed Swift; `build-helper-maven-plugin` adds the directory as a source root and the JSON as a
  resource beside `MergeTable`.  A server build therefore needs Go and protoc on the `PATH`
  (the generator is Go and drives protoc), in CI as well.

Why `wt-crdt` owns the doc.v1 classes rather than taking them from `api`: the dependency points
the other way (`api` depends on `wt-crdt`), and the engine must not pull in Quarkus.  For now
`api` still generates every file under `proto/` itself (its `src/main/proto` symlink), so the
doc.v1 classes exist twice on `api`'s classpath, identical and from the same protoc; `api`'s own
copy wins.  The intended end state is that `api` generates only its service packages and resolves
the doc.v1 imports from the `.proto` files in the `wt-crdt` jar
(`quarkus.generate-code.grpc.scan-for-imports=all` already allows that), which is an `api` change.

The `conformance` module generates Java for `crdt-conformance/schema/vector.proto` the same way,
importing doc.v1 from the `wt-crdt` jar, and replays every vector in `ConformanceTest`
(xref:testing.adoc[Testing]).  Both modules' JaCoCo reports exclude the generated packages.

All services are `@Blocking`-free: Hibernate Reactive with the reactive PG client, as in
dissipate-server.  Interceptors (in order): request id, OIDC token, principal resolution,
protovalidate, rate limit, OpenTelemetry span.

As built (SRV-014): the rate limit is not an interceptor.  Principal resolution is lazy (the token
is validated when the RPC first asks for the caller, inside its reactive session), so an
interceptor does not know the account; the limits are taken in `RoleGuard` instead, which every RPC
already calls -- `authenticated()` against the account's bucket, `require(document, role)` against
the account's and the document's -- and per change on the push path.  Quarkus's own gRPC tracing
interceptor starts the server span at the default priority (0), after the WireTuner interceptors;
`SpanRequestIdInterceptor` runs after it (priority -100) and puts `wt-request-id` on the span.

The protovalidate interceptor (`ValidationInterceptor`, delivered with SRV-009) checks every
inbound message, each frame of a client stream included, and closes the call with
`INVALID_ARGUMENT / VALIDATION_FAILED` and the violations in `google.rpc.BadRequest` (field path
to rule message).  The gRPC server accepts inbound messages up to 4 MiB + 64 KiB
(`quarkus.grpc.server.max-inbound-message-size`, raised from 2 MiB by SRV-004): a change may be
4 MiB encoded and travels alone when it is larger than a 1 MiB bulk frame, and the Vert.x gRPC
server's own default, 256 KiB, is below even the bulk frames of xref:api-conventions.adoc[API
conventions].  One server-wide limit cannot also be the 1 MiB cap of a multi-change `PushChanges`
frame, so `ChangeRules` enforces that cap and the 4 MiB change cap itself
(`INVALID_ARGUMENT / VALIDATION_FAILED`).

`DocumentService` (SRV-009) checks document RPCs through `RoleGuard` and space RPCs (Create,
List, Search, folders) through space membership: a space is the caller's own account or a team
they belong to; any team member, a guest included, may list and search it and sees only the
documents they can open; creating needs team member or above on a live team.  As built
(SRV-007): Fork and Duplicate start the copy from the source's state at the fork point -- the
newest snapshot at or before it plus the tail through `wt-crdt` (`DocumentStates`, reading cold
segments where the hot log has been compacted) -- stored as the copy's snapshot at the same
`server_seq`, so the copy keeps every node id, register OpId and unstable tombstone (which a
branch needs, xref:branches.adoc[Branches]) and its head starts at the
fork point with no log rows below it; the caller's extra changes follow, the source's blob
references and thumbnail are carried over, and the caller's replicas are bound on the copy with
the seqs the state holds.  An extra change already in the source's hot log with the same bytes is
dropped, with other bytes is `REPLICA_CONFLICT`.  A fork point the retained history cannot rebuild
is `FAILED_PRECONDITION / HISTORY_UNAVAILABLE`.  (Deviation: the copy is not re-issued as one
creation change with fresh ids; the server does not generate ops, and a branch must keep the
parent's ids.)
Rename, MoveToFolder, Trash and Restore tell every live subscription on the document
(`DocumentEvent` `Renamed`, `Moved`, `Trashed`, the caller as actor) once their transaction has
committed (SRV-005).

`BlobService` (SRV-008) streams uploads into 8 MiB S3 multipart parts while hashing, completes
the multipart upload only when size and sha256 match the header and aborts it otherwise, so a
bad upload never becomes visible.  A blob the server already holds is still hashed end to end
before the document gets its reference (a hash alone must not grant access) but is not stored
again.

`BranchService` and `VersionService` (SRV-011, `api/.../branch`, `api/.../history`) are
specified as built on xref:branches.adoc[Branches] and
xref:history.adoc[Version history] (Server).  SRV-011 added the reason
`MERGE_STALE`.  COLLAB-019 resolves a branch's roles through its parent, cascades trash, restore and
moves from the parent, and fans out `BranchEvent`s; COLLAB-020 reads history through a touched-node
index and across cold segments (same pages).  IO-008's storage quota on `BlobService.Upload` is
specified on xref:saving.adoc[Saving] (Server).

`ShareService` (SRV-010, `api/.../share`) is specified as built on
xref:sharing.adoc[Sharing] (Server): members by account or by email (a pending invitation
for an unknown address, bound at the invitee's sign-in), roles, removal, links with role, expiry,
argon2id password and team restriction, access requests, ownership transfer, and the document events
every change sends; COLLAB-011 added `SetTeamAccess` (the per-document team override), the
named-role-wins rule, the team-admin rule for moving a document out of a team, and role changes
reaching live sessions from TeamService, space moves and link expiry (`RoleNotices` over
`LiveSessions`).

SRV-008 and SRV-009 added the reasons `DOCUMENT_EXISTS`, `SPACE_NOT_FOUND`, `FOLDER_NOT_FOUND`,
`HISTORY_UNAVAILABLE`, `BLOB_NOT_FOUND` and `BLOB_MISMATCH`; they are rows of the Errors table in
xref:api-conventions.adoc[API conventions] and values of `sync.v1.ErrorReason`.

== Ingest path

. Interceptors resolve the principal and validate the request (`PushChange`, one change;
  `PushChangeBatch`, up to 32; `PushChanges`, a stream of frames).
. `ReplicaQueue`: pushes from one replica are handled in arrival order on this node, one at a
  time, so pipelined unary calls keep their seq order without the client waiting for each
  ack.  A batch or a bulk frame is fed through the same queue change by change.
. `ChangeIngest.accept(document, change)`: one transaction — `SELECT ... FOR UPDATE` the
  document row, check the replica's `last_seq`, allocate `head_seq + 1`, insert `change_log`,
  update `replica`, commit.  A seq that is not `last_seq + 1` fails the call (`SEQ_GAP`) or,
  in a batch, ends the accepted prefix.
. Respond: the unary response carries the `server_seq`; a batch response the prefix of seqs and
  the first rejection.
. Publish `SequencedChange` on Valkey channel `doc:<id>`; every node with a subscription
  subscribes per open document and fans out to its `Subscribe` streams.
. The ingesting node also fans out locally without waiting for Valkey, so the caller's own
  echo and any other subscriber on the same node see the change immediately.

Throughput target: 2,000 accepted changes per second per document on a single node, 50,000
per second across the cluster.  The per-document lock serialises only the sequence number; the
transaction holds it for one insert.

As built (SRV-004, SRV-005; `api/.../sync`):

* *One statement per change, group-committed.*  `ChangeIngest.INSERT` is a single SQL statement:
  an upsert of the `replica` row that binds an unbound replica on seq 1 to the caller's account
  and device (the all-zero device when the call has no `wt-device`) and otherwise advances
  `last_seq` only when the row is bound to the caller, live, and at `seq - 1`; then, only if that
  took, `head_seq + 1` on the `document` row; then the `change_log` insert at the new head.  The
  `UPDATE` of the document row takes the per-document row lock that `SELECT ... FOR UPDATE` would,
  and holds it to the commit.  Holding it through one commit per change caps a document at one
  change per WAL flush (about 1,300 per second against the Postgres container here), so
  `ChangeWriter` group-commits: while one write for a document is in flight, the next ones wait
  and are then sent as one prepared batch, one round trip and one implicit transaction, executed
  in arrival order.  Each statement keeps its own conditions, so a refused change inserts nothing
  while the rest of the batch goes in; a statement error fails every call in its batch.  When a
  change inserted nothing, the replica row (and for an old seq the logged change) is read back to
  answer `REPLICA_CONFLICT` (bound to another account or device, or the same seq with other bytes),
  `REPLICA_EXPIRED` (retired), `SEQ_GAP`, or the silent ack with the original `server_seq`.  A seq
  already accepted but compacted out of the hot log answers `SEQ_GAP` from the head.
* *ReplicaQueue* takes a push's place in its replica's line synchronously in the gRPC handler and
  runs the ingest when every earlier push of that replica on this node has finished.  The caller's
  authorisation (principal, role of editor or above, author) is resolved concurrently as the call
  arrives, and memoised per node for 2 s (`wt.sync.grant-ttl`) under the exact bearer token, device
  and document (`PushGrants`): a revoked device, an expired token or a downgraded role is seen by
  pushes within that time.  A sharing change made on a node forgets that node's decisions for the
  document at once (SRV-010), so a downgrade is refused on the person's next push there; another
  node still honours its memo for up to the 2 s.  A `commenter` may push (COLLAB-030): every change is
  read once for what it does to comments (`CommentOps`), checked against the per-comment ownership
  rules (`CommentRules`, one lookup of the threads and comments it names, none for a change that
  names none), and, once written, recorded in the server's record of comments (`CommentIndex`)
  before it is fanned out (xref:comments.adoc[Comments], As built).
* *Fan-out.*  `SyncBus` holds one dedicated Valkey connection per node for every channel
  subscription (the Quarkus data source would open one connection per subscription); a channel
  `doc:<id>` is subscribed with a document's first local listener and unsubscribed with its last.
  Every frame -- change, presence update, document event -- is published as the node's 16-byte id
  and a 16-byte audience (the account a `RoleChanged` or `AccessRemoved` is for, all zeros for
  everyone; SRV-010) followed by the encoded `ServerFrame`; a subscription takes the frames for
  everyone and those for its own account.  The publishing node delivers to its own listeners at once
  and drops its own echo.  The ingest does not wait for the Valkey publish.  Each subscription puts
  changes back into `server_seq` order (`LiveFeed`): it registers before reading the head, drops
  what the replay covered, holds changes behind a gap, and fills a gap still open after 200 ms
  (`wt.sync.gap-wait`) from the log; when the Valkey connection drops, the bus reconnects,
  resubscribes and has every subscription reread the log up to the head.
* *The author* of a `SequencedChange` is the account the replica is bound to (user id and display
  name); `Participant.role` is filled only in presence.  A change a branch merge replayed keeps its
  replica, which is bound on the branch: its author is read there (COLLAB-004).
* *The history index* (COLLAB-020): the same statement inserts the change's `change_node` and
  `node_name` rows (arrays computed from the change before it is queued) at the new `server_seq`, so
  indexing costs no round trip.
* *Load test* (`IngestLoadTest`): 8 clients on their own connections, each one replica pipelining
  a window of 32 unary pushes, 20,000 changes into one document: about 3,400 accepted changes per
  second on the development Mac (Postgres and Valkey in Docker, JaCoCo on), with `server_seq` dense
  from 1 and every replica's changes in seq order.  The 2,000 floor is a performance budget: it is
  checked by the `perf` profile and CI job, skipped with the measured load on a loaded machine, while
  every build checks the same pipelined scenario at 2,000 changes for density and order
  (xref:testing.adoc#perf-runs[Testing, Where budgets run]).
* *Tests run one node.*  SRV-005's "three clients on two server nodes" is covered by three clients
  on one node plus a frame published to Valkey under another node's id, which reaches the
  subscription through the (resubscribed) channel; a two-node compose run is left to the
  multi-client simulation (TEST-001).

Jobs use `quarkus-scheduler` with a Postgres advisory lock per job so only one node runs each.

As built (SEC-002, SEC-004): `JobLocks` takes `pg_try_advisory_xact_lock` on the job's name in a
transaction of its own held for the run; a node that cannot take it skips the run.  *Domains*
(`DomainJob`, hourly, first run a minute after start) looks every workspace domain up through
`DomainVerifier`: a claimed domain whose record appears is verified unless another team holds it; a
verified domain whose record is missing (or whose lookup fails) three runs in a row loses its
verification, so one DNS outage does not end auto-admit or require-SSO.  *Apple secret*
(`AppleSecretJob`, every 30 days and 30 s after start) is specified on
xref:security.adoc[Accounts, teams and security] (Accounts); without its four settings it does
nothing.  *Invitations* (`InvitationsJob`, COLLAB-011, daily, three minutes after start) deletes
pending document invitations older than `wt.share.invite-ttl` (30 days) and expired team
invitations, and announces each revoke-on-expiry link that expired since the last run to the
people who opened it (a link's expiry itself is applied when roles are read).  *Comment digest*
(`CommentDigestJob`, COLLAB-031, every 5 minutes, two minutes after start) is specified as built on
xref:comments.adoc[Comments].

`SyncService.Ack` also computes the stable point for its one document at once: it records the
replica's `last_ack_seq` (never backwards, clamped to the head; an unbound replica is bound to the
caller as by a push) and raises `document.stable_seq` to the minimum `last_ack_seq` over the
document's live replicas, never lowering it; the response carries the result and the document's
published collection point (`collect_seq`, `collect_time_ms`, D-067).

As built (SRV-007, SRV-013, D-067; `api/.../history`):

* *Snapshotter* (`Snapshotter`, every 2 minutes, a minute after start).  The last-subscription
  trigger is `document.snapshot_due_at`, set when a node's last Subscribe stream on the document
  ends while the head is past the newest snapshot, and cleared by the snapshot.  A snapshot is the
  state at the head (`DocumentStates`: the newest snapshot at or before it, decoded, plus the tail
  from the hot log and cold segments), collected at the document's published collection point when
  _C_ > 0, encoded by `wt-crdt` and stored zstd-compressed as one object
  `snapshots/<document>/<server_seq>` (`Snapshots`); its row carries the state hash, the compressed
  and decompressed sizes, the node count and the point.  A seq already snapshotted is left as it
  is.  The search record is then extracted from the same state (`SearchExtractor`, Search below)
  and the `document_search` row rewritten.  A document that fails is logged and retried at the
  next run; `wt_snapshot_seconds` and `wt_search_extract_seconds` time the two steps.  Snapshots are
  compared with a client's state hash at the same seq and collection point (`SnapshotterTest`,
  `BranchServiceTest`).
* *Compactor* (`Compactor`, hourly).  Deviation: the boundary is `min(newest_snapshot_seq,
  head_seq - 10,000)` rather than `newest_snapshot_seq - 10,000`, so the hot log stays at 10,000
  rows (SRV-007's done-when) while never moving a row no snapshot covers.  Rows go out oldest first
  in segments of about 8 MiB of change bytes (the segment ends with the row that crosses 8 MiB):
  length-delimited `SequencedChange`s (seq and bytes as logged) in one zstd frame under
  `cold/<document>/<from>-<to>` (`SegmentCodec`), with the segment's smallest change horizon; the
  `cold_segment` row is written and the rows deleted in one transaction.  `ChangeReader` serves a
  range the hot log no longer holds from the segment containing its next seq (authors resolved from
  the replica), so `FetchChanges`, Subscribe's replay, forks and history reads see one log.
* *Horizons and the collection point* (D-067, crdt-model.adoc "Stable points, horizons and
  collection points").  A publication is an Ack's answer: the stable point with the server's clock.
  The server cannot see when a client made a change, so a replica's *horizon* is the publication it
  has confirmed receiving -- the answer to its previous Ack, confirmed by acking again (`replica.
  horizon_*` takes the old `published_*`) -- and each accepted change is recorded with that horizon,
  capped by its own `base_server_seq` (the ingest statement reads it from the replica row it
  updates).  The Stability job starts _C_ and _T_ at the smallest horizon over the live replicas,
  lowers _C_ to the horizon of every change sequenced after it with a lower one (hot rows, and cold
  segments by their smallest horizon) until none is, and lowers _T_ to the smallest horizon clock
  after _C_; `document.collect_seq` / `collect_time_ms` hold it and every Ack answers it.  A
  document whose replicas are all retired keeps its point.  Limits, recorded here: a change made
  before its author received a publication but pushed after the author confirmed it (an outbox
  sent after a reconnect's first acks) is credited with the newer horizon, and a replica new to the
  document starts at horizon 0 (holding _C_ at 0 until it has acked twice); an exact horizon needs
  the client to send it with the change (a proposed field on the push requests, SYNC track).
  Subscribers are not sent the point on the stream (no `ServerFrame` case carries it); they
  receive it in their Ack answers every 2 seconds.
* *Stability* (`Stability`, every 5 minutes).  Retires every replica whose `last_seen_at` (a push or
  an ack) is 90 days old (`wt.replica.retire-after`, `wt_replica_retired_total`); its pushes, acks
  and subscriptions then answer `REPLICA_EXPIRED`, and it no longer counts towards the stable point
  or the collection point.
* *Trash* (`TrashJob`, daily).  Deletes documents trashed 30 days ago with their branches, after
  deleting their snapshot and cold-segment objects, then every blob no document, thumbnail or
  published file references that is at least a day old (so an upload whose reference is being
  written is not taken), object first, and logs how many documents and blobs went.  Share-link
  expiry stays in the Invitations job.

== Search

The one place the server reads artwork, and only through the generic node tree.  The search
extractor walks the snapshot the snapshotter just built and collects, without interpreting
geometry or layout: `CommonProps.name` and `note` of every live node, the plain text of every
text block (the character sequence read out, marks ignored), swatch, style, symbol and brush
names, the document's keywords and description (xref:file-info.adoc[Adding file information]) and page names.
Names go into `names` as lines and into `names_body` as a `simple` tsvector; text and notes go
into `body`.  The `simple` configuration is deliberate: documents mix languages and product
names, and stemming in the wrong language hides matches.  Trigrams make a name match on any
substring ("logo" finds "Logotype v3"); the tsvector makes text match by word.

[source,protobuf]
----
// proto/wiretuner/docs/v1/document.proto (sketch, PROTO-007)
rpc Search(SearchRequest) returns (SearchResponse);

message SearchRequest {
  string query = 1 [(buf.validate.field).string = { min_len: 1, max_len: 256 }];
  // Personal space or one team; documents the caller cannot open are never returned.
  string space_id = 2;
  string cursor = 3;
  uint32 page_size = 4 [(buf.validate.field).uint32.lte = 50];
}
message SearchHit {
  string document_id = 1;
  // Where it matched and the matching text with <b> markers from ts_headline / the
  // trigram-matched line: the library shows it under the document's name.
  repeated SearchMatch matches = 2;
  float rank = 3;
}
message SearchMatch { SearchField field = 1; string highlighted = 2; }
enum SearchField { SEARCH_FIELD_UNSPECIFIED = 0; DOCUMENT_NAME = 1; OBJECT_NAME = 2; TEXT = 3;
                   NOTE = 4; SWATCH = 5; STYLE = 6; SYMBOL = 7; KEYWORD = 8; PAGE = 9; }
message SearchResponse { repeated SearchHit hits = 1; string next_cursor = 2; }
----

`Search` runs one query: `document.name ILIKE` or `names % query` (trigram similarity) or
`body @@ websearch_to_tsquery('simple', query)` or `names_body @@ ...`, joined to the caller's
visible documents in the space, ordered by `ts_rank` then name similarity, cursor-paged by
`(rank, document_id)`.  Highlights come from `ts_headline` on `body` and from the matching line
of `names`; the field is recovered from a prefix each line carries (`o:`, `s:`, `p:` ...).

As built (SRV-009): the whole-record `names % query` is diluted by every other line of a long
record, so a name matches by `ILIKE '%query%'` (wildcards in the query escaped) or by word
similarity `query <% names` (and the same two against the live `document.name`); text and names
also match by word through the two vectors.  The rank is one number, `ts_rank(body) +
ts_rank(names_body) + greatest(word_similarity(query, name), word_similarity(query, names))`,
so the keyset is `(rank desc, document_id)`.  Highlights are computed per line: every line of
`names` and `body_text` that contains the query or matches it by word; a names line matched as a
substring has the substring bolded by the server, a line matched by word gets `ts_headline`'s
`<b>` markers; text and note lines count only as word matches.  At most five lines are reported
per hit, plus the document name when it matched.  The prefixes are `o:` object name, `s:` swatch,
`st:` style, `sy:` symbol, `k:` keyword, title or description, `p:` page (in `names`), and `t:`
text block, `n:` note (in `body_text`); SRV-007 writes them (`SearchExtractor`): every live node's
name (neither it nor an ancestor deleted, and not under the comments collection), brushes as `o:`
since the search has no brush field, the settings' `info` title, description and keywords, and
one line per non-blank line of a multi-line value.  The
index lags the log by the snapshotter's cadence (at most 2 minutes for a document being edited
heavily, and one run after the last subscription closes), which the guide describes as "a few
minutes".  Document *names* are also matched live from `document.name`, so a rename is
searchable at once.  Nothing here is on the ingest path.

== Scaling

* Stateless API nodes behind an L4 load balancer with HTTP/2; subscriptions are long-lived
  server streams, so drain on deploy is 60 s with a `DocumentEvent.RECONNECT` hint.  Unary
  pushes need no affinity: a replica whose calls land on two nodes only risks a `SEQ_GAP`
  round trip.  A Connect / gRPC-Web gateway, when one is deployed, sits between the balancer
  and the nodes and speaks plain gRPC to them (xref:api-conventions.adoc[API conventions]).
* Valkey is a single fan-out bus; at the design scale (10,000 open documents, 3 sessions each)
  it is far from a bottleneck.  Sharding by document id is the escape hatch.
* Postgres: `change_log` is the only hot table; partitioned and append-only, with the compactor
  keeping it small.  Read replicas serve `FetchChanges`.
* Object storage: R2 (no egress fees) in production, MinIO locally; presigned URLs are *not*
  used for documents (all reads go through the API for authorisation); they are used for blob
  uploads over 8 MiB.  As built (SRV-008) every upload still streams through the API into S3
  multipart parts, because `BlobService.Upload` has no presigned variant in `blob.proto`; a 200
  MiB upload takes a few seconds against local MinIO.  Presigned uploads need a proto addition.

== Observability

* Traces: every RPC, with `wt-request-id` as a span attribute; the ingest transaction and the
  Valkey publish are child spans.
* Metrics: `wt_changes_accepted_total{document}`, `wt_subscriptions_open`,
  `wt_push_inflight{replica}`, `wt_seq_gap_total`, `wt_ingest_seconds`, `wt_backlog_bytes`
  (from `PushChanges`), `wt_snapshot_seconds`, `wt_search_extract_seconds`, `wt_search_seconds`,
  `wt_stable_lag_seq` (head − stable, the GC health signal), `wt_replica_retired_total`.
* Logs: JSON, one line per accepted change at DEBUG, one per subscription at INFO.
* Dashboard: `server/grafana/wiretuner.json` committed and loaded in compose.

As built (SRV-014, `api/.../observability`):

* *Per RPC*: Quarkus's gRPC binder (`quarkus.micrometer.binder.grpc-server.enabled`):
  `grpc_server_processing_duration_seconds`, `grpc_server_requests_received_messages_total` and
  `grpc_server_responses_sent_messages_total` per `service`, `method` and `statusCode`.
* *Per document* (`document` tag): `wt_changes_accepted_total`, `wt_subscriptions_open` (live
  Subscribe streams on the node), `wt_backlog_bytes` (a summary of `PushChanges` upload sizes) and
  `wt_stable_lag_seq` (head − stable after each `Ack`).  A document's gauges are registered with its
  first subscription on the node and removed with its last, so idle documents cost no series.
* *Node-wide*: `wt_ingest_seconds` and `wt_search_seconds` (with histogram buckets for quantiles),
  `wt_seq_gap_total`, `wt_rate_limited_total`, and `wt_push_inflight` -- the replica queue's size,
  without the `replica` tag the list above names (a tag per replica would be unbounded).
  `wt_snapshot_seconds`, `wt_search_extract_seconds` (SRV-007) and `wt_replica_retired_total`
  (SRV-013) are node-wide too.
* *Rate limits* (`RateLimiter`): a token bucket per account and one per document in Valkey
  (`rl:a:<account>`, `rl:d:<document>`), refilled continuously at `wt.limits.*.rate` per second up
  to `wt.limits.*.burst` (5,000 and 20,000 for both), taken from by one Lua script that uses Valkey's
  clock and takes from both buckets or neither.  Every RPC costs 1, a push one per change.  A node
  leases 32 tokens at a time per (account, document) and spends them locally for up to a second, so a
  pipelined window costs one Valkey round trip rather than 32 (the load test's rate would otherwise
  drop by a third); near the limit it falls back to the exact cost.  Refusal is
  `RESOURCE_EXHAUSTED / RATE_LIMITED` with `RetryInfo`: the time until the emptier bucket holds the
  cost again.  The Valkey client pool is raised to 24 connections and 8,192 waiters for it.
* *Compose*: `prometheus` (`server/grafana/prometheus.yml`, scraping `/q/metrics` of the `api`
  service and of an API on the host every 5 s, port 9090) and `grafana` (port 3300, anonymous
  viewer, the data source and the dashboard provisioned from `server/grafana/provisioning`).  The
  dashboard's rows: overview, per document (changes/s, sessions, backlog bytes/s, stable lag),
  ingest (latency quantiles, gaps), and RPCs (calls, errors and latency per method).
