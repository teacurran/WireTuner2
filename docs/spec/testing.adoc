= Testing
include::_attributes.adoc[]
:page-slug: testing

Two engines in two languages must agree byte for byte, and a document must survive any
interleaving of edits from any number of people who may each be offline for days.  Tests here
are the specification's teeth.

== Conformance vectors

`crdt-conformance/vectors/<area>/<name>.textproto`, one `wiretuner.conformance.v1.Vector` in
protobuf text format.  The schema is `crdt-conformance/schema/vector.proto` -- test tooling,
outside `proto/`, so buf and the merge-table generator never see it (CRDT-011):

[source,textproto]
----
name: "registers/concurrent-writes-one-register"   # must equal the path below vectors/
description: "..."
schema_override { ... }                    # optional: reinterpret the merge table for this vector
setup { change { ... } }                   # Changes applied to every replica first (server_seq = index + 1)
replica { id: 1 change { ... } }           # concurrent work per replica, in seq order
replica { id: 2 change { server_seq: 4 ... } }   # server_seq: the server's number, when sequenced
deliveries { order: [1, 2] }               # each occurrence delivers that replica's next change;
deliveries { order: [2, 1] }               #   every order must converge to the same hash
deliveries { picks { replica: 2 seq: 1 } picks { replica: 1 seq: 1 } picks { replica: 2 seq: 1 } }
                                           # or: changes by replica and seq, any order, repeats allowed
deliveries { order: [2, 1] collect { after: 1 stable_seq: 2 now_ms: 0 } }
                                           # garbage collection after that many changes (CRDT-010)
position { lo: "\x80" seed: 2 expect: "\x81\xce\x0f" }   # fractional positions, byte for byte
append_run { seed: 1 count: 1000 max_length: 40 last: "..." }
strip { change { ... } expect { ... } }    # LocalOnly.strip of a change, alike in both engines
expect {
  state_hash: "…"                          # hex SHA-256, crdt-model.adoc "Canonical encoding"
  snapshot_hash: "…"                       # hex SHA-256 of the encoded DocumentSnapshot (CRDT-009)
  node {
    id { counter: 1 replica: 7 }
    node_hash: "…"                         # optional: lets a mismatch name the node
    register { path { ... } value { ... } op { ... } losing { ... } }   # read-outs; no value = unset
    register { path { ... } absent: true }                              # never written (a local-only path)
    tree { parent { ... } position: "..." deleted: false children { ... } }
    sequence { path { ... } elements { ... } deleted { ... } }         # live elements and tombstones, in order
    set { path { ... } members { ... } }                               # exactly these members
    text { path { ... } text: "..." chars { ... } deleted { ... }        # live string, live ids, tombstones
           runs { start: 0 length: 2 attributes { value { ... } mark { ... } } } }   # exactly these runs
  }
}
----

Changes in a vector are the schema's `wiretuner.conformance.v1.Change`, field for field
`doc.v1.Change` plus `server_seq`, whose NodeProps adds a test kind (`TestProps`, NodeProps field
1000: sets of strings, packed scalars, `ElementId`s and `OpId`s, a flat sequence, a nested
contour -> anchors sequence, and a TEXT field `text = 9` shaped like doc.v1 `RichText` -- `TestChar`
with a `TestParagraph` at 6 -- plus a STRUCT `tail = 10`).  `TextMark` carries a `TestMarkValue`
whose cases sit at their doc.v1 `TextMarkValue` numbers (`font_family` 1, `size` 3, `url` 13,
`feature` 21) plus a test `bold` at 30; test-kinds.textproto declares the rows the engines read
through (`RichText.chars`, `TextChar.paragraph`, `TextMark.value`, the `feature` case).  The runners encode each change and decode it as a `doc.v1.Change`,
so the test kind reaches the engines as an unknown field, exactly like a field newer than the
replica; `crdt-conformance/schema/test-kinds.textproto` declares its merge table and both runners
apply it before a vector's own overrides.  The doc.v1 kinds are mirrored in the vector NodeProps
with their numbers and names (checked by server/conformance), so vectors write them as doc.v1
does.  Both engines replay every vector: `ConformanceTests` in `WTCRDTTests` (Swift, generated
vector types committed under `Tests/WTCRDTTests/Conformance/Generated` by `make -C crdt-conformance
generate`) and `ConformanceTest` in `server/conformance` (JUnit, vector types generated by the
Maven build; wt-crdt's own tests compile vector.proto too, so they write changes on the test kind
in text format as `WTCRDTTests`' `Scenario` does).  The vector NodeProps mirrors every doc.v1 kind
(`ConformanceRunnerTest` fails when doc.v1 adds one; add it with its import, and its file to
`schema/swift-module-mappings.asciipb`).  A vector fails when a delivery order diverges from the first ("delivery [2, 1]
diverges from [1, 2] at node 1:7"), when the hash differs from `expect` (naming the first node
whose `node_hash` differs, or listing every actual node hash, which is also how a new vector's
hashes are recorded: leave them empty, run one engine, copy, then confirm the other engine
agrees), or when a read-out, the retained losing writes or a generated position differs.  Each
delivery order's snapshot must also be the same bytes, hash to `snapshot_hash`, and decode to a
state that encodes to the same bytes again (CRDT-009); `snapshot_hash` is recorded like
`state_hash`.  A `picks` delivery may repeat changes and take a replica's changes out of seq
order (CRDT-008); such a vector keeps them independent, since the hub delivers each replica's
changes in order and a sequence element or character op whose target has not arrived is a no-op.  Both
engines check the same committed hashes, which is what proves them equal.  `make -C
crdt-conformance run` runs both; the vectors take well under a second each.

`schema_override` exists for merge rules no schema field uses yet: it replaces one field's
policy, declares a message MERGE_VARIANT, or adds a row, for that vector only (the variant vector
of CRDT-001 declares `NavigationProps` a variant because doc.v1 has none yet).  Vectors avoid
`-0.0` and NaN payloads: swift-protobuf omits `-0.0` where protobuf-java writes it, so the two
languages encode the same text differently.

A vector's `strip` cases run `LocalOnly.strip` (xref:crdt-model.adoc#local-only[Local-only
fields]) on each `change` and compare the result with `expect` as a message; `registers/local-only-*`
use them, and `absent: true` on an expected register, for what never reaches the state.

A delivery's `collect` entries (CRDT-010) run `collect(stableSeq:now:)` after `after` of its
changes (0: right after the setup); since every delivery must reach one state, a vector that
collects collects the same points in every delivery, at different moments.

Every task that adds a field or a merge rule adds vectors.  Both engines run every vector in
CI (CRDT-011); a divergence names the vector and the first differing node.  The fuzzer
(<<fuzzing>>) writes vectors in the same format and minimises any failure into a new one.

== Fuzzing

As built by CRDT-012.  One generator, in Swift, writes a corpus of conformance vectors; WTCRDT
replays every delivery of each and records the hashes it reached; wt-crdt replays the corpus and
must reach the same hashes.  A shared seed with a generator in each language was the other
choice; a corpus was chosen because there is then one generator to keep right (two would drift,
and a drift reads as a divergence), the Java side is the conformance runner unchanged, and every
case -- and every failure -- is already a vector anyone can read, replay in either engine and
commit.

* `FuzzGenerator` (`WTCRDTTests/Fuzz`): from one `SplitMix64` seed, each vector simulates two to
  four replicas (random 64-bit ids) editing a document of test-kind nodes through a hub.  A
  replica edits against its own state (creates, moves, deletes and restores nodes; sets, clears
  and struct-writes registers; inserts, moves, deletes, restores and edits flat and nested sequence
  elements; types, deletes and marks text, sets paragraph registers; adds and removes string and
  scalar set members), pushes and pulls in random interleavings, drops off the network for a while
  and keeps editing, and collects at the points the hub publishes under the garbage-collection
  protocol (crdt-model.adoc, "Stable points, horizons and collection points"), with a clock that
  moves on by up to three days a step so deleted nodes compact.  Each replica's own application
  order (its changes as it made them, the others' as it pulled them, its collections) and the
  server log's become the deliveries, which must all reach one state and one snapshot; the
  simulated replicas' own states must hash the same.
* `FuzzTests.generatedVectorsConvergeInWTCRDT` runs `WT_FUZZ_OPS` ops (default 20,000) from
  `WT_FUZZ_SEED` (default 1) in vectors of `WT_FUZZ_ROUND_OPS` (250), writing
  `fuzz/<seed>-<index>.textproto` into `WT_FUZZ_CORPUS` when set; `FuzzCorpusTest`
  (server/conformance) replays such a corpus and lists what failed in `<corpus>-java-failures.txt`.
  `make -C crdt-conformance fuzz` runs both (part of `make conformance`); the nightly job runs
  `make -C crdt-conformance fuzz FUZZ_OPS=1000000 FUZZ_SWIFT='-c release -Xswiftc -enable-testing'`.
* Minimising: `FuzzMinimizer` shrinks a failing vector by delta debugging over its deliveries,
  changes, collections and ops (an op becomes as many `Noop`s as it took counters, so later ids
  hold).  A vector WTCRDT's own deliveries disagree on is minimised at once into
  `<corpus>-minimized`; one wt-crdt disagrees on is minimised by `make -C crdt-conformance
  fuzz-minimize` (run by `fuzz` on failure), which asks the Java oracle (`FuzzOracle`, run with the
  test classpath server/conformance writes to `target/test-classpath.txt`) about every candidate.
  A minimised vector is committed under `crdt-conformance/vectors/fuzz/` with a description once
  the bug is fixed.
* Run times on the development Mac (M-series, debug Swift build, JDK 25): 20,000 ops -- 80
  vectors, about 2,200 collections -- take 8.3 s in WTCRDT (generation and replay) and 1.9 s in
  wt-crdt; `make -C crdt-conformance fuzz` takes 43 s end to end with the Maven build.  The nightly million
  (3,990 vectors, 111,257 collections, no divergence) takes 210 s in WTCRDT (release build,
  writing the corpus included) and 73 s in wt-crdt, 6.5 minutes end to end with both builds.  A
  cross-engine minimisation costs about 20 s per vector (one JVM start per candidate).

Both engines were checked against the fuzzer by breaking them on purpose (collecting interior
tombstones): WTCRDT failed its own run, and wt-crdt, broken alone, failed the corpus and was
minimised against the oracle to vectors of a few changes.

== Multi-client simulation

`WTTestSupport.Simulation` (TEST-001) runs N in-process clients (real `WTSync` and `WTCRDT`)
against the compose server through a proxy that scripts latency, loss, partitions and long
offline periods.  Scenarios, each asserting hash convergence and the expected sync-state
transitions:

. Three users editing one path for ten minutes with 200 ms latency, with pipelined pushes
  deliberately reordered, and once more in gateway (batch) mode.
. One user offline for 48 simulated hours producing 30,000 ops while two others produce
  5,000; reconnect; verify the review sheet's classification and, after "Keep the merged
  result", convergence.
. Same, with "Save my version as a copy": original converges to the remote state, copy holds
  the local state.
. Replica store copied to a second client: `REPLICA_CONFLICT`, rotation, no id collision.
. Replica retired by the stability job, reconnect, salvage.
. Server node restart mid-session; Valkey restart; Postgres failover to the replica.
. A viewer's role downgraded mid-session.
. Token expiry every minute for an hour.

NOTE: Until TEST-001, the sync client is tested in `WTSyncTests` against `FakeSyncServer`, an
in-process stand-in for `SyncGrpcService` (acceptance rule, Welcome with the snapshot hint, replay,
FetchChanges, FetchSnapshot) with injectable faults: delayed (reordered) and lost pushes, one-shot
rejections, dropped and duplicated live frames, disconnects, silent streams, bulk uploads cut off
mid-way.  The same fake is served over grpc-swift's in-process transport to test
`GRPCSyncTransport` end to end.  `SyncSimulationTests` runs seeded rounds of loss and reordering in
both push modes.  `ReconcileTests` plays scenarios 2 to 5 in miniature against the same fake
(an overlap holding the outbox, *Keep the merged result*, *Save my version as a copy*'s revert, a
store copied to a second Mac, an expired replica salvaged onto a collected snapshot), and
`BlobTests` and `PresenceTests` drive the blob queue and the presence model through fakes of
`BlobService` and the subscription.  `SyncIntegrationTests` runs two clients against the compose server and is
skipped unless `WT_SYNC_IT=1` (`WT_SYNC_API`, `WT_SYNC_KEYCLOAK` override the local URLs).

[[simulator]]
NOTE: As built by TEST-001 (`WTTestSupport/Sources/WTTestSupport/Simulation`, scenarios in
`WTTestSupportTests/Simulation`).  A `SimClient` is wired as WTApp's `DocumentSession` wires a
window: a `LocalStore`, the WTModel `Document` over it as the sink, a real `SyncClient` with a
`LocalPresence`, `stateReplaced` reloading the façade and a collection point advancing the horizon.
Every edit is a WTModel command (paths, shapes, names, deletes, text typing, marks and paragraph
breaks) performed under a unique label.  Deviations from the paragraph above: *(1) the server.*  The
scenarios run in every `swift test` against `SimServer`, an in-process `SyncService` for any number
of documents, people and devices that follows the server as built: acceptance in the server's order
with replica binding to (account, device), `Welcome` with the snapshot hint, replay, presence, `Pong`,
`RoleChanged`/`AccessRemoved` to the person's own subscriptions, `FetchChanges` and `FetchSnapshot`,
tokens expiring on the simulated clock, `Ack` with the monotone stable point and the recorded
horizons, the Stability job (retirement after 90 simulated days, (C, T) computed as `Stability.java`
does), the snapshotter collecting at (C, T), `Fork`, and scripted node restarts (abrupt, or a drain
with `RECONNECT`), Valkey restarts (live frames lost, then every subscription failed) and Postgres
failovers (calls fail, the push in flight commits and loses its reply).  The compose server is the
other backend (`SimulationBackend`, `ComposeSimulationTests`, `WT_SIM_COMPOSE=1`): scenario 1 in
both modes and the cloned store of scenario 4 run against it, with `WT_SIM_COMPOSE_RESTART=1`
adding `docker compose restart` of api and valkey mid-run; the scenarios that need the server
scripted (retirement, roles, token lifetimes) run in-process only, and the compose stack has no
Postgres replica to fail over to.  *(2) the proxy* is a `SyncTransport` per client
(`ProxyTransport` over a `NetworkLink`) rather than a TCP proxy: gRPC multiplexes the calls on one
HTTP/2 connection, so only a call-level proxy can reorder two pushes or lose one answer.  It
applies latency and jitter to every call, answer and frame, holds pipelined pushes back so later
ones overtake them, loses requests or answers, drops the connection after a subscription frame
(failing the stream and every call in flight) and partitions the client (token refreshes fail
too).  *(3) time* is simulated (`SimClock`): a scenario runs compressed (ten minutes in six real
seconds), and offline days, token lifetimes and retention windows are jumps of the clock that
the server, the clients' change timestamps and their reconnect gap all read, with a skew per
client.  Each fault a call meets is drawn from the seed and the call's own key (link, kind,
replica, seq, attempt), so the operating system's scheduling does not change which push is lost.
*Checks* (`Simulation.expectConverged`, after `settle()`): every outbox empty and every client at
the log's head; each `Document` showing its store's state; every state -- collected at the
server's collection point, as replicas compare -- hashing like the server's own log; each replica's
seqs dense in the log and no op id twice; every change a client made in the log by its label
(unless discarded, or dropped whole by salvage); no client ever in `error`.  A failure names the
scenario, the seed (`WT_SIM_SEED` replays it), each client's state and link, the differing nodes,
and the end of the trace, and writes the whole trace to `$WT_SIM_REPORTS` (default
`$TMPDIR/WTSimulation`)`/<scenario>-seed<seed>.log`.  The eight scenarios run in native and gateway
mode (`ScenarioTests`); `RandomizedSimulationTests` runs seeded runs of two to four clients with
random modes, networks and skews under random partitions of up to 36 hours, restarts and a
first-time opener bootstrapping from a snapshot (`WT_SIM_SEEDS`, `WT_SIM_RUNS=n`).  The whole suite
takes about 80 s (debug build, M-series), within TEST-001's 10 minutes in the package-tests step of
CI.  Scenario 2 holds the time from *Keep the merged result* to convergence (1,000 changes, 30,000
ops, up through `PushChanges` or batches) to a `PerfBudget` of 5 s (1.4 s measured, release).  Findings, each fixed at the
root and now held by an ordinary test: *(a)* D-067 as first built never published a collection
point above 0 -- the server credits a change with the publication its author confirmed by acking
again, and `SyncClient` acked only when its applied seq moved, so every change's horizon was at
most its seq - 2 and the job's lowering step walked C down to 0.  The client now confirms every
answer that raised the stable point, polls while the point is below its applied seq, waits for
its older changes before confirming, and keeps its horizon across relaunches
(xref:sync-protocol.adoc[Sync protocol], "The client as built"); scenario 5 expects the job's own
point at or past the deletion, with a recent clock, and compacts and salvages on it
(`SimServer.publishCollectionPoint` stays for tests that want a given point).  *(b)* A change
refused with `VALIDATION_FAILED` for its op count was resent as one `Noop` per counter, over the
limit again, for as long as the session lasted (403 refusals in 0.3 s; any change of more than
10,000 counters, such as a long paste, met it).  The replacement is now one `Noop`, a refused
replacement is the `error` state, and a change over the limits is split through salvage before it
is sent (`SimulationChecksTests`: each over-limit change is refused once; clients that know the
limit converge with none refused).  *(c)* Reconciling applied the review rules on every
reconnect, so a connection dropped for a few seconds while people edited one object opened the
whole-document review holding the outbox (one object in common is 100% of a small session);
xref:decisions.adoc#D-070[D-070] merges a brief reconnect without holding and gives the share rule
a five-object minimum, and scenario 1 expects no review at all.  *(d)* The server read `wt-device`
leniently and bound any other value to the all-zero device, so clients sending a non-UUID device
shared one binding; it now refuses one with `INVALID_ARGUMENT` (`PrincipalInterceptor`), and so
does `SimServer`, whose clients' devices are UUIDs derived from their names
(`Simulation.deviceID(for:)`); `SyncIntegrationTests` and the compose backend send UUIDs too.
Scenario 7 counts its steps (`Simulation.steps`) rather than running for a simulated duration, so
the downgrade at step 30 happens on a loaded machine too.  Feature scenarios run in the same suite
(their suites' names end in `ScenarioTests`, so `make client-sim` picks them up): comments in the
review and in restore (COLLAB-032, `CommentScenarioTests`), the colour list (COLOR-022,
`SwatchScenarioTests`) and data merge (DATA-023, `DataMergeScenarioTests`, with `SimDataService`
standing in for the data service); together they add about 10 s to the suite.

== Geometry and rendering

* `WTGeometry`: property tests against numeric references; a corpus of 200 boolean cases
  including tangencies; fuzzed random paths never crash or hang.
* `WTRender`: golden-image tests for a corpus of documents (built for the purpose), rendered by the Core Graphics reference renderer
  and compared at 1× and 4× with a per-pixel tolerance; bitmap render vs. PDF render compared
  pairwise.  The goldens are Core Graphics output: Core Graphics is the truth.
* Metal/CG parity (REND-007): every corpus document is rendered by the Metal tile renderer
  and by the Core Graphics renderer over the same tile keys, at 1×, 2× and 4× and at canvas
  rotations of 0°, 15° and 90°, in Preview and Keyline, and compared tile by tile.  A tile
  passes when every pixel more than one pixel away from an edge in the coverage mask matches
  within 2/255 per channel, edge pixels match within 40/255 (MSAA against analytic coverage),
  and no more than 0.1% of the tile's pixels fail either bound.  A failing tile is written out
  as a triptych (CG, Metal, difference) named by document and tile key.  The test runs on the
  CI Mac's GPU; a Mac without one skips it and CI marks the run incomplete rather than green.
+
NOTE: As built by REND-007 (`WTRenderTests/MetalParityTests.swift`).  "More than one pixel
away from an edge" is judged on the Core Graphics tile: a pixel whose 3 × 3 neighbourhood is
one colour.  Tiles have a white background; every corpus case runs in Preview, Keyline and its
own mode.  Triptychs go to `$TMPDIR/WTRenderParity/<case>@<scale>x_<angle>deg_<mode>_<tile
key>.png`.  Without a usable Metal device the parity, canvas and frame-time suites are disabled
through Swift Testing's `.enabled(if:)` and report as skipped, never passed; the client
workflow should fail its parity step when `swift test` reports those suites skipped on the
GPU runner.  The self-test swaps every declared fill rule in the Metal path and asserts that
the failing tiles are exactly those where Core Graphics, given the swapped rules, fails against
itself.  The frame-time gate (`MetalFrameTimeTests`) plays a 10 s pan, pinch and rotate of the
50,000-rectangle design point at 120 Hz wall-clock pacing through `MetalTileCanvas` into a
2880 × 1800 offscreen texture and sums each frame's main-actor update and encode time with its
GPU time; it holds 8.3 ms only in the perf run (<<perf-runs>>) and otherwise reports the
figures.
+
NOTE: As built by the ATTR render tasks (`WTRenderTests/Support/AttributeCorpus.swift`).  The golden
corpus holds 45 cases, each with its own view size; the ATTR cases run through goldens and
REND-007 parity like the rest.  The bitmap/PDF gate is skipped (`comparesPDF`) for cases with
sampled paints -- noise, textures, lenses, the gradient grid -- which PDF embeds at 4 pixels per
point while bitmaps sample at device resolution, and for patterns, which stay vector in PDF;
`PatternPaintTests.pdfExportAndScreenAgree` and `GradientTests.pdfOutputMatchesTheScreen` hold
those to their own bounds (the appearance pages' ATTR-014 and ATTR-027 notes).  The tiled page and
contour timings hold their budgets only in the perf run (<<perf-runs>>); the brush spray's is
reported there as a known issue (the ATTR-010 note).
* `WTText`: layout goldens for the type chapter's features (columns, tabs, rules, on-path).
+

with axes on every paragraph and justified (100 ms), a 1,000-row tab table (50 ms), 10,000

chart, connector and animation budgets are held in the perf run only (<<perf-runs>>) and reported
otherwise.

== Import and export

Round-trip corpus per format: export then import must reproduce geometry within tolerance and
preserve names, layers, colors and text.  Third-party fixtures (SVG test suite, PDF samples,
UFO reference fonts) are vendored with their licences.

NOTE: As built by IMG-008 to IMG-015.  The importers' round trips run the package's own
exporters (PDF, Illustrator, SVG, DXF, every bitmap format) over the export corpus, import the
result, and compare `ImportedScene.scenePaths` geometry, names, layer groups, colours and text,
plus a rendering of `ImportedScene.exportScene()` against the original page.  Format fixtures
that the exporters cannot produce (hand-written PDF operators, legacy Illustrator PostScript,
AutoCAD/LibreCAD/Blender-style DXF, SVG features) are written inline in the tests; no
third-party files are vendored yet, so the W3C SVG suite subset and the 50-PDF corpus named by
IMG-012 and IMG-009 are still to add.

== UI

XCUITest through the harness in TEST-002.  Each feature page's tasks name their UI tests.  The
harness runs with a real compose server for collaboration tests (two app instances on the CI
Mac, driven in one test).

The harness lives in `client/WTAppUITests/Support`:

[cols="1,3"]
|===
|Helper |What it does

|`WireTunerUI.launch()`
|Launches the app with `-WTUITesting` and `-WTSocketAudit` (tokens in memory, no keychain, no stored session that
could open a socket) and waits for the document window.  `element(_:)` finds anything by
accessibility identifier; `canvas`, `selectTool(_:)`, `drag(from:to:modifiers:)` and
`click(at:modifiers:)` (points in canvas view points, modifiers held for the whole gesture),
`chooseMenu(["Edit", "Select", "All"])` (a path of titles, submenus hovered) and
`chooseMenuItem(command:in:)` (by `menu.<command id>`), `panel(_:title:)` (a panel body,
shown through the Window menu and brought to the front of its group when needed).

|`canvasState`, `waitForCanvas(_:toBe:)`
|The canvas's accessibility value is `changes=<n> selected=<n>`: the number of document changes
and of selected objects.  Tests observe the document through it instead of pixels; a tool test
asserts "one drag, one change" by waiting for `changes` to step by one.

|`ScreenshotCapture.capture(_:named:in:)`
|Attaches a screenshot to the result and, when `WT_DOCS_IMAGES` names a directory, writes it
there as `<name>.png`.  The UI test runner receives only variables with the `TEST_RUNNER_`
prefix, so the book's screenshots are refreshed with

|`SandboxAudit.assertNoSockets(in:) { ... }`

`launch()` always passes) runs `SocketMonitor`, which `fstat`s every descriptor of the process
every 5 ms and tells sockets apart by descriptor and kernel socket id (`proc_pidfdinfo`'s

gains `net=<n> unix=<n>`, the distinct internet and Unix-domain sockets seen since launch.  The
audit compares the counts before and after the block (after a 250 ms settle) and fails on any
new internet socket, and on a new Unix-domain socket when asked (`includeUnixDomain`; system
frameworks may open those themselves).  Auditing from the runner with `lsof -p` was preferred --
no code in the app, and it would audit the release build -- but Xcode signs the XCUITest runner
with the App Sandbox (`com.apple.security.app-sandbox` in its entitlements), which cannot
inspect another process; self-reporting also samples 10 times more often than `lsof` can run.
Its limits: DEBUG builds only, and a socket that lives less than one 5 ms interval can be
missed.

*Unit-test host.*  A unit-test launch (`XCTestConfigurationFilePath` set) turns off AppKit's

== Coverage and SonarQube

Every build reports to SonarQube at `https://sonar.villagecompute.com`, and the coverage gate
requires *95% line coverage and 95% branch coverage* on new and overall code, for the server
and for the client alike.  For the client, "branch" means llvm-cov *region* coverage, because
the Swift toolchain produces no branch data (xref:decisions.adoc#D-066[D-066], below).  A pull
request whose gate fails does not merge.

[cols="1,3"]
|===
|Side |How coverage is produced and reported

|Server (Java)
|`quarkus-jacoco` instruments every Maven module (`api`, `wt-crdt`, `conformance`); each
module's `target/site/jacoco/jacoco.xml` is listed in `sonar.coverage.jacoco.xmlReportPaths`
and `sonar-maven-plugin` merges them into one figure (SRV-001: JaCoCo's `report-aggregate`
needs a module that depends on all others, which the reactor does not have).  JaCoCo reports lines and branches natively.  Sonar
configuration lives in `server/pom.xml` `sonar.*` properties, never in a
`sonar-project.properties` (the Maven plugin ignores that file), exactly as dissipate-server
does.  Generated sources (`target/generated-sources/**`, protobuf stubs) are excluded from
analysis and from the denominator.

|Client (Swift)
|Every `swift test` and `xcodebuild test` run is built with `-enable-code-coverage` and produces

|Projects

[[client-branch-gate]]
The client's branch gate is llvm-cov region coverage (xref:decisions.adoc#D-066[D-066]).  The
Swift compiler's coverage mapping (Xcode 26.4, Swift 6.3) emits line and function regions but no
branch regions: `llvm-cov export -format=lcov` on a Swift binary writes `BRF:0` and no `BRDA`
records (APP-001 found this), so Sonar never has a branch or condition measure for
`wiretuner-client`, and a `branch_coverage` condition there would be vacuously met rather than
measured.  What llvm-cov does count for Swift is *regions*: every `if`/`guard`/`switch` arm,
each operand of `?:` and `??`, every loop body and closure has its own counter, so an untaken
arm is an uncovered region exactly as it would be an uncovered branch.  The client gate is
therefore 95% lines *and* 95% regions, enforced in CI by `regions-gate.swift`, with Sonar's
`wiretuner-client` gate carrying the line conditions only.  Sonar's generic coverage format has
no field for regions, so the region figure lives in the job summary, not on the Sonar
dashboard.  `lcov-to-sonar.swift` still converts `BRDA` records whenever they are present, so if
a future toolchain emits them the client gate can gain the branch conditions without a pipeline
change.  The converter also reads a line count above `Int64.max` as 0 hits: Xcode's llvm-cov
emits wrapped-negative counters for some Swift pattern-matching loops (for example
`DA:262,18446744073709551588`), and one such line used to reject the whole tracefile.

Two limits of the server as installed (SonarQube Community Build 26.9) shape the pipeline:

* *No pull-request analysis.*  A PR scan would publish the PR's figures as main's, so both
  `sonar` jobs skip the upload on pull requests unless the repository variable
  `SONAR_PR_ANALYSIS` is `true` (set it once the server supports PR analysis, through a
  commercial edition or the community branch plugin; the jobs then pass
  `sonar.pullrequest.key`/`branch`/`base` from the event).  Until then a PR is blocked by the CI
  gates above, which apply the same 95% bars to the same files, not by Sonar's status check.
* *No Swift analyzer.*  The Community Build's language list has no Swift, so the scanner may not
  index `.swift` files and the generic coverage report may then attach to nothing; the client
  line gate is enforced by `regions-gate.swift` (`--minimum-lines 95`) regardless.  Verify on
  the first CI run that `wiretuner-client` shows a coverage measure; if it does not, the options
  are a commercial edition or the community `sonar-swift` plugin.

The token is read from `SONAR_TOKEN` or, when that is unset, `~/.sonar-token` for local runs
(`make sonar-server`, `make sonar-client`, `configure-gates.sh`) and from the `SONAR_TOKEN`
secret in CI, where it appears only as `${{ secrets.SONAR_TOKEN }}` in a step's `env:` and
reaches the scanners through that environment variable, never a command-line flag.  It is never
written into the repository, a `pom.xml`, or a log: `tools/sonar/check-no-token.sh` fails both
workflows if any file holds a `squ_`/`sqp_`/`sqa_` token, printing only file and line.

Design consequences of the 95% branch (client: region) target:

* Client UI code is written so it is testable without a screen: view models and tools are
  plain types driven by `CanvasEvent`s and observed state; AppKit views are thin.  XCUITest
  covers the thin layer.  The tool framework (APP-003) and panel framework (APP-004) exist
  partly so that this split holds everywhere.
* Server RPCs are exercised through the gRPC surface with Testcontainers, not by mocking the
  service class; every error reason in xref:api-conventions.adoc[API conventions] has a test
  that reaches it.
* Generated code, `main()` entry points and Objective-C bridging shims are excluded explicitly
  and listed in the Sonar configuration so the exclusion is visible in review.
* A task is not done while its Sonar gate is red (xref:building.adoc[Building]).

[[perf-runs]]
=== Where budgets run

A test that times something asserts two different things: that the work is right (dense
`server_seq`, the right bytes, the event arrives) and that it was fast enough.  Only the first is a
property of the code alone; the second is also a property of the machine, and a shared, loaded
machine fails it for no fault of the code.  So the two are kept apart:

* *Correctness in every build.*  A performance scenario's functional assertions run in the
  default suite, at a smaller volume where the volume is only there for timing (the ingest
  scenario pushes 2,000 changes rather than 20,000; ten viewers read the published bundle rather
  than 100; `wt-crdt` types 200 characters into a 20,000-character text, round-trips a 2,000-node
  document through snapshot frames, and checks that late moves on a 5,000-node tree land as
  in-order delivery would).  The coverage gate is taken over this suite.
* *Budgets in the perf job and on idle machines.*  Every timing assertion is a `@PerfTest`
  (JUnit tag `perf`), which the default surefire run excludes and the `perf` Maven profile
  selects: `cd server && ./mvnw -Pperf -pl wt-crdt,api -am verify -Dgroups=perf`.  Each writes its
  figure (measure, measured value, budget, met or missed) to its module's
  `target/perf-results.md`.  The `perf` job of `.github/workflows/server.yml` runs it after
  `verify`, copies both tables into the job summary, and fails only on a missed budget.  Each
  module carries its own `PerfTest`, `LoadGuard` and `PerfReport` test classes, alike: `wt-crdt` is
  a pure library and does not depend on the api or its tests.
* *Skipped with the reason under load.*  Before it runs, a `@PerfTest` reads the one-minute load
  average (`getloadavg`); above 1.5 times the machine's cores it is skipped with the measured load
  as the reason -- "load 97.2 over 18.0 (12 cores x 1.5)" -- and listed as skipped in the table.
  A loaded machine yields a skip, never a false failure.  `-Dwt.perf.load-factor=0` turns the
  guard off to see the figures anyway.

[[client-perf-runs]]
==== Client budgets

The client keeps the same rule with one helper, `PerfBudget`, written once in
`client/Packages/WTTestSupport/Shared/PerfBudget.swift` and linked (a symbolic link,
`Support/PerfBudget.swift`) into every test target that holds a budget, `WTAppTests` included.
It is not a product of the WTTestSupport package: that package depends on every other one, so a
test target depending on it would make SwiftPM resolve gRPC, NIO and GRDB for packages that have
no remote dependencies.

* *Correctness in every build.*  A timed scenario's functional assertions are ordinary
  `#expect`s and run in every `swift test` and in `make client-test`, whose coverage gate is taken
  over them.  Only the timing goes through `PerfBudget.expect(measured, within: budget)`.  Where a
  volume is only there for timing (WTCRDT's and WTSync's design point, the 2400 dpi plate, the
  4 MP trace) the default run uses a smaller one and `PerfBudget.isMeasuring` selects the full
  one.
* *Budgets in the perf run.*  `PerfBudget.expect` holds a figure only when `WT_PERF=1` is set
  and the test module is a release build (`swift test -c release -Xswiftc -enable-testing`).  A
  budget whose debug figure is meaningful says why (`enforcedInDebug:`); only the app's two
  budgets do, because the app's tests build Debug only, and unoptimised code within a budget is
  within it optimised too.  A budget known to be missed on current hardware says so
  (`knownIssue:`): a miss is recorded as a known issue and reported, not failed.  `make
  client-perf` runs, in release with `WT_PERF=1` and one test at a time (`--no-parallel`: Swift
  Testing otherwise runs a suite's tests side by side, and a budget sharing the cores with its
  own suite misses by up to five times while the load average stays under the guard), the tests
  of every package whose tests call `PerfBudget`, then the app's `CanvasPerformanceTests` and `CommandPaletteModelTests` (Debug) with
  `TEST_RUNNER_WT_PERF=1`.  Each budget appends a row (measure, measured, budget, build, and met,
  missed or skipped with the reason) to `client/build/perf-results.md` (`WT_PERF_RESULTS` names
  another file) and prints it prefixed `PERF`; the sandboxed test host cannot write outside its
  container, so the target takes the app's rows from the log.  The `perf` job of
  `.github/workflows/client.yml` runs it after `test`, copies the table into the job summary,
  and fails only on a missed budget or a failing test.
* *Skipped with the reason under load.*  When a budget is checked, a one-minute load average
  (`getloadavg`) above 1.5 times the active cores skips it with the measured load as the reason
  -- "load 29.3 over 18.0 (12 cores x 1.5)" -- listed in the table.  `WT_PERF_LOAD_FACTOR`
  changes the factor; `0` turns the guard off.  Without `WT_PERF=1`, or in a debug build, nothing
  is checked or written, so a loaded machine running the coverage gate cannot fail a budget.

`xref:` target against the page list and every `Depends on::` id against defined anchors, so a
dangling task id fails the build.
