{product} can be driven by scripts in three ways: by AppleScript through Script Editor, by
Shortcuts and Automator-style workflows through App Intents, and by JavaScript scripts written
in {product}'s own Script Editor panel and run from its Scripts menu.  All three expose the same
things -- documents, pages, master pages, layers, the objects on them and their properties,
export and printing -- and all three produce ordinary document changes that sync and are
undoable like anything done by hand.  JavaScript goes further: it can fetch data from the web
(through the {product} cloud), drive a data merge (xref:data-merge.adoc[Data merge]) and show
its own small dialogs.  The scripting surface in version 1 is deliberately small; it grows with
the features that ship.

== AppleScript

{product} publishes a scripting dictionary.  To read it, open Script Editor (in
`/Applications/Utilities`), choose menu:File[Open Dictionary…] and pick {product}.  The
dictionary has three suites:

[cols="1,3"]
|===
|Suite |Contents

|Standard
|`open`, `close`, `quit`, `count`, `exists`, `get`, `set`, `make`, `delete`, `duplicate`, `print`.

|{product}
|Classes `document`, `page`, `master page`, `layer`, `graphic` (with subclasses `path`, `group`,
`text block`, `image`, `symbol instance`), `swatch`, `style`; commands `export`, `find and
replace text`, `go to page`, `add page`, `release child page`, `apply master page`, `share link`.

|Text
|`text`, `paragraph`, `word`, `character` of a `text block`, with `font`, `size`, `leading`,
`color` properties.
|===

Documents are addressed by name or by library id; pages by index in page order or by name.  A
script line like `set page size of page 2 of document "Brochure" to {595, 842}` is one change,
labelled "Script: set page size" in the history, and one undo step for the person who ran it.

To run a script:

. Write it in Script Editor and click btn:[Run], or
. save it as an application, or drop it in `~/Library/Scripts/Applications/{product}/` to have it
  appear in the system Script menu.

A script runs as *you*: it can only open documents you can open and edit those you can edit.  A
script that edits a document someone else is in behaves exactly as if you were typing -- they see
the changes arrive.

=== What scripts can do in version 1

* Open, create (from a template), rename, close and export documents; list a library folder.
* Add, duplicate, remove, reorder, resize and go to pages; apply, create and release master
  pages; add and remove guides; set grid size and units.
* Read every object's kind, name, notes, bounds, layer, fill and stroke summary, and text; set
  name, notes, position, size, visibility, lock, layer and simple fill and stroke colors; delete
  and duplicate objects; make rectangles, ellipses, lines and text blocks.
* Find and replace text, with the same options as the Find Text panel
  (xref:find-replace.adoc[Find and replace]).
* Export a document or page in any export format with its options
  (xref:exporting.adoc[Exporting]).
* Print with a named print preset (xref:printing.adoc[Printing]).
* Generate a document report (xref:file-info.adoc[File info]).

Not in version 1: editing path points, effects, gradients, symbols, styles, blends and other
attribute detail.  Reading them returns a summary; setting them fails with a clear error.

== JavaScript

JavaScript is the scripting language for anything more than a few lines: batch changes with
conditions and loops, scripts that fetch data from the web and put it in the document, data
merge sources and transformations, and small tools you want to run with a keyboard shortcut.
Scripts run inside {product}, using the `wt` API described below, and every change a script
makes is an ordinary, labelled, undoable document change.

=== Writing a script

Choose menu:Window[Script Editor] to open the Script Editor panel.  It has an editor with
syntax coloring and completion for the `wt` API, a btn:[Run] button (kbd:[Cmd+Return]), a
btn:[Stop] button, and a console beneath the editor where `console.log` output, errors and the
web requests a script made are listed.  The panel's pop-up chooses which script is open: a new
untitled script, one from your Scripts folder, one stored in the document, or one from a team
library.

A script is a JavaScript module.  The simplest script runs top to bottom:

[source,javascript]
----
// Name every unnamed text block after its first words.
for (const block of wt.document.objects.where({ kind: "text", name: "" })) {
  block.name = block.text.split(/\s+/).slice(0, 3).join(" ");
}
console.log("done");
----

Each property assignment is one document change, labelled after the script ("Script: Name
blocks") and undoable with kbd:[Cmd+Z].  To make a run of changes one undo step, wrap them:

[source,javascript]
----
wt.document.transaction("Number the pages", () => {
  wt.document.pages.forEach((page, i) => { page.name = `Page ${i + 1}`; });
});
----

Modern JavaScript is available: modules, `async`/`await`, classes, template strings, `Map`,
`Set`, `Intl` for number and date formatting.  Type definitions for the whole `wt` API ship with
{product} (`wiretuner.d.ts`, in the Scripts folder after first launch) so an external editor
such as Visual Studio Code offers completion and type checking; the Script Editor panel uses the
same definitions for its own completion.

=== The `wt` API

[cols="1,3"]
|===
|Object |What it gives you

|`wt.document`
|The front document: `name`, `pages`, `masterPages`, `layers`, `objects` (every object, with
`where({...})` filters by kind, name, layer or page), `selection` (read and set), `fields` and
`dataSources` (xref:data-merge.adoc[Data merge]), `swatches`, `styles`; `transaction(label,
fn)`; `export(options)` and `print(preset)`.  `wt.documents` lists the open documents and
`wt.open(name)` opens one from your library.

|Objects
|Every page, layer and object is a JavaScript object whose properties mirror the Object panel:
`name`, `notes`, `bounds`, `position`, `size`, `visible`, `locked`, `layer`, `fill`, `stroke`,
`text` (text blocks), `url`.  Reading is free; setting a property makes one change.  Methods:
`duplicate()`, `remove()`, `moveTo(layer)`, `bringToFront()`, `sendToBack()`.  Creation:
`wt.document.createRectangle({...})`, `createEllipse`, `createLine`, `createText({...})`,
`createBarcode({...})`, `placeImage(data, {...})`.  The same limits as AppleScript apply in
version 1: path points, effects, gradients, symbols, styles and blends are readable as
summaries and not settable.

|`wt.fetch(url, options)`
|Makes a web request and returns a response with `status`, `headers`, `text()` and `json()`.
The request is made by the {product} cloud on your behalf, not by your Mac: the host must be
permitted for your team or your account, and `options.credential` names a credential stored in
the cloud (xref:data-merge.adoc#hosts[Hosts and permissions]).  Method, headers and body are
set in `options` as with the browser `fetch`.  A script cannot open any other connection.

|`wt.records`
|Inside a data merge: `wt.records.all()` (the resolved records), `wt.records.current()` (the
previewed record), `wt.records.merge({ to: "pages" \| "pdf" \| "printer", ... })` to run a merge
from a script, `wt.records.fields` for the field definitions.

|`wt.ui`
|`alert(message)`, `confirm(message)` (true or false), `prompt(message, defaultText)`,
`choose(message, ["A", "B"])`, `openFile({ types })` and `saveFile({ suggestedName })`, which
show the standard panels and return the file's contents or a writer -- the only way a script
touches files.  `progress(title)` returns an object with `update(fraction, text)` and `done()`
so long scripts show a progress sheet with a Cancel button.

|`console`
|`log`, `warn`, `error`, `table`; output goes to the Script Editor console.
|===

=== Where scripts live

[cols="1,3"]
|===
|Place |Use

|Your Scripts folder
|`~/Library/Application Support/WireTuner/Scripts/`.  Any `.js` file here appears in the
Scripts menu; subfolders become submenus.  Choose menu:Scripts[Open Scripts Folder] to get
there.  These are yours, on this Mac.

|The document
|A script saved *into a document* (btn:[Save to Document] in the Script Editor) travels with it:

|A team library

=== Running a script

Do one of the following:

* Choose it from the menu:Scripts[] menu.
* Press kbd:[Cmd+/] and type its name in the command palette
  (xref:workspace.adoc[The workspace]).
* Give it a keyboard shortcut under menu:{product}[Settings… > Shortcuts]: scripts are listed
  in the *Scripts* group like any command (xref:customizing.adoc[Customizing shortcuts and
  toolbars]).
* Click btn:[Run] in the Script Editor.
* Let a data merge run it, as a source or a field transform (xref:data-merge.adoc[Data merge]).

A script runs on the front document and as *you*: it can only open what you can open and edit
what you can edit.  While it runs, the Script Editor's btn:[Stop] and the progress sheet's
btn:[Cancel] stop it after the current change; what it already did stays and can be undone.  A
script that runs for more than a minute without showing progress is stopped with a message.
Nothing runs a script on its own: not opening a document, not a collaborator's action, not a
timer.

=== What a script cannot do

Scripts are sandboxed:

* No file system, except the files you choose in the open and save panels through `wt.ui`.
* No shell, no other applications, no AppleScript from JavaScript.
* No network, except `wt.fetch`, which goes through the {product} cloud with its permitted hosts
  and credentials.
* No access to your account, your credentials or other documents you have not opened.
* A limit on memory and on time between progress updates, so a runaway script cannot freeze
  {product}.

== Working with others

Scripts and shortcuts change documents on your behalf, and to everyone else those changes look
like yours.  A long-running script that touches many objects sends its work as it goes, so
collaborators see it progress; its history entries are labelled "Script: …" so anyone can tell
what a run did.  A script cannot lock a document or stop others from editing while it runs; if it
needs a quiet document, run it on a branch (xref:branches.adoc[Branches]).

A script that runs while you are offline works on the local copy and its changes sync afterwards
like any others.  Intents that need the server -- *Share Link*, opening a document not cached on
this Mac -- fail immediately with an *offline* error rather than waiting.  So does `wt.fetch`,
which needs the {product} cloud.

JavaScript scripts stored in a document or a team library are shared like anything else in
that document: if a collaborator edits a script while you have it open in the Script Editor,
the panel shows a notice with *Reload*; your unsaved edits are kept until you decide.  Two
people saving the same script at the same moment: the later save stands, and the other is
listed in the sync review so it can be brought back.  A script is always run as last saved,
never half-typed.

== Specification

=== Data model

Every mutating script command -- AppleScript, App Intent or JavaScript -- maps onto an existing
`WTModel` command and therefore onto ordinary changes; the change label is prefixed `Script: `
(AppleScript and JavaScript) or `Shortcut: ` (App Intents) followed by the command name or, for
JavaScript, the script's name and the property set (`Script: Number the pages`).

JavaScript adds one node kind, `script`, for scripts stored in a document or a team library
document.  Script nodes live under the well-known `assets` collection (0:9).

[source,protobuf]
----
// proto/wiretuner/doc/v1/script.proto (DATA-001; `script` = 241 in the DATA block)

// NodeProps.kind case `script`.  A script is saved whole from the Script Editor, so
// `source` is one ATOMIC register: a script is always run as last saved by somebody, never
// as a character-level merge of two people's edits.  Name (CommonProps.name, as for every
// named kind) and description are independent registers.
message ScriptProps {
  CommonProps common = 1;
  string description = 2 [(buf.validate.field).string.max_len = 1024];
  string source = 3 [(buf.validate.field).string.max_len = 1048576,
                     (wt.crdt.field).merge = MERGE_ATOMIC];
  // Set when copied from a team library so *Update from Library* can find the original.
  // The LIB epic's LibrarySource (symbol.proto): document id, node, server_seq.
  LibrarySource library = 4 [(wt.crdt.field).merge = MERGE_ATOMIC];
}
----

Scripts in the user's Scripts folder are files, not document state.  Keyboard shortcuts for
scripts are entries in the user's shortcut set (BASIC epic), keyed by the script's path or node
id.

=== Merge semantics

Script changes are user changes; every rule on the feature's own page applies unchanged.  One
consideration is specific to scripts: a script that iterates over "every page" or "every graphic"
evaluates the collection once per command, so an object created by a collaborator mid-run is
simply not visited.  A script writing to an object a collaborator deletes mid-run gets no error
(the edit applies to the deleted node) and the ordinary edit-vs-delete review entry.

JavaScript adds:

* `wt.document.transaction` groups its property sets into one change (chunked at 10,000 ops
  under one label, one undo step); outside a transaction every property set is its own change.
  A script stopped mid-transaction leaves the ops emitted so far as one change -- a consistent,
  partially-applied document, never a half-applied op.
* A `script` node's `source` is ATOMIC: two people saving concurrently keep the later save; the
  loser is listed in the review sheet under *same register* with both sources in the preview.
  `name` vs. `source` edits from two sides both survive.  Delete vs. save: the save lands on the
  deleted node; *Restore* brings the script back with the saved source.
* A script that reads a collection (`wt.document.objects`) gets a snapshot of the merged state at
  that call; objects created by collaborators later in the run are not visited unless the
  script reads again.
* A data-merge transform or source references its script node by `NodeRef`; deleting the script
  makes the field's transform read as none (`REF_FALLBACK_UNSET`) and the source fail with
  "script missing" in the panel.

=== Offline behavior

Local commands work offline.  `share link`, opening uncached documents and library listing beyond
the cache return `errOfflineRequired` (AppleScript error 1001; App Intents `.offline` failure with
a localized reason).  JavaScript: `wt.fetch` rejects with an `OfflineError` immediately; team
library scripts already listed in the menu run from the cached copy, but browsing a library
needs the network.

=== Server

Nothing beyond storing and relaying changes for AppleScript, App Intents and the `wt.document`
API.  `Share Link` uses `ShareService` (SRV-010).  `wt.fetch` is `DataSourceService.Proxy`
(xref:data-merge.adoc[Data merge], DATA-006): the server makes the request with the scope's
allowlist, credentials, rate limits, SSRF guard and audit log; the client never opens a
connection to a third-party host.  Team library scripts are listed through `ListLibraries`
(LIB-015).

=== Client

* `WTApp/Scripting/WireTuner.sdef` with the three suites; `NSScriptCommand` subclasses per verb;
  scriptable object wrappers over `WTModel` nodes keyed by node id (`id` property is the node id
  as a string, stable across runs) using `NSUniqueIDSpecifier`.
* Undo: one script command = one change = one undo step; a `tell` block with many commands is
  many steps.  The scripting bridge batches nothing across commands, deliberately, so a killed
  script leaves a consistent, partially-applied document rather than a half-batch.
* Rate: a script emitting more than 20 changes per second is throttled by the outbox (changes
  are queued, never dropped).
* App Intents: `AppIntent` types in `WTApp/Intents` with `AppEntity` for documents (queryable
  through the library cache), `AppEnum` for formats and orientations; results as `IntentFile`
  where a file is produced.
* Errors follow Apple's scripting error codes with human-readable messages; permission errors
  name the role required.

One command registry:: `WTApp/Commands/CommandRegistry` is the single table of every user
command: menu items, the command palette, keyboard shortcuts, `NSScriptCommand` subclasses,
`AppIntent`s and the `wt` API are all thin adapters over it.  Each entry names the `WTModel`
command it runs, its parameters, its label, and whether it is available for the current
selection.  Adding a command to the registry adds it to every surface; nothing is scriptable in
one language and not another.

JavaScript runtime:: `WTScripting` (a package in `WTApp`'s workspace, depending on `WTModel`
and `WTInterchange`) hosts JavaScriptCore.  One `JSContext` per run, in a `JSVirtualMachine`
per document, on a dedicated `ScriptRunner` actor; the `wt` object is installed as
`JSExport`-conforming Swift bridges over `WTModel`.  Property reads take a snapshot of the
merged state; property sets and method calls hop to the main actor, run the registry command,
and return after the change is emitted.  `wt.document.transaction` opens a command group
(APP-011) and closes it on return or throw.  Sandbox: the context has no `require`, `import()`
of files, `XMLHttpRequest`, `WebSocket`, timers beyond `setTimeout` (capped at 60 s), or file
APIs; `wt.ui.openFile`/`saveFile` go through `NSOpenPanel`/`NSSavePanel` and hand back
contents or a writer, never a path.  Limits: 256 MiB per virtual machine, 60 s wall-clock
between progress updates (then stopped with `ScriptTimeout`), 20 changes per second throttled by
the outbox as for AppleScript.  Errors carry file, line and column into the console.  Module
syntax is supported by wrapping the script in a module record; `export`ed functions
(`records`, `transform`) are looked up by name by the data-merge engine.

`wt.fetch`:: Serializes the request into `DataSourceService.Proxy` (method, URL, headers, body
up to 1 MiB, `credential`), maps `HOST_NOT_ALLOWED` to the consent sheet on a personal
document (then retries) and to an error naming the admins on a team document, and returns a
`Response`-like object.  Every call is logged to the console with host, path, status and size.
There is no other network primitive in the context.

Typings:: `wiretuner.d.ts` is generated from the bridge declarations at build time (a `wt-typegen`
tool over the `JSExport` protocols with doc comments) and shipped in the app bundle; on first
launch it is copied to the Scripts folder next to a `README`.  The Script Editor's completion
reads the same file.

Script Editor panel:: `WTApp/Panels/ScriptEditorPanel`: an `NSTextView`-based editor with
JavaScript syntax coloring and `d.ts`-driven completion, the script chooser pop-up (untitled,
Scripts folder, document scripts, team libraries), btn:[Run]/btn:[Stop], btn:[Save],
btn:[Save to Document] and btn:[Save to Library…], and the console (a table of log entries with
level, text, and request rows).  Saving a document or library script writes `ScriptProps.source`
whole as one change "Save script".  A remote change to the open script shows the *Reload*
notice; the buffer is kept.

Scripts menu and library:: `menu:Scripts[]` is built from an `FSEvents`-watched Scripts
folder (files and subfolders), the front document's `script` nodes, and the team libraries'
script nodes from the library cache; *Open Scripts Folder*, *Script Editor* and *Reload
Scripts* at the bottom.  Every entry is registered in the command registry with a `script:`
prefix, so the command palette and the shortcut editor see them.  Team library scripts run
from the cached library document; *Save to Library…* writes into the chosen library document
through the same path the Library panel uses for symbols (LIB-014).

[[as-built-javascript]]
==== As built (DATA-011; DATA-012 model half)

Where the runtime is:: In `WTModel` (`Script*.swift`), not a `WTScripting` package: the runtime
drives `WTModel` commands and nothing else needs it, and JavaScriptCore is a system framework.
`ScriptRunner.run` evaluates on the calling thread and `runDetached` on a thread of its own (a
class rather than an actor: a script blocks its thread while a command is performed);
`ScriptTarget` is where writes land -- `CoreScriptTarget` over a `DocumentCore`,
`DocumentScriptTarget` over the window's `Document` (each call hops to the main actor and waits),
`ReadOnlyScriptTarget` for data-merge transforms and sources, which may not change the document.
The command registry adapter is not built (the registry is WTApp's): `wt` calls the `WTModel`
commands directly.

Bridge and typings:: `wt` is built by a JavaScript prelude (`ScriptPrelude`) over natives on a
hidden `__wt` object, with proxies whose property sets become commands, instead of `JSExport`
protocols.  `wiretuner.d.ts` is `ScriptTypings.declarations`, kept beside the bridge and checked
member by member by a test, not generated by a `wt-typegen` tool; the `tsc` check of the corpus
is not run (no Node toolchain on the build machine).  Objects are addressed by node id strings
(`"counter-replica"`).  Readable: `name`, `notes`, `locked`, `visible`, `bounds`, `position`,
`size`, `url`, `text`, a barcode's `value` and `symbology`, `layer`, `page`, `binding`, and `fill`
and `stroke` as summaries; settable: name, notes, locked, position, layer, url, text, a barcode's
value and symbology, a layer's name, visibility and lock, a page's and a swatch's name, a document
script's name and source.  `placeImage` refuses in version 1; `export` and `print` go to the
window (`ScriptHost`) and refuse without one.

Transactions:: Sets inside `transaction` are queued and emitted as `CompositeCommand`s of at most
10,000 ops under `Script: <label>`, all one undo step (30,000 sets make three changes); reads inside
a transaction see the state at the last flush.  Creation and text replacement flush first so their
effects are visible.  A throw or stop flushes what was queued and closes the group.

Sandbox and limits:: `require`, `XMLHttpRequest`, `WebSocket`, `fetch`, `importScripts`,
`EventSource`, `Worker` and `setInterval` throw `SandboxError` naming the rule; `setTimeout` runs
after the script's body, capped at 60 s.  The wall clock is JavaScriptCore's execution time limit
(`JSContextGroupSetExecutionTimeLimit`, looked up at run time: there is no public API to interrupt a
running context), polled every 50 ms and re-armed on each poll; it also carries btn:[Stop] and the
progress sheet's btn:[Cancel].  JavaScriptCore has no per-machine heap cap, so the 256 MiB limit is
two guards: allocations through `ArrayBuffer`, typed arrays, `String.prototype.repeat` and
`Array.prototype.fill` over the limit throw `RangeError: ScriptMemoryLimit`, and the watchdog stops
a script when the process's footprint has grown past the limit since the run started.

Modules:: The source is rewritten, not loaded as a module record: `export` declarations and lists
become ordinary declarations collected into the exports, and the body runs inside an async function
on the script's first line (so line numbers hold and top-level `await` works); `import` of other
modules is not supported.  `ScriptContext.call` awaits a returned promise.

Data merge and `wt.fetch` (DATA-012 model half, DATA-015 partly):: `ScriptTransformer` runs field
transforms with one context per script for the whole record set, the wall clock per record; a
transform that throws or times out leaves the raw value and is reported, and a timed-out context
is replaced.  `ScriptRecordSource.records` runs a script source's `records(params)` export and
records the hosts `wt.fetch` reached.  `wt.fetch` resolves through `ScriptFetching`
(`WTSync.DataScriptFetcher`, the server's `Proxy`), logging each request to the console;
`wt.records` (`all`, `current`, `fields`) reads the `RecordSet` a run is given, and `wt.ui` and
`wt.records.merge` go to `ScriptHost`.  The Script Editor panel, the Scripts menu, the consent
sheet and *Show Hosts* are WTApp's and not built.
