A connector line links two objects and stays linked: move either object and the line reroutes
itself to keep them joined.  Connectors are the quick way to draw call-out lines, organization
charts and flowcharts.  A connector is drawn with the current stroke, so its arrowheads,
width and dashes come from the Object panel like any other stroke
(xref:stroke-attributes.adoc[Stroke attributes]).

== Drawing a connector

To draw a connector between two objects:

. Choose the Connector tool.
. Move the pointer over the first object.  The pointer changes to show the object can be
  connected, and as you move near its top, bottom, left or right edge, that side highlights.
. Press on the side you want the line to leave from and drag.
. Drag to a side of the second object and release.  The line is routed with right-angle
  bends from the first side to the second.

Release over empty canvas and the connector ends at a free point there; it then follows only
the object it starts from.

To move a connector's end:

* With the Connector tool, drag an end point to another object (or another side of the same
  object), or to empty canvas to free it.

To reverse a connector:

. Select it.
. Choose menu:Modify[Alter Path > Reverse Direction].  Its arrowheads swap ends.

To reshape a connector by hand:

. With the Connector tool, click the connector.  A handle appears on each straight run of the
  line.
. Drag a handle to slide that run sideways.  The bends adjust to keep the line connected.  The
  reshaped route is kept as the objects move; the line snaps back to automatic routing if the
  objects move so far that a different number of bends is needed.

A connector cannot be dragged on its own with the Pointer tool: move the objects it connects.
It can be selected, styled, deleted, and included in a group with its objects.

== Working with others

When a collaborator moves an object, every connector attached to it reroutes on your screen
at once, because a connector stores *which* objects it joins, not where they were.  Two people
dragging the two ends of one connector to different objects keep both changes.  If someone
deletes an object a connector is attached to, that end of the connector stays where the
object was and becomes a free end; deleting the other object too leaves a plain line you can
keep or discard.  Restoring the deleted object reconnects it.

== Specification

=== Data model

`doc/v1/connector.proto`.  The geometry of a connector is *never stored*; it is derived on
read from the two ends and the current bounds of the referenced nodes.

[source,protobuf]
----
message ConnectorProps {                      // NodeProps.kind case `connector` = 25 (DRAW block)
  CommonProps common = 1;                     // transform is unused (identity); name, notes
  // ATOMIC: node, side and point are always written together by an attach, and a merged end
  // with one person's node and another's side would attach to a side nobody chose.
  ConnectorEnd start = 2 [(wt.crdt.field).merge = MERGE_ATOMIC];
  ConnectorEnd end = 3 [(wt.crdt.field).merge = MERGE_ATOMIC];
  AppearanceProps appearance = 4;                  // strokes only; fills ignored
  // Manual reshape: sideways offset of each intermediate straight run of the routed line, in
  // pasteboard units, in route order.  ATOMIC: the list only makes sense as a whole for one
  // route shape.  Read as automatic when its length differs from the current route's run
  // count.  At most 64 entries.
  repeated double run_offsets = 5 [(wt.crdt.field).merge = MERGE_ATOMIC];
}

message ConnectorEnd {
  // The object this end is attached to.  Dangling (deleted, unknown, or a kind without
  // bounds) reads as unset, making this a free end at `point`.
  NodeRef node = 1 [(wt.crdt.field).on_dangling = REF_FALLBACK_UNSET];
  ConnectorSide side = 2;                     // TOP, BOTTOM, LEFT, RIGHT; ignored when free
  // Free position, and the fallback when `node` dangles.  Written whenever the end is
  // attached or moved (the attachment point at that moment), so a deleted object leaves the
  // end where it was.
  Point point = 3 [(wt.crdt.field).merge = MERGE_ATOMIC];
}
enum ConnectorSide {
  CONNECTOR_SIDE_UNSPECIFIED = 0;             // the side facing the other end
  CONNECTOR_SIDE_TOP = 1; CONNECTOR_SIDE_BOTTOM = 2; CONNECTOR_SIDE_LEFT = 3; CONNECTOR_SIDE_RIGHT = 4;
}
----

The endpoint position for an attached end is the midpoint of the chosen side of the node's
*rendered bounds* (after its transform, stroke widths included), computed at read time.

=== Merge semantics

Remote move of a connected object:: No connector op is involved.  The mover writes the
object's `transform`; every replica re-derives the connector on read.  This is the key
property: connectors cannot lag or conflict with the objects they follow.

Two people re-attach the two ends:: `start` and `end` are separate registers; both survive.

Two people re-attach the same end:: `ConnectorEnd` is ATOMIC, so the greater OpId's node,
side and point win together; the review sheet lists the connector under *same register* with
both attachments named by object.

Delete the object vs. attach to it:: The attach applies; the ref dangles; the end reads as
free at `point`.  Restoring the object reconnects it because the ref is intact.

Reshape vs. object move:: `run_offsets` is kept if the route still has the same number of
runs; otherwise it reads as automatic and stays in the register for the next matching route.

Reverse Direction:: Swaps `start` and `end` (two STRUCT writes) and reverses `run_offsets`,
negating each offset (an offset is to the right of its run's direction, which reversing turns
around), so the line keeps its shape.
Concurrent re-attach of one end may land on the "wrong" end after the swap; the review sheet
lists the connector as *both edited*.

Read-time normalizations::
* Dangling `node` → free end at `point`.
* Both ends free → a plain routed line between the two points (still a connector; the tool
  can re-attach either end).
* Both ends attached to the same node → drawn as a loop leaving one side and entering the
  other; if the sides are equal, drawn as a short stub outside that side.
* `run_offsets` length mismatch → automatic routing.
* `common.transform` ignored.

=== Offline behavior

Works offline.  Dragging an end coalesces to one write per field.

=== Server

Nothing beyond storing and relaying changes.

=== Client

Routing:: `WTGeometry.routeConnector(startPoint:startSide:endPoint:endSide:) -> [Point]`, an
orthogonal (Manhattan) router: leave each side by a 12 pt stub, then join the stubs with one
or two bends chosen by the relative position of the ends (the classic flowchart elbow), no
obstacle avoidance.  `run_offsets` slide the intermediate runs.  Output is a
`Path` with corner points; arrowheads and stroke come from REND-002.

Dependency tracking:: `WTModel` keeps a reverse index node → connectors referencing it, built
from the merged state and maintained on every applied change, so REND-004 can invalidate a
connector's bounds when a referenced node's transform, size or stroke changes, locally or
remotely.  Hit-testing uses the derived path.

Tool:: `ConnectorTool`: hover highlights connectable nodes (any node with bounds except
connectors and guides) and the nearest side; press-drag-release writes a `CreateNode`;
dragging an end of an existing connector writes that `ConnectorEnd`; clicking a connector
shows run handles; handle drags write `run_offsets`.

Object panel:: The connector section shows the two ends (object name and side, or "free")
and lets the user pick the side from a pop-up; the stroke section is the ordinary one.

Undo:: One group per creation, per end drag, per handle drag.

NOTE: As built by DRAW-035 and DRAW-037 (render half; `WTRender/Connectors`).  Routing is
`WTRender.ConnectorRouter.route(_:bounds:)`, not `WTGeometry.routeConnector` (WTGeometry is another

router it offers `.straight` and `.curved` (one cubic leaving each side along its normal, handles

the tool and the Object panel are other tracks'.  An end with `SIDE_UNSPECIFIED` takes the side of

at the middle; facing the same way, beyond the further stub; facing away, around through the middle
of the other axis; one horizontal and one vertical stub, one bend when it is ahead of both, else
two.  Intermediate runs are the route's segments other than the first and last (after merging
collinear corners); an offset moves its run to the right of its direction.  An attached end sits
on the item's geometry grown by half its widest stroke (`ConnectorRendering.attachmentBounds`), not
