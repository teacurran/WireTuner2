*Publish as HTML* turns a document into a web page: one folder holding an `index.html`, one SVG
(or PNG) per page, the images, fonts and video the pages need, and a stylesheet.  Open the
folder in a browser and the document is there, links working, animation playing, at any screen
size.  You can publish to a folder on your Mac, or publish to a *web link* -- a read-only copy
hosted for you that anyone with the link can open, updated each time you publish again.

Named *HTML settings* control what the publisher produces.  The built-in *Default* setting
writes SVG pages, JPEG images and embedded fonts into a folder called `{product} HTML Output`
in your Documents folder.  You can edit it, add your own, and publish the same document several
times with different settings -- once as crisp SVG for modern browsers, once as PNG for an email
client -- as long as each goes to a different folder or name.

NOTE: {product} writes SVG for vector art and has no setup assistant: the Setup sheet is short
enough to fill in directly.

== Publishing

To publish a document as HTML:

. Choose menu:File[Publish as HTML…].  The Publish sheet opens.
. Choose an *HTML setting* from the pop-up menu, or click btn:[Setup…] to create or edit one (see
  below).
. Under *Pages*, choose *All* or enter a range.
. Under *Publish to*, choose *Folder on this Mac* or *Web link*.
. Optionally select *Show output warnings* to see, when publishing finishes, a list of anything
  that could not be reproduced exactly.
. Optionally select *Open when done* and choose a browser from the pop-up menu -- your default
  browser, any browser installed, or btn:[Other…] to pick an application.
. Click btn:[Publish].

Publishing runs in the background; the progress appears in the sheet, which you can close and
reopen from the same menu.  When it finishes, the folder is revealed in the Finder (or the web
link is copied to the clipboard), the browser opens if you asked for it, and the warnings list
appears if there was anything to report.

=== Output warnings

The warnings list names each object that lost something in translation, with a btn:[Show] button
that selects it on the canvas:

* effects rasterized because SVG has no equivalent (some raster effects, transparency knockout
  groups);
* fonts converted to outlines because the font's license does not permit embedding, or because
  the font was missing (xref:font-substitution.adoc[Font substitution]);
* links whose URL could not be made valid;
* links on stroke-only paths, which respond only on the stroke in image maps;
* a placed SVG animation that depends on script (xref:svg-animation.adoc[SVG animations and browser preview]);
* pages larger than 16,384 pixels on a side at the chosen scale, which are clamped in PNG mode.

Text encoding is always UTF-8; there is no option.

Colors need no option either.  sRGB colors are written as hex; Display P3, OKLCH and Lab
colors are written the way current browsers read them (`color(display-p3 …)`, `oklch(…)`,
`lab(…)`) with an sRGB version beside each for browsers that do not, so a wide-gamut brand
red is that red on a P3 screen and the nearest sRGB red elsewhere
(xref:spot-process.adoc[Spot and process colors]).  PNG output embeds the Display P3 profile
when the document holds such colors (xref:export-bitmap.adoc[Exporting bitmaps]).

Everything is relative, so the folder can be moved, zipped, mailed, or dropped onto any static
host.  Files are named deterministically, so republishing over the same folder changes only what

== Publishing to a web link

A web link is the same output, hosted by {product} and served at a permanent address such as
`https://pub.wiretuner.app/d/3f9c…/`.  Use it to hand a client a preview, to show a page on a
phone, or to keep a "latest" URL that always shows the current state of the document.

To publish to a web link:

. Choose menu:File[Publish as HTML…] and pick an HTML setting.
. Under *Publish to*, choose *Web link*.
. Choose who can open it:
  *People with access to this document* (they sign in) or *Anyone with the link*.
. Click btn:[Publish].  The address appears in the sheet and is copied to the clipboard.

The address stays the same each time you publish again; viewers who reload see the newest
publish.  Every publish is listed under menu:File[Publish as HTML… > Published links…] with its
date, the setting used and who published it, and any of them can be reopened, downloaded as a
folder, or *unpublished*, which makes the address stop working.  Unpublishing is not undoable but
publishing again restores it at the same address.

Publishing to a web link needs a network connection; the option is disabled offline with a note
saying so.  Changing who can open the link later is done in the *Published links* sheet or on the
document's share settings (xref:sharing.adoc[Sharing documents]).

NOTE: A web link is a *copy*.  Viewers cannot edit, comment, or see later changes until someone
publishes again.  To collaborate on the document itself, share it instead.

== Working with others

Publishing reads the document at the moment you click btn:[Publish] and does not change it, so
collaborators see nothing happen.  The HTML settings themselves are part of the document -- a
setting you add appears in everyone's Setup sheet, and if two people edit the same setting at
once the later edit wins field by field (your *Fonts* choice and their *Scale* choice both
survive).  The output folder location is the one thing that stays yours, because a path on your
Mac means nothing on theirs.

Two people can publish the same document to its web link at the same time; the one that finishes
uploading later becomes the current one, and both are listed.  If you publish while a
collaborator's latest changes are still syncing to you, they are not in the output; the
*Published links* sheet shows the document version each publish was made from, so you can tell.

=== Data model

HTML settings live in the document's `settings` node so they are shared; the local folder is
`local_only`.  Published links are server records, not document state.

The *Default* setting is not stored: it is synthesized at read time when the sequence is empty,
and materialized (created as an element) the first time someone edits it, so a document that has
never been published carries no settings.

Published links are server state, in package `wiretuner.publish.v1`:

[source,protobuf]
----
// publish.proto (sketch)
service PublishService {
  // Registers a publish whose files are already uploaded as blobs.  Idempotent on publish_id.
  rpc CreatePublish(CreatePublishRequest) returns (Publish);
  rpc ListPublishes(ListPublishesRequest) returns (ListPublishesResponse);
  rpc SetPublishAccess(SetPublishAccessRequest) returns (Publish);   // who may open the link
  rpc DeletePublish(DeletePublishRequest) returns (google.protobuf.Empty);   // unpublish
}

message PublishManifest {
  // Path inside the bundle -> blob hash and media type.  Paths are relative, normalized,
  // no "..", at most 4096 entries.
  repeated PublishFile files = 1;
}
message PublishFile { string path = 1; bytes sha256 = 2; string media_type = 3; uint64 size = 4; }

message Publish {
  string publish_id = 1;         // client-supplied UUIDv7
  string document_id = 2;
  uint64 server_seq = 3;         // document version the bundle was rendered from
  string setting_name = 4;
  string published_by = 5;       // user id
  google.protobuf.Timestamp published_at = 6;
  PublishAccess access = 7;      // MEMBERS or ANYONE_WITH_LINK
  string url = 8;                // https://pub.<host>/d/<document_id>/
  bool current = 9;              // the one the url serves
}

=== Merge semantics

`html_settings`:: SEQUENCE.  Concurrent edits to different fields of one setting both apply;
the same field resolves LWW.  A setting deleted concurrently with an edit stays deleted (the
element's `deleted` register), and the review sheet lists "edited an HTML setting that was
deleted" with *Restore*.  Two people adding a setting with the same name produce two settings;
the Setup sheet shows both and appends " (2)" to the later one's display name (read-time only).
`location`:: `local_only`; never on the wire.  A setting arriving from another replica has no
location on this Mac and shows "Choose a folder" until one is picked.
Publishing:: Reads a consistent snapshot of the model on the main actor (the display list is
built from one state), then renders on a background task.  Nothing is written to the document.

=== Offline behavior

* Publishing to a folder works offline.  Placed images and SVG animations whose blobs have not been
  downloaded yet are rendered as their placeholders and listed in the warnings; the sheet offers
  btn:[Wait for downloads] when any are pending and the network is up.
* Publishing to a web link is disabled offline (the radio button is dimmed with "Needs a
  connection").  It is never queued: a publish made from stale state hours later is not what the
  user asked for.
* The *Published links* sheet shows the cached list offline, read-only.

=== Server

`PublishService` and a static file endpoint, both in the Quarkus `api` module.

* `CreatePublish` verifies the caller has at least *editor* on the document, that every
  `sha256` in the manifest exists in blob storage and is associated with the document
  (`document_blob`), that total size is under 512 MiB and file count under 4096, and that
  every path is a safe relative path.  It inserts a `publish` row and `publish_file` rows, marks
  the publish current, and emits a document event so other clients refresh the sheet.
* Serving: `GET https://pub.<host>/d/<document_id>/{path}` on a *separate origin* from the app
  and the API, so published HTML can never read app cookies or call the API with the viewer's
  credentials.  The handler resolves the current publish, checks access (`ANYONE_WITH_LINK`, or a
  signed-in member for `MEMBERS`, via the Keycloak session cookie set on the pub origin after a
  redirect through the API), and streams the blob from R2/MinIO with `Content-Type` from the
  manifest, `Cache-Control: private, max-age=0, must-revalidate` and an `ETag` of the blob hash.
  Responses carry `Content-Security-Policy: sandbox allow-same-origin; default-src 'self'
  data: blob:; script-src 'none'` -- the bundle needs no scripts; `X-Content-Type-Options:
  nosniff`; `Referrer-Policy: no-referrer`.  Path `""` and `"/"` serve `index.html`.
* `DeletePublish` removes the rows; blobs are retained by the ordinary history rules and
  garbage-collected with the document.  Publishes are deleted with the document.
* Access defaults to the document's share-link policy when one exists, else `MEMBERS`.
* Rate limit: 30 publishes per document per hour (`RESOURCE_EXHAUSTED` with `RetryInfo`).

As built (WEB-011, WEB-012; `proto/wiretuner/publish/v1/publish.proto`, `api/.../publish`):

* *Schema.*  buf's STANDARD lint wants every RPC to take and return its own messages, so the
  sketch's `Publish` and `google.protobuf.Empty` results are `CreatePublishResponse`,
  `SetPublishAccessResponse` (each holding the `Publish`) and `DeletePublishResponse`; a
  `GetPublish` (the publish and its manifest) is added.  `SetPublishAccess` names the publish.
  `Publish` also carries `file_count` and `total_size`.  No new error reasons: an unknown publish
  is `NOT_FOUND / DOCUMENT_NOT_FOUND`, a blob the document does not reference `BLOB_NOT_FOUND`, an
  oversized bundle `VALIDATION_FAILED`; path safety, the 4,096-file cap and unique paths are
  protovalidate rules.  `PublishesChanged` is `sync.v1.DocumentEvent` case 10.
* *Service.*  Creating is idempotent on `publish_id` (a retry answers the first publish; the
  same id for another document is `VALIDATION_FAILED`).  The bundle size is summed from the blob
  records, not the manifest's `size`.  `PUBLISH_ACCESS_UNSPECIFIED` takes the document's link
  policy: anyone with the link when the document has a live (unrevoked, unexpired) share link,
  else members.  `DeletePublish` is idempotent; deleting the current publish leaves the link
  dead until the next publish.  Listing and getting need any role, the rest editor.  The rate
  limit is a `RateLimiter` token bucket `rl:p:<document>` (`wt.publish.per-hour`).
* *Origin.*  A Vert.x HTTP server of its own on `wt.publish.origin.host`:`wt.publish.origin.port`
  (8090; the `pub.<host>` name routes there), not a route of the API's server.  The path is
  parsed raw: `.`/`..`, empty segments, encoded `/` or `\`, control characters and invalid
  percent-escapes or UTF-8 are 400, never resolved.  `GET` and `HEAD` only (405 otherwise);
  `/d/<document>` redirects to `/d/<document>/`; `If-None-Match` answers 304.  No cookie is set
  or read.
* *Deferred:* the members-only sign-in hand-off (Keycloak session cookie on the pub origin after a
  redirect through the API) waits for its security review; a members-only publish answers 403
  meanwhile.  Anyone-with-link publishes are served in full.
* *Load test* (`PublishServiceTest`): a 200-file bundle, 100 concurrent viewers each fetching every
  file (20,000 requests) from MinIO through the origin; the p95 is printed and must stay under
  200 ms.

=== Client

* Accessibility: every emitted `<img>` and inlined SVG carries the object's alt text
  (`CommonProps.alt`; `aria-hidden` when decorative), image-map `<area>` elements carry the
  link alt with the object alt as fallback, and areas are listed in the page's reading order
  (xref:names-notes.adoc[]).

* `WTInterchange.HtmlPublisher` builds a bundle in a temporary directory from a `Document`
  snapshot and an `HtmlSetting`, using the SVG writer (IO epic, extended by WEB-005 and
  WEB-018), the bitmap encoders (WEB-006), the font subsetter (WOFF2 via a bundled `woff2`
  static library; `fsType` checked for embedding permission), and the placed-SVG-animation
  emitter (WEB-028).  The output is deterministic for a given snapshot and setting: file names are
  content hashes for assets and page numbers for pages, so republishing over a folder rewrites
  only changed files.
* Whole-pages mode: one `<img src="pages/page-N.svg">` per page in a page-sized `<section>`;
  in SVG mode links live inside the SVG (`<a>`), so the SVG is inlined with `<object>` rather
  than `<img>` when the page has links, because `<img>` does not follow anchors.  PNG mode uses
  `<img usemap>` with `<area shape="poly">` from the flattened outline (`WTGeometry`
  flattening at 0.25 px tolerance) and `shape="rect"` per text line for ranges.
* Positioned-objects mode: one file per top-level node, `position:absolute` with `left/top/
  width/height` from the node's page-space bounds (effects' expanded bounds included) and
  `z-index` from stacking order; background layers (below the separator) are still rendered as
  one file per page.
* Colors: every `Color` is serialized by CMS-015's CSS Color 4 serializer.  In SVG, an sRGB
  color is the presentation attribute (`fill="#e63946"`); a Display P3, OKLab or Lab color
  is written twice -- the attribute holds the sRGB fallback (COLOR-024's gamut mapping) and
  a `style` on the same element holds `fill: color(display-p3 …)`, `oklch(…)` or `lab(…)`,
  which wins in a browser that parses it and is dropped, leaving the attribute, in one that
  does not.  Gradient stops use `stop-color` the same way.  In `style.css` (page background,
  positioned-object backgrounds) the fallback declaration precedes the wide-gamut one.  In
  PNG mode the pages are rendered through IO-021's rasterizer with `rgb_space = AUTO`, so a
  document with wide-gamut colors gets Display P3-tagged PNGs.  Colors in placed bitmaps
  are untouched (WEB-006 handles their profiles).
* The Publish sheet is an `NSViewController` sheet hosting SwiftUI, with progress from an
  `AsyncStream` and cancellation.  Warnings are a list with btn:[Show] calling the selection
  API.  *Open when done* uses `NSWorkspace.open(_:withApplicationAt:configuration:)`; the
  browser list comes from `NSWorkspace.urlsForApplications(toOpen: URL)` for an `.html` URL.
* Publish to web link (`WTSync.PublishUploader`): upload every file of the bundle through
  `BlobService.Upload` (largest last, reusing hashes the server already has via `Stat`), then
  `CreatePublish` with the manifest.  Progress in the sheet; resumable per blob; cancel deletes
  nothing on the server (uploaded blobs are harmless orphans until GC).
* Undo: nothing on this page is undoable except edits to HTML settings, which are one change
  per field commit labelled "Change HTML setting".

first 16 bytes of its SHA-256 in hex, so the same image or subset on several pages is one file.  A
font whose `fsType` forbids embedding (or that has no TrueType outlines, or is a variable instance)
is outlined, and the SVG writer reports it (`SVGDocument.outlinedFonts`), which the bundle raises as
an *outlined font* warning on the text's node.  Deviation: a page (or object) SVG that links images
or fonts is embedded with `<object>`, like a page with links, because an SVG loaded by `<img>` loads
no other file.  Placed SVG animations (`ExportScene.svgAnimations`, `HTML/HTMLAnimations.swift`)
play unless *Poster only*: the node's item in the page is emptied (so the poster is not drawn and no
other item moves) and the file is put back over the page, in the `<section>` after the page's
picture, in a `<div class="anim">` whose CSS `transform` is the node's transform (natural size in
points, `transform-origin: 0 0`), inlined with its XML declaration, doctype, comments, `<script>`
and `on…` attributes removed (a `scriptAnimation` warning when it had script); a file
with script under *Allow scripts* is written to `animations/<hash>.svg` and embedded with
`<object>` instead.  *On the web* becomes `style.css` rules on the wrapper's id: paused without
autoplay or until `:hover` for *Play on hover*, `animation-iteration-count` infinite or 1 for *Loop*
and *Once* (CSS animations only; SMIL timelines play as the file says).  Deviations: the animations
sit above the whole page picture, so an object stacked above a placed animation is drawn beneath it;
posters are not written to `animations/` (the page no longer draws them).  The corpus
(`WTInterchangeTests/HTMLPublishCorpusTests.swift`, `HTMLWebKitRenderTests.swift`): twenty documents
-- the export corpus's eight fixtures, links with a page link, placed bitmaps, three pages, two
layers, text in two faces with a text-range link, Display P3 and OKLab fills, a fractional page
size, a 400-point page, a coloured page background, pages of two sizes, an empty page and a title
and names that need escaping -- each published under all eight layout × page mode × vector
format combinations.  Every HTML file passes an in-process HTML5 checker
(`Support/HTML5Checker.swift`: doctype, `html`/`head`/`body`, `meta charset` first, one non-empty
`title`, the elements and attributes the publisher may write, img `src` and `alt`, integer
`width`/`height`, `usemap` naming a map, `area` inside a `map` with `alt` and well-formed `coords`,
unique ids and map names, no bare `&`, no obsolete markup, every referenced file in the bundle);
every SVG file parses as XML and passes the SVG 1.1 element and attribute tables the SVG exporter's
tests use, with its images, fonts and page links present; republishing is byte-identical.  When
HTML Tidy is installed it runs over every page too (offline), and no error is allowed.  Each page of
each bundle is then loaded from disk into a headless `WKWebView` (package tests, macOS only) and its
`<section>` snapshotted and compared with the Core Graphics renderer's render of the page at the
snapshot's scale: at most 2% of pixels may differ by more than 40 in a channel (3% for text and
3.5% for the half-pixel edges of a fractional page, 6% for the sampled paints and raster effects
SVG filters approximate).  Found and fixed by it: fractional page sizes were written as `width` and
`height` on `<img>` and `<object>`, which HTML requires to be integers (now rounded, the style sheet
sizing the picture to the page's exact size); an SVG page's page links named `page-2.html` or
`#page-2` from inside `pages/` or `objects/` and navigated only the `<object>`'s frame (now
`../page-2.html` or `../index.html#page-2` with `target="_top"`, and same-tab links `_top` too:
`SVGWriter.sameTabTarget`); PNG pages ignored *Page background* White (drawn over the page
colour); and in Positioned objects each object's PNG was painted over the page colour, hiding the
objects beneath it (object PNGs are now transparent).  Deviations: the validator is not the W3C's
(vnu needs Java and a download; none runs in CI), and the CSS Color 4 on/off rendering of a P3 fill
is not compared (a `WKWebView` offers no switch for it); the P3 and OKLab fills are compared as
rendered.  Known issue, recorded in the render test: PNG pages draw placed images as their
placeholders, because the package's bitmap exporter has no `ImageStore` (as every bitmap export
from the package does); SVG pages carry the images.  The WebKit comparison takes about ten minutes
in a Debug `swift test` under load, most of it the PNG pages' rendering.  The WTModel
half that fills `ExportScene.svgAnimations` from `svg_animation` nodes is `ExportSnapshot`'s (WEB-024's
`SvgAnimationInfo` and the asset blobs).

NOTE: As built by WEB-013, the `WTSync` half (`WTSync/PublishUploader.swift`).  `PublishUploader` runs
