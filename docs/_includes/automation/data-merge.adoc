Data merge turns one designed page into many: a mailing label for every address in a list, a
name badge for every attendee, a product card for every row a web service returns, a ticket
with its own QR code for every order.  You design the page once, mark the places where the data
goes, connect a source of records, and {product} produces a page -- or a printed sheet, or a
PDF -- for each record.  The data itself stays where it lives: in a file, in a spreadsheet you
paste from, behind a web API, or in a script you write.  The document only knows the names of
the *fields* it expects and where each one goes.

Fields and placeholders are shared with everyone in the document, records can come from a web
API or a script as well as from a file, and a merge can go straight to the printer or to a PDF
without making pages.

== How data merge works

Three things take part:

Fields::
Named slots the document declares -- `first_name`, `address_line_1`, `photo`, `ticket_code`.
Each field has a type: *Text*, *Number*, *Date*, *Boolean* (yes/no), *Image* or *Link*.  Fields
are part of the document and everyone in it sees the same list.

Bindings::
The places where fields go: a placeholder like `{{first_name}}` inside a text block, an image
object that takes its picture from an Image field, an object that is shown or hidden by a
Boolean field, a link that comes from a Link field, or a barcode generated from a field's value.
Bindings are part of the document too.

Sources::
Where the records come from: a CSV, TSV or JSON file, a table pasted from a spreadsheet, a web
API, or a script.  The *definition* of a source (which file, which URL, how its columns map to
fields) is part of the document; the *records* are fetched when you preview or merge and are not
stored in the document -- except for a small sample you can choose to embed so that everyone
sees realistic data in the preview.

With those in place you preview any record on the canvas, then *merge*: to real pages in the
document, to a PDF, or straight to the printer.

== Defining fields

Fields can be created by hand or taken from a source.

To add a field by hand:

. In the Data panel, click btn:[+] under *Fields*.
. Type a name.  Names are letters, digits and underscores, and must be unique in the document;
  `first_name` and `First Name` are the same field.
. Choose a type:
+
[cols="1,3"]
|===
|Type |Holds

|*Text* |Any text.  The default.
|*Number* |A number.  Formatted with the field's number format when placed.
|*Date* |A date or a date and time.  Formatted with the field's date format when placed.
|*Boolean* |Yes or no.  Used to show or hide objects.  Values `true`, `yes`, `1`, `x` and
`on` count as yes; anything else, including an empty value, counts as no.
|*Image* |A picture: a web address, a file path relative to the source file, or, from a script,
image data.  Used by image bindings.
|*Link* |A web address.  Used to set an object's attached link (xref:urls.adoc[Attaching
URLs]).
|===
. Optionally set a *Format* (Number and Date fields, below) and a *Transform* script.
. Click btn:[Add].

To take the fields from a source, connect the source and choose *Add Fields from Source* from the
options menu.  Every column or property of the source that is not yet a field is added, with its
type guessed from the first records; change any guess by double-clicking the field.

Renaming a field renames it everywhere it is used; deleting a field that is used somewhere asks
you first, and the places that used it show `{{missing}}` until you delete or rebind them.

=== Number and date formats

A Number or Date field carries a format that decides how its value is placed:

* *Number*: a pattern such as `#,##0.00` or `0`, a currency (`€#,##0.00`), a percentage, or
  *As is* to place the raw text.  The locale pop-up decides the decimal and grouping characters
  (`1,234.56` or `1.234,56`).
* *Date*: a pattern such as `d MMMM yyyy` or `MM/dd/yy`, or one of the locale's standard styles
  (*Short*, *Medium*, *Long*).  Values are read as ISO dates (`2026-09-21`,
  `2026-09-21T14:30:00Z`) or in the locale's common forms; a value that cannot be read is placed
  as it is and listed in the merge report.

A Text field has no format; use a transform script for anything beyond the plain value.

=== Transforming a field with a script

Any field can run a script on its value before it is placed: join a first and last name, pick the
right salutation, look up a price band, upper-case a code.  Choose *Transform…* in the field's
settings and pick a script that exports a `transform` function:

[source,javascript]
----
// Salutation from a title and last name; falls back to the first name.
export function transform(value, record, field) {
  if (record.title && record.last_name) return `${record.title} ${record.last_name}`;
  return record.first_name;
}
----

The function receives the field's raw value, the whole record and the field's name, and returns
the value to place.  It runs for the preview and for every merged record.  How scripts are
written and where they live is on xref:scripting.adoc[Scripting and automation].

== Placing fields in the document

=== Text placeholders

A placeholder is a field's name between double braces inside a text block.  It takes the
formatting of the text around it, so a bold, 14-point placeholder produces bold, 14-point data.

To place a text placeholder, do one of the following:

* With the Text tool, type `{{` followed by the field name and `}}` -- for example
  `{{first_name}}`.  As soon as the closing braces are typed, the placeholder becomes one unit:
  it is selected as a whole, deleted as a whole, and shown with a light tint so you can tell it
  from ordinary text.  If the name matches no field, the placeholder is shown in red and the
  Data panel offers to create the field.
* Put the insertion point where the field should go and drag the field from the Data panel, or
  choose it from *Insert Field* in the panel's options menu.

A text block can hold any number of placeholders mixed with ordinary text:

[listing]
....
{{first_name}} {{last_name}}
{{address_line_1}}
{{address_line_2}}
{{city}} {{postcode}}
....

A placeholder can also stand alone as an entire text block; that is simply a block with one
placeholder in it.  To bind a whole block to a field without a placeholder in the text -- so that
the field's value replaces everything the block contains -- select the block and choose the field
under *Text* in the Object panel's *Data* section.

The tint that marks placeholders is a display aid only; it never prints or exports.  Turn it off
with the *Highlight data fields* preference (menu:{product}[Settings… > Automation]).

=== Binding an object

Objects other than text bind to a field through the *Data* section of the Object panel:

[cols="1,1,3"]
|===
|Binding |Field type |Effect

|*Image*
|Image
|The selected image object shows the record's picture, scaled to fit the object's frame the way
the original was placed (the picture's proportions are kept; the frame is the crop).  Only image
objects can take this binding; an empty frame is made by importing any placeholder picture.

|*Visibility*
|Boolean
|The object is shown when the value is yes and hidden when it is no.  Any object or group can
take it -- a "VIP" badge, a "sold out" stamp, an alternative layout.

|*Link*
|Link
|The object's attached link (xref:urls.adoc[Attaching URLs]) is set from the record.  Useful for
PDF and HTML output.

|*Text*
|Any
|The whole text block's contents are replaced by the value.  The block's first character's
formatting is used.  For a barcode object, the barcode's content comes from the field.
|===

An object has at most one binding.  A bound object shows a small data badge at its corner on the
canvas (never in output).

=== Barcodes and QR codes

A *barcode* is an object that draws a code from a piece of text: fixed text you type, or a
field's value, so every record gets its own.

To add a barcode:

. Choose *Insert Barcode…* from the Data panel's options menu (or menu:File[Data Merge > Insert
  Barcode…]).
. Choose the kind: *QR code* or *Code 128*.
. Choose *Field* and pick the field whose value becomes the code, or choose *Text* and type the
  content.
. Click btn:[Insert].  The barcode is placed at the center of the view; drag it where it belongs.

A barcode is a normal object: it has a fill color (the bars), sits on a layer, can be scaled and
rotated, and can be turned into paths with menu:Text[Convert to Paths] if you need to edit the
bars.  Its settings are in the Object panel:

[cols="1,3"]
|===
|Setting |Effect

|*Kind* |*QR code* or *Code 128*.
|*Content* |*Field* with a field pop-up, or *Text* with a text field.
|*Error correction* (QR) |*Low*, *Medium*, *Quartile* or *High*.  Higher levels survive more
damage and make a denser code.  *Medium* by default.
|*Quiet zone* |The blank margin around the code, in modules (QR) or in points (Code 128).  Keep
the default unless the scanner has trouble.
|*Show text* (Code 128) |Prints the encoded text under the bars in the object's font.
|===

A value that a kind cannot encode (Code 128 takes ASCII only; a QR code holds at most about 2,900
characters at *Low*) draws as a hatched rectangle and is listed in the merge report.

== Connecting a data source

A document has one data source at a time.  Choose *Connect…* in the Data panel and pick a kind.
Changing the source keeps the fields; the new source's columns are matched to them by name, and
anything that does not match is shown in the *Mapping* table so you can pair columns to fields
by hand.

=== A CSV or TSV file

. Choose *Connect… > CSV or TSV File…* and pick the file.
. {product} reads the first row as the column names, detects the delimiter (comma, tab or
  semicolon) and the text encoding (UTF-8 with or without a byte-order mark, UTF-16, or
  Windows Latin-1 as a fallback), and shows the first rows.  Correct any of those in the sheet
  if the guess is wrong.
. Click btn:[Connect].  Columns whose names match fields are mapped automatically; choose *Add
  Fields from Source* to create the rest.

The file stays where it is: {product} remembers its location on this Mac and reads it again
whenever you click btn:[Refresh] or merge.  Collaborators on other Macs do not have the file --
see <<sample,Embedding a sample>> for what they see.  To make the whole file part of the
document, choose *Embed All Records* from the options menu; a file up to 20 MB can be embedded,
and the source then works for everyone, everywhere, until you refresh it from the file again.

A column named with an image field's name, holding a file path, is read relative to the CSV
file's folder, so a folder of photos next to the CSV works as expected.

=== A JSON file

. Choose *Connect… > JSON File…* and pick the file.
. The file must hold an array of objects, or an object with an array in it.  Type the *Records
  path* to the array if it is not the top level (`data`, `result.items`).
. Nested properties are addressed with dots: `address.city`, `tags[0]`.  Map them to fields in
  the *Mapping* table or let *Add Fields from Source* create a field for every property of the
  first record.

=== A pasted table

Copy rows from Numbers, Excel, Google Sheets or any table and choose *Connect… > Pasted Table*.
The rows are read exactly like a TSV file and are stored *in* the document, so a pasted source
works for everyone and offline.  Paste again over the same source to replace the rows.

=== A web API

An API source fetches records from a web service each time you refresh or merge.  The request
is made by the {product} cloud, not by your Mac: your Mac tells the service what to fetch, the
service calls the API with the credential you stored there, and the records come back to you.
This is why an API source needs a connection, why a credential is entered once and never seen
again, and why every collaborator gets exactly the same records.

// TODO screenshot: the API source sheet with URL, headers, records path, pagination and mapping sections

. Choose *Connect… > Web API…*.
. Fill in the request:
+
[cols="1,3"]
|===
|Setting |Meaning

|*Method* |*GET* or *POST*.
|*URL*
|The address.  It may contain parameters in braces -- `+https://api.example.com/orders?since={{since}}+`
-- which you fill in the panel's *Parameters* section before each fetch.  Parameter defaults are
part of the document; the values you type are yours.
|*Headers* |Name and value pairs sent with each request (`Accept: application/json`).  Put no
secret here; that is what a credential is for.
|*Body* (POST) |The request body, with the same `{{param}}` templating.
|*Credential*
|The name of a credential stored in the cloud for your team (or for you, in a personal
document).  How it is sent -- bearer token, basic authentication, an API key header, or an
OAuth 2 client-credentials token -- is part of the credential, not of the document.
|*Records path*
|Where the records are in the response: `$.data[*]`, `$.results[*].item`, or empty when the
response itself is an array.
|*Pagination*
|*None*; *Next URL* with the path to the next page's address in each response (`$.next`),
followed until it is empty; or *Page number* with the name of the page parameter, requested
from 1 until a page returns no records.  *Maximum pages* stops a runaway source.
|*Timeout* |Seconds to wait for each response.  30 by default.
|*Mapping* |Each field paired with a path inside a record (`$.customer.first_name`).
|===
. Click btn:[Test].  If the host is not yet permitted (see <<hosts,Hosts and permissions>>),
  {product} says so and, for a personal document, asks whether to permit it.  The first page is
  fetched and the records it found are shown.
. Click btn:[Connect].

Refreshing an API source fetches every page again.  A fetch runs in the background with a
progress bar in the panel; click btn:[Stop] to keep what has arrived so far.  A team's sources
share a fair-use limit on how many requests they can make per minute; a fetch that reaches it
pauses and tells you.

=== A script

A script source is a JavaScript function that returns the records, for anything the other kinds
cannot express: a service with an unusual response, records built from two requests, or data
generated on the fly.  Choose *Connect… > Script…* and pick a script from your Scripts folder,
the document, or a team library that exports a `records` function:

[source,javascript]
----
export async function records(params) {
  const res = await wt.fetch(`https://api.example.com/tickets?event=${params.event}`, {
    credential: "ticketing-api",
  });
  const tickets = await res.json();
  return tickets.map(t => ({
    first_name: t.holder.first,
    last_name: t.holder.last,
    seat: `${t.block}-${t.row}-${t.seat}`,
    qr_payload: t.checkin_url,
  }));
}
----

The function returns an array of plain objects; each property becomes a column that maps to a
field by name.  `wt.fetch` goes through the same cloud service as an API source, with the same
permitted hosts and the same credentials -- a script never connects from your Mac directly.  See
xref:scripting.adoc[Scripting and automation] for the `wt` API.

=== Credentials

A credential is a secret a source needs -- a bearer token, a user name and password, an API key,
or an OAuth 2 client id and secret.  You enter it once; it is stored, encrypted, by the {product}
cloud for your team (or for you, in a personal document), and the document refers to it *only by
name*.  The secret is never shown again, never comes back to any Mac, never syncs, and never
appears in the history.  The cloud adds it to the request when it fetches on your behalf, and only
for the host it was created for.

To add a credential:

. Choose *Credentials…* from the Data panel's options menu.
. Click btn:[+], type a name (`ticketing-api`), choose the kind and enter the secret.
. Enter the host the credential may be sent to.  A credential is only ever sent to that host,
  whatever a source or script asks for.
. Click btn:[Save].  The secret leaves the sheet and is not displayed again; btn:[Replace] and
  btn:[Remove] are the only later operations.

In a team document, only team admins add, replace or remove credentials; anyone with the editor
role can fetch with them, and admins can see who did (the fetch log in the team settings).  In a
personal document the credentials are the owner's; editors you have shared the document with are
full editors and fetch with them like you do while the share lasts, and the owner can remove a
credential at any time.

=== Hosts and permissions [[hosts]]

The cloud only ever connects to hosts that have been permitted:

* For a *team*, a team admin keeps the list of permitted hosts in the team settings
  (xref:sharing.adoc[Sharing, teams and roles]).  A source or script that names another host
  fails with a message naming the host and the admins to ask.
* For a *personal* document, you keep your own list.  The first time a source or script in one
  of your documents names a new host, {product} asks whether to permit it, and the answer is
  remembered on your account for every Mac you use.

*Show Hosts* in the Data panel's options menu lists the hosts the document's sources and scripts
reach and whether each is permitted; for a personal account it lets you revoke any.
menu:File[Document Info…] lists the same hosts for anyone reviewing the document.

Nothing connects on its own.  A source fetches when you click btn:[Refresh], btn:[Test] or
btn:[Merge]; a script runs when you run it.  Opening a document never runs a script or
fetches data.

=== Embedding a sample [[sample]]

Records are not in the document, so a collaborator on another Mac -- or you, on a train --
would see `{{first_name}}` and nothing better.  *Embed Sample* in the options menu stores the
first five records in the document (up to 2 MB, pictures included).  Everyone then sees realistic
data in the preview, and the record navigator works offline with those five records.  The sample
is refreshed whenever you refresh the source with the option on.  *Embed sample records* in
menu:{product}[Settings… > Automation] turns this on for every source you connect.

== Previewing records

Turn on *Preview* in the Data panel and every placeholder, bound object and barcode on the
canvas shows the current record.  Step through records with the arrows, type a number, or
choose menu:File[Data Merge > Next Record] and menu:File[Data Merge > Previous Record] (give them
keys under menu:{product}[Settings… > Shortcuts]).  The preview is live: edit the text
around a placeholder, move a bound image, restyle a barcode, and the preview follows.

The preview is yours alone.  It changes nothing in the document, collaborators do not see it,
and it is not what prints -- the document prints with placeholders unless you merge.  Turn
*Preview* off to see the placeholders again.

Fields whose values do not fit are marked in the preview: a text block whose text overflows
shows its overflow mark, and the *Records* section lists how many records overflow somewhere
so you can fix the layout before merging.

== Merging

Click btn:[Merge…] in the Data panel.  The sheet's *To* pop-up decides what a merge produces;
the options beneath it are shared by every target.

=== Merge to Pages

*Merge to Pages* creates real pages in the document, one per record (or one per group of
records), with the values baked in.  The result is ordinary artwork: edit any page, print, export
or share it like any other.

. Select the page or pages that make up the template.  Several pages become one *set*, so a
  two-page template makes two pages per record.
. Choose *To: Pages*.
. Under *Records*, choose *All*, or a range (`1-50`, `51-`, `3, 7, 12`).
. Choose the layout:
* *One record per page* copies the template page(s) once per record.
* *Multiple records per page* lays a grid of copies of the *selected objects' bounds* on each
  page -- for labels, badges and cards.  Set *Columns* and *Rows*, the *Gap* between them, the
  *Margins* from the page edge, and whether records run *Across then down* or *Down then
  across*.  The sheet previews the grid and says how many pages the records need.
. Set the finishing options (below) and click btn:[Merge].

The new pages go immediately after the template in page order and are named after the template
and the record (`Label · 1`, `Label · 2`, …).  The template pages are untouched.  The whole merge
is one entry in the history ("Merge 250 records to pages") and one undo step, however many pages
it makes; a large merge shows progress and can be cancelled, which undoes what it had made.

Text flow links between blocks on the template page are kept between the copies of those
blocks on each merged page.  Bound images get their pictures; barcodes get their codes;
placeholders become plain text in the placeholder's formatting; visibility bindings remove the
hidden objects.  The merged pages carry no bindings, so merging again does not touch them.

=== Merge to PDF or Print

*Merge to PDF* and *Print Merge* send records straight to the export or print pipeline without
making pages.  This is the path for a 10,000-piece mailing: nothing is added to the document,
collaborators are not flooded with pages, and the output starts at once.

. Choose *To: PDF* or *To: Printer*.
. Choose the records and layout as above.
. For PDF, choose *One file* or *One file per record*, and the file name pattern.  The pattern
  takes the tokens from xref:exporting.adoc#naming[Exporting] plus any field in braces:
  `invoice-\{order_id}` names each file after its record.  Names that collide get a numeric
  suffix.  The PDF options (xref:export-pdf.adoc[Exporting PDF]) are the document's current ones.
. For the printer, the standard Print dialog opens with the *{product}* pane
  (xref:printing.adoc[Printing]); page ranges refer to the merged output.
. Click btn:[Merge].  A progress sheet counts records; btn:[Cancel] stops after the current one.

The output is exactly what *Merge to Pages* followed by an export or print would produce, page
for page.

=== Finishing options

These apply to every target:

[cols="1,3"]
|===
|Option |Effect

|*Remove blank lines*
|A line in a text block that would contain nothing but an empty field (and spaces or
punctuation) is removed, so an empty `{{address_line_2}}` does not leave a gap.  On by default.

|*Text that does not fit*
|*Shrink to fit* reduces the type size of the overflowing block, down to the *Minimum size*
you set, until it fits; *Leave and report* keeps the size and lists the record in the report.

|*Report*
|After the merge, a report lists every record with an overflowing block, an image that could not
be fetched, a value a barcode could not encode, or a date or number that could not be read.
Click a row to preview that record.
|===

=== Exporting data

*Export Data…* in the options menu writes the records as the document sees them -- after
mapping, formats and transforms -- to a CSV file.  Use it to keep what an API returned, to hand
generated codes back to a spreadsheet, or to check a transform.  Choose the fields and the
record range, and whether to include a `record` column with the record's number in the merge.

== Working with others

* *Fields, bindings and the source definition are shared.*  When a collaborator adds a field,
  it appears in your Data panel; when they bind an image, you see its data badge.  A field
  renamed by one person is renamed for everyone, in every placeholder.
* *Previews are private.*  Your record 12 and your collaborator's record 40 do not interfere.
  Their canvas shows placeholders, or their own preview.
* *A merge to pages is a normal change.*  Everyone sees the new pages arrive, page by page for a
  large merge.  If two people merge at the same time, both sets of pages are created; the sync
  review lists the two runs and offers to keep both, one after the other, or remove one.
* *The records are not in the document* -- unless the source is a pasted table, an embedded
  file, or an embedded sample.  A collaborator without the file sees the embedded sample and can
  design against it; only someone with the file can merge the full set.  An API source, on the
  other hand, gives everyone with the editor role the same records, because the cloud fetches
  them with the team's credential.
* *Offline*, pasted and embedded sources work completely.  A file source works on the Mac that
  has the file.  An API source, and a script that fetches, needs the connection: offline, the
  panel shows the last embedded sample and says so, and merging waits until you are online.

== Specification

=== Data model

Everything shared lives on the well-known `settings` node: the fields, the sources and the
mapping.  Bindings are a mark in `TextMarkValue` and one message on `CommonProps`.  Barcodes are
a node kind.  Records are never document state; an embedded sample or pasted table is a blob.
Credentials, allowlists and the fetch audit are *server* state, sketched afterwards.

[source,protobuf]
----
// proto/wiretuner/doc/v1/data.proto (sketch; normative for meaning and merge policy)
package wiretuner.doc.v1;

message SettingsProps {
  // ...
  // DATA block.  Fields and sources are SEQUENCEs so people can add, rename and remove
  // them independently; every reference to a field is by its element id, never by name.
  repeated DataField data_fields = 80 [(wt.crdt.field).merge = MERGE_SEQUENCE];
  repeated DataSource data_sources = 81 [(wt.crdt.field).merge = MERGE_SEQUENCE];
  // Which source is connected (one at a time in v1; the sequence keeps the others so
  // switching back restores their settings).  Dangling reads as "none connected".
  ElementId data_source_active = 82 [(wt.crdt.field).merge = MERGE_ATOMIC];
  // Preview state.  Never leaves this Mac.
  DataPreview data_preview = 83 [(wt.crdt.field).local_only = true];
}

enum DataFieldType {
  DATA_FIELD_TYPE_UNSPECIFIED = 0;   // reads as TEXT
  DATA_FIELD_TYPE_TEXT = 1;
  DATA_FIELD_TYPE_NUMBER = 2;
  DATA_FIELD_TYPE_DATE = 3;
  DATA_FIELD_TYPE_BOOLEAN = 4;
  DATA_FIELD_TYPE_IMAGE = 5;
  DATA_FIELD_TYPE_LINK = 6;
}

// A field.  STRUCT: name, type, format and transform are independent edits.
message DataField {
  ElementId id = 1;
  // Unique among live fields when written; [A-Za-z_][A-Za-z0-9_]*, compared case-insensitively.
  // IGNORE_IF_ZERO_VALUE: a SetFields that does not write the name carries "".
  string name = 2 [(buf.validate.field).string = {max_len: 64, pattern: "^[A-Za-z_][A-Za-z0-9_]*$"},
                   (buf.validate.field).ignore = IGNORE_IF_ZERO_VALUE];
  DataFieldType type = 3;
  FieldFormat format = 4;             // STRUCT; only NUMBER and DATE read it
  // A `script` node in this document exporting `transform`.  Dangling = no transform.
  NodeRef transform = 5 [(wt.crdt.field).on_dangling = REF_FALLBACK_UNSET];
}

message FieldFormat {
  string pattern = 1 [(buf.validate.field).string.max_len = 64];   // ICU number or date pattern; "" = As is / locale default
  string locale = 2 [(buf.validate.field).string.max_len = 32];    // BCP 47; "" = the merging user's locale
}

// A source.  `spec` is a VARIANT: switching a source from File to Web API and back keeps
// both configurations.  `mapping` and `sample` sit beside the variant because every kind

=== Merge semantics

Fields:: SEQUENCE elements; `name`, `type`, `format` and `transform` are independent registers.
Two people renaming one field: LWW, both names in the review sheet under *same register*.  A
rename concurrent with a new binding elsewhere: no conflict, the binding holds the element id.
Two people creating fields with the same name concurrently: both live; *read-time
normalization* -- among live fields with equal names (case-insensitive) the one with the smaller
element id keeps the name and the others display with a numeric suffix (`first_name (2)`) until
someone renames them; mappings and bindings are by id and unaffected.

Deleting a field that has bindings:: `ElementDelete` on the field.  Every `field` mark and
`data_binding` naming it dangles: placeholders render as `{{missing}}` in red, bound objects show
a *missing* badge and are treated as unbound (an image keeps its last pixels, a visibility
binding shows the object).  The live client shows a notice with *Restore field*; the review
sheet lists "field removed with N bindings" with *Restore* (`deleted = false`) beside the
ordinary delete entry.  Restoring makes every dangling reference resolve again.

Placeholder marks:: A `field` mark is a normal Peritext mark with non-expanding anchors.  Typing
*inside* the span (someone editing the placeholder characters) stays inside the mark; the merge
ignores the span's characters and replaces the whole span, so the outcome is still the value.
Deleting every character of the span removes the placeholder (a mark covering nothing covers
nothing).  Two overlapping `field` marks: the one with the greater OpId wins where they overlap,
as for any attribute.  A `field` mark placed by one user while another types just before or
after the span: the anchors exclude the typed text, as intended.

Bindings:: `data_binding` is ATOMIC LWW.  Two people binding one object to different fields:
later wins, the loser is listed.  A binding written to a node someone deletes: ordinary
edit-vs-delete.

Sources:: STRUCT registers inside a VARIANT: one person changing the URL while another adds a
header keeps both; a kind switch keeps the other kind's fields.  `sample` is ATOMIC: two
refreshes with the option on keep the later blob (the earlier is retained as a blob and in the
log; no review entry -- a sample is disposable).  `mapping` elements merge as any SEQUENCE.
`data_source_active` is one register.  A `credential_name` naming a credential that does not
exist in the scope is not a merge problem: the fetch fails with `CREDENTIAL_MISSING` and the
panel offers *Credentials…*.

Merge to Pages vs. everything::
* *Vs. template edits*: copies hold the template as the merger saw it.  Edits to the template
  after the merge do not propagate; edits concurrent with it land on the template only.
* *Two users merging concurrently*: two runs of pages, each contiguous in its own creator's
  order but interleavable with the other run because both generated positions after the same
  template page.  `WTSync` detects "two merge runs after the same page" (two sets of changes
  labelled `Merge … to pages` whose first page position follows the same template) and the
  review sheet lists one entry with *Keep both, one after the other* (moves the later run's
  pages after the earlier run's last page, one change), *Remove theirs* and *Remove mine*
  (`SetDeleted` on that run's pages and their objects).  The live client shows the same choice
  as a notice.
* *Vs. page moves and reorders*: the `move vs move` and reorder rules of
  xref:pages.adoc[Pages] apply to merged pages as to any page.
* *Vs. field deletion*: a merged page has no bindings, so nothing dangles.
* *Cancel* mid-merge undoes the pages created so far by the ordinary undo path (`deleted =
  true`), which is why chunks carry the same label.

Barcodes:: STRUCT; `value` and `symbology` are independent registers.  Read-time: a value the
symbology cannot encode draws the hatched placeholder and is reported at merge; a Code 128
`quiet_zone` below 0 reads as 10; a QR `quiet_zone` below 0 reads as 4.

Read-time normalizations, collected::
* `data_source_active` dangling or deleted: no source connected.
* A `FieldMapping` whose field dangles is ignored; a field with no live mapping maps to the
  column of its own name.
* A `data_binding` whose field type does not suit the kind (an IMAGE binding to a TEXT field)
  is treated as unbound with the *missing* badge.
* `timeout_s = 0` reads 30; `first_page = 0` reads 1; `max_pages = 0` reads 1000.
* A `DataPreview.record_index` past the last record reads as the last record.
* An `HttpSource.url` that is not `https` reads as invalid: the panel shows the error and the
  server rejects the fetch.

=== Offline behavior

* Pasted and complete-embedded sources are fully functional offline: preview, merge to pages,
  merge to PDF and print.
* A file source works on any Mac holding a valid bookmark; elsewhere it falls back to the
  embedded sample, and the panel says *Showing embedded sample*.
* An HTTP source is a server call, so offline it is the embedded sample only: preview works on
  the sample; *Refresh*, *Test* and any merge that needs the full set are disabled with an
  *offline* message rather than queued.  A script source that calls `wt.fetch` behaves the
  same; one that does not runs offline.
* Merge to Pages offline: images for IMAGE fields come from the source (embedded, file-relative
  path or already-cached blob); any that cannot be obtained produce an image node with the
  `pixels` register unset (rendered as the empty placeholder) and a report row.  Blobs the
  client creates (file-relative images, script data) join `blobs_pending` and upload with the
  usual rules (xref:importing.adoc[Importing]); blobs the server fetched through `FetchAsset`
  are already on the server and need no upload.
* Embedding a sample offline writes the blob locally and queues its upload; the `sample`
  register syncs before the blob and collaborators see "sample uploading" until it lands.
* Credentials and allowlists are server state: adding, replacing or revoking them needs the
  connection and the sheets say so.

=== Server

This is the one page on which the server does real work beyond storing and relaying changes
and blobs: it is the only thing that ever calls a customer's API.  Decision recorded in
xref:decisions.adoc[Decisions] ("API calls run on the server").

Why on the server::
* Credentials never reach a laptop, a local store, a package export or the change log; a lost
  Mac leaks nothing.
* Customers with strict APIs can allowlist one egress address, the service's, instead of every
  designer's home network.
* Abuse control (rate limits, response caps, host allowlists) and the audit trail live in one
  place, and the audit answers "who fetched what, when".
* Every collaborator gets identical records, because one fetcher with one credential produced
  them.

Consequences::
* API sources and `wt.fetch` need the network; offline means the embedded sample.
* The server gains its first outbound HTTP client, with the attack surface that implies (SSRF);
  the guard below is not optional.
* The server never stores a response: records stream to the caller and are gone.

Secret store (DATA-005):: `data_credential` rows hold an envelope-encrypted secret: a random
per-row data key encrypts the secret material (AES-256-GCM), and the data key is wrapped by the
service master key (`WT_DATA_MASTER_KEY` from the environment or a KMS-backed key in
production; `key_id` records which, so keys can rotate).  `PutCredential` requires the team
`admin` role in the team scope, or the account itself in the personal scope; `DeleteCredential`
the same (xref:decisions.adoc#D-062[D-062]).  The secret is decrypted only inside the fetch path, in memory, for
the duration of one request; it is never logged, never returned, and `ListCredentials` returns
metadata only.

Fetch proxy and SSRF guard (DATA-006):: A Quarkus REST client (`quarkus-rest-client`) with:
`https` only; the URL's host resolved *once* and every resolved address checked against the
blocked ranges (loopback, link-local, RFC 1918, CGNAT, unique-local and multicast, the
metadata addresses `169.254.169.254` and `fd00:ec2::254`) before connecting to *that* address
(the DNS-rebinding defence: the connection is pinned to the checked address); no redirects
followed automatically -- a `3xx` to the same host is followed up to three times, to another
host it is an error `HOST_NOT_ALLOWED`; connect timeout 10 s, read timeout `timeout_s` capped
at 120 s; response body capped at 64 MiB per page (16 MiB for `Proxy`, 200 MiB for
`FetchAsset`, matching the blob limit); `Content-Type` of a page must be JSON; at most 16
concurrent fetches per team and 4 per account.  The credential is injected per kind; for
`OAUTH2_CLIENT` the access token is obtained from `token_url` and cached in memory until 60 s
before expiry.  Headers from the request definition are validated against the secret-header
denylist (`Authorization`, `Proxy-Authorization`, `Cookie`, `X-Api-Key`, and the credential's
own header) and refused with `INVALID_ARGUMENT` naming the header.

Allowlists (DATA-007):: `data_allowed_host` per team (written by admins through the RPCs, shown
in the team settings sheet) or per account (written by the consent prompt: the client calls
`PutAllowedHost` on the user's own scope after the sheet).  A host entry is `host[:port]`,
exact match, case-insensitive; no wildcards in v1.  A fetch to a host not in the scope's list
fails with `HOST_NOT_ALLOWED` carrying the host and, for a team, the admin display names.

Rate limits and audit (DATA-008):: Token buckets per team (600 requests per minute, burst 100)
and per account (120 per minute, burst 20), configurable per team by operators; exceeded
returns `RESOURCE_EXHAUSTED` with `RetryInfo` and the panel pauses.  Every `Fetch`,
`FetchAsset` and `Proxy` writes one `data_fetch_audit` row on completion with status, page,
record and byte counts -- never a URL query string beyond the path, never headers or bodies.
Rows are retained 90 days.  `ListFetchAudit` is admin-only and is surfaced in the team settings
sheet's *Data fetches* list.

Pagination engine and extraction (DATA-009):: The server expands `{{param}}` references,
executes page after page according to `Pagination`, applies `records_path` and the requested
`paths` (JSONPath subset, same grammar as the client's file reader: `$`, `.name`, `['name']`,
`[n]`, `[*]`, `..name`), and streams `RecordPage`s.  `cursor` is an opaque, signed token holding
the next URL or page number so a client can resume after a disconnect.  `max_records`,
`max_pages` and the team's caps end the stream with `next_cursor = ""`.

Roles:: `Fetch`, `FetchAsset` and `Proxy` require the editor role on `document_id`, evaluated as
for any document RPC; the scope (team or owner account) is derived from the document row, so a
shared personal document lets its editors fetch with the owner's credentials for as long as the
share lasts, and the audit names who did.

==== As built (DATA-002, DATA-005 to DATA-009)

The proto is `proto/wiretuner/data/v1/data.proto` (every message and field carries its comment);
the server is `+server/api/.../api/data+`.  Where it differs from the sketches above:

Schema (DATA-002)::
* One `Scope` message (a `oneof` of `team_id` and `account_id`, required) replaces
  `CredentialScope` and serves credentials, hosts and the audit alike.  `ListCredentials` and
  `ListAllowedHosts` take `document_id` *instead of* a scope (CEL: exactly one), so an editor who
  is neither the owner nor a team admin -- the collaborator on a shared personal document -- can
  read the names the document's sources may use.  Team scope reads are open to any team member,
  a guest included; writes need the team `admin` or `owner` role (`ROLE_INSUFFICIENT`; a
  non-member gets `TEAM_NOT_FOUND`); an account scope is the account's own (`SPACE_NOT_FOUND`
  for anyone else's).
* Metadata messages: `Credential` (name, kind, host, creator id and name, `created_at`,
  `rotated_at` = when the secret was last replaced), `AllowedHost`, `FetchAuditEntry` with a
  `FetchKind` (`SOURCE`, `SCRIPT`, `ASSET`), and `FetchProgress` (page number, bytes, records so
  far).  Deletes answer `deleted`; lists page with opaque cursors (`page_size` <= 50).
* `PutCredentialRequest` has one CEL rule per kind (the fields that kind takes, and no others);
  `token`, `password`, `header_value` and `client_secret` are marked `debug_redact`.  The server
  logs every data-service request at DEBUG through `Redaction`, which prints those fields as
  `<redacted>` (there is no general logging interceptor to annotate for; the redaction is keyed
  on the proto option, so a future one reuses it).
* `ProxyRequest` gains `timeout_s` (0 reads 30, at most 120); `method` is one of the five
  listed; URLs everywhere are `https` by pattern.  `FetchRequest` requires a non-empty
  `source.url` (doc.v1's rule ignores an empty one).  `ListFetchAuditRequest` filters by
  document, host and account.  `FetchAsset` is unary as sketched (the blob comes back through
  `BlobService`).  The four error reasons already existed in `sync.v1.ErrorReason`.
* `HOST_NOT_ALLOWED` carries `host` in its `ErrorInfo` metadata and, for a team, `admins` (the
  owner's and admins' display names, else emails, joined by ", ").  A host refused for its
  addresses, a redirect that leaves the host, and a credential sent elsewhere use the same
  reason with only `host`.

Secret store (DATA-005)::
* `data_credential` keeps the wrapped data key in its own column, `wrapped_key`, beside
  `ciphertext` (12-byte nonce, then the AES-256-GCM output); rotation rewrites `wrapped_key` and
  `key_id` only.  The secret is sealed with the scope and name as associated data, so a
  ciphertext copied to another row does not open.  Putting an existing name replaces the secret,
  kind and host and keeps the row, its creator and `created_at`.
* `WT_DATA_MASTER_KEY` (`wt.data.master-key`) is comma-separated `id:base64` 32-byte keys, the
  first current and the rest kept to unwrap rows not yet rotated.  No KMS integration yet: a KMS
  key would replace the `MasterKeys` bean.  Without a key, `PutCredential` fails (`INTERNAL`).
* The *Credential key rotation* job runs two minutes after start and daily (not on demand):
  rotating is putting a new key first in the variable and keeping the old one until the job has
  run; with every row under the current key it does nothing.

Fetch proxy and SSRF guard (DATA-006)::
* The client is the Vert.x core `HttpClient`, not `quarkus-rest-client`: pinning needs
  `RequestOptions.setServer` (connect to the checked address while SNI, certificate
  verification and `Host` use the name), which the REST client does not expose.  Names resolve
  through one configured resolver, as workspace domains do (`+wt.data.dns.*+`, defaulting to
  `+wt.dns.*+`), A and AAAA, once per call per host.
* Blocked, beyond the list above: `0.0.0.0/8`, the IETF, documentation, benchmarking and
  6to4-relay IPv4 blocks, `240.0.0.0/4` and broadcast; IPv6 unspecified, the IPv4-compatible
  block, discard, Teredo, ORCHID, documentation, site-local and local-use NAT64; IPv4-mapped,
  NAT64 (`64:ff9b::/96`) and 6to4 addresses are judged by the IPv4 address they carry.  URLs with
  user information, and numeric hosts that are not dotted quads (`2130706433`, `0x7f000001`),
  are refused before any lookup.
* Same-host redirects keep the method and body, except a 303, which becomes a GET without a
  body.  The timeout covers one whole exchange (connect, headers and body) per hop; `FetchAsset`
  uses 120 s.  `FetchAsset` holds the body in memory (at most 200 MiB) to hash it before the
  single content-addressed PUT.  The page cap applies to the bytes as sent: the client never asks
  for or decompresses an encoded body.
* The header denylist adds the connection headers the server owns (`Host`, `Content-Length`,
  `Transfer-Encoding`, `Connection`, `Keep-Alive`, `Upgrade`, `TE`, `Trailer`,
  `Proxy-Connection`, `Expect`) and refuses names that are not HTTP tokens.  `Proxy` returns
  every upstream status as it is, headers lower-cased and joined, without `set-cookie` and the
  connection headers.
* OAuth 2: the client authenticates to `token_url` with HTTP Basic (RFC 6749 2.3.1); the token
  request goes through the SSRF guard but not the allowlist (whoever may store the credential
  also keeps the allowlist); a token with no `expires_in`, or one of 60 s or less, is not reused.
* Concurrency caps (16 per team, 4 per account) are counted per API node.
* The only address exemption is `wt.data.egress.exempt-addresses`, set by the tests alone (the
  HTTPS stub on 127.0.0.1, whose self-signed certificate `wt.data.egress.trust-pem` trusts).
  Plain `http` is never fetched, in tests either.

Allowlists (DATA-007)::
Entries are stored normalised: lower case, `:443` dropped, so `api.example.com` and
`api.example.com:443` are one entry.  IPv6 literals are not accepted as entries.

Rate limits and audit (DATA-008)::
* One token per upstream request (each page of a `Fetch`, each `FetchAsset` and `Proxy`; OAuth
  token requests are free) from the team's bucket (`rl:dt:<team>`, team documents) and the
  caller's (`rl:da:<account>`), through the SRV-014 limiter's script without leasing.  Per-team
  operator overrides are not built (the rates are `+wt.data.limits.*+`).  Of DATA-008's first check,
  "700 requests in a minute yield 600 successes" cannot hold for a bucket of burst 100 refilling
  at 600 a minute (which admits 700 in the first minute); the test asserts the burst of 100 and
  `RetryInfo` on the 101st.
* `data_fetch_audit` names the scope `team_id` XOR `owner_account_id` and the caller
  `account_id`, and adds `path` (the first request's path, never its query; a CHECK forbids
  `?`) and the source's element id (`source_counter`, `source_replica`).  `status` is `OK`,
  `CANCELLED` (the client went away), or the error's reason (else its gRPC code).  A request
  refused before it connects (allowlist, rate limit, credential) is audited too; a call refused
  before the role check is not.
* `ListFetchAudit` is also open to an account for its own scope: the fetches made in its
  personal documents, by it and by the editors it shared them with.
* Metrics: `wt_data_fetches_total{kind,status}` and `wt_data_fetch_bytes_total{kind}`.

Pagination engine and extraction (DATA-009)::
* `{{param}}` (spaces allowed inside the braces) takes the typed value, else the source's
  default, else empty; in the URL it is percent-encoded (everything but `A-Z a-z 0-9 - . _ ~`),
  in the body inserted as typed.  The expanded URL is then checked like any other.
* NEXT_URL: the value at `next_url_path` is resolved against the URL the page came from (after
  redirects); pages after the first are GETs without a body; a next URL that is not an `https`
  URL this server fetches ends the fetch with `UPSTREAM_ERROR`, and a next page on a host
  outside the allowlist with `HOST_NOT_ALLOWED`.  PAGE_PARAM sets (or replaces) the query
  parameter.  The server's record cap is `wt.data.max-records`, 100,000.  Every page is preceded
  by its progress frame; a page must answer 2xx with a JSON media type (`application/json` or
  `+json`).
* The cursor is `base64url(JSON position) . base64url(HMAC-SHA256)`, the key derived from the
  current master key; the position is bound to a SHA-256 of the request without its cursor (its
  parameters in key order).  Rotating the master key invalidates outstanding cursors.
* The JSONPath subset, exactly:
+
[listing]
....
path  = ""                    the root
      | "$" step*
      | bare                  any text not starting with "$": the one member of that name
step  = "." name              member
      | "[" quoted "]"        member; 'single' or "double" quotes; \\ \' \" escape
      | "[" index "]"         array element: 0, or digits without a leading zero (at most 9)
      | "[*]"                 every array element, or every member value of an object
      | ".." name             that member of the node and of every node below it
name  = one or more of A-Z a-z 0-9 _ - $ or any non-ASCII character
....
+
Anything else is refused, and the vectors name the kind: `filter` (`+[?(...)]+`), `script`
(`+[(...)]+`), `slice` (`[0:2]`), `union` (`[0,1]`), `negative_index`, `syntax` (`+.*+` included).
Matches are in document order (objects keep their source member order).  A path without `+[*]+`
or `..` is *definite*.  `records_path` selects every match, except that a definite path
matching one array selects its elements, so `$.data` reads like `+$.data[*]+` and the empty path
reads a root array's elements (or a root object as one record).  A record field is a definite
path's first match as text, or an indefinite path's matches as a compact JSON array; nothing
matched, or JSON null for a definite path, is absent.  Compact JSON has no whitespace, keeps
member order, writes numbers as their source text (`12.990` stays `12.990`) and escapes only
`"`, `\` and the control characters (`\b \f \n \r \t`, others as `\u00xx`).
* The shared vectors are `server/api/src/test/resources/jsonpath-vectors/vectors.json`: `paths`
  (document as JSON text, path, every match as compact JSON, or the refusal kind) and `records`
  (document, `records_path`, `paths`, the expected records).  DATA-004's reader runs them
  unchanged.

Tests (DATA-006's "compose-hosted mock")::
An in-JVM HTTPS stub (`EgressStub`, a JDK `HttpsServer` with a committed self-signed certificate
for `+*.wt.test+`, `localhost` and `127.0.0.1`) plays every upstream, and the DNS stub answers A
and AAAA for the test hosts, so the SSRF cases -- private and metadata answers, mixed answers,
rebinding after the check, redirects off the host, TLS names that do not match -- run inside
`./mvnw verify` without compose.

=== Client

Packages:: `WTInterchange.DataSources` (file parsers, the data service client), `WTModel`
(fields, bindings, merge engine), `WTRender` (barcodes, preview substitution), `WTApp` (Data
panel, merge sheet, credentials and hosts sheets), `WTInterchange/Print` and
`WTInterchange/Export` (streamed merge).

Parsers (client-side sources)::
* CSV/TSV: RFC 4180 with quoted fields, embedded newlines and doubled quotes; delimiter chosen
  by the most consistent column count over the first 50 rows among `,`, `;` and tab; encoding by
  BOM, then UTF-8 validity, then Windows-1252.  Streaming: files are read row by row so a
  200 MB CSV merges without loading it whole.
* JSON: files over 64 MiB are refused with the size in the message; smaller files are parsed
  once and records addressed by path with the same JSONPath subset the server implements.
* Pasted table: the TSV parser over the pasteboard string.

Data service client:: `DataSourceClient` wraps `DataSourceService`: `fetch(source, params,
paths)` returns an `AsyncSequence` of `RecordPage`s and resumes from the last `next_cursor` on
a dropped stream; `fetchAsset(url, credential)` for IMAGE fields (result hash goes straight
into a `PixelSource`; the blob is already server-side, so the local cache downloads it as for
any remote image); `proxy` for `wt.fetch`.  `HOST_NOT_ALLOWED` on a personal document opens
the consent sheet (`NSAlert`, naming document and host), which on *Allow* calls
`PutAllowedHost` on the account scope and retries; on a team document it shows the host and the
admin names.  `CREDENTIAL_MISSING` offers the credentials sheet.  Every fetch is logged to the
Script Editor console with host, path, status, pages and size -- never headers or bodies.  The
client never opens a connection to any host but the {product} service.

Credentials and hosts sheets:: `Credentials…` lists `ListCredentials` metadata and offers
btn:[+], btn:[Replace] and btn:[Remove]; the secret fields are cleared the moment
`PutCredential` returns.  *Show Hosts* lists the hosts referenced by the connected source's URL,
by script sources' recorded hosts (the last run's `wt.fetch` targets, kept in the local store),
and by the scope's allowlist, with revoke on a personal scope.  The Document Info sheet reads
the same derived list (xref:file-info.adoc[Document information]).

Fields and bindings:: `WTModel.DataCommands`: `addField`, `renameField`, `setFieldType`,
`setFieldFormat`, `setFieldTransform`, `deleteField` (with the binding count for the
confirmation), `setSource`, `setMapping`, `setSample`, `insertPlaceholder(at:field:)` (a
`TextInsert` of the field's name in braces plus the `field` mark, one change "Insert field"),
`bind(node:field:kind:)`, `unbind`.  The Text tool recognizes a completed `{{name}}` typed run
and converts it in place (delete the braces and name, re-insert with the mark) as one change,
so the placeholder is one unit; a name matching no field gets the mark with a zero element id,
which renders in red and drives the "create field" offer.

Record resolution:: `RecordSet` (in `WTModel`) is the resolved list for a source: raw records
from a parser, the data service or a script, mapping applied, per-field type coercion, formats
(ICU through `NumberFormatter` and `DateFormatter` with the field's locale) and transforms
(run through the DATA-011 runtime, one `JSContext` for the whole set, values cached per
record).  It is a value type consumed by preview, merge and export alike, so the three cannot
disagree.

Preview:: `WTRender` takes an optional `RecordSubstitution` (record + field values) with the
display list; text layout substitutes each `field` span's characters with the value before
`TXT-001` layout, images with a binding draw the picture from the local blob cache (downloads
happen in the background with the placeholder meanwhile), visibility bindings skip the node,
barcodes encode the value.  The substitution is keyed by the `DataPreview` register, so
toggling it is a view invalidation, not a document change.  Placeholder tinting and data badges
are canvas overlays and never reach export.

Merge engine:: `MergeEngine.plan(template pages, records, layout, options) -> [MergedPage]`
where a `MergedPage` is a list of `(source node, substitutions, transform)` for one output page.
Two consumers: `MergeToPages` turns each `MergedPage` into `CreateNode` ops (page, deep copies
with substituted text, replaced pixels, cleared bindings, recreated flow links by an id map),
batched into changes of at most 10,000 ops, all labelled `Merge N records to pages`, grouped
into one undo step (APP-011); `MergeToOutput` renders each `MergedPage` through `WTRender` with
the substitution directly into `PrintPlanView` (`knowsPageRange` answers the merged count;
`rectForPage` maps to the template page's geometry) or the PDF exporter's page loop, so nothing
is written to the document.  Multiple records per page: the grid's cells are the template
page's *selected objects' union bounds*; each cell is a translated copy of those objects only,
laid out in the chosen order within the page's margins.  Blank-line removal runs on the
substituted paragraph: a paragraph whose remaining characters are whitespace or punctuation
and which contained at least one placeholder is deleted with its terminator.  Shrink-to-fit
re-lays the block in 0.5 pt steps down to the minimum; overflow that remains is a report row.

Images from IMAGE fields:: A URL goes through `FetchAsset` (server-side, same allowlist and
credential) and returns a blob hash; a relative path is resolved against the file source's
folder and script data is taken as bytes, each through `ImageImporter` (IMG-002, with the
*Downsample* preference) into a local blob and a pending upload.  The bound image node's `crop`
and `transform` are kept and the picture is fitted by adjusting `dpi` so the frame is the crop,
matching *Merge to Pages* and preview.  A picture fetched once is cached by URL for the run.

Barcodes:: `WTRender` rasterizes nothing: a QR matrix (own encoder, ISO/IEC 18004, versions
1--40, byte mode with UTF-8; `CIQRCodeGenerator` is used only to cross-check in tests) and a
Code 128 pattern (subsets A/B/C with automatic switching, checksum) are emitted as one
rectangle path per module or bar, so PDF and print are vector.  Hit testing is the bounds
rectangle.  *Convert to Paths* writes those rectangles as a `path` group.

Data panel and sheets:: `WTApp/Panels/DataPanel` (SwiftUI body in the standard panel host), the
source sheets, the merge sheet with its live grid preview, the report window, the credentials
sheet, *Show Hosts*.  Merge progress is a sheet with cancel; Merge to Pages cancel runs the undo
of the chunks so far.

Export data:: `RecordSet` to CSV (RFC 4180, UTF-8 with BOM for spreadsheet compatibility),
IMAGE fields as their URL or path, plus the optional `record` column.

Undo:: Each panel edit is one change.  A merge to pages is one undo step covering all its
chunks.  Preview changes are not undoable (view state).

=== Security

* Nothing on this page runs without a user action in the foreground: btn:[Refresh], btn:[Test],
  btn:[Merge], running a script, or a transform during those.  Opening a document, receiving a
  change, or a collaborator's action never triggers a fetch or a script on this Mac or on the
  server.
* API calls run on the server, never on the Mac.  The client speaks only to the {product}
  service; scripts get no direct network either -- `wt.fetch` is `DataSourceService.Proxy`.
  Outbound hosts are allowlisted per team by admins, or per account by the consent prompt;
  redirects to other hosts are refused; private and metadata address ranges are blocked with
  the connection pinned to the checked address.
* Credentials are written once through `PutCredential`, envelope-encrypted at rest, decrypted
  only inside one request, bound to one host, never returned, never in a change, snapshot,
  package, blob, log or report.  The document carries names only, so a package export or a
  leaked local store discloses nothing.
* Rate limits per team and per account, response caps per call, concurrency caps, and a 90-day
  audit trail (who, which document, which host, when, how much -- no payloads) that team admins
  can read.
* Embedded samples are document data like any pasted text: whoever can read the document can
  read them.  The *Embed Sample* command says so the first time it is used.
* Transform and source scripts run in the DATA-011 sandbox: no file system, no shell, no
  sockets; network only through `wt.fetch`, which is the proxy above; wall-clock limit per
  record.

NOTE: As built by DATA-018 (render half; `WTRender/Barcodes`).  `QRCode.encode` (byte mode, UTF-8,
versions 1--40, four levels, the eight masks with ISO 18004's penalty rules) and `Code128` (the
shortest symbol over sets A, B and C with changes and shifts, by dynamic programming; modulo-103
check) are pure Swift.  `BarcodeRendering.item` draws a `BarcodeSpec` as one atomic group: a clear
fill over the bounds (so the bounds rectangle hits), the bars as one path of rectangles -- a QR
code's dark modules merged into one rectangle per horizontal run -- in the first fill's paint, and
for Code 128 with *Show text* the value centred under the bars.  Code 128 bars are 15% of the
symbol's width tall, at least 18 pt.  `BarcodeRendering.paths` gives *Convert to Paths* its
rectangles.  An unencodable value draws `HatchedPlaceholder` (29 × 29 pt for QR, 60 × 30 pt for
Code 128).  The ISO 18004 annex vectors use numeric and alphanumeric modes, which this encoder does
not; module-for-module agreement is checked against `CIQRCodeGenerator` instead (with the mask it
chose), decoding with `CIDetector`; Vision's `VNDetectBarcodesRequest` is the Code 128 reference
decoder.  The Object panel section, *Insert Barcode…* and the merge test are WTApp's and WTModel's.

NOTE: As built by DATA-018 (model half; `WTModel/Barcodes.swift`).  `Barcodes.spec` reads a
`barcode` node (unset symbology QR, unset error correction M, a quiet zone of 0 the symbology's
default, the first fill's paint or black) and the builder draws it with `BarcodeRendering.item`
under its transform.  Commands: `InsertBarcode` ("Insert Barcode"; black fill), `SetBarcodeFields`
("Change barcode", one register per field given, so concurrent `value` and `symbology` edits both
survive) and `ConvertBarcodesToPaths` ("Convert to Paths": one path of the bars' rectangles with
the barcode's transform and stack; an unencodable barcode is left alone).  Bound fields are
substituted since DATA-003 (`RecordSubstitution.barcodeValue`, below): in the preview, in *Merge to
Pages* copies and in merged output, and a value the symbology cannot encode is a report row.  The
Object panel section and the *Insert Barcode…* menu item (WTApp) are not built.

Merge to PDF and print (DATA-021, model and export halves)::

Review rows and multi-client scenarios (DATA-023; `WTSync/DataMergeReview.swift`, simulator `WTTestSupportTests/Simulation/DataMergeScenarioTests`)::
* `Divergence.measure` adds two kinds of row beside the object entries, both always listed (like

* *Two merge runs* (`MergeRunConflict`): a run is consecutive changes of one replica whose labels
end in `Merge N record(s) to pages` (a prefix is allowed, so scripted labels match); its pages are
the `page` nodes they created and its objects the created nodes whose parent they did not create.
A run *follows* the nearest page before its first page, in page order, that no run on either side
created -- the template, or the page the merge was placed after.  A local and a remote run
following the same page make one row (several runs on one side after that page are joined).  The
choices are commands against the merged state: *Keep both, one after the other* (`MoveNode` of the
later run's live pages, in their current order, between the earlier run's last page and the next
other page; "later" is the run whose first page id is greater; nil when already in order), *Remove
theirs* and *Remove mine* (`SetDeleted` on that run's pages and objects).  The live notice for two
runs arriving while both are online is WTApp's and not built.

`make client-sim`): rename vs bind, delete vs placeholder (the row and its *Restore*), duplicate
names, URL vs header, sample race, two merge runs with each choice, merge vs template edit, an API

File readers (DATA-004; `WTModel/DataFileReading.swift`, `WTModel/DataJSON.swift`)::
* In `WTModel`, not `WTInterchange.DataSources`: the readers produce `DataRecord`s and `DataTable`s,
which are WTModel's, and WTInterchange does not depend on WTModel.
* `DataTextEncoding.detect` reads a byte-order mark (UTF-8, UTF-16 either way), then a BOM-less
UTF-16 from the zero bytes on one side, then UTF-8 validity (a sequence cut at the end of the 64 KiB
sample allowed), else Windows-1252.  `DataFileReader.detectDelimiter` picks among `,`, `;` and tab
the one whose field count (more than one) is shared by the most of the first 50 rows, preferring
more fields.  `FileSource.encoding` stores the IANA name (`utf-8`, `utf-16le`, `utf-16be`,
`windows-1252`), `delimiter` the character.
* `DelimitedByteParser` is the RFC 4180 state machine over bytes: the structural characters are
single bytes in UTF-8 and Windows-1252, so a row is split before its fields are decoded; UTF-16 is
transcoded to UTF-8 chunk by chunk (an odd byte or a high surrogate held back for the next chunk).
`DataFileReader.forEachRow` reads 1 MiB at a time, so a file of any size streams in constant
memory; the test streams 200,000 rows (the 1 M-row fixture and the 2 GB address-space bound are not
run in the debug suite).  Empty values are absent, as in `DataTable`.
* JSON files over 64 MiB are refused with their size; smaller ones are parsed into `JSONNode`, an
order-keeping tree whose numbers keep their source text, and read with `JSONPath` -- the grammar
above, refusals named `filter`, `script`, `slice`, `union`, `negative_index` and `syntax`.
`DataJSON.records(in:recordsPath:paths:)` applies the server's records-path and field rules; the
shared vectors (`server/api/src/test/resources/jsonpath-vectors/vectors.json`) run unchanged in
`DataFileReaderTests`.  A JSON file's columns are the member names of its first 20 records; a
mapping path is read as a JSONPath, a column by member name (so a member called `$ref` is a
column).  Nesting deeper than 100 levels is refused.
* `DataFileBookmarks` makes and resolves security-scoped, read-only bookmarks
(`FileSource.bookmark`, local only).  A file source without one -- a collaborator's copy -- shows
the embedded sample.  The pasted-table reader is `DataTable.pasted` (DATA-003).  The *Embed sample
records* preference embeds the first five records again on every *Refresh*.
