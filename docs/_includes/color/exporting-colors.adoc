A palette you have built is worth keeping.  {product} lets you export named colors as a color
library file for other documents and other applications, copy colors directly between open
documents, and -- new in {product} -- keep a *team color library* in the cloud that every
document on your team can draw from.

== Exporting a color library

To export colors as a library:

. Open the Swatches panel's Options menu and choose *Export…*.
. In the sheet, tick the colors to export.  Tints are exported with their base; the defaults
  None, White, Black and Registration are never exported.
. Type a library name, and optionally the number of rows and columns the library sheet should
  lay the colors out in, and notes.
. Choose the format: *{product} color library* (`.wtcolors`) or *Adobe Swatch Exchange*
  (`.ase`) for other applications.
. Click btn:[Save] and choose where to put the file.

A `.wtcolors` file saved into the *My Libraries* folder (`~/Library/Application
Support/WireTuner/Colors/`) appears in the Swatches Options menu under *My Libraries* on this
Mac.  Any library file can be brought into a document with *Import…*
(xref:spot-process.adoc[Spot and process colors]).

Colors are also converted on export of *artwork* -- to RGB or CMYK, depending on the format
-- which is described on xref:saving.adoc[Saving] and xref:export-formats.adoc[Export
formats].

== Sharing colors between documents

To copy a color from one open document to another:

* Drag a swatch from one document's Swatches panel and drop it below the list in the other's
  (or on its btn:[Add] arrow).  Dragging a base color brings its named tints along.
* Copy and paste objects: named colors used by the pasted objects are added to the
  destination's list.  A color with the same name but a different value is renamed to its mix
  values on arrival; one with the same name and value is reused.
* Choose *Import from Document…* in the Swatches Options menu, pick another open document,
  and tick the colors you want.

Colors copied this way are *copies*.  Editing the swatch in one document does not change it in
the other; for a color that stays in step across documents, use a team library.

== Team color libraries

A team color library is a color list kept in the cloud and available to every document on
your team.  It is itself a {product} document -- open it, edit its Swatches panel, and the
changes are the library's new version -- so it is edited, shared and versioned like any other
document.

To make a document a team library:

. Open the document.
. Choose menu:File[Make Team Color Library…].
. Name the library and choose which team can use it.  Click btn:[Make Library].

The document keeps its artwork; only its named colors are published.  It appears in the
document library under *Team Libraries*, and in every team document's Swatches Options menu
under *Team Libraries*.

To use colors from a team library:

. In the Swatches Options menu choose the library under *Team Libraries*.
. Tick the colors you want and click btn:[Add].

The colors are added to the document as swatches that remember where they came from.  When
the library changes, documents that use its colors show a dot beside *Team Libraries* in the
Options menu; choose *Update from Library…* to see which of your swatches differ from the
library and bring them up to date.  Colors you have renamed or edited locally are listed
separately so you can decide.

Team libraries need the network the first time you open one; after that the last version you
saw is kept on your Mac and works offline.

== Working with others

Exporting is local: nobody else sees a file you save.  Dragging colors between documents adds
swatches to the destination like any other addition, visible to everyone with that document
open.

A team library is a shared document, so editing it is collaborative in the usual way: the
list is one list, later edits to one swatch stand, renames and recolors both survive.
Publishing the library does not push changes into anyone's document; each document's editor
chooses when to update, and *Update from Library…* is a normal change in that document that
everyone sees.

== Specification

=== Data model

`SwatchProps.library` and `library_key` (xref:swatches.adoc[Swatches]) record a swatch's
origin.  For a team library the `library` value is `team:<library document id>` and the key is
the source swatch's node id, so *Update from Library…* can match swatches after renames on
either side.

Server-side, a team library is a flag on the document plus a published snapshot pointer:

[source,protobuf]
----
// proto/wiretuner/docs/v1/library.proto (sketch)
message ColorLibraryInfo {
  string document_id = 1;       // the library document
  string team_id = 2;
  string name = 3;
  uint64 published_seq = 4;     // server_seq of the version consumers see
  int64 updated_ms = 5;
}
service ColorLibraryService {
  rpc Publish(PublishColorLibraryRequest) returns (PublishColorLibraryResponse);     // make / update
  rpc Unpublish(UnpublishColorLibraryRequest) returns (UnpublishColorLibraryResponse);
  rpc List(ListColorLibrariesRequest) returns (ListColorLibrariesResponse);         // per team
  rpc Fetch(FetchColorLibraryRequest) returns (FetchColorLibraryResponse);          // the swatches at published_seq as a ColorLibrary
}
----

`Fetch` returns a `ColorLibrary` (xref:spot-process.adoc[Spot and process colors]) computed
by the server's `wt-crdt` engine from the library document's snapshot at `published_seq` --
the one place on this page the server reads document content.  Consumers never open a live
session on the library document to use it.  Publishing happens on every change to the library
document by default (the library "is" the document); a team can switch a library to manual
publishing, in which case menu:File[Publish Library Version] sets `published_seq`.

The `.wtcolors` file and `.ase` writer are on xref:spot-process.adoc[Spot and process colors].

=== Merge semantics

Export reads; it writes nothing.  Cross-document drags and *Import from Document…* create
swatch nodes in the destination (xref:swatches.adoc[Swatches]); node ids are the destination
replica's, never the source's, so documents never share ids.  Paste carrying named colors
creates missing swatches in the same change as the pasted objects, with references cached.

*Update from Library…* is one change in the consuming document: `SetFields value` (and
`name`, `spot` when the user ticked those) per selected swatch.  LWW per register against
concurrent edits.  Two people updating from the same library version at once write identical
values, so the merge is the same whoever wins.

Editing the library document is ordinary swatch editing.  Nothing in a consuming document
references a node of the library document; there are no cross-document references, so
offline consumers, deleted libraries and team membership changes never leave a dangling
reference.

=== Offline behavior

Export, cross-document copy and *Import from Document…* work offline.  *Team Libraries*
lists libraries from the last `List` seen on this Mac, and each library's last fetched
`ColorLibrary` is cached under `~/Library/Application Support/WireTuner/Colors/team/`;
adding from a cached library works offline, and the update dot is only shown when a `List`
succeeded.  Making a document a team library needs the network and is disabled offline with
an explanation.

=== Server

Beyond storing and relaying: the `ColorLibraryService` above, a `color_library` table
(document, team, name, published_seq), and `Fetch` computing the swatch list from a snapshot
with the Java engine.  Access: `List`/`Fetch` for team members; `Publish`/`Unpublish` for the
document's owner.  Unpublishing or deleting the library document leaves consumers' swatches
intact (they are copies).

As built (COLOR-020, `api/.../library`, V13):

* *Names.*  The RPCs are `PublishColorLibrary`, `UnpublishColorLibrary`, `ListColorLibraries`
  and `FetchColorLibrary` (request and response messages as sketched): buf's standard lint wants
  `<Rpc>Request`, and `ListRequest` is already `DocumentService.List`'s in the package.
  `ColorLibraryInfo` also carries `mode` (`ColorLibraryMode`: `AUTOMATIC`, `MANUAL`) and
  `published_by_account_id`.  `ColorLibrary` and `LibraryColor` are in
  `proto/wiretuner/lib/v1/colorlib.proto` as sketched on xref:spot-process.adoc[Spot and process
  colors], added by this task ahead of COLOR-013, with two fields the sketch lacked so a tint
  survives: `tint_of` (the base's key) and `tint_percent`; a tint's `value` is its base's color.
* *Publishing.*  `PublishColorLibrary` needs the owner's powers on the document (its owner, or a
  team admin on a team document).  A team document is published to its own team; a personal
  document to a team named in `team_id` that its owner belongs to above guest; anything else is
  `FAILED_PRECONDITION / TEAM_ROLE_INVALID`.  An empty name is the document's name for a new
  library and "unchanged" for an existing one; `UNSPECIFIED` mode keeps the current mode
  (automatic for a new library).  Publishing never touches the document's content or sharing.
* *Automatic and manual versions.*  In automatic mode nothing is written on change: the published
  version is the document's head, read when `List` or `Fetch` asks, and `updated_ms` is the later
  of the last `PublishColorLibrary` and the time the head change was sequenced (the publish time
  alone once that row has been compacted to a cold segment).  The update dot therefore also lights
  for changes that touch no swatch; *Update from Library…* then shows nothing to update.  In
  manual mode a publish takes `server_seq` (0 = the head; past the head is `INVALID_ARGUMENT /
  VALIDATION_FAILED`), extracts the colors at that seq there and then, and stores them with the
  row (`color_library.colors`), so a manual version older than the history retention window still
  answers.  The menu:File[Publish Library Version] command is a `PublishColorLibrary` with no
  other field.
* *Fetch* (`ColorLibraries`) reads the document's state at the published seq through
  `DocumentStates` (the newest snapshot at or before it plus the tail, as the snapshotter builds
  it) and walks the swatches collection (0:5) in list order through the generic node tree, as the
  search extractor does: live color and tint swatches, the protected defaults left out, gradient
  swatches and any other kind skipped.  A color's key is its swatch's node id as
  `<counter>:<replica>`; a tint whose base is not in the library carries the color it cached.  The
  server computes no color.  `known_seq` equal to the published seq answers the library without
  its colors.  A 5,000-swatch library fetches in about 80 ms on the development Mac under load
  (budget 200 ms, `ColorLibraryServiceTest`, perf profile).
* *Access.*  `List` and `Fetch` need membership of the library's team above guest (a guest is
  `PERMISSION_DENIED / ROLE_INSUFFICIENT`), and no role on the document: a personal document's
  colors reach the team without sharing the document.  To someone outside the team a library
  reads as absent (`NOT_FOUND / DOCUMENT_NOT_FOUND`); `List` of another team is `TEAM_NOT_FOUND`.
* *Deleting.*  A library whose document is in the trash is not listed and does not fetch (it is
  unpublished for its consumers); restoring the document brings it back as it was, and purging the
  document deletes the row (`ON DELETE CASCADE`).  `UnpublishColorLibrary` deletes the row and is a
  no-op for a document that is not a library.  There is no `is_color_library` flag on the
  document resource: the row is the flag.

=== Client

* `WTInterchange`: `.wtcolors` and `.ase` writers; export sheet.
* `WTApp`: cross-document drag through the `ColorRef` pasteboard type carrying an encoded
  `LibraryColor` list (tints included); *Import from Document…* sheet listing open documents;
  *Team Libraries* submenu built from the cached `List`; *Update from Library…* sheet with a
  three-way listing (unchanged, library changed, edited locally).
* `WTSync`: a small `ColorLibraryClient` actor (List with cache, Fetch with cache, update
  dot from `updated_ms` comparison).
* `WTModel`: `UpdateSwatchesFromLibrary` command.

NOTE: As built by COLOR-021's model and sync halves.  `WTSync.ColorLibraryClient` (an actor over
`ColorLibraryTransport`; `GRPCColorLibraryTransport` is grpc-swift 2 with the usual metadata, on
its own connection) pages through `ListColorLibraries`, caches the listing and each fetched
`FetchColorLibraryResponse` as files in `~/Library/Application Support/WireTuner/Colors/team/`,
sends the cached `published_seq` as `known_seq` and keeps the cached colours when the answer
leaves them out, falls back to the cache when the server cannot be reached, and lights the update
dot only on a current listing, for a cached library whose `updated_ms` is newer than the cached
one.  In `WTModel`, `ImportLibraryColors` with `ColorLibraries.teamOrigin(id)` records the origin,
`LibraryUpdate.classify` makes the three-way listing and `UpdateSwatchesFromLibrary` writes it.
*Deviation*: the listing needs no stored base version -- an import or update writes
`library_key` in the same op as the colour, name and spot, so a register written by a later op
means "edited locally" and a difference without one means "library changed" (both changed reads
as edited locally).  The menu items and the sheet are WTApp's.

NOTE: As built by COLOR-019's and COLOR-021's WTApp halves (`WTApp/Color/ColorWell.swift`
`ColorDrop`, `ColorSheets.swift`, `TeamColorLibraries.swift`, `ColorFeatures.swift`).  A swatch
dragged to another document's panel, well or attribute row is created there with its tints by
`ImportLibraryColors` (origin `document:<source id>`, fresh node ids, the clash rule) and then
referenced; *Import from Document…* lists the other open documents' colours to tick.  The *Team
Libraries…* sheet (from the Swatches Options menu, marked `•` when a library has an update) lists
each team's libraries from `ColorLibraryClient` (`GRPCColorLibraryTransport.http2`, cached in
`ColorLibraryClient.defaultDirectory()`), adds a library's colours with the `team:<id>` origin and
opens *Update from Library…* with the three-way listing ticked where the library changed.
menu:File[Make Team Color Library…] (a team picker) and menu:File[Publish Library Version] are
disabled without a document or a client and, once a listing has fallen back to the cache, offline
with the explanation.  *Not done*: paste carrying named colours (the clipboard's, not this panel's).
