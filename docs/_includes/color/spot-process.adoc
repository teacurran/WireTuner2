Every color in a {product} document is two things at once: a *value* in some color space
(how much cyan, or how much red) and a *kind* of ink -- spot or process -- that only matters
when the document is separated for a press.  This page explains both, how to convert between
them, and the color libraries that supply ready-made, press-matched colors.

== Spot and process colors

Commercial printing lays down inks one plate at a time.

Process colors::
Built from the four process inks: cyan, magenta, yellow and black (CMYK).  A process color is
separated onto four plates, and the press mixes it by overprinting halftone dots.  Almost any
color can be approximated this way, which is why a document with many colors is usually
printed in process.

Spot colors::
A single premixed ink, on its own plate.  A spot color prints exactly as the ink
manufacturer mixed it -- no halftone rosette, no color shift -- and is the right choice for a
brand color, a metallic, a fluorescent, or a two-color job.  Each spot color adds a plate, so
each one costs money at the press.

The Swatches panel shows the kind at a glance: process names are *italic*, spot names are
upright.  The kind is a property of the *swatch*, not of the color value: a spot color can be
defined in any color space, and converting it to process does not change how it looks on
screen, only how it separates (xref:printing.adoc[Printing]).  Unnamed colors are always
process.

To convert a color between spot and process:

. In the Swatches panel, select the swatch.
. From the Options menu choose *Make Spot* or *Make Process*.

Everything that uses the swatch follows.  The default *Black* is a spot swatch that prints on
the process black plate, so it never separates into four; *Registration* prints on every
plate.  Neither can be converted.

== Color spaces

A color space is the set of numbers that define a color, and the meaning of those numbers.
Every color in a {product} document carries its space with it, so a color means the same
thing on every Mac that opens the document, however that Mac's screen is made.  {product}
stores colors in five spaces and lets you mix in seven ways.

[cols="1,3"]
|===
|Space or mode |Use

|*CMYK*
|Cyan, magenta, yellow and black as percentages, 0--100 each.  The space of print.  A color
mixed in CMYK is stored in CMYK.

|*RGB* (sRGB)
|Red, green and blue, 0--255 each (or a hex triplet such as `#E63946`).  The space of the web
and of every screen made before wide-gamut displays: the safe choice when a color must look
the same in a browser, a video or another application.  Stored as sRGB.

|*Display P3*
|Red, green and blue again, 0--255 each, in the wider space of every Mac display since 2016,
of iPhones and of most current televisions: deeper reds, oranges and greens than sRGB can
name.  Stored as Display P3.  A P3 color shows fully on a P3 display; on a display that
cannot reach it, it is shown as the nearest color that display can make, and the Color Mixer
tells you so (xref:color-mixer.adoc[Color Mixer]).  The color in the document is not touched.

|*OKLCH*
|Lightness (0--100%), chroma (how colorful, from gray upward) and hue (0°--360°): a way of
*picking* a color in which equal slider moves look like equal changes.  Colors mixed in OKLCH
are stored as OKLab, a space wide enough for anything a screen or a press can show.

|*Lab*
|The device-independent space that swatch books and color libraries are measured in
(CIELAB).  You do not mix in Lab; Lab colors arrive from libraries and `.ase` files and are
shown with a *Lab* badge.  Loading one into the Mixer shows it in OKLCH.

|*HLS*
|Hue (0°--360°), lightness and saturation (0--100%).  The classic way of finding related
colors -- every hue at one saturation, say.  Colors mixed in HLS are stored in your default
RGB space (sRGB or Display P3, below).

|*System* (the macOS color picker)
|Opens the standard macOS Colors panel with its wheel, sliders, crayons and pencil.  Whatever
you pick is stored as Display P3 on a Mac that can show it, in your default RGB space
otherwise.
|===

Which to choose: if the piece is going to press, mix in CMYK, and do not judge a process
color by how it looks on your monitor unless your display is calibrated and color management
is set up (xref:color-management.adoc[Color management]).  If it will be seen on Apple
screens, in an app, or in a current browser, mix in Display P3 or OKLCH and use the wider
range.  If it must match a color that was specified as sRGB -- a brand hex value, a style
sheet you do not control -- mix in RGB or type the hex value.  Mixing in one space and
outputting in another means a conversion somewhere -- at export or at the printer -- and
conversions shift colors.

The *Default color space for new colors* preference (xref:preferences.adoc[Preferences]),
Display P3 unless you change it, decides the space a color gets when nothing else fixes it:
the RGB mode the Color Mixer opens in, HLS results, the System picker's result, colors picked
from images with the Eyedropper, and colors pasted from other applications.  Set it to sRGB
when everything you make must stay inside sRGB.  Hex values are always sRGB; the CMYK,
Display P3 and OKLCH modes always store what they say.

To convert a named color to another space:

. Press kbd:[Tab] to deselect everything.
. In the Swatches panel, select the swatch.  Only named colors can be converted here; name an
  unnamed color first (xref:swatches.adoc[Swatches]).
. From the Options menu choose *Convert to > sRGB*, *Convert to > Display P3* or
  *Convert to > CMYK*.

The conversion picks the nearest value in the other space.  sRGB to Display P3 is exact:
every sRGB color exists in P3, so the color looks the same and only its numbers change.
Display P3 to sRGB keeps every color that sRGB can show and pulls the rest in -- such a color
loses some vividness but keeps its hue and lightness -- so a document meant for the web can be
made sRGB-safe in one pass.  To or from CMYK goes through the document's profiles
(xref:color-management.adoc[Color management]) and is not reversible: RGB → CMYK → RGB does
not return the original, though the color may look identical afterwards even though its
numbers changed.  The space badge beside the swatch changes to show the result.

== Color libraries

A color library is a list of ready-made colors, usually from a color-matching system whose
printed swatch books tell a printer exactly which ink to mix.  Importing a color from a
library gives you its name (which the printer will recognise), its value, and its kind.

{product} ships these libraries:

[cols="1,1,3"]
|===
|Library |Kind |Contents

|Crayon |Process, sRGB |The familiar crayon-box names.
|Grays |Process, CMYK |Tints of black in 5% steps.
|Web Safe |Process, sRGB |The 216 colors of the browser-safe cube, named by RGB and hex value.
|Process |Process, CMYK |A grid of CMYK mixes in 10% steps, for quick swatch building.
|===

A library records the space of each of its colors, so a color you import arrives in the
space its maker defined it in -- sRGB for the bundled screen libraries, Lab for measured
swatch books, Display P3 for a library you export from a document that uses it.

Libraries from color-matching systems -- PANTONE, Focoltone, Toyo, DIC, Munsell -- are
trademarked and licensed by their owners.  {product} opens them when you have a library file
from the vendor or from another application (see below); it does not bundle them.

To add colors from a library:

. Open the Swatches panel's Options menu and choose the library by name, or choose *Import…*
  and pick a library file.
. In the library sheet, select colors.  kbd:[Cmd]-click to add to the selection,
  kbd:[Shift]-click for a range, or type in the search field to filter by name.
. Click btn:[Add].

Imported colors keep their library name and key, land in a group named after the library, and
show the library name in the Object panel.  Colors already in the document are not added
twice: if the swatch already exists (same library and key), the sheet shows it ticked and
dimmed.

Library files {product} reads:

[cols="1,3"]
|===
|Format |From

|`.wtcolors` |{product}'s own library, as written by *Export…* (xref:exporting-colors.adoc[Exporting and sharing colors]).
|`.ase` |Adobe Swatch Exchange, written by Illustrator, Photoshop and most other tools.  Spot/process and CMYK/RGB/LAB are honoured: RGB entries are read as sRGB (the format has no space tag) and LAB entries as Lab colors.
|`.act` |Photoshop color tables (sRGB only).
|===

Libraries you import from files are remembered: they appear in the Options menu under *My
Libraries* on this Mac.  Libraries shared with your whole team live in the cloud; see
xref:exporting-colors.adoc[Exporting and sharing colors].

== Working with others

Converting a swatch between spot and process, or between color spaces, is a change to that
swatch and everyone sees it at once, with the badge and the italic name updating in their
panel.  Two people converting the same swatch in opposite directions at the same moment
cannot both win; the later choice stands.  Converting the space while someone else adjusts
the value is the one case to watch: their adjustment and your conversion both set the value,
so the later one stands and the other is offered back in the review after an offline
session.

Importing from a library adds swatches like any other addition.  If two of you import the
same library color at the same time you get one swatch each; the second is marked as a
duplicate in the panel and you can remove either.

== Specification

=== Data model

`Color`, `ColorSpace`, `Cmyk`, `Rgb`, `Lab` and `SwatchProps.spot`, `library`, `library_key`
are defined on xref:swatches.adoc[Swatches].  The space of a swatch is the set case of
`Color.components` together with the `Color.space` tag; both sit inside one ATOMIC register,
so converting the space is one write of `value` and a space change is a value change.
`LibraryColor.value` below is the same `Color`, so a library carries each color's space.

Library files are not part of the document:

[source,protobuf]
----
// proto/wiretuner/lib/v1/colorlib.proto -- a .wtcolors file (text protobuf), not a node
message ColorLibrary {
  string name = 1;                     // shown in the Options menu
  string notes = 2;
  uint32 rows = 3;                     // layout hint for the sheet
  uint32 columns = 4;
  repeated LibraryColor colors = 5;
}
message LibraryColor {
  string key = 1;                      // stable identifier within the library ("PANTONE 300 C")
  string name = 2;                     // display name; equals key when the vendor gives no other
  Color value = 3;
  bool spot = 4;
  string group = 5;                    // optional sub-group (a book's page)
  string tint_of = 6;                  // a tint: its base's key in this library; empty = base not in it
  double tint_percent = 7;             // a tint: 1..100 (value is the base's color); 0 = not a tint
}
----

As built: the file is `proto/wiretuner/lib/v1/colorlib.proto`, added by COLOR-020 (team color
libraries return a `ColorLibrary`) with `tint_of` and `tint_percent`, which the sketch lacked and
without which an exported or published tint could not come back as a tint of its base
(xref:exporting-colors.adoc[Exporting and sharing colors]).

=== Merge semantics

[cols="1,1,3"]
|===
|Field |Policy |Concurrent case

|`spot`
|ATOMIC
|Make Spot vs Make Process on one swatch: LWW.  Either vs a recolor: both keep.

|`value` (space conversion)
|ATOMIC
|*Convert to* is a write of `value`; it races any concurrent recolor, or a concurrent
conversion to another space, as an ordinary LWW on `value`.  The review sheet lists a *same
register* loss with both values in their own spaces ("Mine: #E63946, Theirs: 0c 80m 90y 0k";
"Mine: p3(1 0.2 0.1), Theirs: #FF3319").  There is no attempt to convert the winner into the
loser's space; whichever wins is the color, in its space, and its badge follows.

|`library`, `library_key`
|ATOMIC each
|Written together by import and by Update from Library; a concurrent recolor keeps the
origin, which is the intended meaning ("this is PANTONE 300, adjusted").

|Library import (creation)
|--
|Concurrent imports of the same library color create two swatches with the same name; the
duplicate-name normalization on xref:swatches.adoc[Swatches] applies.  Import never writes
to an existing swatch.
|===

Read-time normalizations::
* `Color` with no case set (a malformed write) reads as CMYK 0/0/0/0 -- white -- so a
  broken color is visible rather than a crash.
* `Color.space` is read against the set case.  `cmyk` ignores the tag.  `rgb` tagged `LAB`
  or `OKLAB` reads as sRGB with the components as-is; `lab` tagged `SRGB` or `DISPLAY_P3`
  reads as CIELAB.
* A `space` value this client does not know (written by a newer client for a space added
  later) reads as sRGB with the components as-is for `rgb`, and as CIELAB for `lab`.  The
  components are clamped to the space's range for display.  Nothing is written: the tag
  stays in the state (the merge table from `Welcome` preserves it) so newer clients still
  read the color as intended.
* `Lab` components outside the range of their space (an OKLab `l` of 40, say) are clamped on
  read.

Tints of a color mix toward white in the color's own space: CMYK scales its inks toward
zero, sRGB and Display P3 interpolate toward (1, 1, 1), CIELAB toward (100, 0, 0) and OKLab
toward (1, 0, 0), all linearly by the tint percentage (xref:tints.adoc[Tints]).  A tint
therefore carries its base's space and badge.
* A `spot` swatch with `role = REGISTRATION` or `BLACK` is spot regardless of the register;
  a `WHITE` one is process regardless.

Conversions work offline.  Bundled libraries are in the app bundle; *My Libraries* are files
on this Mac.  Team libraries need the network once, then are cached
(xref:exporting-colors.adoc[Exporting and sharing colors]).
