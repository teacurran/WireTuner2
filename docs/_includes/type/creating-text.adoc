Every piece of text in a {product} document lives in a *text block*: an object you create with
the Text tool and then type into.  A text block behaves like any other object -- you can move
it, color it, transform it, stack it on a layer -- and inside it the text has its own world of
fonts, paragraphs, tabs and styles.  This page covers the moment of creation: choosing between
a block that grows as you type and one with a fixed size, typing the first characters, and what
happens to that text when several people are in the document at once.  What you can do with the
block afterwards is on xref:text-blocks.adoc[Working with text blocks]; formatting is on
xref:type-specifications.adoc[Setting type specifications] and the pages that follow it.

Text you type takes the default text attributes shown in the Object panel when nothing is
selected, or the text style currently chosen in the Styles panel
(xref:text-styles.adoc[Text styles], xref:default-attributes.adoc[Default attributes]).

== Two kinds of text block

Auto-expanding::
Grows to fit whatever you type.  Lines never wrap on their own; the block gets wider with each
character and taller with each kbd:[Return].  This is what a *click* with the Text tool creates.
Use it for labels, headings, callouts -- anything where you want to decide the line breaks
yourself.

Fixed-size::
Has a width and height you set.  Text wraps at the right edge and, when there is more text than
fits, the extra is hidden and the block shows an overflow mark in its link box (see
xref:text-blocks.adoc[Working with text blocks] for overflow and linking).  This is what a
*drag* with the Text tool creates.  Use it for body copy and anything that must stay inside a
layout.

A block can be fixed in one dimension and auto-expanding in the other, and you can convert
between the kinds at any time (xref:text-blocks.adoc[Working with text blocks]).

== Creating a text block

To create text:

. Choose the Text tool in the Tools panel (kbd:[T]).
. Do one of the following:
* Click on the page to create an auto-expanding block, then type.  Press kbd:[Return] to start a
  new line (a new paragraph).
* Drag on the page to create a fixed-size block of that width and height, then type.  Lines wrap
  at the block's right edge; kbd:[Return] starts a new paragraph.
* kbd:[Option]-click to create a block and open it straight away in the Text Editor window
  (xref:editing-text.adoc[Editing text]).
* Click inside an existing text block to place the insertion point there and continue typing.
. To finish, click outside the block, press kbd:[Esc], or choose another tool.

While you type, the text ruler appears above the block showing its width, tabs and indents
(xref:tabs-indents.adoc[Tabs, indents and margins]).  Hide it with menu:View[Text Rulers].

A click that creates a block and is followed by no typing leaves nothing behind: an empty
auto-expanding block is discarded the moment you deselect it.

.Modifier keys while creating
[cols="1,3"]
|===
|Key |Effect

|kbd:[Shift] while dragging
|Constrains the new fixed-size block to a square.

|kbd:[Option] while dragging
|Draws the block from its center instead of from a corner.

|kbd:[Option]-click
|Creates the block and opens the Text Editor window for it.

|kbd:[Esc]
|Ends editing and returns to the Pointer tool with the block selected.
|===

=== What the Text tool does after you finish

By default the Text tool hands over to the Pointer tool as soon as you click away from a new
block, so that your next click selects and moves rather than starting another block.  If you are
placing many labels in a row, turn off the *Text tool reverts to Pointer* preference
(menu:{product}[Settings… > Text]) and the tool stays active until you choose another.

A second preference, *New text blocks auto-expand* (on by default), decides what a click
creates.  Turn it off and a click makes a fixed-size block of a default size instead; drag
always makes a fixed-size block.

== Typing

Text in {product} is Unicode throughout.  Anything macOS can type, {product} can set: accented
characters via the press-and-hold accent popover, emoji and symbols from the Character Viewer
(kbd:[Control+Cmd+Space]), right-to-left scripts, and CJK input through the system input
methods.  Text you are composing with an input method (the underlined "marked" text) is yours
alone until you commit it; collaborators see it appear when you press kbd:[Return] or the
composition ends.

NOTE: One document can mix any scripts your fonts support.

Typing at the insertion point inserts before the character to its right and takes the
formatting of the character to its left (or of the one to the right at the start of a
paragraph).  How formatting spreads when you type at the edge of bold or colored text is
described on xref:type-specifications.adoc[Setting type specifications].

kbd:[Return] ends a paragraph.  The new paragraph inherits the alignment, indents, tabs and
style of the one you split (xref:paragraphs.adoc[Paragraphs]).  For a line break without a new
paragraph, insert an *End of line* character (kbd:[Shift+Return], or
menu:Text[Special Characters > End of Line]).  The other special characters are on
xref:editing-text.adoc[Editing text].

== Working with others

Text is the part of a document people most often edit at the same time, so {product} treats a
text block as something several people can be inside at once.

* Every collaborator editing a block shows a colored caret with their name, and their selection
  as a tinted highlight.  Their caret stays on the right character as you type around it, and
  yours does the same on their screen.
* Two people typing in the same paragraph each see the other's characters appear where they
  were typed.  If you both type at the very same spot, each person's run of characters stays
  together -- the words do not interleave letter by letter.
* If someone deletes a block you are typing in, the block disappears from your canvas and a
  notice appears with a *Restore* button.  Nothing you typed is lost: restoring brings the block
  back with both your text and theirs.
* Creating a block is yours alone until you finish; no one can select it before your first
  character exists, and an empty block you abandon never reaches anyone.

After working offline, your typing merges into whatever others typed in the meantime,
paragraph by paragraph.  Where both of you changed the same paragraph, the review sheet shows
that paragraph with both versions and lets you keep yours, theirs or the merge
(xref:reconcile.adoc[Reconciling offline edits]).

== Specification

This page is the canonical home of the text data model.  Every other page in the *Type* group

=== Data model

A text block is a node of kind `text`.  The same kind is used for text attached to a path and
text flowed inside a path (xref:text-on-path.adoc[Text on a path]); those set `on_path` and
carry the path as a child node.

[source,protobuf]
----
// proto/wiretuner/doc/v1/text.proto (sketch; normative for meaning and merge policy)
package wiretuner.doc.v1;

// NodeProps.kind case `text`.
message TextProps {
  CommonProps common = 1;
  // The characters and their formatting marks.  Paragraph properties ride on newline
  // elements inside this field (see ParagraphProps).  Fugue + Peritext, see crdt-model.
  RichText text = 2 [(wt.crdt.field).merge = MERGE_TEXT];

  // Geometry and container settings.  STRUCT: width, inset and column count are
  // independent choices and merge independently.
  TextBlockProps block = 3;

  // Linked flow.  The whole flow's text lives on the chain's head; members other than
  // the head keep their own `text` dormant while linked.  Both links are ATOMIC registers;
  // a dangling link reads as unset and ends the chain (see text-blocks).
  NodeRef next_link = 4 [(wt.crdt.field).on_dangling = REF_FALLBACK_UNSET];
  NodeRef prev_link = 5 [(wt.crdt.field).on_dangling = REF_FALLBACK_UNSET];

  // Set when the text is attached to, or flowed inside, a path (text-on-path).  The path
  // is this node's child of kind `path`.  Unset for an ordinary block.
  TextOnPathProps on_path = 6;

  // Fill and stroke drawn on the *block* (its rectangle), not on the glyphs.  Same
  // AppearanceProps sequence the ATTR epic defines for paths; text-color describes it.
  AppearanceProps block_appearance = 7;

  // Paragraph properties of the final paragraph, which has no terminating newline element
  // to carry them.  STRUCT.
  ParagraphProps tail_paragraph = 8;
}

message TextBlockProps {
  bool auto_width = 1;          // hollow side handles: grows with the longest line
  bool auto_height = 2;         // hollow bottom handle: grows with the line count
  double width = 3;             // points; the value shown while auto_width is false
  double height = 4;            // points; the value shown while auto_height is false
  // Inset of the text from the block's rectangle.  STRUCT: the four sides are edited
  // independently in the Object panel.
  Inset inset = 5;
  // Show the block's stroke and fill.  Off hides them without deleting them.
  bool display_border = 6;
  // Columns, rows, rules and flow order (columns-tables).
  ColumnsRows columns = 7;
  // Balance, modify-leading, copyfit and first-line leading (columns-tables).
  AdjustColumns adjust = 8;
  // Horizontal (default) or vertical writing (text-effects).
  WritingDirection direction = 9;
}

message Inset { double left = 1; double right = 2; double top = 3; double bottom = 4; }

// Enums whose zero was meaningful gain an UNSPECIFIED zero that reads as that value (buf
// lint's ENUM_ZERO_VALUE_SUFFIX); text.proto is normative for the numbers.
enum WritingDirection {
  WRITING_DIRECTION_UNSPECIFIED = 0;  // reads as HORIZONTAL
  WRITING_DIRECTION_HORIZONTAL = 1;   // lines run left to right, stack downward
  WRITING_DIRECTION_VERTICAL = 2;     // lines run top to bottom, stack right to left
}
----

`RichText` is not a message the client edits field by field; it is the engine's `MERGE_TEXT`
state, read out as an attributed string.  Its wire form is only needed in snapshots:

[source,protobuf]
----
// The snapshot encoding of a MERGE_TEXT field.  Clients read it through the engine.
message RichText {
  repeated TextChar chars = 1 [(wt.crdt.field).merge = MERGE_SEQUENCE];   // Fugue order; includes unstable tombstones
  repeated RichTextMark marks = 2 [(wt.crdt.field).merge = MERGE_ATOMIC];  // Peritext marks anchored to character ids
}

message TextChar {
  ElementId id = 1;                 // the TextInsert op counter that created it
  uint32 codepoint = 2;             // one Unicode scalar; U+000A ends a paragraph,
                                    // U+FFFC is an inline graphic (see marks)
  bool deleted = 3;
  ElementId left_origin = 4 [(wt.crdt.field).merge = MERGE_ATOMIC];   // Fugue tree position; needed to place late inserts
  ElementId right_origin = 5 [(wt.crdt.field).merge = MERGE_ATOMIC];
  // Present only on U+000A: the paragraph this newline terminates.  Each field is its own
  // register; the ParagraphProps message is STRUCT.
  ParagraphProps paragraph = 6;
}

// One formatting mark as the snapshot stores it (ops.proto's TextMark is the op that creates
// it, so this message cannot share its name).  A mark's value is one attribute; a bold red word
// carries two marks.  Later marks of the same attribute win where they overlap (by OpId).
message RichTextMark {
  OpId id = 1 [(wt.crdt.field).merge = MERGE_ATOMIC];
  Anchor start = 2;                 // before/after a character id
  Anchor end = 3;
  TextMarkValue value = 4;
}

message Anchor {
  ElementId char = 1;               // zero id = start (for `before`) or end (for `after`)
  bool before = 2;                  // false = after the character
}
----

`TextMarkValue` is the vocabulary of character formatting.  Exactly one field is set per mark.
Each field's page documents its meaning; they are gathered here so that one `TextMark` op
covers all of them.

[source,protobuf]
----
message TextMarkValue {
  oneof value {
    string font_family = 1;         // PostScript family name; see font-substitution
    string font_style = 2;          // face name within the family ("Bold Italic")
    double size = 3;                // points
    Leading leading = 4 [(wt.crdt.field).merge = MERGE_ATOMIC];
                                    // mode + value (type-specifications)
    double kerning = 5;             // % of an em between this char and the next; span = 1
    double range_kerning = 6;       // % of an em applied across the span
    double baseline_shift = 7;      // points, positive raises
    double horizontal_scale = 8;    // percent, 100 = normal
    ColorRef fill = 9;              // glyph fill; a swatch reference or literal (COLOR epic)
    BasicStroke stroke = 10;        // glyph stroke, the ATTR epic's stroke.proto; unset = none
    TextEffect effect = 11;         // highlight, inline, shadow, strikethrough, underline, zoom
    NodeRef style = 12 [(wt.crdt.field).on_dangling = REF_FALLBACK_CACHED];
                                    // character style (text-styles); cached = resolved attrs
    // 13 reserved: a range link is the WEB epic's `string link = 40` (web/urls.adoc).
    string language = 14;           // BCP 47; spelling and hyphenation (editing-text)
    bool no_break = 15;             // "Selected words": never break a line inside the span
    CaseStyle case = 16;            // small caps rendering (editing-text, Convert Case)
    NodeRef inline_graphic = 17 [(wt.crdt.field).on_dangling = REF_FALLBACK_UNSET];
                                    // the child node drawn in place of U+FFFC (text-effects)
    bool overprint = 18;            // print-time overprint of the glyph fill (PRINT epic)
    bool no_hyphen = 19;            // "Inhibit hyphens in selection" (paragraphs)
    FontVariation axes = 20 [(wt.crdt.field).merge = MERGE_ATOMIC];
                                    // variable-font axis values (type-specifications)
    FeatureSetting feature = 21;    // one OpenType feature's state; identity = (feature, tag)
  }
}
// A mark's value is written whole and is one register (marks are never edited in place;
// a new mark supersedes by OpId), so a plain `oneof` is correct here and MERGE_VARIANT is
// not needed.  The same holds for TextEffect (text-effects).

// A point in a variable font's design space.  ATOMIC as a mark value: a named instance is
// one choice, and a slider drag rewrites the whole list.  Tags the font lacks are ignored on
// read and values are clamped to the axis range (type-specifications).
message FontVariation {
  repeated Axis axes = 1 [(wt.crdt.field).merge = MERGE_ATOMIC];   // part of the one ATOMIC value
}
message Axis {
  string tag = 1 [(buf.validate.field).string = {len: 4}];   // "wght", "wdth", "slnt", "opsz", custom
  double value = 2;
}

// One OpenType feature as a tri-state.  A mark carries one tag; marks with different tags
// stack, and overlapping marks of the same tag resolve by OpId like any attribute -- the
// attribute identity is (feature, tag), the only mark whose identity includes part of its
// value.  DEFAULT is a value: writing it returns the span to the font's own default and
// competes with concurrent ON/OFF writes by OpId instead of vanishing.
message FeatureSetting {
  string tag = 1 [(buf.validate.field).string = {len: 4}];   // "liga", "smcp", "ss01", ...
  FeatureState state = 2;
}
enum FeatureState {
  FEATURE_STATE_UNSPECIFIED = 0;    // reads as DEFAULT
  FEATURE_STATE_DEFAULT = 1;        // the font's own default for this feature
  FEATURE_STATE_ON = 2;
  FEATURE_STATE_OFF = 3;
}

// The same tri-states on a text style, where they are STRUCT registers rather than marks
// (text-styles).  One optional field per feature the Character section offers; an absent
// field is "no selection" (leave the text alone), DEFAULT forces the font's default.
message FeatureSettings {
  optional FeatureState liga = 1;   optional FeatureState dlig = 2;
  optional FeatureState smcp = 3;   optional FeatureState c2sc = 4;
  optional FeatureState onum = 5;   optional FeatureState lnum = 6;
  optional FeatureState tnum = 7;   optional FeatureState pnum = 8;
  optional FeatureState frac = 9;   optional FeatureState swsh = 10;
  optional FeatureState calt = 11;
  optional FeatureState ss01 = 21;  // ... through ss20 = 40, one field per stylistic set
}

// Leading is a mode plus a number.  Always ATOMIC at the field: the number is meaningless
// without the mode.
message Leading {
  LeadingMode mode = 1;
  double value = 2;
}
enum LeadingMode {
  LEADING_MODE_UNSPECIFIED = 0;     // reads as EXTRA
  LEADING_MODE_EXTRA = 1;           // "+": size + value points   (value 0 = solid)
  LEADING_MODE_FIXED = 2;           // "=": exactly value points
  LEADING_MODE_PERCENT = 3;         // "%": size × value / 100    (auto = 120)
}
enum CaseStyle { CASE_STYLE_UNSPECIFIED = 0; CASE_STYLE_NONE = 1; CASE_STYLE_SMALL_CAPS = 2; }
----

Character formatting applied to a selection becomes marks; character formatting applied with
no selection (the "insertion point" case, or with nothing selected at all) becomes either the
*pending format* for the next typed characters (client state, not written) or the document's
default text attributes (xref:default-attributes.adoc[Default attributes]).

=== Merge semantics

Characters:: `TextInsert` places characters in the Fugue tree between `left_origin` and
`right_origin` (CRDT-005).  Two people typing at the same position produce two contiguous runs
in a deterministic order (by the first character's OpId), never interleaved letters.  A
deletion removes character ids; a concurrent insert next to a deleted character still lands
where its origins say, so typing into a word someone else is deleting leaves the typed letters
standing alone at that spot.  Both outcomes are what a user expects and neither is reviewed as
a conflict unless the same paragraph was touched offline by both sides.

Marks:: A `TextMark` is a span between two anchors with an `OpId` (CRDT-006).  Marks of the
same attribute resolve by OpId where they overlap; marks of different attributes stack.
Expansion rules per attribute:
+
[cols="2,1,3"]
|===
|Attribute |End anchors |Effect on typing at the edges

|`font_family`, `font_style`, `size`, `leading`, `range_kerning`, `baseline_shift`,
`horizontal_scale`, `fill`, `stroke`, `effect`, `style`, `language`, `case`, `overprint`,
`axes`, `feature`
|start `before`, end `before` the next char
|Typing at the end of the span extends it (bold stays bold); typing at the start does not.

|`link` (web/urls.adoc), `no_break`, `no_hyphen`, `inline_graphic`, `kerning`
|start `before`, end `after` the last char
|Neither edge grows: a link and a kerning pair cover exactly their characters.
|===
+
Concurrent bold vs. typing inside the span: the typed characters are inside the anchors and
come out bold.  Concurrent bold vs. typing just after the span's last character: the anchor
`before next` is on a character that the new text was inserted before, so the new text is
inside the span and bold -- the same result as sequential typing.  Two people applying
different fonts to overlapping ranges: each character shows the font from the mark with the
greater OpId that covers it; the review sheet's paragraph diff lists both.  For `feature`
marks "the same attribute" means the same `tag`: a `liga` mark and an `ss01` mark stack, two
`liga` marks resolve by OpId (xref:type-specifications.adoc[Setting type specifications]).  The
reset arrow writes DEFAULT as the tag alone (`FEATURE_STATE_UNSPECIFIED`, which reads as
DEFAULT): the mark still competes with ON and OFF by OpId, and where it wins the run carries no
`feature` attribute for that tag -- it reads as no mark, as crdt-model.adoc says of a value
holding its default.  An explicit `FEATURE_STATE_DEFAULT` is accepted and lays out the same.
The conformance vectors `marks/feature-*`, `marks/axes-later-mark-wins-whole-tuple` and
`registers/style-features-and-axes` pin these rules (TYPE-045).

Paragraphs:: Each paragraph's properties live on its terminating newline element.  Splitting a
paragraph (typing kbd:[Return]) inserts a newline whose `paragraph` registers are an explicit
copy of the terminator's values as the typist saw them.  Concurrently changing the paragraph's
alignment writes the *original* terminator, so after the merge the second half has the new
alignment and the first half keeps the copy.  Joining paragraphs (deleting a newline) keeps the
surviving terminator's properties; a concurrent property change on the deleted newline lands on
a tombstone and is lost -- the review sheet lists it under *same text* with the lost values.
Alternative considered: no copy on split, with a newline inheriting from the next terminator
until written -- rejected because it makes a paragraph's look depend on its neighbor after
every edit.

Text vs. block deletion:: A block deleted (`deleted = true`) while someone types into it keeps
receiving their characters; the live client shows a *Restore* notice
(xref:text-blocks.adoc[Working with text blocks]).  Offline, the review sheet lists the block
under *edit vs delete* with *Restore*.

Creation:: The node is created by the first typed character's change (`CreateNode` + the first
`TextInsert` in one change, labelled "Type"), not by the click.  Presence shows the creator's
caret in a block other clients cannot see yet; that is acceptable for the second or so involved.

Read-time normalizations::
* A `text` whose `chars` contain no U+000A has a single paragraph governed by `tail_paragraph`.
* A `size` mark of 0 or below, or above 10,000 pt, renders as the default size (validators reject
  the op on ingest, but the engine never assumes it).
* A mark whose start anchor sorts after its end anchor (possible after concurrent deletions
  collapsed the span) covers nothing.
* Two U+FFFC characters referring to the same `inline_graphic` node draw it once, at the first.

=== Offline behavior

Typing offline coalesces adjacent `TextInsert` ops in the outbox (xref:offline.adoc[Offline]);
change boundaries follow the undo grouping rule below, so history shows words, not keystrokes.
Nothing on this page needs the server.

=== Server

Nothing beyond storing and relaying changes.  The server validates `TextInsert.chars` for
well-formed UTF-8 and a 64 KiB per-op limit; longer pastes are split by the client.

=== Client

Package:: `WTText` (layout, Core Text), `WTModel` (commands), `WTApp` (Text tool, `TextView`).

Layout:: TXT-001 lays out an attributed string built from the merged `RichText`.  Every glyph
run keeps the character ids it came from, so a caret is a `(node, Anchor)` and hit testing
returns an `Anchor`, never an integer offset.  Auto-expanding blocks are laid out with an
unbounded width (or height) and the resulting bounds written back into `TextBlockProps` only
when a dimension is *fixed*; auto dimensions are derived at read time and never stored.

Undo grouping of typing:: Consecutive typed characters are one undo step and one change on the
wire while all of the following hold: same text node; each insert is adjacent to the previous
insert (the caret has not moved); no more than 1 s has elapsed since the previous keystroke;
the previous character was not whitespace or the new one is whitespace (a word plus its
trailing space is one group; the first letter of the next word starts another); no other
command ran in between.  kbd:[Return], kbd:[Tab] and special characters always close a group.
Backspace runs group the same way.  Input-method composition is one group per committed
string.  The change label is "Type" for inserts, "Delete text" for deletions.
+
As built (TYPE-002): `WTModel` performs every keystroke as its own local change and joins them
into one undo step; the one change per group on the wire is WTSync's outbox coalescing
(`Coalescer`, adjacent `TextInsert`s become one op), so "hello world" is two undo steps and,
once coalesced, two sent inserts ("hello " and "world").  A keystroke (`InsertText` with
`typing`, `DeleteText` with `backspace`) keys its step by the character it continues from
(`UndoCoalescing.text`, `TextEditKey`): an insert joins a step left open at its left origin and
leaves it open at the character it typed; a backspace joins at the character it deletes and
leaves the step open at the live character before it.  A moved caret, a switch between typing
and deleting, or any other command therefore starts a new step without a separate "caret moved"
signal.  kbd:[Return], kbd:[Tab], U+2028, U+000C and U+FFFC, and any string of more than one
character (a paste, a committed input-method string), are steps of their own.

Commands (TYPE-002):: `TextNode` reads a text node from the merged state: live characters,
`Anchor` ↔ live offset, paragraphs with their terminator and merged `ParagraphProps`, and decoded
runs.  The commands, each one change taking anchors resolved when it runs: `CreateTextBlock`
(`.point` auto-expanding, `.area` fixed-size; with text, one change labelled "Type" with the
pending format as marks), `InsertText`, `DeleteText`, `SplitParagraph`, `JoinParagraph`,
`ApplyMark` (and `ApplyMark.remove`, a mark of the cleared value), `SetParagraph` (named
registers on every touched paragraph's terminator or `tail_paragraph`; tabs are element ops and
are refused) and `SetTextBlock`.  A split, and every newline an insert types, copies the split
paragraph's registers and tab stops onto the new newline.  Character and paragraph styles are
applied as a `style` mark and the `style` register; resolving their settings and clearing
overrides is TYPE-034, and linked flows are TYPE-007.  `TextLayoutReading` turns a `TextNode`
into WTText's `TextContent` and block `TextContainer` and draws it through the document's
`DocumentFontIndex.layoutEngine`.  The scene draws text blocks through it (TYPE-003):
`NodeKind.text` (130) is a kind WTModel reads and the object commands act on (moved, transformed,
locked, deleted like any object; its `common` is field 1 and it has no attribute stack of its own
-- `block_appearance` is not drawn yet), and `DocumentDisplayListBuilder.textLayout` holds a
`TextSceneLayout` over the document's engine.  The engine's caches are main-actor state, so a
builder given one must build on the main actor (the app's `DocumentHandle` does); builders
without one -- export, baking, previews -- draw no text.  A font activation reaches the drawn text
through `invalidate` with the nodes `DocumentFontIndex.fontsChanged` names.

Text tool:: A `Tool` (APP-003) owning an `NSTextInputClient` implementation for the canvas so
that dictation, marked text and the Character Viewer work.  kbd:[Esc] ends editing.
+
As built (TYPE-003, TYPE-010): `TextTool` (WTApp/Tools) makes the gestures and draws the
overlay; `TextEditingSession` (WTApp/Text) is the model -- the block (or, before the first
character, the place a click or drag made for it), the selection as two anchors in the
`TextNode.anchor(at:)` form (before a character, or the end), the pending format and the input
method's marked text.  The canvas is the `NSTextInputClient` (`CanvasTextInput.swift`); while the
tool edits, keys go through `interpretKeyEvents` and the key-binding selectors (`moveWordLeft:`,
`deleteToBeginningOfLine:` ...) come back to the tool; with no input context (tests) the tool maps
the arrows, deletes, Return and Tab itself.  Every edit is a `TextKeystroke` (WTApp) resolved
against the state it runs on, and the session queues edits and moves behind a change still on
its way, so a keystroke typed while the new block is being created, or an arrow right after
typing, acts on the text the change before left.  The first character is `TypeNewTextBlock`
(`CreateTextBlock` with it, one change labelled "Type"), which leaves the undo step open at that
character so the rest of the first word joins it.  While text is edited Space types, Command no
longer pushes the temporary Pointer, and Edit menu Cut, Copy, Paste, Select All and Clear act on
the text (plain text on the pasteboard, line ends read as paragraph ends); kbd:[Shift+Return]
types an end of line (U+2028).  An emptied block is deleted when editing ends.  Deviations:
kbd:[Option]-click behaves as a click until the Text Editor exists (TYPE-011); the composition is
drawn over the text at the insertion point (underlined, in the overlay) rather than laid out
inside the line; the caret does not blink.
