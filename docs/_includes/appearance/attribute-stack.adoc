Every object in {product} carries a list of *attributes*: the strokes that outline it, the fills
that color its interior, and the effects that alter how those look.  An object can have several
of each, in any order, and the order is part of the design: a narrow white stroke above a wide
black one makes a keyline; a translucent gradient above a solid fill makes a sheen.  The Object
panel is where you build and rearrange that list.  This page covers the list itself; the pages
that follow cover what each stroke, fill and effect can be
(xref:stroke-attributes.adoc[Strokes], xref:fill-attributes.adoc[Fills],
xref:gradients.adoc[Gradients], xref:live-effects.adoc[Live effects]).

== The Attributes list

Open the Object panel with menu:Window[Object] (kbd:[Cmd+F3]).  With an object selected, the
upper part of the panel lists its attributes; the lower part edits whichever attribute is
selected in the list.  Select the object's own row at the top of the list to edit the object
itself (its dimensions, name and so on; see xref:object-panel.adoc[The Object panel]).

// TODO screenshot: Object panel with a path selected showing a stroke above two fills and one effect

The list is painted from the bottom up.  The bottom-most attribute is drawn first and every
attribute above it is drawn over it, so the item at the top of the list is the one you see in
front.  A newly drawn object gets one fill with one stroke above it.  Where an effect sits in the
list matters too; the effects pages explain what an effect applies to.

Each row shows an icon for its kind (stroke, fill or effect), a short description ("Basic, 2 pt",
"Gradient, Linear", "Lens, Transparency"), and a visibility checkbox.

=== Adding a stroke or a fill

To add a stroke to the selected objects, do one of the following:

. Click btn:[Add Stroke] at the bottom of the Object panel.
. Choose *Add Stroke* from the panel's action menu (the gear button).

To add a fill:

. Click btn:[Add Fill].
. Choose *Add Fill* from the panel's action menu.

A new stroke or fill is inserted directly above the attribute selected in the list, or at the
top of the list when nothing is selected, and becomes the selected attribute so you can set it
up immediately.  It starts as a Basic stroke or Basic fill using the current default color and
width (see xref:default-attributes.adoc[Default attributes]).

Effects are added the same way with btn:[Add Effect]; see xref:live-effects.adoc[Live effects].

=== Removing, duplicating and hiding

To remove an attribute:

. Select it in the Attributes list.
. Click btn:[Remove Item], press kbd:[Delete], or choose *Remove* from the action menu.

To duplicate an attribute:

. Select it in the Attributes list.
. Choose *Duplicate* from the action menu, or kbd:[Option]-drag the row to a new position.

The copy is inserted directly above the original with identical settings.

To hide an attribute without removing it, clear its visibility checkbox.  A hidden attribute is
skipped when the object is drawn, printed or exported, but keeps all of its settings and comes
back when you check the box again.  Hidden attributes are shown dimmed in the list.

=== Reordering

To change the painting order, drag a row up or down within the list.  A horizontal insertion
line shows where it will land.  Strokes, fills and effects can be interleaved freely; nothing
forces strokes to stay above fills.

=== Working on several objects

When more than one object is selected, the list shows the attributes the objects have in common
by position and kind, and "Mixed" wherever they differ.  Adding, removing, reordering or editing
an attribute applies to each selected object separately.  Selecting a group edits the group's
own attributes if it has any; to edit the objects inside, subselect them
(xref:grouping.adoc[Grouping]).

== Applying color

Color reaches a stroke or fill by several routes, all described in
xref:applying-color.adoc[Applying color]; in brief:

* Select the stroke or fill in the Attributes list and pick a color in its editor.
* Drag a swatch from the Swatches panel onto a row in the Attributes list.
* Drag a swatch onto an object on the canvas: dropping on the interior colors the top-most
  visible fill, dropping on the outline colors the top-most visible stroke.  Holding
  kbd:[Control], kbd:[Option] or kbd:[Cmd+Option] while dropping makes a gradient instead
  (xref:gradients.adoc[Gradients]).
* Use the stroke and fill wells at the bottom of the Tools panel.  Each well shows the color of
  the top-most visible stroke or fill of the selection and opens a color pop-up.  Clicking a
  well's *None* swatch sets that attribute's color to None; clicking the swap arrow exchanges the
  two colors.

The wells and the swatch-drop targets always act on the top-most visible attribute of their
kind.  To color a lower one, select it in the Attributes list.

== Default attributes

With nothing selected, the Object panel shows the document's default attributes: the list a
newly drawn object will receive.  Edit it exactly as you would an object's list -- add a second
stroke, change the default width, pick a fill color -- and every object you draw from then on
starts that way.  Defaults are part of the document and are shared with collaborators; see
xref:default-attributes.adoc[Default attributes].

== Working with others

Attributes are shared like everything else in the document.  When someone else adds a stroke to
an object you have selected, the row appears in your Attributes list at once, with their
presence color on its edge for a moment.  You can keep editing your own attribute while they
edit theirs: two people changing different attributes of one object, or different settings of
the same attribute, both get what they asked for.

If you and a collaborator reorder the same list at the same time, both moves happen; the result
is the same on every screen, and the list simply reflects where each dragged item ended up.  If
someone removes an attribute you are in the middle of editing, the row disappears from your
list; your edit is not lost silently -- it is recorded, and if the removal turns out to have been
a mistake, the attribute can be restored with your edit in it.

After working offline, your attribute changes merge in when you reconnect.  Where you and
someone else changed the same setting of the same attribute, the later change stands and the
review sheet lists the setting with both values so you can pick
(xref:collaboration.adoc[Collaboration]).

== Specification

=== Data model

Every drawable node kind (path, rectangle, ellipse, text block, group, symbol instance, image)
carries an `AppearanceProps`.  It is also the type of the document's default attributes on the
settings node (xref:default-attributes.adoc[Default attributes]).

[source,protobuf]
----
// proto/wiretuner/doc/v1/appearance.proto (sketch)

// The attribute stack.  Three sequences, one order: the positions of all three share one
// fractional-index space, so the stack the user sees is every live element of `fills`,
// `strokes` and `effects` sorted by position (bytewise), then element id.  A fill can
// therefore sit above a stroke.  Painting order is ascending position: bottom first.
message AppearanceProps {
  repeated Fill fills = 1 [(wt.crdt.field).merge = MERGE_SEQUENCE];
  repeated Stroke strokes = 2 [(wt.crdt.field).merge = MERGE_SEQUENCE];
  // Owned by the FX epic; reserved here so every consumer sees one stack.
  repeated Effect effects = 3 [(wt.crdt.field).merge = MERGE_SEQUENCE];
}

// One fill in the stack.  The active kind is an enum register and every kind's settings
// are sibling STRUCT messages rather than a `oneof`: a `oneof` has no defined merge for
// its discriminator and would discard the other cases' values, whereas here switching
// Basic -> Gradient -> Basic gets the old basic color back, and a concurrent kind change
// and a concurrent edit of the old kind's settings both survive (see Merge semantics).
// The kind and the cases sit in a MERGE_VARIANT message one level down, because a
// SEQUENCE element cannot itself be declared MERGE_VARIANT.
message Fill {
  ElementId id = 1;                 // required first field for MERGE_SEQUENCE
  bool hidden = 2;                  // skipped when painting; settings kept
  FillSettings settings = 3 [(wt.crdt.field).merge = MERGE_VARIANT];
}

message FillSettings {
  FillKind kind = 1;                // which sibling message is live
  BasicFill basic = 2;              // fill-attributes.adoc
  GradientFill gradient = 3;        // gradients.adoc
  LensFill lens = 4;                // fill-attributes.adoc
  CustomFill custom = 5;            // fill-attributes.adoc
  PatternFill pattern = 6;          // fill-attributes.adoc
  TexturedFill textured = 7;        // fill-attributes.adoc
  TiledFill tiled = 8;              // fill-attributes.adoc
}

enum FillKind {
  FILL_KIND_UNSPECIFIED = 0;        // read as BASIC
  FILL_KIND_BASIC = 1;
  FILL_KIND_GRADIENT = 2;
  FILL_KIND_LENS = 3;
  FILL_KIND_CUSTOM = 4;
  FILL_KIND_PATTERN = 5;
  FILL_KIND_TEXTURED = 6;
  FILL_KIND_TILED = 7;
}

// One stroke in the stack; same shape as Fill.
message Stroke {
  ElementId id = 1;
  bool hidden = 2;
  StrokeSettings settings = 3 [(wt.crdt.field).merge = MERGE_VARIANT];
}

message StrokeSettings {
  StrokeKind kind = 1;
  BasicStroke basic = 2;            // stroke-attributes.adoc
  BrushStroke brush = 3;            // stroke-attributes.adoc
  CalligraphicStroke calligraphic = 4;
  CustomStroke custom = 5;
  PatternStroke pattern = 6;
}

enum StrokeKind {
  STROKE_KIND_UNSPECIFIED = 0;      // read as BASIC
  STROKE_KIND_BASIC = 1;
  STROKE_KIND_BRUSH = 2;
  STROKE_KIND_CALLIGRAPHIC = 3;
  STROKE_KIND_CUSTOM = 4;
  STROKE_KIND_PATTERN = 5;
}

// Effect is specified in live-effects.adoc (effects.proto, where ATTR-001 creates it with
// these two fields).  Its first two fields are the same:
//   ElementId id = 1;  bool hidden = 2;
// and its kind and settings are likewise an `EffectSettings settings` MERGE_VARIANT.
----

Colors inside every kind message are `ColorRef` (xref:applying-color.adoc[Applying color]): an
ATOMIC register holding either a `NodeRef` to a swatch (with the swatch's value cached) or an
inline `Color`, or the well-known *None*.

=== Merge semantics

Stack elements::
Insert, move and delete of an element are independent registers (`MERGE_SEQUENCE`), so
reordering by one user and editing by another both apply.  Two concurrent moves of the same
element: the later position wins.  Two concurrent inserts "above the same row", possibly in
different sequences (a fill and a stroke): their positions are generated in the same gap and
almost never collide; when they do, element id order decides.  Because positions are shared
across `fills`, `strokes` and `effects`, the merged order is well defined without any engine
knowledge of the three-way split.

`hidden`::
ATOMIC boolean.  Concurrent hide and show: later wins; the review sheet lists it as a same-register
conflict only if the local write lost.

`kind` and the kind messages::
`settings` is MERGE_VARIANT: `kind` is an ATOMIC enum; each kind message is STRUCT.  A changes a fill from Basic to Gradient
while B changes the basic color: both registers apply; the fill renders as a gradient, and B's
color is stored in `basic` and shows again if anyone switches back.  The review sheet shows B
"Fill type changed to Gradient by A; your color change is kept but not visible" and offers *Use
mine* (which re-asserts `kind = BASIC`).

Edit of a removed element::
A removes a fill while B edits it.  The element is a tombstone with B's write applied.  The
review lists "edited a fill that was removed" and offers *Restore*, which re-inserts the element
(a fresh id, since sequence deletes are not reversible) at the same position with the merged
settings.

Multi-object edits::
A command over several objects writes one change with one `SetFields` per object, so a
collaborator sees them land together and undo removes them together.

Read-time normalizations::
* `kind` unset or unknown (a newer client's value) reads as BASIC for fills and strokes; the
  unknown kind's registers are preserved for other clients.
* An element whose live kind message has never been written (possible when a client sets `kind`
  without settings) reads with that kind's defaults.
* Positions from the three sequences that compare equal are ordered by element id, fills before
  strokes before effects only when ids are also equal, which cannot happen.

=== Offline behavior

Nothing beyond the general rules.  Consecutive edits to one register (dragging a width slider)
coalesce in the outbox.

=== Server

Nothing beyond storing and relaying changes.  The server never interprets an appearance.

=== Client

Model:: `WTModel` exposes `Appearance` as a value type with a computed `stack: [Attribute]`
(the interleaved, position-sorted view) and commands `addFill`, `addStroke`, `addEffect`,
`removeAttribute`, `duplicateAttribute`, `moveAttribute(to:)`, `setHidden`, `setFillKind`,
`setStrokeKind`.  Each command produces one change labelled for the Undo menu ("Add Fill",
"Reorder Attributes").  Position generation for a move uses the merged neighbors' positions,
whatever sequences they belong to.

Rendering:: `WTRender` (REND-002) paints the stack in ascending position: for each visible
element, a fill paints the path's interior (an open contour is closed by a straight line for
filling only), a stroke paints along the contour, an effect is applied per the effects pages.
Hidden elements are skipped at display-list build time so they cost nothing.

Hit testing:: The interior hits if any visible fill paints there (a fill whose color is None
does not); the outline hits if any visible stroke covers the point, using the widest visible
stroke's half width plus the pick tolerance (REND-003).

Object panel:: The Attributes list is an `NSOutlineView` subclass hosted in the inspector
framework (APP-007), one row per stack element, with drag-and-drop reordering, an
`NSButton` checkbox for visibility, and the kind editors registered per `FillKind` /
`StrokeKind`.  Remote changes update rows in place without disturbing an editor that has
keyboard focus.

Undo:: One command, one undo step.  A drag reorder is a single step at drop time.

NOTE: As built by ATTR-004 (`WTRender/Appearance.swift`, `StrokeExpansion.swift`, `HitTester.swift`).
WTRender does not import `WTProto`, so the stack kinds are display-list values WTModel fills in:
`Paint` gained `.gradient`, `.pattern`, `.custom`, `.textured`, `.tiled` and `.lens`
(`FillKinds.swift`), and `StrokePaint` gained `kind` (`.basic`, `.brush`, `.calligraphic`,
`.custom`; `StrokeKinds.swift`).  A Pattern stroke is a Basic stroke whose paint is
`.pattern`, so its outline is the Basic stroke's.  `Appearance(stack:)` takes
`StackElement`s (element and `hidden`) and drops the hidden ones, which is the build-time
skip.  Every element lowers to `PaintedRegion`s (a path, a rule and a paint, or brush copies as
nested display items) that both renderers fill.  *None* for hit testing is `Paint.isNone`:
*None*, a gradient without stops and a tiled fill whose tile has no area; every other fill,
lenses and transparent Custom fills included, hits anywhere inside the path.  The outline
tolerance uses the widest stroke among the width-outlined kinds (Basic, Pattern, Custom and
a brush's cached Basic stroke); a Brush stroke hits inside its copies' symbol frames and a
Calligraphic stroke inside its swept nib.  The Metal renderer draws paints other than a solid
colour through a per-item texture (docs/spec/client.adoc, NOTE on the ATTR paints).

`setFillKind`/`setStrokeKind` of Client), `EditAttribute` (any registers of a fill's or stroke's
`settings`, paths in `AttributeFields`) and `SetAppearanceColor` (the live kind's colour register,
so a colour dropped on a Pattern stroke recolours the pattern).  The per-list `MoveAppearance` of
OBJ-004 stays.  Deviations: `SetAttributeKind` also seeds a kind whose message was never written
(the current colour and width carried over, a fresh `seed` for brushes and Custom fills, a Transparency
lens at 50, Circles, Burlap, 100% tile scale, the checker bitmap), so a newly chosen kind draws at once;
it refuses Gradient, which the gradient commands choose (ATTR-024).  Creation now draws the keys of an
object's initial fills and strokes from one run, fills first, because separately generated keys
interleaved at random once the lists share the position space.  The stack commands take the settings
node too (`SettingsProps.defaults.appearance`): with nothing selected they edit the default
attributes; copying them onto new objects remains OBJ-037's.  `Appearances.resolve` lowers every

ATTR-008, resolves brush nodes; effects are the FX epic's), decodes `Subtree` tiles and lens snapshots

NOTE: As built by ATTR-003 (`WTApp/Inspectors/AttributesList.swift`, `AttributesListView.swift`).
Since APP-007 the list is the `NSOutlineView` subclass `PropertiesOutlineView`
(`WTApp/Inspector/PropertiesOutline.swift`) in the Object panel's host, fed a `PropertiesTree` on every
render by `PropertiesOutlineController`, which reloads only when the rows changed and keeps one item
per row, so the outline keeps its selection.  It shows the root row, then the rows top first, each
with its kind icon, description and an `NSButton` visibility checkbox (mixed when the objects
differ), and a *Contents* row for one group.  The outline's own arrow keys navigate it and kbd:[Delete]
removes the selected row.  The buttons are btn:[Add Stroke], btn:[Add Fill], btn:[Add Effect] (a menu
of the effect kinds, added with their default settings), btn:[Remove Item] and the action menu.
Dragging a row reorders it, or duplicates it with kbd:[Option] down at the drop; the drag carries
the row's display position under `com.villagecompute.wiretuner.attribute-row`.  The row editors are
the APP-007 registry's, one per list rather than one per `FillKind` / `StrokeKind` (the fill and
stroke editors switch on the kind themselves).  The selected row is remembered by the first
target's element (`AttributesState`) and the editor is identified by it, so a remote insert neither
moves the selection nor rebuilds the focused editor.  With several objects a row shows only where
every object has an element of the same list at the same position; its description reads "Mixed"
where they differ.  A colour dropped on a fill or stroke row -- the `ColorRef` payload of the colour
panels and wells, or an `NSColor` from another application -- colours that row only.  Selecting an
effect row names it; effects are edited by FX-003.  The "UI tests" are unit
tests of the list model, its actions, the outline controller driven with an `NSOutlineView`, and
the views rendered in an `NSHostingView`.
